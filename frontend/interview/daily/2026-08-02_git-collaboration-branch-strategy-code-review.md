## G1. Git에서 브랜치란 무엇이고, HEAD는 무엇인가요? 🔴

**💬 30초 답변**
> Git의 커밋들은 각 커밋이 **부모 커밋을 가리키는 방향 그래프(DAG)**를 이룹니다. **브랜치는 특정 커밋을 가리키는 40바이트짜리 포인터(이동식 라벨)**일 뿐이고, 커밋을 새로 만들면 그 라벨이 자동으로 앞으로 이동합니다. **HEAD는 "지금 내가 어디 있는지"를 가리키는 포인터**로, 보통 현재 브랜치를 가리킵니다(`HEAD → main → 커밋`). 그래서 브랜치 생성은 파일 복사가 아니라 **포인터 하나 추가**라 매우 가볍고 빠릅니다.

**📖 핵심 개념**

🎯 **비유**: 커밋 그래프는 **기차 선로**, 커밋은 **역**, 브랜치는 **"현재 종점"을 표시한 깃발**입니다. 새 역(커밋)을 놓으면 깃발이 그 역으로 옮겨집니다. HEAD는 **"내가 탄 기차"**를 가리키는 표식이라, 브랜치를 바꾸면(checkout/switch) HEAD가 다른 깃발로 옮겨갑니다.

📌 **핵심 사실들**
- 커밋은 **불변(immutable)**입니다. 커밋의 SHA-1 해시는 내용·부모·작성자·시간으로 계산되므로, "커밋을 수정"하는 명령(`amend`, `rebase`)은 실제로는 **새 커밋을 만들고 포인터를 옮기는 것**입니다. 원래 커밋은 잠시 남아 있다가 참조가 사라지면 GC 대상이 됩니다.
- `main`, `feature/login` 같은 브랜치 이름은 `.git/refs/heads/` 아래의 파일 하나이고, 그 내용은 커밋 해시 한 줄입니다.
- **detached HEAD**: HEAD가 브랜치가 아니라 커밋을 직접 가리키는 상태(`git checkout <해시>`). 여기서 만든 커밋은 어떤 브랜치도 안 가리켜서, 다른 곳으로 이동하면 "떠내려가" 잃어버릴 수 있습니다(→ 새 브랜치를 만들어 붙잡아야 함).

```
       A───B───C  (main)   ← main 브랜치는 C를 가리킴
                \
                 D───E  (feature)  ← feature 브랜치는 E를 가리킴
HEAD → feature
```

**🔥 예상 꼬리질문**
- Q. 브랜치를 많이 만들면 저장 공간을 많이 쓰나요? → A. 아니요. 브랜치 자체는 포인터라 거의 0바이트입니다. 공간은 커밋(스냅샷)이 차지하며, Git은 동일 파일을 블롭으로 공유해 중복 저장하지 않습니다.
- Q. `git switch`와 `git checkout` 차이는? → A. `checkout`이 브랜치 이동·파일 복원을 모두 담당해 헷갈려서, Git 2.23부터 브랜치 이동은 `switch`, 파일 복원은 `restore`로 역할을 분리했습니다.

<details><summary>📝 한 줄 요약</summary>커밋=부모를 가리키는 불변 스냅샷의 DAG, 브랜치=커밋을 가리키는 가벼운 이동 포인터, HEAD=현재 위치. 그래서 브랜치는 싸고 빠르다.</details>

## G2. 대표적인 Git 브랜치 전략들을 비교해 주세요 🔴

**💬 30초 답변**
> 대표적으로 **Git Flow, GitHub Flow, Trunk-Based Development, GitLab Flow**가 있습니다. 핵심 축은 **"장수(長壽) 브랜치를 몇 개 둘 것인가"**와 **"배포 주기가 어떤가"**입니다. Git Flow는 `main`·`develop`·`release`·`hotfix`·`feature`로 브랜치가 많아 **정기 릴리스·버전 관리가 명확한 대신 복잡**합니다. GitHub Flow는 `main` + 짧은 feature 브랜치만 두고 **PR→리뷰→머지→즉시 배포**하는 단순한 CD 친화 전략입니다. Trunk-Based는 아주 짧게 사는 브랜치(하루 이내)를 `main`에 자주 통합해 **CI/CD·기능 플래그와 궁합**이 좋습니다. 스타트업·웹 서비스는 GitHub Flow 또는 Trunk-Based가 흔하고, 저는 팀 규모·배포 주기에 맞춰 고르겠다고 답합니다.

**📖 핵심 개념**

🎯 **비유**: 브랜치 전략은 **"공동 작업실의 규칙"**입니다. Git Flow는 **격식 있는 대형 출판사**(초안·교정·출간 라인이 다 분리), GitHub Flow는 **블로그 팀**(글 쓰고 리뷰받고 바로 발행), Trunk-Based는 **실시간 위키**(작은 수정을 자주 본문에 반영, 미완성은 커튼(플래그)으로 가림).

📌 **전략별 비교**

| 전략 | 장수 브랜치 | 특징 | 잘 맞는 상황 |
|---|---|---|---|
| **Git Flow** | `main`+`develop`(+release/hotfix) | 브랜치 역할이 명확, 규칙 많고 복잡, 머지 잦음 | 버전 릴리스(앱·라이브러리), 여러 버전 동시 유지보수 |
| **GitHub Flow** | `main` 하나 | feature 브랜치→PR→리뷰→머지→배포. 단순 | 웹 서비스, 지속 배포(CD) |
| **Trunk-Based** | `main`(trunk) 하나 | 아주 짧은 브랜치/직접 커밋, 하루 내 통합, 기능 플래그로 미완성 숨김 | 성숙한 CI/CD, 고빈도 배포 |
| **GitLab Flow** | `main`+환경/릴리스 브랜치 | GitHub Flow에 `staging`/`production` 등 환경 브랜치를 더함 | 환경별 배포 단계가 필요한 팀 |

📌 **Git Flow의 브랜치 역할**(면접에서 자주 물음)
- `main`(또는 `master`): 배포된 안정 버전. 태그(`v1.2.0`)를 붙임.
- `develop`: 다음 릴리스를 위한 통합 브랜치.
- `feature/*`: 기능 개발. `develop`에서 따서 `develop`으로 머지.
- `release/*`: 릴리스 준비(버전 확정·QA). `develop`→`release`→`main`+`develop`.
- `hotfix/*`: 운영 긴급 수정. `main`에서 따서 `main`+`develop`으로.

📌 **왜 요즘 웹은 Trunk-Based/GitHub Flow로 기우나?**: 장수 브랜치는 오래 살수록 `main`과 멀어져 **머지 지옥(merge hell)**과 **거대 PR**을 낳습니다. 작게 자주 통합하면 충돌이 작고, CI가 매 통합을 검증하며, 릴리스는 태그/플래그로 분리하는 편이 **배포를 더 자주·안전하게** 만든다는 것이 현대 DevOps(DORA) 연구의 결론입니다. 미완성 기능은 **feature flag(기능 플래그)**로 코드에는 넣되 사용자에게는 숨깁니다.

**🔥 예상 꼬리질문**
- Q. Git Flow의 단점은? → A. 브랜치와 머지 단계가 많아 오버헤드가 크고, `develop`·`release`가 오래 살면서 `main`과 벌어져 통합 비용이 커집니다. 배포가 잦은 웹 서비스엔 과합니다.
- Q. 기능이 아직 안 끝났는데 어떻게 main에 자주 머지하나요? → A. **기능 플래그**로 코드 경로를 껐다 켤 수 있게 하거나, UI에 노출만 막고 로직을 점진 병합합니다. 이렇게 하면 미완성 코드도 통합·CI 검증은 계속 받습니다.
- Q. 팀에 뭘 추천하겠나요? → A. 정답은 없고 트레이드오프입니다. 소규모·잦은 배포면 GitHub Flow, 버전 릴리스가 중요한 라이브러리면 Git Flow, CI/CD가 잘 갖춰졌으면 Trunk-Based를 권합니다.

<details><summary>📝 한 줄 요약</summary>Git Flow(브랜치 많음·정기 릴리스), GitHub Flow(main+PR·즉시 배포), Trunk-Based(초단명 브랜치+플래그·고빈도 배포), GitLab Flow(환경 브랜치 추가). 축은 "장수 브랜치 수 × 배포 주기".</details>

## G3. merge와 rebase의 차이는 무엇인가요? 🔴

**💬 30초 답변**
> 둘 다 "다른 브랜치의 변경을 내 브랜치로 합친다"는 목적은 같지만 **히스토리를 남기는 방식**이 다릅니다. **merge**는 두 브랜치를 잇는 **병합 커밋(merge commit)**을 새로 만들어 **가지가 갈라졌다 합쳐진 사실을 그대로 보존**합니다. **rebase**는 내 커밋들을 **떼어내 대상 브랜치의 최신 끝에 하나씩 다시 붙여**, 마치 처음부터 최신 위에서 작업한 것처럼 **선형(linear) 히스토리**를 만듭니다. rebase는 커밋 해시가 바뀌므로(=새 커밋), **이미 공유(push)된 브랜치엔 함부로 쓰면 안 됩니다.**

**📖 핵심 개념**

🎯 **비유**: merge는 **두 강물이 합류하는 지점을 지도에 표시**하는 것(합쳐진 흔적이 남음), rebase는 **내 지류를 통째로 들어 본류 하류 끝에 다시 이어 붙여** 강을 한 줄기로 곧게 펴는 것입니다. 곧게 펴는 대신 "원래 언제 갈라졌는지"의 흔적은 지웁니다.

```
# 상황: feature가 main에서 갈라진 뒤 main에 새 커밋 M2가 생김
main:    A───B───M2
              \
feature:       C───D

# git merge main (feature에서 실행)  → 병합 커밋 X 생성
feature: A───B───M2
              \        \
               C───D───X   (X = 두 부모 M2, D)

# git rebase main (feature에서 실행)  → C,D를 M2 위로 복제(C',D')
feature: A───B───M2───C'───D'   (선형, C/D는 새 해시)
```

📌 **핵심 규칙 — "이미 push된 커밋은 rebase 금지"(황금률)**: rebase는 커밋을 새로 만들어(해시 변경) 기존 커밋을 버립니다. 남이 이미 그 커밋을 받아갔다면, 히스토리가 갈라져 협업자에게 강제 푸시(`--force`) 충돌·혼란을 줍니다. **혼자 쓰는 로컬 브랜치에서 정리용으로만** rebase하고, 공유 브랜치엔 merge를 씁니다. 부득이 push된 브랜치를 rebase했다면 `--force-with-lease`로 안전하게 밀어냅니다.

📌 **언제 무엇을?**
- **깔끔한 히스토리 선호 / PR 올리기 전 내 커밋 정리** → rebase(로컬).
- **협업 브랜치 통합 / "이 지점에서 합쳤다"는 맥락 보존** → merge.
- 실무에선 자주 **"로컬은 rebase로 정리 → main에는 merge(또는 squash merge)"** 조합을 씁니다.
- `git pull` 시 `--rebase` 옵션(`git pull --rebase`)은 원격 변경 위에 내 로컬 커밋을 얹어 **불필요한 병합 커밋을 줄여** 깔끔합니다.

**🔥 예상 꼬리질문**
- Q. `git pull`은 내부적으로 뭘 하나요? → A. `git fetch`(원격 최신 가져오기) + `git merge`(현재 브랜치에 병합)의 조합입니다. `--rebase`를 주면 merge 대신 rebase를 합니다.
- Q. rebase 중 충돌이 나면? → A. 커밋을 하나씩 다시 얹으므로 **커밋마다 충돌이 날 수 있습니다.** 해결 후 `git add` → `git rebase --continue`, 포기하려면 `git rebase --abort`로 원상복구합니다.
- Q. `git merge --no-ff`는 왜 쓰나요? → A. fast-forward가 가능해도 **일부러 병합 커밋을 남겨** "이 브랜치가 여기서 합쳐졌다"는 단위를 히스토리에 보존하려는 것입니다(기능 단위 추적에 유용).

<details><summary>📝 한 줄 요약</summary>merge=병합 커밋으로 갈라짐 보존(비선형), rebase=커밋을 재작성해 최신 위로 얹어 선형화(해시 변경). 공유된 커밋은 rebase 금지. 로컬 정리는 rebase, 협업 통합은 merge.</details>

## G4. fast-forward 머지와 3-way 머지, squash 머지는 어떻게 다른가요? 🟡

**💬 30초 답변**
> **fast-forward(FF) 머지**는 대상 브랜치가 갈라진 뒤 새 커밋이 없어서, 그냥 **브랜치 포인터를 앞으로 옮기기만** 하면 되는 경우입니다(새 커밋 없음, 히스토리 선형). **3-way 머지**는 양쪽 모두 갈라진 뒤 각자 커밋이 생겨, 공통 조상 + 양쪽 끝 **세 지점을 비교해 병합 커밋을 새로 만드는** 경우입니다. **squash 머지**는 feature 브랜치의 여러 커밋을 **하나의 커밋으로 압축**해 대상 브랜치에 얹는 방식으로, `main` 히스토리를 "PR 하나 = 커밋 하나"로 깔끔하게 유지할 때 씁니다.

**📖 핵심 개념**

📌 **세 방식 비교**

| 방식 | 새 커밋 생성 | 히스토리 | 언제 |
|---|---|---|---|
| **fast-forward** | ❌ (포인터만 이동) | 선형 | 대상 브랜치에 새 커밋이 없을 때(자동) |
| **3-way merge** | ✅ 병합 커밋 1개 | 갈래 보존 | 양쪽 다 진행됐을 때 |
| **squash merge** | ✅ 압축 커밋 1개 | 선형(중간 커밋 사라짐) | PR을 커밋 1개로 합쳐 main을 깔끔히 |

🎯 **비유**: FF는 **줄이 하나뿐이라 그냥 앞으로 걸어가는 것**, 3-way는 **두 줄이 갈라졌다 매듭(병합 커밋)으로 묶는 것**, squash는 **여러 장의 메모를 한 장으로 요약해서 붙이는 것**입니다.

📌 **squash의 트레이드오프**: `main`은 깔끔해지지만 feature 브랜치의 **세부 커밋 이력·부분 되돌리기 단위는 사라집니다.** GitHub의 PR 머지 옵션 3가지("Merge commit / Squash and merge / Rebase and merge")가 정확히 이 선택지입니다. 팀 컨벤션에 따라 대체로 **"PR 1개 = 의미 있는 변경 1단위"면 Squash**를 많이 씁니다.

```bash
git merge --ff-only feature   # FF 가능할 때만 머지(아니면 실패) — 선형 유지 강제
git merge --no-ff feature      # 항상 병합 커밋 생성 — 기능 단위 보존
git merge --squash feature     # 변경만 스테이징, 커밋은 내가 직접(하나로)
```

**🔥 예상 꼬리질문**
- Q. FF 머지의 단점은? → A. 브랜치가 있었다는 흔적이 히스토리에 안 남아, "이 커밋들이 어떤 기능 묶음이었는지" 추적이 어렵습니다. 그래서 `--no-ff`를 규칙으로 쓰는 팀도 있습니다.
- Q. Rebase and merge와 Squash and merge의 차이는? → A. Rebase는 **모든 커밋을 각각** 선형으로 얹고, Squash는 **하나로 합쳐** 얹습니다.

<details><summary>📝 한 줄 요약</summary>FF=포인터만 이동(새 커밋 없음, 선형), 3-way=병합 커밋 생성(갈래 보존), squash=여러 커밋을 하나로 압축(main 깔끔·세부 이력 손실). GitHub PR 머지 3옵션이 이것.</details>

## G5. 병합 충돌(conflict)은 왜 생기고 어떻게 해결하나요? 🔴

**💬 30초 답변**
> 충돌은 **두 브랜치가 같은 파일의 같은 영역(줄)을 서로 다르게 바꿨을 때**, Git이 어느 쪽을 택할지 자동 결정할 수 없어 발생합니다. Git이 파일에 `<<<<<<<`, `=======`, `>>>>>>>` 마커로 양쪽 버전을 표시하면, 개발자가 **의미를 이해하고 최종 코드로 직접 정리**한 뒤 마커를 지우고 `git add`→`git commit`(또는 `rebase --continue`)로 마무리합니다. 충돌은 "에러"가 아니라 "사람의 판단이 필요하다는 신호"입니다.

**📖 핵심 개념**

🎯 **비유**: 두 사람이 **같은 문서의 같은 문장**을 각자 다르게 고쳐 온 상황입니다. Git은 서로 다른 문장을 못 합치니 "여기 둘이 겹쳐요, 어떤 걸 쓸지 정해주세요"라고 나란히 보여주는 것뿐입니다.

```text
<<<<<<< HEAD (현재 브랜치)
const title = "안녕하세요";
=======
const title = "반갑습니다";
>>>>>>> feature/greeting (합치려는 브랜치)
```
위에서 위쪽이 현재(HEAD) 버전, 아래쪽이 병합 대상 버전입니다. 최종적으로 원하는 한 줄만 남기고 마커 3줄을 모두 지웁니다.

📌 **해결 절차**
1. `git status`로 충돌 파일 확인.
2. 각 파일에서 마커를 찾아 **양쪽 의도를 이해하고 올바른 결과로 편집**(둘 다 살릴 수도, 한쪽만 택할 수도).
3. `git add <파일>`로 "해결됨" 표시.
4. merge면 `git commit`, rebase면 `git rebase --continue`, cherry-pick이면 `git cherry-pick --continue`.
5. 포기하고 되돌리려면 `git merge --abort` / `git rebase --abort`.

📌 **충돌을 줄이는 습관**
- **작게 자주 통합**(장수 브랜치·거대 PR 회피) — 충돌 표면적이 줄어듭니다.
- **자동 포맷터(Prettier)·정렬 규칙 통일** — 서식 차이로 인한 가짜 충돌 방지.
- **`main`을 자주 rebase/merge로 최신화** — 뒤늦게 큰 충돌을 한 번에 만나는 걸 방지.
- 대규모 리팩터링·파일 이동은 팀과 **타이밍 조율**.

**🔥 예상 꼬리질문**
- Q. `git rerere`가 뭔가요? → A. "reuse recorded resolution". 이전에 해결한 충돌 패턴을 기록해 **같은 충돌이 또 나면 자동으로 재적용**해 줍니다. 반복 rebase에 유용합니다.
- Q. 충돌 시 특정 쪽을 통째로 택하려면? → A. `git checkout --ours <파일>`(현재 브랜치 버전) 또는 `--theirs <파일>`(상대 버전)로 파일 단위 선택 후 `add`합니다. (rebase 중엔 ours/theirs 의미가 뒤바뀌니 주의.)
- Q. 병합 도구를 쓸 수 있나요? → A. `git mergetool`로 VS Code 등 3-way 머지 UI를 띄워 시각적으로 해결할 수 있습니다.

<details><summary>📝 한 줄 요약</summary>같은 파일 같은 줄을 양쪽이 다르게 바꾸면 충돌. 마커(<<<< ==== >>>>)를 이해해 최종 코드로 편집→add→continue/commit. 작게 자주 통합·포맷 통일이 최고의 예방책.</details>

## G6. 잘못된 커밋을 되돌리는 reset, revert, cherry-pick은 각각 언제 쓰나요? 🔴

**💬 30초 답변**
> **reset**은 브랜치 포인터를 과거 커밋으로 **되감아** 이후 커밋을 "없던 일"로 만드는 것으로, 히스토리를 바꾸므로 **로컬 전용**입니다(`--soft`/`--mixed`/`--hard`로 작업 내용 보존 정도가 다름). **revert**는 문제 커밋의 변경을 **취소하는 새 커밋을 추가**해, 히스토리를 지우지 않고 안전하게 되돌립니다 → **이미 공유된 브랜치는 revert**를 씁니다. **cherry-pick**은 다른 브랜치의 **특정 커밋 하나만 골라 현재 브랜치에 복제**하는 것으로, "핫픽스 커밋만 release 브랜치에도 반영" 같은 상황에 씁니다.

**📖 핵심 개념**

🎯 **비유**: reset은 **문서를 이전 저장 시점으로 되돌려 이후 내용을 지우는 것**(공유 문서엔 위험), revert는 **"3번 문단을 취소함"이라는 정정 문단을 새로 덧붙이는 것**(이력 보존), cherry-pick은 **다른 문서의 한 문단만 복사해 붙여넣는 것**.

📌 **`reset` 3가지 모드** (핵심 단골 질문)

| 모드 | 브랜치 포인터 | 스테이징(index) | 작업 디렉터리 | 쓰임 |
|---|---|---|---|---|
| `--soft` | 이동 | 유지 | 유지 | 여러 커밋을 하나로 다시 커밋(변경 다 보존) |
| `--mixed`(기본) | 이동 | 초기화 | 유지 | 커밋만 취소, 변경은 다시 add하려 할 때 |
| `--hard` | 이동 | 초기화 | **덮어씀(삭제)** | 전부 버리고 깨끗이 되돌림(**위험**) |

```bash
git reset --soft HEAD~1    # 마지막 커밋만 취소, 변경은 staged로 남김
git reset --mixed HEAD~1   # 마지막 커밋 취소, 변경은 unstaged로
git reset --hard HEAD~1    # 마지막 커밋과 변경 내용까지 완전 폐기(주의)

git revert <해시>          # 해당 커밋의 반대 변경을 새 커밋으로 추가(안전)
git cherry-pick <해시>     # 특정 커밋을 현재 브랜치에 복제
```

📌 **선택 기준 한 줄**: **혼자 로컬에서 정리 → reset**, **이미 push되어 남과 공유됨 → revert**. `--hard`는 작업 디렉터리까지 날리니, 실행 전 항상 "정말 버려도 되나"를 확인합니다.

**🔥 예상 꼬리질문**
- Q. `reset --hard`로 커밋을 날렸는데 되살릴 수 있나요? → A. 대개 가능합니다. `git reflog`에 HEAD 이동 이력이 남아 있어 그 해시로 `git reset --hard <해시>` 하면 복구됩니다(참조가 사라져 GC되기 전까지).
- Q. revert도 충돌이 날 수 있나요? → A. 네. 취소하려는 커밋 이후 같은 영역이 또 바뀌었으면 충돌이 나며, 일반 충돌처럼 해결합니다.
- Q. 머지 커밋을 revert하려면? → A. `-m` 옵션으로 **어느 부모를 기준(mainline)으로 되돌릴지** 지정해야 합니다(`git revert -m 1 <머지해시>`).

<details><summary>📝 한 줄 요약</summary>reset=포인터 되감기(히스토리 변경, 로컬 전용, soft/mixed/hard로 보존 정도 차이), revert=취소 커밋 추가(안전, 공유 브랜치용), cherry-pick=특정 커밋만 복제. 공유됐으면 revert, 로컬이면 reset.</details>

## G7. 좋은 커밋은 어떻게 작성하나요? (원자적 커밋과 Conventional Commits) 🟡

**💬 30초 답변**
> 좋은 커밋은 **원자적(atomic)**이어야 합니다 — **하나의 논리적 변경 = 하나의 커밋**이라 되돌리기·리뷰·이력 추적이 쉽습니다. 커밋 메시지는 **"무엇을·왜"**를 요약(제목)하고 필요하면 본문에 배경을 씁니다. 팀에서는 **Conventional Commits**(`feat:`, `fix:`, `refactor:` 같은 접두어) 규칙을 자주 써서, 메시지를 기계가 읽어 **자동 버전 관리(SemVer)·CHANGELOG 생성**에 활용합니다.

**📖 핵심 개념**

📌 **원자적 커밋의 이점**: "로그인 버그 수정 + 버튼 색 변경 + 리팩터링"을 한 커밋에 섞으면, 나중에 버그 수정만 되돌리거나 리뷰하기 어렵습니다. 변경을 성격별로 쪼개면(`git add -p`로 부분 스테이징) 각 커밋이 독립적으로 의미를 가집니다.

📌 **Conventional Commits 형식**
```
<type>(<scope>): <설명>

[본문 - 선택]
[푸터 - 선택, 예: BREAKING CHANGE, 이슈 번호]
```
자주 쓰는 `type`: `feat`(기능), `fix`(버그), `docs`(문서), `style`(포맷), `refactor`(리팩터링), `test`(테스트), `chore`(빌드·설정), `perf`(성능). 예:
```
feat(auth): 소셜 로그인 카카오 연동 추가

- OAuth 콜백 라우트와 토큰 교환 로직 구현
- 실패 시 에러 토스트 노출

Closes #142
```

📌 **좋은 메시지 관습**: 제목은 명령형·현재형("추가한다"보다 "추가")으로 짧게(대략 50자 이내), 본문은 "왜 이렇게 했는지"를 남깁니다. 코드는 "무엇을"을 이미 보여주므로 커밋 메시지는 **"왜"**를 채우는 게 가치가 큽니다.

**🔥 예상 꼬리질문**
- Q. Conventional Commits가 실무에서 왜 유용한가요? → A. `feat`→minor, `fix`→patch, `BREAKING CHANGE`→major처럼 **자동으로 SemVer 버전 산정·릴리스 노트 생성**(예: semantic-release)이 가능해집니다.
- Q. 커밋을 너무 잘게 쪼개면? → A. 컴파일도 안 되는 중간 상태 커밋이 많아지면 오히려 `bisect`·리뷰가 어렵습니다. "각 커밋이 그 자체로 동작·의미가 완결"되는 선이 이상적입니다.
- Q. 이미 올린 커밋 메시지를 고치려면? → A. 마지막 것은 `git commit --amend`, 과거 것은 `git rebase -i`로 `reword`. 단 공유된 커밋이면 히스토리 변경 주의.

<details><summary>📝 한 줄 요약</summary>원자적 커밋(하나의 논리 변경=하나의 커밋)으로 되돌리기·리뷰가 쉬워지고, Conventional Commits(feat/fix/…)로 메시지를 규격화해 자동 버전·CHANGELOG까지 얻는다. 메시지엔 "왜"를 남겨라.</details>

## G8. 좋은 Pull Request와 코드 리뷰 문화는 어떤 것인가요? 🔴

**💬 30초 답변**
> 좋은 PR은 **작고(리뷰 가능한 크기), 목적이 하나이며, 설명(무엇을·왜·어떻게 테스트했는지)이 충실**합니다. 리뷰어는 **정확성·가독성·설계·엣지 케이스·보안**을 보되, **취향 다툼은 자동화(린터·포맷터)에 맡기고 사람은 논리와 맥락에 집중**합니다. 리뷰는 **코드를 비판하되 사람을 비난하지 않고**, 강제인지 제안인지를 구분해(예: `nit:`) 명확히 소통하는 문화가 핵심입니다. 저는 리뷰이로서 방어적이지 않게 피드백을 받아들이고, 리뷰어로서는 근거와 대안을 함께 제시하려 합니다.

**📖 핵심 개념**

📌 **좋은 PR 만들기 (리뷰이 관점)**
- **작게 쪼갠다**: 400줄 넘는 PR은 리뷰 품질이 급락합니다. 큰 기능은 여러 PR로 나눕니다.
- **설명을 쓴다**: 배경/변경 요약/스크린샷(UI)/테스트 방법/관련 이슈 링크. 리뷰어의 맥락 파악 시간을 아껴줍니다.
- **셀프 리뷰 먼저**: 올리기 전 diff를 스스로 훑어 디버그 코드·오타·불필요한 변경을 제거합니다.
- **CI 통과 상태로 올린다**: 테스트·린트가 빨간 PR을 남에게 리뷰시키지 않습니다.

📌 **좋은 리뷰하기 (리뷰어 관점)**
- **무엇을 보나**: ① 요구사항을 충족하는가(정확성) ② 읽기 쉬운가(가독성·네이밍) ③ 설계가 적절한가(중복·확장성) ④ 엣지 케이스·에러 처리 ⑤ 보안·성능 리스크 ⑥ 테스트가 충분한가.
- **자동화에 위임**: 세미콜론·들여쓰기·import 정렬 같은 스타일은 **Prettier/ESLint/CI**가 잡게 하고, 사람은 로직·구조에 집중.
- **어조**: "이건 틀렸어요"보다 "이 경우 X면 널 에러가 날 것 같은데, 옵셔널 체이닝은 어떨까요?"처럼 **근거+대안**. 칭찬도 남깁니다.
- **강도 표시**: 반드시 고쳐야 함 vs 취향 제안을 구분(`nit:`=사소, `blocking:`=머지 전 필수)해 오해를 줄입니다.
- **빠른 턴어라운드**: 리뷰가 며칠 밀리면 브랜치가 낡아 충돌·재작업이 커집니다. 리뷰는 우선순위 높게.

🎯 **비유**: 코드 리뷰는 **논문 동료 심사**와 같습니다. 목표는 "누가 옳은지"가 아니라 **코드베이스를 함께 더 좋게** 만드는 것. 그래서 코드를 다루되 사람을 다치게 하지 않는 언어가 중요합니다.

📌 **왜 리뷰를 하나?**: 버그 조기 발견, 지식 공유(버스 팩터 감소), 코드 일관성 유지, 주니어 성장. 단순 결함 검출을 넘어 **팀의 집단 코드 소유권**을 만드는 장치입니다.

**🔥 예상 꼬리질문**
- Q. 리뷰 지적에 동의가 안 되면? → A. 감정이 아니라 근거로 대화합니다. "이 방식은 X 이유로 의도했다"를 설명하고, 그래도 갈리면 트레이드오프를 적어 팀 컨벤션·상급자 판단에 맡깁니다. 방어적으로 굴지 않는 게 핵심입니다.
- Q. PR이 너무 커서 리뷰가 힘들 때는? → A. 리뷰 전에 커밋 단위로 나눠 보거나, 저자에게 논리 단위로 PR 분할을 요청합니다. 예방이 최선.
- Q. CODEOWNERS나 브랜치 보호 규칙을 아나요? → A. `CODEOWNERS`로 특정 경로 변경 시 담당자 리뷰를 필수화하고, 브랜치 보호 규칙으로 "CI 통과 + N명 승인" 없이는 `main` 머지를 막을 수 있습니다.

<details><summary>📝 한 줄 요약</summary>좋은 PR=작고·목적 하나·설명 충실·CI 통과·셀프리뷰 완료. 좋은 리뷰=정확성/가독성/설계/엣지케이스/보안에 집중, 스타일은 자동화에 위임, 코드를 비판하되 사람은 존중, 강도(nit/blocking) 명시. 목표는 함께 더 나은 코드베이스.</details>

## G9. 실무에서 자주 쓰는 Git 명령과 복구 기법은? 🟢

**💬 30초 답변**
> `git stash`(작업 임시 보관), `git reflog`(HEAD 이동 이력으로 잃은 커밋 복구), `git bisect`(이분 탐색으로 버그 유발 커밋 찾기), `git cherry-pick`(특정 커밋만 가져오기), `git rebase -i`(커밋 정리) 등을 상황에 맞게 씁니다. 특히 **reflog는 "실수로 날린 커밋도 대개 복구 가능"**하다는 Git의 안전망이라 알아두면 든든합니다.

**📖 핵심 개념**

📌 **자주 쓰는 명령**
```bash
git stash                 # 커밋 안 한 변경을 임시 보관하고 워킹트리를 깨끗이
git stash pop             # 보관한 변경 되돌려 적용
git reflog                # HEAD가 지나온 모든 위치(커밋·리셋·체크아웃) 이력
git reset --hard <해시>   # reflog에서 찾은 해시로 복구
git bisect start          # 버그 유발 커밋을 이분 탐색으로 추적
git rebase -i HEAD~5      # 최근 5개 커밋을 squash/reword/reorder 등으로 정리
git log --oneline --graph --all  # 커밋 그래프를 한눈에
git blame <파일>          # 각 줄을 누가 언제 바꿨는지 추적
```

📌 **reflog = Git의 안전망**: rebase/reset/amend로 "잃어버린 것 같은" 커밋도 `reflog`에 이동 이력이 남아 해시로 되살릴 수 있습니다(참조가 사라진 커밋이 GC로 정리되기 전, 기본 약 2주 이상). 그래서 Git에서 **완전히 잃어버리는 일은 생각보다 드뭅니다.**

📌 **bisect**: "언제부터 깨졌는지 모르는 버그"를 만났을 때, 정상 커밋(good)과 깨진 커밋(bad)을 지정하면 Git이 **중간 지점을 이분 탐색**하며 물어봐, `O(log n)`번의 테스트로 원인 커밋을 특정합니다.

**🔥 예상 꼬리질문**
- Q. stash와 브랜치 커밋의 차이는? → A. stash는 "이름 없는 임시 서랍"이라 빠르지만, 오래 쌓이면 관리가 어렵습니다. 오래 둘 작업은 브랜치로 커밋하는 편이 안전합니다.
- Q. `.gitignore`에 이미 추적 중인 파일을 넣으면? → A. 이미 추적된 파일은 계속 추적됩니다. `git rm --cached <파일>`로 추적에서 빼야 무시됩니다.

<details><summary>📝 한 줄 요약</summary>stash(임시 보관)·reflog(잃은 커밋 복구 안전망)·bisect(버그 커밋 이분 탐색)·rebase -i(커밋 정리)·blame(라인 이력). reflog 덕에 Git에서 커밋을 완전히 잃는 일은 드물다.</details>

## ✅ 오늘의 핵심 요약

- **브랜치는 커밋을 가리키는 가벼운 포인터**, HEAD는 현재 위치. 커밋은 불변 스냅샷의 DAG.
- **브랜치 전략**은 "장수 브랜치 수 × 배포 주기"의 트레이드오프: Git Flow(정기 릴리스)·GitHub Flow(즉시 배포)·Trunk-Based(고빈도+플래그)·GitLab Flow(환경 브랜치).
- **merge**는 갈래 보존(비선형), **rebase**는 선형화(해시 변경)—**공유된 커밋은 rebase 금지**.
- 되돌리기: **로컬이면 reset, 공유됐으면 revert**, 특정 커밋만이면 cherry-pick. reflog는 복구 안전망.
- **코드 리뷰**의 목표는 승패가 아니라 함께 더 나은 코드베이스—작은 PR·충실한 설명·자동화 위임·존중하는 어조.
