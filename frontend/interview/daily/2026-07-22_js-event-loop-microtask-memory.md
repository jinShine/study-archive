## D1. JS는 싱글 스레드인데 어떻게 비동기를 처리하나요? 🔴

**💬 30초 답변**
> 자바스크립트 엔진 자체는 **콜 스택이 하나뿐인 싱글 스레드**라, 한 번에 하나의 작업만 실행합니다. 그런데도 화면이 멈추지 않고 네트워크·타이머를 동시에 처리하는 것처럼 보이는 이유는, 비동기 작업을 **JS 엔진이 아니라 런타임(브라우저/Node)이 대신 처리**해 주기 때문입니다. 브라우저가 `setTimeout`·`fetch`·DOM 이벤트 같은 걸 백그라운드에서 처리하다가, 완료되면 그 콜백을 **큐에 넣고**, 콜 스택이 비었을 때 **이벤트 루프**가 큐에서 꺼내 실행합니다. 즉 "JS는 싱글 스레드지만, 런타임 환경은 멀티 스레드"입니다.

**📖 핵심 개념**

🎯 **비유**: 주방장(JS 엔진)은 한 명뿐입니다. 하지만 주방장이 "3분 타이머 맞춰줘", "이 재료 배달 좀 받아줘"라고 하면 **주방 보조들(브라우저 Web API)** 이 그 일을 맡습니다. 타이머가 울리거나 배달이 도착하면 보조는 결과를 **주문서 대기줄(큐)** 에 올려두고, 주방장은 지금 하던 요리(콜 스택)를 끝내면 대기줄에서 다음 주문을 가져와 처리합니다. 주방장은 언제나 한 번에 한 요리만 하지만, 대기·배달은 병렬로 돌아갑니다.

📌 **꼭 구분할 3가지 주체**

- **JS 엔진** (V8 등): 콜 스택 + 힙(heap). 실제로 코드를 실행하는 곳. **싱글 스레드**.
- **Web API / 런타임 API**: `setTimeout`, `fetch`, `addEventListener`, DOM 등. 엔진이 아니라 **브라우저(또는 Node)가 제공**하며, 백그라운드에서 비동기로 처리한다.
- **이벤트 루프 + 큐**: 백그라운드에서 완료된 콜백을 큐에 모아두었다가, 콜 스택이 비면 하나씩 꺼내 콜 스택으로 올린다.

📌 **"비동기 = 멀티 스레드"가 아니다**: JS의 비동기는 **동시에 여러 JS 코드가 실행되는 것이 아니라**, "지금 당장 안 해도 되는 일을 나중으로 미뤄서, 메인 스레드를 막지 않는 것"입니다. 실제 무거운 계산(예: 큰 배열 정렬)을 `setTimeout`으로 감싸도 병렬 처리되지 않습니다 — 진짜 병렬이 필요하면 **Web Worker**(별도 스레드)를 써야 합니다.

**🔥 예상 꼬리질문**

- **Q. `while(true){}` 같은 무한 루프를 돌리면 어떻게 되나요?**
  A. 콜 스택이 영원히 안 비므로 이벤트 루프가 큐를 처리하지 못합니다. 타이머·클릭·렌더링이 전부 멈춰 **탭이 완전히 얼어붙습니다**(freeze). 싱글 스레드의 대가입니다.
- **Q. 그럼 무거운 연산은 어떻게 처리하나요?**
  A. 작업을 잘게 쪼개 `setTimeout`/`requestIdleCallback`으로 나눠 메인 스레드에 숨 쉴 틈을 주거나, 아예 **Web Worker**로 별도 스레드에서 돌립니다. Worker는 메인과 메모리를 공유하지 않고 `postMessage`로 통신합니다.
- **Q. Node.js도 싱글 스레드인가요?**
  A. JS 실행 스레드는 하나지만, 내부적으로 **libuv의 스레드 풀**(기본 4개)이 파일 I/O·암호화 같은 작업을 병렬 처리합니다. 개념 구조(엔진은 싱글, 런타임은 백그라운드 처리)는 브라우저와 같습니다.

<details><summary>📝 한 줄 요약</summary>JS 엔진은 콜 스택 1개짜리 싱글 스레드지만, 비동기 작업은 브라우저/Node 런타임이 백그라운드에서 처리하고 콜백을 큐에 넣어준다. 이벤트 루프가 스택이 빌 때 큐에서 꺼내 실행 → "싱글 스레드지만 논블로킹".</details>

## D2. 콜 스택 · 태스크 큐 · 마이크로태스크 큐 — 이벤트 루프의 한 사이클을 설명해 주세요 🔴

**💬 30초 답변**
> 이벤트 루프는 "콜 스택이 비었는가?"를 계속 확인하는 반복문입니다. 한 사이클(tick)은 이렇습니다: ①**콜 스택의 동기 코드**를 전부 실행하고, ②스택이 비면 **마이크로태스크 큐를 하나도 남김없이 전부** 비우고(마이크로태스크가 또 마이크로태스크를 만들면 그것까지), ③그 다음 필요하면 **렌더링**을 하고, ④마지막으로 **매크로태스크(태스크) 큐에서 딱 하나**를 꺼내 실행합니다. 그리고 다시 ②로 돌아가 마이크로태스크를 비웁니다. 핵심은 **"매크로태스크는 한 번에 하나, 마이크로태스크는 매번 전부 비운다"** 입니다.

**📖 핵심 개념**

📌 **네 개의 무대**

- **콜 스택(Call Stack)**: 지금 실행 중인 함수들이 쌓이는 곳. 함수 호출 시 push, 리턴 시 pop. 스택이 비어야 다음 태스크를 받을 수 있다.
- **힙(Heap)**: 객체·배열 등이 실제로 저장되는 메모리 공간.
- **태스크 큐(Task Queue = 매크로태스크 큐)**: `setTimeout`/`setInterval` 콜백, DOM 이벤트, `MessageChannel` 등. 여러 개일 수 있으며 우선순위가 다르다.
- **마이크로태스크 큐(Microtask Queue)**: Promise의 `.then/.catch/.finally`, `await` 이후 코드, `queueMicrotask`, `MutationObserver`. **매크로태스크보다 항상 우선.**

🎯 **비유**: 매크로태스크 큐는 "오늘 처리할 큰 안건들의 회의 목록", 마이크로태스크 큐는 "그 안건 하나를 처리한 직후 반드시 정리해야 하는 잔무들"입니다. 큰 안건 **하나**를 처리할 때마다, 다음 큰 안건으로 넘어가기 전에 쌓인 **잔무를 전부** 끝냅니다.

📌 **한 tick의 정확한 순서 (브라우저 기준)**

```
1. (직전 매크로태스크 or 초기 스크립트 실행) → 콜 스택 소진
2. 마이크로태스크 큐가 빌 때까지 전부 실행
   (실행 중 새로 생긴 마이크로태스크도 이번 턴에 다 처리)
3. (필요 시) requestAnimationFrame 콜백 실행 → 스타일/레이아웃/페인트 렌더링
4. 매크로태스크 큐에서 "딱 하나" 꺼내 콜 스택으로 → 다시 1번으로
```

📌 **가장 중요한 규칙 2가지**
1. **마이크로태스크는 "전부", 매크로태스크는 "하나씩"**: 매크로태스크 사이사이마다 마이크로태스크 큐 전체를 비운다.
2. **마이크로태스크가 우선한다**: 매크로태스크가 대기 중이어도, 마이크로태스크가 있으면 그것부터 처리한다. 그래서 Promise 콜백은 `setTimeout` 콜백보다 항상 먼저 실행된다.

```javascript
console.log('1');                          // 동기
setTimeout(() => console.log('2'), 0);     // 매크로태스크
Promise.resolve().then(() => console.log('3')); // 마이크로태스크
console.log('4');                          // 동기

// 출력: 1 → 4 → 3 → 2
// (동기 코드 전부 → 마이크로태스크(3) → 매크로태스크(2))
```

> ⚠️ **주의: 마이크로태스크 기아(starvation)**. 마이크로태스크는 "전부 비울 때까지" 실행되므로, 마이크로태스크 안에서 계속 새 마이크로태스크를 만들면(예: `.then` 안에서 또 `Promise.resolve().then`을 무한히) 렌더링과 매크로태스크가 **영영 실행되지 못하고 화면이 멈춥니다.** 재귀적 비동기 반복이 필요하면 마이크로태스크가 아니라 매크로태스크(`setTimeout`)로 쪼개야 합니다.

**🔥 예상 꼬리질문**

- **Q. "콜 스택이 비었을 때"란 정확히 언제인가요?**
  A. 현재 실행 중인 스크립트(또는 매크로태스크 콜백)의 모든 동기 코드가 끝나 스택에서 다 pop된 순간입니다. 그 직후 마이크로태스크 체크포인트가 돌아갑니다.
- **Q. `<script>` 태그 하나의 실행도 태스크인가요?**
  A. 네, 스크립트 최초 실행 자체가 하나의 매크로태스크로 취급됩니다. 그 스크립트가 끝나면 마이크로태스크 큐가 비워집니다.
- **Q. Node.js의 이벤트 루프도 똑같나요?**
  A. 큰 그림(마이크로태스크 우선)은 같지만, Node는 **phase(timers, pending, poll, check, close)** 로 나뉘고, `process.nextTick`이 Promise 마이크로태스크보다도 **먼저** 실행되는 별도 큐를 가진다는 차이가 있습니다. 브라우저엔 `process.nextTick`이 없습니다.

<details><summary>📝 한 줄 요약</summary>이벤트 루프 한 tick: 동기 코드 소진 → 마이크로태스크 큐 전부 비움 → (rAF·렌더링) → 매크로태스크 하나 실행 → 반복. 규칙: 매크로는 하나씩, 마이크로는 전부·우선. 마이크로태스크 무한 생성은 화면을 멈춘다.</details>

## D3. 매크로태스크와 마이크로태스크의 차이는? 실행 순서 문제를 풀어 주세요 🔴

**💬 30초 답변**
> **매크로태스크**는 `setTimeout`·`setInterval`·DOM 이벤트·`MessageChannel`처럼 이벤트 루프가 **한 사이클에 하나씩** 처리하는 작업이고, **마이크로태스크**는 Promise 콜백·`await` 이후·`queueMicrotask`·`MutationObserver`처럼 **현재 작업이 끝나자마자 다음 매크로태스크 전에 전부** 처리되는 작업입니다. 핵심 규칙은 "**동기 → 마이크로태스크 전부 → 매크로태스크 하나 → (다시) 마이크로태스크 전부...**". 그래서 같은 시점에 등록해도 **Promise 콜백이 setTimeout보다 먼저** 실행됩니다.

**📖 핵심 개념**

📌 **분류표**

| 구분 | 예시 | 처리 방식 |
|------|------|-----------|
| **매크로태스크** | `setTimeout`, `setInterval`, `setImmediate`(Node), I/O, UI 렌더링/이벤트, `MessageChannel.postMessage` | 한 tick에 **1개** |
| **마이크로태스크** | `Promise.then/catch/finally`, `await` 이후 코드, `queueMicrotask`, `MutationObserver` | 매 tick마다 **전부** |

📌 **단계적 예제 (면접 단골)**

```javascript
console.log('script start');

setTimeout(() => console.log('setTimeout'), 0);

Promise.resolve()
  .then(() => console.log('promise1'))
  .then(() => console.log('promise2'));

console.log('script end');
```

**출력:**
```
script start
script end
promise1
promise2
setTimeout
```

**풀이:**
1. 동기 코드 실행 → `script start`, `script end` 출력. `setTimeout` 콜백은 매크로태스크 큐로, 첫 `.then`은 마이크로태스크 큐로 등록.
2. 콜 스택이 비면 마이크로태스크를 전부 처리 → `promise1` 출력. 이 `.then`이 반환되며 다음 `.then`(promise2)이 마이크로태스크 큐에 **새로 추가됨**. 큐가 아직 안 비었으니 이어서 처리 → `promise2` 출력.
3. 마이크로태스크가 다 비었으니 매크로태스크 하나 처리 → `setTimeout` 출력.

📌 **조금 더 꼬인 예제**

```javascript
console.log('A');

setTimeout(() => {
  console.log('B');
  Promise.resolve().then(() => console.log('C'));
}, 0);

Promise.resolve().then(() => {
  console.log('D');
  setTimeout(() => console.log('E'), 0);
});

console.log('F');

// 출력: A → F → D → B → C → E
```
**포인트**: `D`(마이크로태스크) 안에서 만든 `E`(매크로태스크)는 큐 맨 뒤로 간다. `B`(첫 setTimeout) 안에서 만든 `C`(마이크로태스크)는 그 매크로태스크가 끝난 **직후** 처리된다. 그래서 B 다음이 E가 아니라 C.

> 💡 **면접 포인트**: 출력 순서를 맞히는 것보다 **"왜"** 를 설명하는 게 중요합니다. "마이크로태스크 큐는 매 매크로태스크 사이마다 완전히 비워진다"는 규칙 하나로 모든 문제를 일관되게 풀 수 있다는 걸 보여주세요.

**🔥 예상 꼬리질문**

- **Q. `queueMicrotask`는 언제 쓰나요?**
  A. Promise 없이 "지금 동기 코드가 끝난 직후, 다음 매크로태스크 전에" 콜백을 실행하고 싶을 때 씁니다. `Promise.resolve().then(fn)`과 타이밍은 같지만 불필요한 프로미스 객체를 안 만들어 의도가 더 명확합니다.
- **Q. `setTimeout(fn, 0)`과 `queueMicrotask(fn)` 중 뭐가 먼저?**
  A. `queueMicrotask`가 항상 먼저입니다. 마이크로태스크가 매크로태스크보다 우선이기 때문입니다.
- **Q. `MutationObserver`가 마이크로태스크라는 게 왜 중요한가요?**
  A. DOM 변경을 감지하는 콜백이 마이크로태스크로 돌기 때문에, 렌더링(페인트) 전에 여러 DOM 변경을 모아서(batch) 처리할 수 있습니다. 성능상 유리합니다.

<details><summary>📝 한 줄 요약</summary>매크로태스크(setTimeout·이벤트)는 tick당 1개, 마이크로태스크(Promise·await·queueMicrotask)는 매 tick 전부·우선 처리. 출력 순서 문제는 "동기 → 마이크로 전부 → 매크로 하나 → 반복" 규칙으로 일관되게 풀린다.</details>

## D4. `setTimeout(fn, 0)`은 정말 0ms 뒤에 실행되나요? 🟡

**💬 30초 답변**
> 아닙니다. `setTimeout(fn, 0)`은 "0ms 뒤 실행"이 아니라 **"최소 0ms 뒤, 그리고 콜 스택이 비고 마이크로태스크가 다 처리된 뒤에 실행"** 을 의미합니다. 지연 시간은 **최소 보장값일 뿐 정확한 실행 시각이 아닙니다.** 게다가 HTML 명세상 **중첩된 타이머는 최소 4ms로 클램핑**되고, 탭이 백그라운드면 브라우저가 더 크게 늦춥니다(1초 이상). 그래서 `setTimeout(0)`의 실제 의미는 "이 코드를 **매크로태스크로 미뤄서 지금 동기 흐름을 막지 않고 나중에 실행**"입니다.

**📖 핵심 개념**

📌 **지연 시간이 지켜지지 않는 이유들**
- **콜 스택이 비어야 함**: 앞선 동기 코드가 100ms 걸리면, `setTimeout(fn, 0)`도 최소 100ms 뒤에 실행된다. 타이머는 "이 시각 이후 **자격이 생긴다**"는 뜻이지 "이 시각에 실행"이 아니다.
- **마이크로태스크가 먼저**: 스택이 비어도 마이크로태스크 큐를 다 비운 뒤에야 매크로태스크(타이머)로 넘어간다.
- **4ms 클램핑**: 명세상 타이머가 **5단계 이상 중첩**되면 최소 지연이 4ms로 강제된다(재귀적 `setTimeout` 폭주 방지).
- **백그라운드 스로틀링**: 비활성 탭에서는 타이머가 1초 이상으로 느려진다(배터리·CPU 절약).

📌 **그래서 `setTimeout(0)`은 이럴 때 쓴다**
- 무거운 작업을 잘게 쪼개 **메인 스레드에 숨 쉴 틈**을 줄 때 (렌더링·입력 반응 유지).
- "현재 실행 스택이 완전히 끝난 **다음**에 실행"을 보장하고 싶을 때 (예: DOM이 완전히 갱신된 뒤 값 읽기 — 단, 이 목적엔 보통 마이크로태스크나 `requestAnimationFrame`이 더 정확).

```javascript
console.log('start');
setTimeout(() => console.log('timeout callback'), 0);
// 아래 무거운 동기 루프가 끝나야 위 콜백이 실행됨
const t = Date.now();
while (Date.now() - t < 500) {} // 500ms 블로킹
console.log('end');

// 출력: start → end → (약 500ms 뒤) timeout callback
// "0ms"였지만 실제로는 500ms 넘게 걸림
```

> ⚠️ **정밀한 타이밍이 필요하면 `setTimeout`을 믿지 마세요.** 애니메이션엔 `requestAnimationFrame`, 정밀 측정엔 `performance.now()`, 정확한 간격 반복엔 "다음 목표 시각을 계산해 보정하는" 방식이나 Web Worker 기반 타이머를 씁니다.

**🔥 예상 꼬리질문**

- **Q. `setInterval`의 위험성은?**
  A. 콜백 실행이 지정 간격보다 오래 걸려도 브라우저는 계속 큐에 쌓으려 하므로, 콜백이 밀리면 실행이 몰리거나 드리프트(누적 오차)가 생깁니다. 정밀한 반복은 `setTimeout`을 재귀로 호출하며 매번 목표 시각을 보정하는 편이 안전합니다.
- **Q. `setTimeout(0)`과 `Promise.resolve().then()`의 차이를 한마디로?**
  A. 둘 다 "나중에 실행"이지만, Promise는 **마이크로태스크(현재 tick 안, 렌더링 전)**, setTimeout은 **매크로태스크(다음 tick, 렌더링 후)** 입니다. Promise가 훨씬 빨리·자주 실행됩니다.

<details><summary>📝 한 줄 요약</summary>setTimeout(0)은 "0ms 뒤"가 아니라 "최소 0ms + 스택 비고 + 마이크로태스크 소진 후"에 실행되는 매크로태스크. 중첩 시 4ms 클램프, 백그라운드 탭은 더 느림. 지연값은 "최소 보장"일 뿐 정확한 시각이 아니다.</details>

## D5. `requestAnimationFrame`·`requestIdleCallback`은 이벤트 루프 어디에 끼나요? 🟡

**💬 30초 답변**
> `requestAnimationFrame`(rAF)은 **다음 화면을 다시 그리기(repaint) 직전에** 콜백을 실행합니다. 즉 이벤트 루프의 "렌더링 단계" 바로 앞이라, 보통 초당 60회(모니터 주사율)에 맞춰 호출됩니다. 애니메이션을 `setTimeout`이 아니라 rAF로 해야 하는 이유가 이것 — **화면 갱신 주기에 정확히 동기화**돼 부드럽고, 백그라운드 탭에선 자동으로 멈춰 자원을 아낍니다. `requestIdleCallback`은 반대로 **브라우저가 한가할 때(유휴 시간)** 낮은 우선순위 작업을 실행하는 용도입니다.

**📖 핵심 개념**

📌 **한 프레임 안의 순서 (대략)**

```
매크로태스크 하나 실행
  → 마이크로태스크 전부 소진
  → requestAnimationFrame 콜백들 실행   ← 여기! (레이아웃 계산 직전)
  → 스타일 계산 → 레이아웃(reflow) → 페인트 → 합성
  → (남는 시간이 있으면) requestIdleCallback 실행
```

📌 **왜 애니메이션은 rAF인가**
- **주사율에 동기화**: 브라우저가 "이제 곧 그린다" 하는 시점에 맞춰 콜백을 주므로, 프레임을 놓치거나 중복 그리는 낭비가 없다. `setTimeout(16)`은 주사율과 어긋나 끊김(jank)이 생긴다.
- **자동 일시정지**: 탭이 백그라운드거나 화면 밖이면 rAF가 호출되지 않아 CPU·배터리를 아낀다.
- **레이아웃 스래싱 방지에 유리**: rAF 안에서 DOM 읽기/쓰기를 정리하면 강제 동기 레이아웃을 줄일 수 있다.

```javascript
function animate(timestamp) {
  // timestamp: 프레임 시작 시각 (performance.now() 기준)
  box.style.transform = `translateX(${(timestamp / 10) % 300}px)`;
  requestAnimationFrame(animate); // 다음 프레임 예약
}
requestAnimationFrame(animate);
```

📌 **`requestIdleCallback`**: 로그 전송, 사전 로딩, 비필수 계산처럼 "급하지 않은 일"을 프레임의 남는 시간에 처리. 콜백은 `deadline.timeRemaining()`으로 남은 시간을 확인해 오래 걸리면 다음 유휴 시간으로 미룬다. (Safari 미지원 등 호환성 주의 — React의 스케줄러는 이 개념을 자체 구현으로 대체한다.)

> 💡 **면접 포인트**: "React 18의 동시성 스케줄러가 왜 필요한가"와 연결하면 좋습니다. rAF/idle 개념처럼 **렌더링을 잘게 쪼개 우선순위대로 처리**해 메인 스레드를 막지 않으려는 것이 동시성 렌더링의 목표입니다.

**🔥 예상 꼬리질문**

- **Q. rAF 콜백은 마이크로태스크인가요 매크로태스크인가요?**
  A. 둘 다 아닙니다. 이벤트 루프의 **렌더링 단계에 속한 별도의 콜백**으로, 마이크로태스크가 모두 처리된 뒤·페인트 직전에 실행됩니다.
- **Q. `setTimeout`으로 애니메이션을 만들면 뭐가 문제인가요?**
  A. 주사율과 동기화되지 않아 프레임이 밀리거나 겹쳐 끊김이 생기고, 백그라운드 탭에서도 계속 돌아 자원을 낭비합니다.

<details><summary>📝 한 줄 요약</summary>rAF는 페인트 직전(렌더링 단계)에 실행돼 주사율과 동기화 → 애니메이션 필수. 백그라운드 탭에선 멈춰 자원 절약. requestIdleCallback은 유휴 시간에 비급한 작업 처리. 둘 다 마이크로/매크로태스크와 별개 단계.</details>

## D6. async/await는 이벤트 루프 관점에서 어떻게 동작하나요? 🔴

**💬 30초 답변**
> `async/await`는 **Promise의 문법적 설탕(syntactic sugar)** 입니다. `await`를 만나면 함수 실행이 **거기서 일시 중단**되고, 제어권을 호출한 쪽으로 돌려줍니다(그래서 뒤 코드가 블로킹되지 않음). `await`가 기다리던 값이 준비되면, **`await` 다음 줄부터의 코드가 "마이크로태스크"로 큐에 등록**돼 나중에 이어 실행됩니다. 즉 `await` 뒤의 코드는 `.then()` 콜백과 동일한 타이밍(마이크로태스크)에 돌아갑니다. "동기처럼 보이지만 실제로는 Promise 체인"이라는 게 핵심입니다.

**📖 핵심 개념**

🎯 **비유**: `await`는 함수 실행에 붙이는 **책갈피**입니다. "여기까지 읽었다"고 표시해두고 책(콜 스택)을 덮어 다른 일을 하다가, 기다리던 게 준비되면 책갈피 위치부터 다시 읽습니다. 다시 읽는 그 순간은 "지금 당장"이 아니라 "마이크로태스크 차례가 됐을 때"입니다.

📌 **`await` 뒤 코드 = 마이크로태스크**

```javascript
console.log('script start');       // 1

async function async1() {
  console.log('async1 start');     // 2
  await async2();
  console.log('async1 end');       // 6  ← await 뒤 = 마이크로태스크
}
async function async2() {
  console.log('async2');           // 3
}

async1();
console.log('script end');         // 4

Promise.resolve().then(() => console.log('promise'));  // 5

setTimeout(() => console.log('timeout'), 0);            // 7
```

**출력:**
```
script start
async1 start
async2
script end
async1 end   ← await 뒤 코드가 마이크로태스크로 실행
promise
timeout
```

**풀이:**
1. `async1()` 호출 → `async1 start` 출력 → `async2()` 호출 → `async2` 출력. `async2`가 반환한 Promise를 `await` → **여기서 async1 일시 중단**, 제어권 반환.
2. 동기 흐름 계속 → `script end` 출력.
3. 콜 스택 소진. 마이크로태스크 큐 처리: 먼저 등록된 `async1 end`(await 재개) → 그 다음 `promise`.
4. 마이크로태스크 다 비운 뒤 매크로태스크 → `timeout`.

📌 **자주 하는 실수 — 불필요한 직렬(순차) await**

```javascript
// ❌ 느림: 순차 실행 (a 끝나야 b 시작) → 총 2초
const a = await fetchA(); // 1초
const b = await fetchB(); // 1초

// ✅ 빠름: 병렬 실행 → 총 1초
const [a, b] = await Promise.all([fetchA(), fetchB()]);
```
서로 의존하지 않는 비동기 작업을 각각 `await`하면 불필요하게 순차 실행됩니다. **독립적이면 `Promise.all`로 병렬화**하세요.

📌 **에러 처리**: `await`한 Promise가 reject되면 그 자리에서 예외가 던져지므로 `try/catch`로 잡습니다. `Promise.all`은 하나라도 실패하면 즉시 reject되므로, "일부 실패는 허용"하려면 `Promise.allSettled`를 씁니다.

> 💡 **면접 포인트**: "`await`가 스레드를 멈추는 게 아니라 **함수만 중단하고 스택은 풀린다**"는 점, 그리고 "`await` 뒤 코드가 마이크로태스크"라는 점 두 가지를 정확히 말하면 이벤트 루프 이해도가 확실히 드러납니다.

**🔥 예상 꼬리질문**

- **Q. `await`가 실제로 스레드를 블로킹하나요?**
  A. 아닙니다. 함수 실행만 일시 중단하고 콜 스택은 비워집니다. 그 사이 다른 이벤트·렌더링이 처리됩니다. "동기처럼 보이는 논블로킹"입니다.
- **Q. `forEach` 안에서 `await`를 쓰면 왜 안 되나요?**
  A. `Array.prototype.forEach`는 콜백의 Promise를 기다려주지 않아 `await`가 무시된 것처럼 동작합니다. 순차가 필요하면 `for...of` + `await`, 병렬이면 `Promise.all(arr.map(async ...))`을 씁니다.
- **Q. 최상위(top-level)에서 await를 쓸 수 있나요?**
  A. ES 모듈(`type="module"`)에서는 **top-level await**가 가능합니다. 일반 스크립트나 CommonJS에서는 async 함수로 감싸야 합니다.

<details><summary>📝 한 줄 요약</summary>async/await는 Promise의 문법 설탕. await는 함수를 일시 중단하고 스택을 풀며, await 뒤 코드는 .then과 같은 마이크로태스크로 재개된다. 스레드 블로킹 아님. 독립 작업은 Promise.all로 병렬화, 배열 순회는 for...of/Promise.all 사용.</details>

## D7. 자바스크립트는 메모리를 어떻게 관리하나요? GC(가비지 컬렉션) 원리는? 🟡

**💬 30초 답변**
> 자바스크립트는 개발자가 메모리를 직접 할당·해제하지 않고, **가비지 컬렉터(GC)가 자동으로** 안 쓰는 메모리를 회수합니다. 판단 기준은 **"도달 가능성(reachability)"** 입니다. 루트(전역 객체·현재 콜 스택의 변수 등)에서 참조를 따라가 **닿을 수 있으면 살아있는 것**, 어디서도 닿을 수 없으면 "가비지"로 보고 회수합니다. 대표 알고리즘은 **Mark-and-Sweep(표시-후-청소)**: 루트에서 도달 가능한 객체를 전부 표시(mark)한 뒤, 표시 안 된 것을 청소(sweep)합니다. 옛날의 참조 카운팅은 **순환 참조**를 회수 못 해 폐기됐습니다.

**📖 핵심 개념**

📌 **도달 가능성(reachability)이 핵심**
- **루트(roots)**: 전역 객체(`window`/`globalThis`), 현재 실행 중인 함수의 지역 변수·매개변수(콜 스택), 클로저가 붙잡은 변수 등.
- 루트에서 참조를 따라가 닿는 모든 객체 = **살아있음**. 안 닿으면 = **회수 대상**.
- 즉 "변수를 `null`로 밀거나 스코프를 벗어나 **아무도 참조하지 않게 되면**" 회수 가능해진다.

🎯 **비유**: 창고(힙)의 물건들을 손전등(루트)에서 뻗은 연결 끈을 따라 비춥니다. 불이 닿는 물건은 "아직 쓰는 것"이라 남기고, 어떤 끈으로도 불이 닿지 않는 물건은 "버려진 것"이라 치웁니다. 물건끼리 서로 끈으로 묶여 있어도(순환 참조) 손전등에서 그 뭉치로 닿는 끈이 없으면 통째로 치워집니다.

📌 **Mark-and-Sweep 2단계**
1. **Mark**: 루트에서 시작해 도달 가능한 객체를 전부 "살아있음"으로 표시.
2. **Sweep**: 표시 안 된 객체의 메모리를 회수.
→ 순환 참조라도 루트에서 닿지 못하면 통째로 회수되므로, 참조 카운팅의 약점을 극복한다.

📌 **참조 카운팅(옛 방식)의 한계**
```javascript
function leak() {
  const a = {};
  const b = {};
  a.ref = b;   // 서로를 참조
  b.ref = a;   // 순환 참조
}
leak();
// 참조 카운팅: a·b의 카운트가 서로 때문에 0이 안 됨 → 회수 못 함 (누수)
// Mark-and-Sweep: 함수 종료 후 루트에서 a·b에 닿을 수 없음 → 통째로 회수 ✅
```

📌 **현대 엔진(V8)의 최적화** — 이름만 알아도 좋음 🟢
- **세대별 GC(Generational)**: 객체를 **Young(새 객체)** 과 **Old(오래 살아남은 객체)** 로 나눔. "대부분의 객체는 금방 죽는다"는 가설에 따라 Young 영역을 자주·빠르게 청소(Scavenge), Old는 가끔 청소(Mark-Sweep-Compact).
- **증분(Incremental)·동시(Concurrent) GC**: 한 번에 멈추고 청소하면 화면이 끊기므로, 작업을 잘게 쪼개거나 별도 스레드에서 돌려 **stop-the-world(전체 멈춤) 시간을 최소화**.

> 💡 **면접 포인트**: "GC가 자동이니까 신경 안 써도 된다"가 아니라, **"자동이지만 도달 가능한 참조를 실수로 남기면 회수가 안 돼 누수가 난다"** 는 균형 잡힌 이해를 보여주세요. GC를 명령으로 강제 실행할 수는 없습니다(개발용 플래그 제외).

**🔥 예상 꼬리질문**

- **Q. GC를 코드로 직접 트리거할 수 있나요?**
  A. 일반적으론 불가합니다. 언제 도는지는 엔진이 결정합니다(메모리 압력 등에 따라). Node에서 `--expose-gc` 플래그로 `global.gc()`를 열 수 있지만 디버깅용입니다.
- **Q. `delete obj.prop`이 메모리를 바로 비우나요?**
  A. 프로퍼티 참조를 끊을 뿐, 그 값이 다른 곳에서도 참조되지 않을 때 비로소 회수 대상이 됩니다. 즉시 해제를 보장하지 않습니다.
- **Q. `null` 할당은 언제 의미 있나요?**
  A. 오래 사는 객체(전역·클로저)가 큰 데이터를 붙잡고 있을 때, 다 쓴 뒤 `null`로 참조를 끊어주면 회수를 도울 수 있습니다. 짧게 사는 지역 변수엔 불필요합니다.

<details><summary>📝 한 줄 요약</summary>JS는 도달 가능성(reachability) 기반 자동 GC. 루트에서 못 닿는 객체를 Mark-and-Sweep으로 회수 → 순환 참조도 해결. V8은 세대별·증분·동시 GC로 멈춤 시간 최소화. 자동이지만 "안 끊은 참조"는 누수가 된다.</details>

## D8. 메모리 누수는 주로 어떤 패턴에서 생기나요? 어떻게 진단·예방하나요? 🔴

**💬 30초 답변**
> 메모리 누수는 "더 안 쓰는데 **참조가 남아 있어** GC가 회수 못 하는" 상황입니다. 프론트엔드 대표 패턴은 ①**제거하지 않은 이벤트 리스너/타이머**(`setInterval`·`addEventListener`), ②**클로저가 큰 데이터를 계속 붙잡는 경우**, ③**분리된(detached) DOM 노드를 JS 변수가 참조**하는 경우, ④**무한히 커지는 전역 캐시/배열**, ⑤**실수로 만든 전역 변수**입니다. 진단은 Chrome DevTools의 **Memory 탭(힙 스냅샷·Allocation timeline)** 으로 하고, 예방은 "**등록한 건 반드시 해제**"(clearInterval, removeEventListener, React `useEffect` cleanup)가 핵심입니다.

**📖 핵심 개념**

📌 **누수 패턴 5가지와 해결**

**① 제거하지 않은 타이머 / 이벤트 리스너 (가장 흔함)**
```javascript
// ❌ 컴포넌트가 사라져도 인터벌이 계속 돌며 heavyData를 붙잡음
setInterval(() => doSomething(heavyData), 1000);

// ✅ React: cleanup으로 반드시 해제
useEffect(() => {
  const id = setInterval(tick, 1000);
  window.addEventListener('resize', onResize);
  return () => {                 // 언마운트 시 정리
    clearInterval(id);
    window.removeEventListener('resize', onResize);
  };
}, []);
```
> ⚠️ `removeEventListener`는 **등록할 때와 동일한 함수 참조**를 넘겨야 제거됩니다. 익명 함수로 등록하면 절대 못 뗍니다.

**② 클로저가 큰 데이터를 붙잡는 경우**
```javascript
function createHandler() {
  const bigData = new Array(1_000_000).fill('*'); // 큰 데이터
  return function () {
    // bigData를 실제로 안 쓰는데도 클로저가 붙잡고 있으면 회수 안 됨
    console.log('clicked');
  };
}
```
→ 클로저는 필요한 변수만 붙잡도록 스코프를 최소화하고, 큰 데이터가 필요 없으면 참조를 남기지 않는다.

**③ 분리된(detached) DOM 노드**
```javascript
// ❌ DOM에서 지웠지만 JS 변수가 아직 참조 → 회수 안 됨
const cache = [];
const el = document.getElementById('item');
cache.push(el);
el.remove();          // 화면에선 사라짐
// 하지만 cache가 el을 붙잡고 있어 메모리에 남음(detached node)

// ✅ 참조도 함께 정리
cache.length = 0;     // 또는 해당 항목 제거
```

**④ 무한히 커지는 전역 캐시/배열**
```javascript
// ❌ 상한이 없는 캐시 → 계속 증가
const cache = {};
function memoize(key, value) { cache[key] = value; }

// ✅ 크기 제한(LRU) 또는 WeakMap(키 객체가 사라지면 자동 회수) 사용
```

**⑤ 실수로 만든 전역 변수**
```javascript
function f() {
  leaked = 'oops';   // var/let/const 없음 → window.leaked 전역 변수 (비엄격 모드)
}
// → 'use strict'로 방지 (참조 에러로 잡힘)
```

📌 **진단 방법 (Chrome DevTools > Memory)**
- **Heap snapshot**: 특정 시점의 메모리 구성. 스냅샷 2개를 비교해 "안 줄어드는 객체"를 찾는다. `Detached`로 필터링하면 분리된 DOM 노드를 볼 수 있다.
- **Allocation instrumentation on timeline**: 시간에 따른 할당 추이. 조작을 반복해도 메모리가 계단식으로 **안 내려오면** 누수 의심.
- **Performance monitor**: JS heap size, DOM node 수가 사용 중 계속 우상향하는지 관찰.

> 💡 **면접 포인트**: "**등록(subscribe)했으면 반드시 해제(unsubscribe)한다**"를 원칙으로 말하고, React라면 `useEffect`의 cleanup 함수, 프레임워크 없으면 `removeEventListener`/`clearInterval`을 짝지어 관리한다는 실무 습관을 보여주면 좋습니다.

**🔥 예상 꼬리질문**

- **Q. SPA에서 메모리 누수가 더 문제인 이유는?**
  A. 페이지 전환 시 새로고침이 없어 오래된 컴포넌트의 리스너·타이머·참조가 정리 안 되면 계속 누적됩니다. 전통적 MPA는 페이지 이동 때마다 리셋돼 상대적으로 덜합니다.
- **Q. React에서 언마운트된 컴포넌트에 setState하면?**
  A. (구버전 기준) 경고가 뜨고, 비동기 콜백이 사라진 컴포넌트를 참조해 누수·오류가 생길 수 있습니다. cleanup에서 구독 해제하거나 `AbortController`로 요청을 취소해 방지합니다.
- **Q. 이벤트 위임(delegation)이 메모리에 유리한 이유는?**
  A. 자식마다 리스너를 다는 대신 부모 하나에만 달아 리스너 수가 줄고, 자식이 추가/삭제돼도 리스너 등록/해제를 신경 쓸 필요가 적어집니다.

<details><summary>📝 한 줄 요약</summary>누수 = 안 쓰는데 참조가 남아 GC 회수 불가. 대표 원인: 안 뗀 타이머·리스너, 큰 데이터 붙잡는 클로저, detached DOM 참조, 무한 캐시, 실수 전역. 예방은 "등록했으면 해제"(useEffect cleanup). 진단은 DevTools Memory 힙 스냅샷 비교.</details>

## D9. WeakMap/WeakSet은 왜, 언제 쓰나요? 🟢

**💬 30초 답변**
> `WeakMap`/`WeakSet`은 **키(또는 값)를 "약하게" 참조**하는 컬렉션입니다. 일반 `Map`은 키를 강하게 붙잡아, 그 객체가 다른 곳에서 안 쓰여도 Map에 있는 한 GC가 회수하지 못합니다. 반면 `WeakMap`은 **키 객체가 다른 곳에서 사라지면 GC가 자동으로 회수**하고, 해당 항목도 함께 없어집니다. 그래서 "객체에 부가 정보(메타데이터)를 붙이되, 그 객체가 사라지면 정보도 자동 정리"하고 싶을 때, 즉 **캐시·프라이빗 데이터 저장·DOM 노드 메타데이터** 관리에 씁니다. 메모리 누수를 구조적으로 예방하는 도구입니다.

**📖 핵심 개념**

📌 **Map vs WeakMap 핵심 차이**

| | `Map` | `WeakMap` |
|---|---|---|
| 키 타입 | 아무거나 | **객체만** (원시값 불가) |
| 키 참조 | **강한 참조**(회수 막음) | **약한 참조**(회수 허용) |
| 순회 | 가능(`keys()`, `size` 등) | **불가**(비결정적이라 금지) |
| 용도 | 일반 매핑 | 객체 수명에 종속된 부가 정보 |

```javascript
let user = { name: 'Kim' };

const strong = new Map();
strong.set(user, 'data');
user = null;   // user 참조를 끊어도
// strong이 그 객체를 붙잡고 있어 GC가 회수 못 함 → 누수 가능

const weak = new WeakMap();
weak.set(user, 'data');
user = null;   // 다른 참조가 없으면
// 키 객체가 회수되며 weak의 항목도 자동으로 사라짐 → 누수 없음
```

📌 **실전 용도**
- **DOM 노드에 데이터 붙이기**: `weakMap.set(domNode, meta)`. 노드가 DOM에서 제거되고 참조가 사라지면 메타도 자동 정리 → detached node 누수 예방.
- **캐시/메모이제이션**: 객체 키 기반 캐시를 만들되, 키가 사라지면 캐시 항목도 자동 회수돼 무한 증가를 막음.
- **클래스의 진짜 프라이빗 데이터**: (`#` 필드 이전 관용구) 인스턴스를 키로 내부 데이터를 WeakMap에 저장.

📌 **주의**: 순회·크기 확인이 불가능하고 내용이 언제 비는지 예측할 수 없다(GC 타이밍 의존). "전체를 나열해야 하는" 용도엔 부적합하고, "객체 하나에 딸린 정보를 그 객체 수명 동안만 유지"하는 용도에 맞다.

> 💡 **면접 포인트**: "`WeakMap`은 키가 GC되면 항목도 자동으로 사라진다"는 한 문장과, "그래서 캐시·DOM 메타데이터 누수를 예방한다"는 실무 연결을 말하면 충분합니다. `WeakRef`·`FinalizationRegistry`까지 알면 더 깊지만, 이들은 "가능하면 쓰지 말라"고 명세가 권고할 만큼 예측이 어렵다는 점도 함께 언급하면 균형 잡힌 답이 됩니다.

**🔥 예상 꼬리질문**

- **Q. 왜 WeakMap의 키는 객체만 되나요?**
  A. 약한 참조는 "이 대상이 다른 곳에서 사라졌는가"를 추적해야 하는데, 원시값은 고유 정체성이 없어(값 자체로 존재) 회수 개념이 성립하지 않기 때문입니다. (일부 스펙 논의에서 심볼 등 예외가 있지만 기본은 객체.)
- **Q. WeakSet은 어디에 쓰나요?**
  A. "이 객체를 이미 처리했는가"를 표시하는 방문 기록처럼, 객체의 소속 여부만 약하게 저장할 때 씁니다. 객체가 사라지면 집합에서도 자동으로 빠집니다.

<details><summary>📝 한 줄 요약</summary>WeakMap/WeakSet은 키(객체)를 약하게 참조 → 키가 다른 곳에서 사라지면 GC가 항목까지 자동 회수. 순회·size 불가. DOM 메타데이터·캐시·프라이빗 데이터에 써서 누수를 구조적으로 예방한다.</details>

## 🎯 오늘의 핵심 5문장 (면접 직전 암기)

1. **JS 엔진은 싱글 스레드(콜 스택 1개)지만, 비동기 작업은 브라우저/Node 런타임이 백그라운드로 처리하고 콜백을 큐에 넣어 이벤트 루프가 실행한다** → "싱글 스레드지만 논블로킹".
2. **이벤트 루프 규칙: 동기 코드 소진 → 마이크로태스크 큐 전부 → (rAF·렌더링) → 매크로태스크 하나 → 반복.** 마이크로태스크(Promise·await)는 매크로태스크(setTimeout)보다 항상 먼저.
3. **`setTimeout(0)`은 "0ms 뒤"가 아니라 "스택 비고 마이크로태스크 소진 후"에 실행되는 매크로태스크**다. 애니메이션은 주사율과 동기화되는 `requestAnimationFrame`을 쓴다.
4. **`await` 뒤 코드는 `.then`과 같은 마이크로태스크로 재개**되며, `await`는 스레드가 아니라 함수만 중단한다. 독립 작업은 `Promise.all`로 병렬화한다.
5. **JS는 도달 가능성 기반 자동 GC(Mark-and-Sweep)** 를 하지만, 안 뗀 타이머·리스너·클로저·detached DOM 참조는 회수를 막아 누수가 된다 → "등록했으면 해제"가 원칙, `WeakMap`으로 구조적 예방.
