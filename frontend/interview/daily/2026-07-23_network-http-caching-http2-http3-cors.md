## D1. 브라우저 주소창에 URL을 치면 화면이 뜨기까지 네트워크에서 무슨 일이 일어나나요? 🔴

**💬 30초 답변**
> 크게 ①**DNS 조회**(도메인 → IP 변환), ②**TCP 연결**(3-way handshake), ③HTTPS면 **TLS 핸드셰이크**(암호화 키 교환), ④**HTTP 요청/응답**, ⑤받은 HTML을 **파싱·렌더링**하는 순서입니다. 이 중 실제 데이터를 받기 전에 붙는 왕복(RTT) — DNS·TCP·TLS — 이 초기 로딩 지연의 큰 몫을 차지합니다. 그래서 성능 최적화는 "왕복 횟수를 줄이는 것"(연결 재사용, HTTP/2·3, `preconnect`)과 "받은 걸 다시 안 받는 것"(캐싱)으로 나뉩니다.

**📖 핵심 개념**

🎯 **비유**: 택배를 받는 과정과 같습니다. ①주소록에서 상대 집 좌표 찾기(DNS), ②전화 걸어 "지금 보낼게요" 확인(TCP handshake), ③둘만 아는 암호로 포장하기로 약속(TLS), ④실제 물건 주고받기(HTTP), ⑤받아서 개봉·정리(렌더링). 물건을 받기 전 통화·약속에만도 시간이 꽤 걸립니다 — 이게 네트워크 지연(latency)입니다.

📌 **각 단계와 프론트엔드 최적화 포인트**

- **DNS 조회**: 도메인을 IP로 변환. 캐시(브라우저/OS/라우터)에 없으면 여러 DNS 서버를 거친다. → `<link rel="dns-prefetch">`, `preconnect`로 미리.
- **TCP 3-way handshake**: SYN → SYN-ACK → ACK. 최소 1 RTT 소요.
- **TLS handshake**: TLS 1.3 기준 1 RTT(재연결 시 0-RTT 가능). 인증서 검증 + 대칭키 합의.
- **HTTP 요청/응답**: 여기서 캐싱·압축(gzip/brotli)·HTTP 버전이 효율을 좌우.
- **렌더링**: 이후는 브라우저 렌더링 문서(Critical Rendering Path) 참고.

📌 **RTT(Round Trip Time)가 핵심 비용**: 대역폭(bandwidth)이 아무리 커도, 요청 하나에 붙는 왕복 지연은 줄지 않는다. 그래서 "요청을 합치고, 연결을 재사용하고, 물리적으로 가까운 곳(CDN)에서 주는" 전략이 중요하다.

**🔥 예상 꼬리질문**

- **Q. `preconnect`와 `dns-prefetch`의 차이는?**
  A. `dns-prefetch`는 DNS 조회만 미리 해둡니다(가볍다). `preconnect`는 DNS + TCP + TLS까지 미리 맺어둡니다(무겁지만 강력). 곧 반드시 쓸 오리진(예: 폰트·API 서버)에만 `preconnect`를 쓰고, 남발하면 오히려 연결 자원을 낭비합니다.
- **Q. 대역폭을 늘리면 웹이 빨라지나요?**
  A. 큰 파일 다운로드(동영상)는 빨라지지만, 작은 리소스가 많은 웹 로딩은 대역폭보다 **지연(RTT)**과 요청 수에 더 민감합니다. 그래서 브로드밴드가 빨라져도 체감 로딩은 지연에 좌우됩니다.
- **Q. CDN은 이 과정에서 무엇을 개선하나요?**
  A. 사용자와 **물리적으로 가까운 엣지 서버**에서 응답해 DNS·TCP·TLS·전송 모든 왕복의 거리를 줄입니다. 정적 자산 캐싱까지 겹쳐 원본 서버 부하도 줄입니다.

<details><summary>📝 한 줄 요약</summary>URL 입력 → DNS → TCP → TLS → HTTP 요청/응답 → 렌더링. 데이터 전송 전에 붙는 왕복(RTT)이 초기 지연의 핵심이라, 최적화는 "왕복 줄이기(연결 재사용·CDN·preconnect)"와 "다시 안 받기(캐싱)"로 요약된다.</details>

## D2. HTTP 캐싱을 설명해 주세요 — 강한 캐시와 약한 캐시(재검증)의 차이는? 🔴

**💬 30초 답변**
> HTTP 캐싱은 "이미 받은 리소스를 다시 안 받게 해서" 속도·트래픽·서버 부하를 줄이는 메커니즘입니다. 두 층으로 나뉩니다. **강한 캐시(strong cache)**는 `Cache-Control: max-age`/`Expires`로 정한 유효기간 동안 **서버에 아예 묻지 않고** 로컬 캐시를 그대로 씁니다(네트워크 요청 0회). 유효기간이 지나면 **약한 캐시(재검증, revalidation)**로 넘어가, `ETag`/`Last-Modified`를 붙여 서버에 "이거 바뀌었어?"라고 조건부 요청을 보냅니다. 안 바뀌었으면 서버가 본문 없이 **304 Not Modified**만 주고, 브라우저는 로컬 캐시를 재사용합니다.

**📖 핵심 개념**

🎯 **비유**: 냉장고 우유(캐시)가 있습니다. **강한 캐시**는 유통기한(max-age)이 남았으면 마트(서버)에 안 가고 그냥 마시는 것. **약한 캐시(재검증)**는 기한이 지났을 때 마트에 전화해서 "내 우유랑 지금 파는 우유 같은 거야?"라고 묻고, 같으면(304) 냉장고 걸 그대로 마시고, 다르면(200) 새로 받아오는 것입니다. 재검증은 "물어보긴 하되, 본문은 안 받을 수 있다"가 핵심.

📌 **캐시 히트의 3가지 결과**

- **강한 캐시 히트**: 네트워크 요청 없음. DevTools에 `(memory cache)` / `(disk cache)`, 200 표기.
- **재검증 히트(304)**: 조건부 요청은 가되, 본문은 안 옴. 헤더만 오가서 절약.
- **캐시 미스(200)**: 전체를 새로 받음.

📌 **강한 캐시 헤더**

- `Cache-Control: max-age=3600` — 3600초 동안 신선(fresh). **권장**.
- `Expires: <절대시각>` — HTTP/1.0 유물. 클라이언트-서버 시계 차이 문제로 `max-age`가 우선·권장.

📌 **캐시 위치**: 메모리 캐시(빠르지만 탭 닫으면 사라짐), 디스크 캐시(영구), 그리고 프록시/CDN 같은 **공유 캐시(shared cache)**. `private`(브라우저만) vs `public`(공유 캐시도 저장 가능) 구분이 여기서 중요.

**🔥 예상 꼬리질문**

- **Q. 강한 캐시와 재검증, 성능상 뭐가 더 좋나요?**
  A. 강한 캐시가 압도적으로 좋습니다. 재검증은 그래도 **왕복 1회**가 필요하고(304라도 RTT 발생), 강한 캐시는 네트워크를 아예 안 탑니다. 그래서 해시 붙인 정적 자산은 강한 캐시(`immutable`)로, HTML처럼 자주 바뀌는 건 재검증으로 설계합니다.
- **Q. 새로고침(F5)과 강력 새로고침(Ctrl+Shift+R)의 캐시 동작 차이는?**
  A. 일반 새로고침은 캐시를 재검증(조건부 요청)하는 경향이 있고, 강력 새로고침은 `Cache-Control: no-cache`를 붙여 캐시를 무시하고 전부 새로 받습니다.
- **Q. POST 요청도 캐싱되나요?**
  A. 기본적으로 안 됩니다. 캐싱은 주로 GET(과 HEAD) 같은 안전·멱등 메서드 대상입니다.

<details><summary>📝 한 줄 요약</summary>강한 캐시(max-age)는 유효기간 동안 서버에 안 묻고 로컬 사용(요청 0회), 만료 후엔 재검증(ETag/Last-Modified 조건부 요청)으로 넘어가 안 바뀌었으면 304로 본문 없이 재사용. 강한 캐시가 성능상 최고.</details>

## D3. `Cache-Control` 디렉티브를 실무에서 어떻게 설계하나요? 🔴

**💬 30초 답변**
> 리소스 성격에 따라 다르게 줍니다. **해시가 파일명에 박힌 정적 자산**(`app.a1b2c3.js`)은 내용이 바뀌면 파일명도 바뀌므로 `Cache-Control: public, max-age=31536000, immutable`로 1년 캐시 + 재검증 생략. 반대로 **HTML 문서**처럼 URL은 고정인데 내용이 자주 바뀌는 건 `no-cache`(매번 재검증)로 최신성을 보장합니다. 절대 캐시하면 안 되는 민감 데이터는 `no-store`. 핵심은 "URL이 바뀌면 영구 캐시, URL이 그대로면 재검증"입니다.

**📖 핵심 개념**

📌 **자주 헷갈리는 디렉티브 정리**

- `max-age=N` — N초 동안 신선. 이 동안 강한 캐시.
- `no-cache` — **캐시는 하되, 쓰기 전 반드시 재검증**. ("캐시 안 함"이 아니다! 이름이 함정.)
- `no-store` — **아예 저장 금지**. 민감 정보(개인정보·결제)에 사용.
- `public` — 프록시·CDN 등 공유 캐시도 저장 가능.
- `private` — 브라우저(최종 사용자)만 저장. 사용자별 응답에 사용.
- `immutable` — 신선한 동안엔 재검증 요청조차 보내지 마라(새로고침 시 불필요한 304 방지).
- `s-maxage=N` — 공유 캐시(CDN) 전용 max-age. 브라우저 `max-age`와 다르게 설정 가능.
- `must-revalidate` — 만료되면 반드시 재검증(오프라인 시 낡은 캐시 사용 금지).

🎯 **비유**: `no-cache`는 "물어보고 써", `no-store`는 "가지고 있지도 마". 이름과 달리 `no-cache`도 캐시를 **저장은** 한다는 점이 면접 단골 함정입니다.

📌 **실무 정석 패턴 (캐시 무효화 전략)**

```
# 1) 해시 파일명 정적 자산 (JS/CSS/이미지 with content hash)
Cache-Control: public, max-age=31536000, immutable

# 2) HTML (진입점, 자주 바뀜, URL 고정)
Cache-Control: no-cache
# → 항상 재검증. 새 배포 시 새 해시 파일명을 참조하게 됨

# 3) 사용자별 API 응답
Cache-Control: private, no-cache

# 4) 민감 데이터 (결제/개인정보)
Cache-Control: no-store
```

이 조합의 마법: HTML은 항상 최신을 재검증해서 받고, 그 HTML이 가리키는 `app.[새해시].js`는 파일명 자체가 바뀌므로 **캐시 무효화(cache busting)**가 자동으로 된다. 바뀌지 않은 자산은 계속 1년 캐시를 재사용한다.

**🔥 예상 꼬리질문**

- **Q. `no-cache`인데 왜 캐시라는 단어가 들어가나요?**
  A. "캐시하지 마"가 아니라 "캐시를 **쓰기 전에** 반드시 서버에 재검증하라"는 뜻입니다. 저장은 합니다. 진짜 저장 금지는 `no-store`입니다.
- **Q. `immutable`을 왜 쓰나요? `max-age`만으로 안 되나요?**
  A. 일부 브라우저는 사용자가 새로고침하면 `max-age`가 남아도 재검증 요청을 보냅니다. `immutable`은 "이 URL의 내용은 절대 안 바뀐다"고 알려 그 불필요한 304 요청까지 없앱니다. 해시 파일명에 최적입니다.
- **Q. CDN 캐시와 브라우저 캐시를 다르게 주고 싶으면?**
  A. `s-maxage`(공유 캐시)와 `max-age`(브라우저)를 따로 지정합니다. 예: `Cache-Control: public, max-age=0, s-maxage=86400` → 브라우저는 매번 재검증하지만 CDN은 하루 캐시.

<details><summary>📝 한 줄 요약</summary>"URL이 바뀌면 영구 캐시(해시 파일명 + immutable, max-age=1년), URL이 그대로면 재검증(no-cache)"이 정석. no-cache는 "저장하되 매번 재검증", no-store는 "저장 금지". s-maxage로 CDN과 브라우저 캐시를 분리.</details>

## D4. ETag / Last-Modified 재검증은 어떻게 동작하나요? `stale-while-revalidate`는? 🟡

**💬 30초 답변**
> 재검증은 "내 캐시가 여전히 유효한지 서버에 최소 비용으로 확인"하는 것입니다. 서버가 응답에 `ETag`(내용의 지문 같은 해시)나 `Last-Modified`(최종 수정 시각)를 붙여주면, 다음 요청 때 브라우저가 각각 `If-None-Match`/`If-Modified-Since` 헤더로 되돌려 보냅니다. 서버가 비교해 안 바뀌었으면 본문 없이 **304**를, 바뀌었으면 새 본문과 함께 **200**을 줍니다. `stale-while-revalidate`는 여기서 한 단계 더 나아가, 만료된 캐시를 **일단 즉시 보여주고(빠름), 뒤에서 몰래 새로 받아** 다음을 대비하는 전략입니다.

**📖 핵심 개념**

📌 **ETag vs Last-Modified**

- **ETag**: 리소스 내용을 대표하는 고유 식별자(보통 해시). 내용이 1바이트만 달라도 바뀐다. 정밀함.
  - 강한 ETag `"abc"` vs 약한 ETag `W/"abc"`: 약한 것은 "의미상 같으면 OK"(바이트 단위 동일까진 보장 안 함).
- **Last-Modified**: 최종 수정 시각. 1초 단위 해상도라 1초 내 여러 번 바뀌면 놓칠 수 있고, 내용이 같은데 시각만 바뀌어도 무효가 됨. → 그래서 **ETag가 더 정밀**하고 우선.

🎯 **비유**: `ETag`는 문서의 지문(내용 기반), `Last-Modified`는 문서에 찍힌 저장 시각(도장). 지문이 더 정확하지만, 도장은 만들기 쉽다.

📌 **재검증 흐름 (그림으로)**

```
[1차 요청]
GET /data.json
← 200 OK
  ETag: "v1-abc"
  Cache-Control: max-age=60

[60초 후, 2차 요청 — 만료됨 → 재검증]
GET /data.json
  If-None-Match: "v1-abc"        ← 브라우저가 되돌려줌
← 304 Not Modified               ← 본문 없음! 캐시 재사용 (절약)
  (또는 바뀌었으면 200 + 새 본문 + 새 ETag)
```

📌 **`stale-while-revalidate` (SWR)**

```
Cache-Control: max-age=60, stale-while-revalidate=300
```

- 0~60초: 신선. 캐시 그대로.
- 60~360초: **만료됐지만** 캐시를 **즉시 반환**(사용자 대기 0) + 백그라운드에서 새로 fetch해 캐시 갱신.
- 360초 이후: 정상 재검증(사용자가 기다림).
→ "약간 낡아도 되니 일단 빠르게, 최신화는 뒤에서" — UX와 신선도의 절충. (참고: TanStack Query·React 이름의 어원이기도 함)

**🔥 예상 꼬리질문**

- **Q. 304 응답은 왜 이득인가요? 어차피 요청은 갔잖아요?**
  A. 왕복 1회는 발생하지만 **본문(payload)을 안 받습니다**. 큰 이미지·번들이라면 헤더 몇 백 바이트만 오가고 수백 KB를 아낍니다. 다만 강한 캐시(요청 0회)보다는 느립니다.
- **Q. ETag가 서버 여러 대(로드밸런싱)에서 문제될 수 있나요?**
  A. 예. 서버마다 ETag 생성 방식(예: inode 기반)이 다르면 같은 파일에 다른 ETag가 붙어 캐시가 계속 무효화될 수 있습니다. 내용 해시 기반으로 일관되게 생성해야 합니다.
- **Q. SWR 전략의 단점은?**
  A. 사용자가 아주 잠깐 **낡은 데이터**를 볼 수 있습니다. 실시간 정확성이 필수인 화면(잔액·재고)에는 부적합하고, 아바타·목록 미리보기 등 약간의 지연 허용 가능한 곳에 적합합니다.

<details><summary>📝 한 줄 요약</summary>ETag(내용 지문)/Last-Modified(수정 시각)를 If-None-Match/If-Modified-Since로 되돌려 재검증 → 안 바뀌면 304(본문 없음). ETag가 더 정밀. stale-while-revalidate는 "낡은 캐시 즉시 반환 + 뒤에서 갱신"으로 속도와 신선도를 절충.</details>

## D5. HTTP/1.1의 한계와 HTTP/2가 해결한 것은? (멀티플렉싱·HOL 블로킹) 🔴

**💬 30초 답변**
> HTTP/1.1은 **연결 하나에서 요청을 한 번에 하나씩** 순서대로 처리합니다. 앞 요청이 느리면 뒤 요청이 다 막히는 **HTTP 레벨 Head-of-Line(HOL) 블로킹**이 생기고, 이를 우회하려고 브라우저가 도메인당 6개 정도 연결을 동시에 여는데 이것도 한계가 있었습니다. HTTP/2는 하나의 TCP 연결 안에서 요청·응답을 **스트림**으로 쪼개 병렬로 주고받는 **멀티플렉싱**을 도입해 이 HOL 블로킹을 해결했습니다. 여기에 **헤더 압축(HPACK)**과 **서버 푸시**(현재는 사실상 폐기 추세)도 추가됐습니다.

**📖 핵심 개념**

📌 **HTTP/1.1의 문제들**

- **HOL 블로킹**: 연결 하나에서 요청은 직렬. 앞 응답이 느리면 뒤가 대기. (파이프라이닝이 있었으나 순서 보장 문제로 사실상 미사용.)
- **연결 6개 제한 우회**: 브라우저가 오리진당 ~6개 TCP 연결을 열어 병렬화 → 연결마다 handshake 비용, 서버 부담. "도메인 샤딩"이라는 꼼수까지 등장.
- **헤더 중복**: 매 요청마다 쿠키·User-Agent 등 큰 헤더를 텍스트로 반복 전송.

🎯 **비유**: HTTP/1.1은 계산대가 하나뿐인 마트에서, 손님(요청)이 한 줄로 서서 앞사람이 끝나야 다음 사람이 계산하는 것. 앞사람이 가격 확인으로 오래 걸리면 뒤가 다 막힘. 여러 줄(연결 6개)을 만들어 우회했지만 계산대 수가 한정적. HTTP/2는 **한 계산대에서 여러 손님 물건을 번갈아 동시에** 처리하는 방식.

📌 **HTTP/2의 핵심 개선**

- **멀티플렉싱**: 하나의 TCP 연결에서 여러 요청/응답을 **스트림**으로 인터리빙. HTTP 레벨 HOL 블로킹 해소. 연결 하나면 충분해 handshake 비용도 절감.
- **바이너리 프레이밍**: 텍스트가 아닌 바이너리 프레임 단위로 통신 → 파싱 효율·다중화 가능.
- **HPACK 헤더 압축**: 반복 헤더를 인덱스 테이블로 압축.
- **스트림 우선순위·서버 푸시**: 우선순위 지정 가능. 서버 푸시는 캐시 문제 등으로 실전에서 외면받아 폐기 추세(대신 `103 Early Hints`/`preload` 사용).

📌 **주의 — HTTP/2도 못 푼 것**: 멀티플렉싱은 **HTTP 레벨**의 HOL만 없앴을 뿐, 그 아래 **TCP 레벨의 HOL**은 그대로다. TCP는 패킷 순서를 보장하므로, 패킷 하나가 유실되면 그걸 재전송받을 때까지 그 연결의 **모든 스트림이 함께 멈춘다**. 이게 HTTP/3가 등장한 이유.

**🔥 예상 꼬리질문**

- **Q. HTTP/2를 쓰면 파일을 여러 개로 쪼개는 게 나은가요, 합치는 게 나은가요?**
  A. HTTP/1.1 시절엔 요청 수를 줄이려 번들을 크게 합쳤지만, HTTP/2는 멀티플렉싱 덕에 요청 수 페널티가 작아 **적당히 쪼개는(코드 스플리팅)** 편이 캐시 효율·초기 로딩에 유리해졌습니다. 다만 너무 잘게 쪼개면 압축률·오버헤드 손해라 균형이 필요합니다.
- **Q. 도메인 샤딩은 이제 안티패턴인가요?**
  A. HTTP/2에서는 그렇습니다. 연결을 하나로 모아야 멀티플렉싱·우선순위가 효과적인데, 샤딩은 연결을 분산시켜 오히려 역효과입니다.
- **Q. HTTP/2는 HTTPS가 필수인가요?**
  A. 스펙상 평문(h2c)도 있지만, 실제 브라우저는 **TLS 위에서만** HTTP/2를 지원합니다. 사실상 HTTPS 필수.

<details><summary>📝 한 줄 요약</summary>HTTP/1.1은 연결당 요청 직렬 → HOL 블로킹, 연결 6개로 우회. HTTP/2는 한 TCP 연결에서 스트림 멀티플렉싱으로 병렬화 + HPACK 헤더 압축. 단, TCP 레벨 HOL 블로킹은 남아 HTTP/3로 이어짐.</details>

## D6. HTTP/3와 QUIC는 무엇을 더 해결했나요? 🟢

**💬 30초 답변**
> HTTP/2가 못 푼 **TCP 레벨 HOL 블로킹**을 해결한 게 HTTP/3입니다. 원인은 HTTP/2가 TCP 위에서 돌기 때문인데, HTTP/3는 아예 전송 프로토콜을 **UDP 기반의 QUIC**로 바꿨습니다. QUIC는 스트림별로 독립적으로 패킷 순서를 관리해서, 한 스트림의 패킷이 유실돼도 **다른 스트림은 멈추지 않습니다**. 게다가 TCP 핸드셰이크와 TLS 핸드셰이크를 하나로 합쳐 **연결 수립이 훨씬 빠르고**(1-RTT, 재연결 0-RTT), IP가 바뀌어도(Wi-Fi ↔ LTE) **연결 마이그레이션**으로 끊기지 않습니다.

**📖 핵심 개념**

📌 **왜 TCP를 버리고 UDP(QUIC)로 갔나**

- TCP는 "순서 보장" 특성상, 패킷 유실 시 재전송을 기다리며 그 연결의 모든 데이터가 멈춤(TCP HOL). HTTP/2 멀티플렉싱의 발목을 잡았다.
- QUIC는 UDP 위에 신뢰성·혼잡제어·암호화를 **직접 구현**하고, 스트림을 독립적으로 관리해 한 스트림 유실이 다른 스트림에 영향 없다.

🎯 **비유**: HTTP/2는 여러 짐(스트림)을 한 컨베이어 벨트(TCP) 위에 순서대로 올린 것 — 앞 짐 하나가 떨어지면 벨트 전체가 멈춤. HTTP/3(QUIC)는 짐마다 **독립된 레일**을 줘서, 한 레일이 막혀도 나머지는 계속 흐름.

📌 **QUIC의 추가 이점**

- **빠른 연결 수립**: 전송+암호화 핸드셰이크 통합 → 최초 1-RTT, 재방문 시 **0-RTT** 가능.
- **연결 마이그레이션**: 연결을 IP·포트가 아닌 **Connection ID**로 식별. 네트워크가 Wi-Fi에서 셀룰러로 바뀌어도 연결 유지(모바일에 특히 유리).
- **항상 암호화**: TLS 1.3이 QUIC에 내장돼 평문 모드가 없다.

📌 **현실 배치**: 브라우저·주요 CDN·구글/유튜브 등이 폭넓게 지원. 클라이언트는 보통 HTTP/2로 시작한 뒤 `Alt-Svc` 헤더로 "나 HTTP/3도 돼"를 알려 다음부터 업그레이드한다. UDP를 막는 일부 방화벽 환경에선 TCP로 폴백.

**🔥 예상 꼬리질문**

- **Q. UDP는 신뢰성이 없는데 어떻게 HTTP를 실어 나르나요?**
  A. QUIC이 UDP 위에서 재전송·순서 재조립·혼잡제어를 **애플리케이션 레벨로 직접** 구현합니다. 즉 UDP의 가벼움을 쓰되 신뢰성은 QUIC이 책임집니다.
- **Q. HTTP/3가 항상 빠른가요?**
  A. 지연이 크거나 패킷 손실이 잦은 모바일 환경에서 특히 유리합니다. 유선·저손실 환경에선 HTTP/2와 큰 차이가 안 날 수 있고, UDP 차단 네트워크에선 폴백 비용이 있습니다.
- **Q. 0-RTT의 보안 위험은?**
  A. 0-RTT 데이터는 재전송 공격(replay)에 취약할 수 있어, 멱등하지 않은 요청(예: 결제 POST)에는 쓰지 않도록 주의합니다.

<details><summary>📝 한 줄 요약</summary>HTTP/3는 TCP를 버리고 UDP 기반 QUIC를 채택해 TCP 레벨 HOL 블로킹을 제거(스트림 독립). 핸드셰이크 통합으로 연결이 빠르고(0/1-RTT), Connection ID로 네트워크 전환에도 연결 유지. TLS 1.3 내장으로 항상 암호화.</details>

## D7. CORS란 무엇이고, 왜 존재하나요? 단순 요청 vs 프리플라이트 🔴

**💬 30초 답변**
> CORS(Cross-Origin Resource Sharing)는 브라우저의 **동일 출처 정책(Same-Origin Policy)**을 안전하게 완화하는 규약입니다. 기본적으로 브라우저는 스크립트가 **다른 출처(origin = 프로토콜+호스트+포트)**의 응답을 읽는 것을 막는데, 서버가 `Access-Control-Allow-Origin` 헤더로 "이 출처는 허용해"라고 명시하면 브라우저가 허용합니다. 이때 부수효과가 있는 요청(PUT/DELETE, 커스텀 헤더 등)은 본 요청 전에 **OPTIONS 프리플라이트**를 먼저 보내 서버 허가를 확인합니다. 중요한 건 CORS는 **서버가 아니라 브라우저가 강제**한다는 점입니다.

**📖 핵심 개념**

📌 **왜 존재하나 — SOP(동일 출처 정책)**: 만약 아무 사이트나 내 로그인 세션으로 은행 API를 마음대로 호출·응답을 읽을 수 있다면 재앙이다. 그래서 브라우저는 기본적으로 교차 출처 응답 읽기를 막고, CORS는 "서버가 명시적으로 허락한 경우에만" 이를 여는 안전장치다.

🎯 **비유**: CORS는 아파트 공동현관 출입 시스템입니다. 방문자(다른 출처)가 오면 경비(브라우저)가 "이 집(서버)이 당신을 허락했나요?"를 확인합니다. 집주인이 방문자 명단(`Access-Control-Allow-Origin`)에 올려두면 통과, 아니면 차단. 경비는 **방문자 편이 아니라 건물(브라우저) 규칙**을 집행합니다.

📌 **단순 요청(Simple Request) vs 프리플라이트(Preflight)**

- **단순 요청**: 아래 조건을 모두 만족하면 프리플라이트 없이 바로 감.
  - 메서드가 GET / POST / HEAD
  - 헤더가 안전한 기본 헤더 위주(`Accept`, `Content-Type` 등)
  - `Content-Type`이 `application/x-www-form-urlencoded` / `multipart/form-data` / `text/plain` 중 하나
- **프리플라이트 요청**: 위 조건을 벗어나면(예: `Content-Type: application/json`, `PUT`/`DELETE`, 커스텀 헤더 `Authorization` 등) 브라우저가 **본 요청 전에 자동으로 OPTIONS**를 보내 허가를 확인.

📌 **프리플라이트 주고받는 헤더**

```
[프리플라이트 요청 — 브라우저가 자동 발송]
OPTIONS /api/users
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

[서버 응답]
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 600      ← 이 결과를 600초 캐시(프리플라이트 반복 방지)
```

**🔥 예상 꼬리질문**

- **Q. CORS 에러가 나면 서버에는 요청이 도달한 건가요?**
  A. 경우에 따라 다릅니다. 프리플라이트가 필요한 요청이면 본 요청은 안 가고 OPTIONS에서 막힙니다. 단순 요청이면 **서버엔 도달·처리까지 됐지만**, 브라우저가 응답을 스크립트에 넘겨주지 않을 뿐입니다(그래서 서버 로그엔 200이 찍혀도 프론트는 에러). 이게 CORS의 핵심 오해 포인트입니다.
- **Q. `Access-Control-Allow-Origin: *`의 문제는?**
  A. 모든 출처 허용이라 편하지만, **credentials(쿠키)와 함께 쓸 수 없습니다**. 인증이 필요한 API엔 구체적 출처를 명시해야 합니다.
- **Q. 프론트에서 CORS 에러를 "코드로" 해결할 수 있나요?**
  A. 근본적으로는 **서버가 헤더를 줘야** 합니다. 프론트 측 우회로는 개발 중 프록시(예: dev server proxy)나 같은 오리진으로 요청을 보내는 BFF/리버스 프록시가 있습니다. `mode: 'no-cors'`는 응답을 읽지 못하게 되니 해결책이 아닙니다.

<details><summary>📝 한 줄 요약</summary>CORS는 동일 출처 정책을 서버가 헤더(Access-Control-Allow-Origin)로 명시 허락할 때만 여는 브라우저 강제 규약. 부수효과 있는 요청(PUT/DELETE·JSON·커스텀 헤더)은 OPTIONS 프리플라이트로 사전 확인. 단순 요청은 서버엔 도달하되 브라우저가 응답 읽기를 차단.</details>

## D8. CORS + 인증정보(쿠키/토큰)는 어떻게 다루나요? 🔴

**💬 30초 답변**
> 교차 출처 요청에 **쿠키를 실어 보내려면** 세 조건이 동시에 맞아야 합니다: ①클라이언트가 `fetch(url, { credentials: 'include' })`(또는 axios `withCredentials: true`), ②서버가 `Access-Control-Allow-Credentials: true`, ③서버의 `Access-Control-Allow-Origin`이 `*`가 아니라 **정확한 출처**여야 합니다. 하나라도 어긋나면 쿠키가 안 붙거나 브라우저가 응답을 차단합니다. 요즘은 쿠키에 `SameSite`/`Secure` 속성까지 얽혀서, 교차 사이트 쿠키는 `SameSite=None; Secure`가 필요합니다.

**📖 핵심 개념**

📌 **credentials 3종 세트 (전부 만족해야 함)**

```javascript
// 클라이언트
fetch('https://api.example.com/me', {
  credentials: 'include',   // ① 쿠키 포함
});

// 서버 응답 헤더
Access-Control-Allow-Origin: https://app.example.com  // ③ 와일드카드 * 금지
Access-Control-Allow-Credentials: true                // ②
```

📌 **`SameSite` 쿠키 속성** (CSRF 방어 + 교차 사이트 동작)

- `Strict`: 교차 사이트 요청엔 쿠키 안 붙음(가장 안전, 외부 링크 유입 시 로그인 풀림 체감).
- `Lax`: 기본값. 안전한 top-level 내비게이션(GET 링크 클릭)엔 붙지만, 교차 사이트 POST/서브리소스엔 안 붙음.
- `None`: 교차 사이트에도 붙음. 단 **반드시 `Secure`(HTTPS)** 동반. 서드파티 쿠키 시나리오에 필요.

🎯 **비유**: 쿠키는 신분증입니다. `credentials: 'include'`는 "신분증 챙겨 갈게", 서버의 `Allow-Credentials: true`는 "신분증 받을게", 정확한 출처 명시는 "너라는 걸 특정해서 받을게". 아무한테나(`*`) 신분증을 받겠다는 건 위험해서 브라우저가 금지합니다.

📌 **쿠키 vs 토큰(Authorization 헤더) 저장 전략**

- **httpOnly 쿠키**: JS로 접근 불가 → XSS로 탈취 어려움. 대신 CSRF 대비(SameSite·CSRF 토큰) 필요. 브라우저가 자동 전송.
- **JS 접근 가능한 저장소(localStorage) + Authorization 헤더**: CSRF엔 강하지만 **XSS에 토큰이 그대로 노출**. `Authorization` 커스텀 헤더는 CORS 프리플라이트를 유발.
→ 보안 자료(웹 보안 편)와 연결: 실무 기본값은 **httpOnly + SameSite 쿠키**를 선호하는 흐름.

**🔥 예상 꼬리질문**

- **Q. `Allow-Origin: *` + credentials 조합이 왜 금지되나요?**
  A. 아무 출처나 남의 쿠키를 실어 인증된 요청을 보내고 응답을 읽을 수 있게 되면 보안이 무너집니다. 그래서 credentials를 쓰면 출처를 반드시 특정하도록 강제합니다.
- **Q. 여러 출처를 허용하려면 `*`도 못 쓰는데 어떻게 하나요?**
  A. 서버가 요청의 `Origin` 헤더를 보고 **화이트리스트와 대조해 해당 출처를 그대로 반사(echo)**해서 `Access-Control-Allow-Origin`에 넣고, `Vary: Origin`을 붙여 캐시 오염을 방지합니다.
- **Q. 서드파티 쿠키 폐기 흐름이 이 설계에 어떤 영향을 주나요?**
  A. 브라우저들이 서드파티 쿠키를 제한하는 방향이라, 교차 사이트 쿠키 의존 인증은 취약해집니다. 같은 사이트(BFF·리버스 프록시로 오리진 통일)나 토큰 기반 설계로 옮기는 흐름이 강해졌습니다.

<details><summary>📝 한 줄 요약</summary>교차 출처에 쿠키를 실으려면 클라이언트 credentials:'include' + 서버 Allow-Credentials:true + Allow-Origin이 구체적 출처(와일드카드 금지) 세 가지가 동시에 필요. 교차 사이트 쿠키는 SameSite=None; Secure 필수. 기본 보안 권장은 httpOnly+SameSite 쿠키.</details>

## D9. HTTPS/TLS 핸드셰이크는 어떻게 동작하나요? 🟡

**💬 30초 답변**
> HTTPS는 HTTP를 **TLS**로 감싸 ①기밀성(암호화), ②무결성(변조 감지), ③인증(상대가 진짜인지)을 보장합니다. 핵심은 TLS 핸드셰이크인데, **비대칭 키(공개키/개인키)로 안전하게 대칭 키를 합의**한 뒤, 실제 데이터는 빠른 **대칭 키로 암호화**합니다. 서버는 CA(인증기관)가 서명한 인증서로 자신이 진짜임을 증명하고, 브라우저는 그 서명 체인을 검증합니다. TLS 1.3에서는 이 과정이 최적화돼 **1-RTT**(재연결 시 0-RTT)로 끝납니다.

**📖 핵심 개념**

🎯 **비유**: 처음 만난 두 사람이 비밀 대화를 하려 합니다. 아무나 못 여는 자물쇠(공개키)를 서로 주고받아, 그 자물쇠로만 잠긴 상자 안에 **공용 비밀번호(대칭키)**를 넣어 교환합니다. 이후 대화는 무겁고 느린 자물쇠 대신 빠른 공용 비밀번호로 암호화합니다. 인증서는 "이 자물쇠가 진짜 그 은행 것"임을 보증하는 공증 도장(CA 서명)입니다.

📌 **왜 비대칭 → 대칭 하이브리드인가**: 비대칭 암호(RSA/ECDHE)는 안전하지만 느리고, 대칭 암호(AES)는 빠르지만 키를 안전하게 공유하기 어렵다. 그래서 **키 교환만 비대칭으로 안전하게** 하고, **실제 데이터 암호화는 대칭키로 빠르게** 하는 하이브리드 구조를 쓴다.

📌 **TLS 1.3 핸드셰이크(간략)**

- ClientHello: 지원 암호 스위트 + 키 공유(공개값) 제시.
- ServerHello: 암호 스위트 선택 + 서버 키 공유 + 인증서 전송.
- 양쪽이 교환한 값으로 **동일한 대칭 세션 키를 각자 계산**(ECDHE) → 키 자체는 네트워크에 안 흐름.
- 이후 애플리케이션 데이터는 세션 키로 암호화. (1-RTT)

📌 **인증서 신뢰 체인**: 서버 인증서 → 중간 CA → 루트 CA. 브라우저/OS에 내장된 루트 CA 목록을 기준으로 서명 체인을 검증한다. 만료·도메인 불일치·자체 서명이면 경고.

📌 **전방향 안전성(Forward Secrecy)**: ECDHE로 매 세션 임시 키를 쓰면, 훗날 서버 개인키가 유출돼도 **과거에 캡처된 트래픽을 복호화할 수 없다**. TLS 1.3은 이를 기본화.

**🔥 예상 꼬리질문**

- **Q. HTTPS는 무엇을 보호하고 무엇은 못 보호하나요?**
  A. 통신 내용(본문·헤더·경로)을 암호화합니다. 다만 **어떤 도메인(호스트)에 접속하는지**는 DNS·SNI에서 드러날 수 있고(→ Encrypted ClientHello로 개선 중), HTTPS는 서버 자체의 취약점(XSS 등)은 막지 못합니다.
- **Q. 중간자 공격(MITM)은 어떻게 막나요?**
  A. 인증서 체인 검증으로 "상대가 진짜인지"를 확인합니다. 공격자가 가짜 키를 끼워넣어도 신뢰된 CA 서명이 없으면 브라우저가 경고합니다. HSTS로 HTTPS 강제까지 하면 다운그레이드 공격도 방어합니다.
- **Q. 0-RTT의 장단점은?**
  A. 재방문 시 핸드셰이크 왕복 없이 즉시 데이터 전송이 가능해 빠릅니다. 단 재전송(replay) 공격 위험이 있어 멱등하지 않은 요청엔 쓰지 않습니다.

<details><summary>📝 한 줄 요약</summary>HTTPS는 TLS로 기밀성·무결성·인증을 제공. 핸드셰이크에서 비대칭 키로 대칭 세션 키를 안전하게 합의하고(하이브리드), 이후 데이터는 빠른 대칭키로 암호화. CA 서명 체인으로 서버 신원 검증, TLS 1.3은 1-RTT + 전방향 안전성 기본.</details>

## 🎯 이 주제를 관통하는 3줄 정리

1. **네트워크 지연의 정체는 왕복(RTT)** — 최적화는 "왕복 줄이기(HTTP/2·3·연결 재사용·CDN)"와 "다시 안 받기(캐싱)" 두 축이다.
2. **캐싱 설계의 원칙** — "URL이 바뀌면 영구 캐시(해시 파일명+immutable), URL이 그대로면 재검증(no-cache/ETag)". `no-cache`는 저장하되 재검증, `no-store`가 진짜 저장 금지.
3. **CORS는 브라우저가 강제하는 규약** — 서버가 헤더로 허락해야 열리고, 부수효과 요청은 OPTIONS 프리플라이트로 사전 확인하며, 쿠키를 실으려면 credentials 3종 세트가 필요하다.
