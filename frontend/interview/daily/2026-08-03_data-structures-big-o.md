## D1. 시간복잡도(Big-O)란 무엇이고, 왜 중요한가요? 🔴

**💬 30초 답변**
> Big-O는 **입력 크기 n이 커질 때 연산 횟수(또는 메모리)가 어떤 비율로 증가하는지**를 나타내는 표기법입니다. 실제 실행 시간(ms)이 아니라 **증가 추세**를 봅니다. 상수와 낮은 차수 항은 무시하고 가장 지배적인 항만 남깁니다(예: `3n² + 5n + 10 → O(n²)`). 자료구조를 고르는 기준이 바로 이 복잡도라서, "이 기능은 데이터가 10배 늘면 느려질까?"를 코드 실행 전에 판단할 수 있게 해 줍니다. 흔한 등급은 O(1) < O(log n) < O(n) < O(n log n) < O(n²) 순으로 나빠집니다.

**📖 핵심 개념**

🎯 **비유**: Big-O는 "요리 레시피의 확장성"입니다. 손님이 2배로 와도 준비 시간이 그대로면 O(1)(예: 미리 만든 소스 한 스푼), 손님 수에 비례하면 O(n)(1인분씩 굽기), 손님끼리 전부 악수시키면 O(n²)(모두가 서로 인사)입니다. **한 명일 땐 다 비슷해 보여도, 1000명이 되면 격차가 폭발**합니다.

📌 **주요 등급과 감각**

| 표기 | 이름 | n=10 | n=1,000 | 대표 예시 |
|---|---|---|---|---|
| O(1) | 상수 | 1 | 1 | 배열 인덱스 접근, Map.get |
| O(log n) | 로그 | ~3 | ~10 | 이진 탐색, 균형 BST 탐색 |
| O(n) | 선형 | 10 | 1,000 | 배열 순회, `indexOf`, `filter` |
| O(n log n) | 선형로그 | ~33 | ~10,000 | 효율적 정렬(`Array.sort`) |
| O(n²) | 제곱 | 100 | 1,000,000 | 이중 for문, 중첩 비교 |

📌 **규칙 3가지**: ① **상수 무시** — `O(2n)`도 `O(n)`. ② **최고차항만** — `O(n² + n)`은 `O(n²)`. ③ **최악(worst case) 기준**이 기본이지만, 해시처럼 "평균 O(1)·최악 O(n)"인 경우는 평균도 같이 언급하는 게 정확합니다.

📌 **시간 vs 공간**: Big-O는 시간뿐 아니라 **공간(메모리) 복잡도**에도 씁니다. 예를 들어 "중복 제거"를 이중 루프로 하면 시간 O(n²)·공간 O(1)이지만, `Set`을 쓰면 시간 O(n)·공간 O(n)입니다. **시간을 아끼려 메모리를 더 쓰는 트레이드오프(time-space tradeoff)**가 실무의 핵심 판단입니다.

```js
// O(n²): 배열끼리 중복 찾기 — 데이터 커지면 급격히 느려짐
function hasDupSlow(arr) {
  for (let i = 0; i < arr.length; i++)
    for (let j = i + 1; j < arr.length; j++)
      if (arr[i] === arr[j]) return true;
  return false;
}

// O(n): Set(해시)로 공간을 더 쓰는 대신 시간을 확 줄임
function hasDupFast(arr) {
  const seen = new Set();
  for (const x of arr) {
    if (seen.has(x)) return true; // has: 평균 O(1)
    seen.add(x);
  }
  return false;
}
```

**🔥 예상 꼬리질문**
- Q. O(1)이 항상 O(n)보다 빠른가요? → A. **점근적으로는** 그렇지만, n이 작으면 상수 계수 때문에 역전될 수 있습니다. Big-O는 "충분히 큰 n"에서의 추세이지 실제 절대속도 보장이 아닙니다.
- Q. `Array.prototype.sort`의 복잡도는? → A. 명세는 구현에 맡기지만 대부분 엔진(V8)이 O(n log n) 정렬(TimSort)을 씁니다. 비교 함수 안에서 무거운 연산을 하면 그 비용이 곱해집니다.
- Q. 왜 최악의 경우를 기준으로 하나요? → A. 성능 보장(SLA)·사용자 경험은 "가장 느릴 때"에 좌우되기 때문입니다. 다만 해시처럼 최악이 드물면 평균을 함께 말합니다.

<details><summary>📝 한 줄 요약</summary>Big-O = 입력이 커질 때 연산량 증가 추세(상수·저차항 무시). O(1)<O(log n)<O(n)<O(n log n)<O(n²). 자료구조 선택의 기준이며, 시간과 공간의 트레이드오프를 판단하는 언어.</details>

## D2. 자바스크립트 배열(Array)은 내부적으로 어떻게 동작하고, 연산별 비용은 얼마인가요? 🔴

**💬 30초 답변**
> 배열은 **인덱스(정수 키)로 값에 접근하는 순차 컬렉션**입니다. 이론적 배열은 메모리에 연속으로 놓여 **인덱스 접근이 O(1)**입니다. 끝에 넣고 빼는 `push`/`pop`은 **분할상환(amortized) O(1)**, 반면 앞에서 넣고 빼는 `unshift`/`shift`는 **뒤 원소들을 전부 한 칸씩 밀어야 해서 O(n)**입니다. 값으로 찾는 `indexOf`/`includes`는 처음부터 훑어야 하니 O(n)이고, 중간 삽입·삭제(`splice`)도 O(n)입니다. 즉 **"끝에서 다루면 빠르고, 앞·중간을 건드리면 느리다"**가 핵심입니다.

**📖 핵심 개념**

🎯 **비유**: 배열은 **번호가 매겨진 사물함 한 줄**입니다. "37번 사물함 열기"는 즉시(O(1))지만, 맨 앞에 새 사물함을 끼우려면 뒤 번호를 전부 다시 붙여야 합니다(O(n)).

📌 **연산별 복잡도표**

| 연산 | 메서드 | 복잡도 | 이유 |
|---|---|---|---|
| 인덱스 접근 | `arr[i]` | O(1) | 주소 계산 한 번 |
| 끝 추가/삭제 | `push`/`pop` | O(1)* | 뒤쪽만 조작 (*분할상환) |
| 앞 추가/삭제 | `unshift`/`shift` | O(n) | 전 원소 재배치 |
| 중간 삽입/삭제 | `splice` | O(n) | 이후 원소 이동 |
| 값 검색 | `indexOf`/`includes`/`find` | O(n) | 순차 탐색 |
| 순회 | `map`/`filter`/`forEach`/`reduce` | O(n) | 전부 방문 |
| 정렬 | `sort` | O(n log n) | 비교 정렬 |

📌 **분할상환(amortized) O(1)이란?** 배열은 내부 용량이 꽉 차면 더 큰 공간을 새로 할당하고 통째로 복사(O(n))합니다. 이 확장은 가끔만 일어나서 **push 여러 번의 평균 비용은 O(1)**로 수렴합니다. "대부분 O(1)인데 아주 가끔 O(n)이 섞여 평균은 O(1)"을 분할상환이라고 합니다.

📌 **JS 배열의 진짜 정체(V8 관점) 🟢**: 자바스크립트 배열은 사실 특별한 객체입니다. V8 엔진은 두 가지 내부 표현을 씁니다. ① **Packed(밀집) 배열** — 인덱스가 0부터 빈틈없이 채워지면 C 배열처럼 연속 메모리에 저장돼 진짜 O(1)로 빠릅니다. ② **Dictionary(사전) 모드** — `arr[1000000] = 1`처럼 큰 구멍(hole)을 만들거나 `delete arr[2]`로 중간을 지우면, 엔진이 이를 해시 맵(희소 배열)으로 전환해 접근이 느려집니다. 그래서 **배열에 `delete`를 쓰지 말고(`splice`나 필터 사용), 구멍(sparse) 만들지 말라**는 조언이 성능 관점에서 나옵니다.

```js
const arr = [10, 20, 30];
arr[2];            // O(1)
arr.push(40);      // 분할상환 O(1)
arr.pop();         // O(1)
arr.unshift(5);    // O(n) — 뒤 원소 전부 한 칸씩 밀림
arr.indexOf(20);   // O(n)

// ❌ 배열에 delete: 값이 사라지고 length는 그대로 → 구멍(hole) 발생
delete arr[1];     // arr === [5, <1 empty item>, 20, 30], 엔진 최적화 깨짐
// ✅ 대신 splice
arr.splice(1, 1);  // O(n)이지만 구멍 없이 제거
```

**🔥 예상 꼬리질문**
- Q. `push`가 O(1)인데 왜 `unshift`는 O(n)인가요? → A. `push`는 맨 끝에만 값을 놓지만, `unshift`는 0번 자리를 비우려고 **기존 원소를 모두 뒤로 한 칸씩 이동**시켜야 하기 때문입니다.
- Q. 배열을 큐(FIFO)로 쓰면 안 되는 이유는? → A. `shift`가 O(n)이라 큐가 커질수록 dequeue가 느려집니다. 대량이면 head 인덱스를 옮기는 방식이나 연결 리스트 기반 큐가 유리합니다(D5 참고).
- Q. `arr.length = 0`과 `arr = []`의 차이는? → A. 전자는 **기존 배열을 비우는 것**이라 이 배열을 참조하는 다른 변수에도 반영되고, 후자는 **새 빈 배열로 교체**라 기존 참조는 그대로 남습니다.

<details><summary>📝 한 줄 요약</summary>배열은 인덱스 접근 O(1), 끝 조작(push/pop) 분할상환 O(1), 앞·중간 조작(unshift/shift/splice)·값 검색 O(n). V8은 밀집 배열을 최적화하니 delete·구멍을 피하라.</details>

## D3. 객체(Object) vs Map/Set, 언제 무엇을 써야 하나요? 🔴

**💬 30초 답변**
> 셋 다 내부적으로 **해시 기반**이라 조회·삽입·삭제가 **평균 O(1)**입니다. 차이는 용도와 특성입니다. **객체(`{}`)**는 "구조가 정해진 레코드"에 적합하지만 키가 문자열/심볼로 강제되고 순서·크기 계산이 불편합니다. **`Map`**은 "임의의 키(객체·함수 포함)로 값을 매핑하는 동적 딕셔너리"에 맞고, **삽입 순서 보장**·`.size`·직접 순회가 됩니다. **`Set`**은 "**중복 없는 값의 모음**"으로 존재 여부 검사(`has`)와 중복 제거에 최적입니다. 요약하면 **고정 스키마 → 객체, 잦은 추가/삭제·비문자열 키 → Map, 유일성·포함 검사 → Set**입니다.

**📖 핵심 개념**

🎯 **비유**: 객체는 **미리 칸이 정해진 서류 양식**(이름·나이 칸), Map은 **자유롭게 라벨을 붙이는 이름표 서랍**(어떤 물건이든 라벨로 꺼냄), Set은 **입장 도장 명단**(같은 사람은 한 번만, "이미 들어왔나?"만 확인).

📌 **비교표**

| 특성 | Object `{}` | Map | Set |
|---|---|---|---|
| 키 타입 | 문자열·심볼만 | **아무 값**(객체·함수도) | (값 자체가 원소) |
| 순서 보장 | 정수키 특수처리 등 미묘 | **삽입 순서 보장** | 삽입 순서 보장 |
| 크기 | `Object.keys(o).length` O(n) | `map.size` **O(1)** | `set.size` O(1) |
| 조회/삽입/삭제 | 평균 O(1) | 평균 O(1) | 평균 O(1) |
| 순회 | `for...in`(프로토타입 주의)/`Object.entries` | `for...of`·`forEach` 직접 | `for...of` 직접 |
| 프로토타입 오염 | `o.hasOwnProperty` 충돌 위험 | 없음(깨끗함) | 없음 |
| JSON 직렬화 | 바로 됨 | 안 됨(변환 필요) | 안 됨 |

📌 **객체의 함정 — 정수형 문자열 키**: 객체는 `"1"`, `"2"` 같은 정수형 키를 **자동으로 오름차순 정렬**해 버립니다. 반면 Map은 넣은 순서를 그대로 지킵니다. "삽입 순서가 의미 있는 데이터"라면 Map이 안전합니다.

📌 **`Set`으로 O(n) 중복 제거**: 배열 중복 제거의 정석은 `[...new Set(arr)]`입니다. 이중 루프(O(n²)) 대신 O(n)으로 끝납니다. 다만 `Set`은 `===`(SameValueZero) 기준이라 **객체는 참조가 같아야 중복으로 봅니다**(내용이 같아도 다른 객체면 별개).

```js
// 1) 고정 스키마 → 객체
const user = { id: 1, name: 'Buzz', role: 'FE' };

// 2) 동적 매핑·비문자열 키 → Map
const cache = new Map();
const keyObj = { page: 1 };
cache.set(keyObj, '결과');    // 객체를 키로!
cache.get(keyObj);            // '결과'  (평균 O(1))
cache.size;                   // O(1)

// 3) 유일성·포함 검사 → Set
const ids = new Set([1, 2, 2, 3]);
ids.has(2);                   // true (평균 O(1))
const unique = [...new Set([1, 1, 2, 3])]; // [1,2,3], O(n)
```

**🔥 예상 꼬리질문**
- Q. "배열 `includes`로 존재 검사"와 "Set `has`"의 차이는? → A. 배열 `includes`는 O(n) 순차 탐색이고, `Set.has`는 평균 O(1)입니다. 반복적으로 포함 여부를 검사한다면 Set이 압도적으로 빠릅니다.
- Q. `WeakMap`/`WeakSet`은 언제 쓰나요? → A. **키가 객체일 때만** 쓰며, 키 객체가 다른 곳에서 참조되지 않으면 GC가 자동 수거합니다. DOM 노드에 부가 데이터를 붙이는 등 **메모리 누수 없이 메타데이터를 매다는** 용도에 좋습니다(순회 불가).
- Q. 그럼 항상 Map이 객체보다 나은가요? → A. 아닙니다. JSON 직렬화·구조 분해·정해진 필드 접근은 객체가 편하고, 리터럴 문법도 가볍습니다. **"키가 동적으로 늘고 줄거나, 비문자열 키·순서·크기가 중요"**할 때 Map으로 갑니다.

<details><summary>📝 한 줄 요약</summary>셋 다 평균 O(1) 해시 기반. 고정 스키마=객체, 동적/비문자열 키·순서·size=Map, 유일성·포함 검사·중복 제거=Set. 반복 포함 검사는 배열 includes(O(n)) 대신 Set has(O(1)).</details>

## D4. 해시 테이블은 어떻게 O(1)을 만들고, 충돌은 어떻게 처리하나요? 🟡

**💬 30초 답변**
> 해시 테이블은 **키를 해시 함수에 넣어 나온 숫자로 저장 위치(버킷 인덱스)를 바로 계산**하는 자료구조입니다. 위치를 "계산"하니까 탐색 없이 바로 접근 → **평균 O(1)**입니다. 문제는 서로 다른 키가 같은 버킷으로 가는 **충돌(collision)**인데, 대표 해법이 ① **체이닝(chaining)** — 한 버킷에 연결 리스트로 여러 값을 매달기, ② **개방 주소법(open addressing)** — 충돌 시 다음 빈 칸을 찾아가기입니다. 충돌이 심하거나 부하율(load factor)이 높으면 최악 O(n)까지 나빠지므로, 엔진은 일정 비율을 넘으면 **버킷을 키우고 재해싱(rehash)**합니다. JS의 객체·Map·Set이 모두 이 원리 위에 있습니다.

**📖 핵심 개념**

🎯 **비유**: 해시 테이블은 **호텔 프런트의 우편함**입니다. 방 번호(키)를 알면 계산으로 우편함 칸을 바로 찾습니다(O(1)). 만약 두 사람의 계산 결과가 같은 칸이면(충돌), 그 칸 안에 쪽지를 여러 장 겹쳐 둡니다(체이닝).

📌 **동작 순서**: `키 → 해시 함수 h(key) → 정수 → % 버킷수 → 버킷 인덱스 → 값 저장/조회`. 좋은 해시 함수는 **입력을 버킷에 고르게 분산**시켜 충돌을 줄입니다.

📌 **충돌 처리 2방식**

| 방식 | 아이디어 | 장점 | 단점 |
|---|---|---|---|
| 체이닝 | 버킷에 리스트로 매달기 | 구현 단순·삭제 쉬움 | 포인터 메모리·캐시 비효율 |
| 개방 주소법 | 빈 다음 칸 탐사 | 캐시 친화·메모리 밀집 | 삭제 까다로움·군집(clustering) |

📌 **부하율과 재해싱**: `부하율 = 저장된 항목 수 / 버킷 수`. 이 값이 커지면 충돌이 늘어 성능이 떨어집니다. 그래서 임계치(예: 0.75)를 넘으면 버킷을 2배로 늘리고 모든 항목을 다시 배치(rehash, 그 순간 O(n))합니다. push의 분할상환처럼, 이 비용도 평균으로 나누면 삽입은 여전히 평균 O(1)입니다.

📌 **면접 포인트 — 왜 "평균 O(1)"이라 말해야 하나**: 이론상 모든 키가 한 버킷에 몰리면 O(n)입니다. 그래서 정확히는 **"평균 O(1), 최악 O(n)"**이라 답하는 게 좋습니다. 실무 엔진은 좋은 해시와 재해싱으로 최악을 거의 만들지 않습니다.

**🔥 예상 꼬리질문**
- Q. 객체 키로 아무 문자열이나 써도 왜 빠른가요? → A. 문자열도 해시 함수로 정수 위치를 계산하기 때문입니다. 키 길이에 따른 해시 계산 비용은 있지만, 탐색 없이 위치를 잡는다는 점은 같습니다.
- Q. 해시 함수가 나쁘면 어떤 일이? → A. 충돌이 폭증해 사실상 연결 리스트 하나가 되어 O(n)이 됩니다. 악의적으로 충돌을 유발하는 **HashDoS 공격**도 있어, 일부 런타임은 시드가 있는 해시를 씁니다.
- Q. Map이 삽입 순서를 지키는데 해시인가요? → A. 네. 해시로 위치를 잡되, 순서 유지를 위해 항목을 별도의 **삽입 순서 연결 구조**로 함께 관리합니다(해시 + 순서 이중 관리).

<details><summary>📝 한 줄 요약</summary>해시 테이블 = 키를 해시로 계산해 버킷 위치를 바로 잡음 → 평균 O(1). 충돌은 체이닝/개방주소법으로 처리, 부하율 높으면 재해싱. 정확히는 "평균 O(1)·최악 O(n)".</details>

## D5. 스택과 큐는 무엇이고, 프론트엔드에서 언제 쓰나요? 🔴

**💬 30초 답변**
> 둘 다 "넣고 빼는 순서 규칙"이 있는 선형 자료구조입니다. **스택(Stack)**은 **LIFO(Last-In-First-Out)** — 마지막에 넣은 걸 먼저 꺼냅니다(접시 쌓기). **큐(Queue)**는 **FIFO(First-In-First-Out)** — 먼저 넣은 걸 먼저 꺼냅니다(줄 서기). 프론트엔드에서 스택은 **되돌리기/다시 실행(undo/redo), 브라우저 뒤로가기 히스토리, 함수 호출 스택, 재귀·DFS**에 쓰이고, 큐는 **이벤트 루프의 태스크 큐, 요청 순차 처리, BFS**에 쓰입니다. JS에는 전용 자료형이 없어 보통 배열로 구현하되, 큐는 `shift`가 O(n)이라 주의합니다.

**📖 핵심 개념**

🎯 **비유**: 스택은 **식당의 접시 더미**(맨 위에 놓고 맨 위부터 뺌), 큐는 **은행 대기 줄**(먼저 온 사람이 먼저 처리).

📌 **연산과 복잡도**: 스택의 `push`/`pop`, 큐의 `enqueue`/`dequeue`는 모두 **개념상 O(1)**이어야 합니다. 배열로 스택을 만들면 `push`/`pop`이 O(1)이라 딱 맞습니다. 하지만 배열로 큐를 만들면 `dequeue = shift`가 **O(n)**이라 데이터가 크면 병목이 됩니다.

```js
// 스택: 배열로 자연스럽게 O(1)
const stack = [];
stack.push('a'); stack.push('b');
stack.pop(); // 'b' (LIFO)

// 큐: 배열 shift는 O(n) → 대량이면 head 포인터로 O(1) 구현
class Queue {
  #items = {};
  #head = 0;
  #tail = 0;
  enqueue(v) { this.#items[this.#tail++] = v; }   // O(1)
  dequeue() {                                       // O(1)
    if (this.#head === this.#tail) return undefined;
    const v = this.#items[this.#head];
    delete this.#items[this.#head++];
    return v;
  }
  get size() { return this.#tail - this.#head; }
}
```

📌 **undo/redo는 스택 2개**: 편집기의 실행취소는 보통 **undo 스택**과 **redo 스택** 두 개로 구현합니다. 새 작업을 하면 undo에 push하고 redo를 비웁니다. Ctrl+Z는 undo에서 pop해 redo로 옮기고, Ctrl+Shift+Z는 그 반대입니다.

📌 **호출 스택(Call Stack)과의 연결**: JS 엔진이 함수 실행을 관리하는 것도 스택입니다(2026-07-22 이벤트 루프 편 참고). 재귀가 너무 깊으면 이 스택이 넘쳐 `Maximum call stack size exceeded`가 납니다. 반대로 이벤트 루프의 **태스크 큐/마이크로태스크 큐**는 큐 구조입니다.

**🔥 예상 꼬리질문**
- Q. 트리를 DFS로 순회할 때 스택, BFS로 순회할 때 큐를 쓰는 이유는? → A. DFS는 "가장 최근에 발견한 노드부터 더 깊이" 파고들어야 하니 LIFO(스택)가 맞고, BFS는 "먼저 발견한 노드부터 같은 깊이를 훑어야" 하니 FIFO(큐)가 맞습니다.
- Q. 스택으로 괄호 검사를 어떻게? → A. 여는 괄호를 push, 닫는 괄호가 오면 pop해서 짝이 맞는지 확인합니다. 코딩테스트 단골 문제입니다.
- Q. 브라우저 뒤로/앞으로가기는? → A. 방문 기록을 스택으로 보면 직관적입니다(뒤로가기 스택·앞으로가기 스택). History API도 이 모델과 유사합니다.

<details><summary>📝 한 줄 요약</summary>스택=LIFO(undo/redo·DFS·호출스택), 큐=FIFO(태스크 큐·BFS·순차처리). push/pop·enqueue/dequeue는 O(1)이어야 함. 배열 스택은 OK지만 배열 큐는 shift가 O(n)이라 head 포인터로 구현.</details>

## D6. 연결 리스트(Linked List)는 무엇이고, 배열과 어떻게 다른가요? 🟡

**💬 30초 답변**
> 연결 리스트는 각 원소(노드)가 **값과 "다음 노드를 가리키는 포인터"**를 함께 갖는 자료구조입니다. 배열처럼 메모리에 연속으로 놓이지 않고 포인터로 흩어져 연결됩니다. 그래서 **중간 삽입·삭제가 (위치를 알 때) O(1)** — 포인터만 다시 연결하면 됩니다. 대신 **인덱스 접근이 O(n)** — n번째를 찾으려면 처음부터 따라가야 합니다. 즉 배열과 정확히 트레이드오프가 반대입니다: **배열은 접근이 빠르고 삽입/삭제가 느리며, 연결 리스트는 삽입/삭제가 빠르고 접근이 느립니다.**

**📖 핵심 개념**

🎯 **비유**: 배열이 **번호표 붙은 사물함 줄**이라면, 연결 리스트는 **보물찾기 쪽지**입니다. 각 쪽지에 "다음 쪽지는 냉장고 뒤"라고 적혀 있어, n번째 쪽지를 보려면 처음부터 순서대로 따라가야 합니다. 대신 중간에 새 쪽지를 끼우려면 앞뒤 쪽지의 안내만 고치면 됩니다.

📌 **배열 vs 연결 리스트 복잡도**

| 연산 | 배열 | 연결 리스트 |
|---|---|---|
| 인덱스 접근 | **O(1)** | O(n) |
| 맨 앞 삽입/삭제 | O(n) | **O(1)** |
| 중간 삽입/삭제(위치 알 때) | O(n) | **O(1)** |
| 값 검색 | O(n) | O(n) |
| 메모리 | 밀집(캐시 친화) | 노드마다 포인터 오버헤드 |

📌 **종류**: 단일 연결 리스트(다음만), 이중 연결 리스트(이전+다음, 양방향 순회), 원형 연결 리스트(끝이 처음으로). LRU 캐시는 보통 **이중 연결 리스트 + 해시 맵**으로 O(1) 갱신을 만듭니다.

```js
// 단일 연결 리스트 노드
class Node {
  constructor(value) { this.value = value; this.next = null; }
}
// head 앞에 삽입: 포인터만 바꾸면 O(1)
function prepend(head, value) {
  const node = new Node(value);
  node.next = head;   // 새 노드가 기존 head를 가리킴
  return node;        // 새 head
}
```

📌 **프론트엔드에서 직접 쓸 일이 많나?** 솔직히 자주 직접 구현하진 않습니다. 하지만 **개념은 도처에 있습니다** — React의 **Fiber 트리**는 노드가 `child`/`sibling`/`return` 포인터로 연결된 구조(2026-07-30 Fiber 편 참고), React Hooks도 내부적으로 **연결 리스트**로 순서를 관리합니다. "왜 훅을 조건문 안에서 쓰면 안 되나"의 근본 이유가 이 순서 기반 연결 구조입니다.

**🔥 예상 꼬리질문**
- Q. 삽입이 O(1)이라면서 왜 실제로는 느릴 수 있나요? → A. **삽입할 위치를 먼저 찾는 데 O(n)**이 들기 때문입니다. "위치를 이미 알고 있을 때" 포인터 재연결만 O(1)입니다.
- Q. 배열이 캐시에 유리한 이유는? → A. 연속 메모리라 CPU가 한 번에 여러 원소를 캐시로 가져옵니다(공간 지역성). 연결 리스트는 노드가 흩어져 캐시 미스가 잦습니다.
- Q. React Hooks가 연결 리스트라 생기는 규칙은? → A. 훅이 **호출 순서로 식별**되므로 조건·반복 안에서 호출하면 순서가 어긋나 상태가 엉킵니다. 그래서 "훅은 최상단에서 항상 같은 순서로" 규칙이 있습니다.

<details><summary>📝 한 줄 요약</summary>연결 리스트 = 값+다음 포인터 노드. 삽입/삭제 O(1)(위치 알 때)·접근 O(n)으로 배열과 정반대 트레이드오프. FE에서 직접 구현은 드물지만 Fiber·Hooks 등 개념이 핵심.</details>

## D7. 트리(Tree)란 무엇이고, 프론트엔드에서 어디에 쓰이나요? 🟡

**💬 30초 답변**
> 트리는 **하나의 루트에서 시작해 부모-자식 관계로 뻗어 나가는 계층 자료구조**입니다(사이클 없음). 프론트엔드 개발자에게 트리는 남 얘기가 아닙니다 — **DOM 자체가 트리**이고, **React의 가상 DOM/Fiber**, **컴포넌트 트리**, **JSON 데이터**, **라우팅 구조**, **댓글/파일 탐색기의 중첩** 모두 트리입니다. 특수한 트리인 **이진 탐색 트리(BST)**는 왼쪽엔 작은 값, 오른쪽엔 큰 값을 두어 **탐색·삽입·삭제를 평균 O(log n)**으로 만듭니다(균형이 깨지면 O(n)). 트리 순회에는 깊이 우선(DFS: 전위/중위/후위)과 너비 우선(BFS)이 있습니다.

**📖 핵심 개념**

🎯 **비유**: 트리는 **회사 조직도**입니다. CEO(루트) 아래 임원, 그 아래 팀원. 위로는 부모가 하나뿐이고 아래로는 여러 자식이 뻗습니다. DOM도 `<html>`(루트) 아래 `<body>`, 그 아래 `<div>`… 똑같은 구조입니다.

📌 **용어**: 루트(root, 최상위), 부모/자식(parent/child), 잎(leaf, 자식 없는 노드), 깊이(depth), 높이(height), 서브트리(subtree). DOM에서 `parentNode`·`children`·`firstChild`가 이 관계를 그대로 노출합니다.

📌 **이진 탐색 트리(BST)가 O(log n)인 이유**: 정렬 규칙(왼쪽<부모<오른쪽)이 있어 **한 번 비교할 때마다 탐색 범위가 절반**으로 줄기 때문입니다(이진 탐색과 같은 원리). 단, 데이터를 정렬된 순서로 넣으면 한쪽으로만 뻗어(사실상 연결 리스트) **O(n)**이 됩니다. 이를 막으려고 **자가 균형 트리(AVL, Red-Black Tree)**가 있고, 이 Red-Black Tree가 여러 언어의 정렬 맵(예: 브라우저 내부·DB 인덱스 등)에서 쓰입니다.

📌 **순회 방법**

| 순회 | 방식 | 특징/용도 |
|---|---|---|
| 전위(preorder) | 노드 → 왼 → 오 | 트리 복제·직렬화 |
| 중위(inorder) | 왼 → 노드 → 오 | BST에서 **정렬 순서**로 방문 |
| 후위(postorder) | 왼 → 오 → 노드 | 자식부터 정리(삭제·계산) |
| 레벨(BFS) | 깊이별 가로로 | 최단 경로·레벨별 처리 |

```js
// DOM도 트리 — 재귀 DFS로 모든 노드 방문 (전위 순회)
function walk(node, visit) {
  visit(node);                       // 현재 노드
  for (const child of node.children) // 자식들로 재귀
    walk(child, visit);
}
walk(document.body, (el) => console.log(el.tagName));
```

**🔥 예상 꼬리질문**
- Q. `document.querySelectorAll`은 트리를 어떻게 도나요? → A. 브라우저가 DOM 트리를 순회(주로 DFS)하며 셀렉터에 맞는 노드를 수집합니다. 그래서 셀렉터가 넓을수록 방문 노드가 많아 느려질 수 있습니다.
- Q. React가 재조정(reconciliation)할 때 트리를 어떻게 비교하나요? → A. 같은 레벨끼리 비교하는 휴리스틱을 쓰고, `key`로 자식의 동일성을 판단합니다(2026-07-30 Fiber 편). 전체 트리를 O(n³)로 비교하지 않고 O(n)에 가깝게 최적화합니다.
- Q. 균형이 왜 그렇게 중요한가요? → A. 균형이 깨지면 트리의 높이가 커지고, 탐색이 O(log n)에서 O(n)으로 퇴화하기 때문입니다.

<details><summary>📝 한 줄 요약</summary>트리 = 루트에서 부모-자식으로 뻗는 계층(사이클 없음). DOM·가상DOM·컴포넌트·JSON이 전부 트리. BST는 평균 O(log n)(불균형 시 O(n)). 순회는 DFS(전/중/후위)와 BFS.</details>

## D8. 그래프 탐색, DFS와 BFS의 차이는 무엇인가요? 🟢

**💬 30초 답변**
> 그래프는 **노드(정점)들이 간선으로 연결된 구조**로, 트리보다 일반적입니다(사이클·다중 연결 허용). 이를 탐색하는 두 방법이 **DFS(깊이 우선)**와 **BFS(너비 우선)**입니다. **DFS**는 한 방향으로 갈 수 있는 데까지 파고든 뒤 막히면 되돌아옵니다 — **스택(또는 재귀)**으로 구현하고, "경로 존재 여부·모든 조합 탐색"에 적합합니다. **BFS**는 가까운 노드부터 층층이 넓게 훑습니다 — **큐**로 구현하고, **가중치 없는 그래프의 최단 경로**에 적합합니다. 둘 다 방문한 노드를 기록해 사이클에 빠지지 않게 하며, 시간복잡도는 **O(V+E)**(정점 수 + 간선 수)입니다.

**📖 핵심 개념**

🎯 **비유**: 미로에서 DFS는 **한 갈래를 끝까지 가 보고 막히면 되돌아오는 탐험가**, BFS는 **출발점에서 동심원을 그리며 조금씩 넓혀 가는 물결**입니다. 그래서 "가장 가까운 출구"를 찾을 땐 물결(BFS)이 유리합니다.

📌 **비교표**

| 항목 | DFS | BFS |
|---|---|---|
| 구현 | 스택 / 재귀 | 큐 |
| 순서 | 깊이 먼저 | 너비(레벨) 먼저 |
| 최단 경로(무가중치) | 보장 안 됨 | **보장됨** |
| 메모리 | 경로 깊이만큼(대체로 적음) | 한 레벨 폭만큼(넓으면 많음) |
| 대표 용도 | 경로 존재·백트래킹·위상 정렬 | 최단 거리·레벨 순회·전파 |

```js
// 인접 리스트 그래프에서 BFS (큐 사용) — 최단 도달 순서
function bfs(graph, start) {
  const visited = new Set([start]);
  const queue = [start];
  const order = [];
  while (queue.length) {
    const node = queue.shift();      // FIFO
    order.push(node);
    for (const next of graph[node]) {
      if (!visited.has(next)) {       // 재방문(사이클) 방지
        visited.add(next);
        queue.push(next);
      }
    }
  }
  return order;
}
```

📌 **프론트엔드와의 접점**: 겉보기엔 알고리즘 대회 얘기 같지만, ① **의존성 그래프**(번들러가 모듈 관계를 그래프로 보고 순회, 2026-07-26 번들링 편), ② **상태 전파/구독 그래프**(반응형 상태 라이브러리), ③ **라우팅·사이트맵**, ④ **친구 추천·관계 시각화** 등에서 그래프 사고가 쓰입니다. 트리 순회(D7)는 사실 사이클 없는 그래프 탐색의 특수한 경우입니다.

**🔥 예상 꼬리질문**
- Q. 방문 기록(visited)을 왜 꼭 둬야 하나요? → A. 그래프는 사이클이 있을 수 있어, 기록이 없으면 같은 노드를 무한 반복 방문합니다. 트리는 사이클이 없어 생략 가능하지만 그래프는 필수입니다.
- Q. DFS를 재귀 대신 반복문으로? → A. 명시적 스택을 두고 pop한 노드의 이웃을 push하면 됩니다. 재귀 깊이 제한(호출 스택 오버플로)을 피할 때 유용합니다.
- Q. 가중치가 있으면 BFS로 최단 경로가 되나요? → A. 아닙니다. 간선마다 비용이 다르면 다익스트라(Dijkstra) 같은 알고리즘이 필요합니다. BFS의 최단 보장은 "모든 간선 비용이 같을 때"만 성립합니다.

<details><summary>📝 한 줄 요약</summary>그래프 탐색 DFS(스택/재귀·깊이 먼저·경로/백트래킹) vs BFS(큐·너비 먼저·무가중치 최단경로). 둘 다 visited로 사이클 방지, O(V+E). 번들 의존성·상태 전파 등 FE에도 그래프 사고가 쓰임.</details>

## D9. 프론트엔드 실무에서 자료구조를 실제로 고르게 되는 순간은 언제인가요? 🔴

**💬 30초 답변**
> "코딩테스트용"이라 생각하기 쉽지만, 실무에서도 **잘못된 자료구조 선택이 성능 병목의 원인**이 됩니다. 가장 흔한 실전 판단은 ① **반복적인 존재 검사·중복 제거는 배열 대신 Set/Map**(O(n) 루프 → O(1) 조회)로 바꾸기, ② **id로 자주 찾는 목록은 배열을 `Map`이나 `{[id]: item}` 형태로 정규화**하기(`find` O(n) → 조회 O(1)), ③ **큐가 필요하면 배열 `shift`(O(n)) 피하기**, ④ **트리 데이터(댓글·카테고리)는 순회·평탄화 방식 정하기**입니다. 요약하면 **"이 데이터를 어떻게 자주 접근/변경하는가"를 먼저 보고 자료구조를 정하는 것**이 실무 감각입니다.

**📖 핵심 개념**

📌 **사례 1 — 목록 정규화(normalization)**: 서버에서 받은 배열을 그대로 두면 특정 항목을 찾을 때마다 `arr.find(x => x.id === id)`로 O(n)입니다. 항목이 많고 조회가 잦다면 **id를 키로 하는 Map/객체로 재구성**하면 조회가 O(1)이 됩니다. Redux Toolkit의 `createEntityAdapter`, 정규화 스토어 설계가 바로 이 원리입니다.

```js
// ❌ 매번 O(n) 탐색
const item = items.find((x) => x.id === targetId);

// ✅ 한 번 O(n)으로 정규화해 두면 이후 조회는 O(1)
const byId = new Map(items.map((x) => [x.id, x]));
const item2 = byId.get(targetId); // O(1)
```

📌 **사례 2 — 대량 리스트의 중복/교집합 처리**: 선택된 id 목록과 전체 목록을 비교해 "선택 여부"를 표시할 때, 배열 `includes`를 반복하면 O(n²)입니다. 선택 목록을 `Set`으로 만들면 각 검사가 O(1) → 전체 O(n)입니다. 체크박스 목록·태그 필터·다중 선택 UI에서 자주 만납니다.

📌 **사례 3 — 트리 데이터 다루기**: 댓글의 대댓글, 카테고리 계층, 조직도는 트리입니다. 렌더링 전 **평탄화(flatten)**할지, 재귀 컴포넌트로 그릴지, 특정 노드를 찾을 때 DFS/BFS 중 무엇을 쓸지 정해야 합니다. 깊은 트리를 재귀로 그릴 땐 성능·스택 깊이도 고려합니다.

📌 **사례 4 — 캐시/메모이제이션**: 계산 결과 캐시는 **Map**(키가 다양), DOM 노드 부가 데이터는 **WeakMap**(누수 방지), LRU 캐시는 **Map + 순서 활용**(Map은 삽입 순서를 보장하므로 가장 오래된 키를 `keys().next()`로 꺼내 제거)로 만듭니다.

📌 **면접에서의 태도**: "왜 이 자료구조를 썼나요?"에 **"습관적으로요"가 아니라 "이 데이터는 조회가 잦고 삽입이 드물어서 O(1) 조회가 되는 Map을 택했습니다"처럼 접근 패턴 → 복잡도 → 선택**의 논리로 답하면 CS 기초가 탄탄하다는 인상을 줍니다.

**🔥 예상 꼬리질문**
- Q. 항상 Map/Set이 정답인가요? → A. 아닙니다. 데이터가 적으면 배열이 더 단순하고 빠를 수도 있고, 순서·직렬화·구조 분해가 필요하면 배열/객체가 낫습니다. **접근 패턴과 규모**로 판단합니다.
- Q. 정규화의 단점은? → A. 원본 순서를 잃을 수 있어(별도 id 배열로 순서 유지), 중첩 관계 관리가 복잡해집니다. 조회 이득과 관리 비용을 저울질합니다.
- Q. React 렌더링 목록에서 자료구조가 성능에 영향을 주나요? → A. 네. 안정적인 `key`(보통 id)로 조회·비교를 O(1)에 하도록 돕고, 매 렌더에서 O(n) 탐색을 반복하지 않게 정규화·메모이제이션을 씁니다(2026-07-16 리렌더 최적화 편).

<details><summary>📝 한 줄 요약</summary>실무 자료구조 선택 = "이 데이터를 어떻게 자주 접근/변경하나"로 결정. 반복 존재검사·중복은 Set, id 조회는 Map/정규화(find O(n)→O(1)), 큐는 shift 회피, 캐시는 Map/WeakMap. 면접에선 "접근 패턴→복잡도→선택" 논리로 답하기.</details>

## 🎯 오늘의 핵심 3줄 정리

1. **Big-O는 자료구조 선택의 언어다** — 입력이 커질 때의 증가 추세(O(1)<O(log n)<O(n)<O(n log n)<O(n²))로, 코드 실행 전에 성능을 판단하고 시간-공간 트레이드오프를 결정한다.
2. **JS의 배열/객체/Map/Set을 복잡도로 구분하라** — 배열은 인덱스 O(1)·앞중간조작 O(n), 해시 기반(객체·Map·Set)은 평균 O(1) 조회. 반복 존재검사·중복 제거·id 조회는 배열 순회(O(n)) 대신 Set/Map(O(1))으로.
3. **스택·큐·연결리스트·트리·그래프는 FE 도처에 있다** — undo/redo·호출스택(스택), 이벤트 루프(큐), Fiber·Hooks(연결 리스트), DOM·가상DOM(트리), 번들 의존성(그래프). 개념을 알면 "왜 이렇게 동작하나"가 설명된다.
