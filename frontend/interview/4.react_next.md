## Q55. 리액트의 가상 돔과 재조정 과정의 역할은 무엇인가요? 🔴

**💬 30초 답변**
> 가상 DOM(Virtual DOM)은 실제 DOM을 본뜬 **JavaScript 객체 트리**입니다. 상태가 바뀌면 새 가상 DOM을 만들어 이전 것과 비교(**diffing**)하고, 바뀐 부분만 실제 DOM에 반영하는 **재조정(reconciliation)** 을 거칩니다. 비싼 실제 DOM 조작을 최소화해 성능을 높이는 게 핵심입니다.

**📖 핵심 개념**

🎯 **비유**: 실제 DOM 조작은 "건물을 직접 부수고 다시 짓는 것"이라 비쌉니다. 가상 DOM은 "설계도 두 장을 비교해 달라진 부분만 시공"하는 방식입니다.

📌 **동작 흐름**
```
상태 변경 → 새 가상 DOM 생성
         → 이전 가상 DOM과 비교 (diffing)
         → 바뀐 부분만 추려냄
         → 실제 DOM에 일괄(batch) 반영 (commit)
```

📌 **재조정(Reconciliation) 휴리스틱**
- **타입이 다르면** 통째로 교체 (`<div>` → `<span>`)
- **타입이 같으면** 속성만 업데이트
- 리스트는 **key**로 같은 항목인지 식별(Q64 연결)

> 💡 **오해 주의**: "가상 DOM은 항상 빠르다"는 틀린 말. diffing 비용도 있어 **직접 최적화한 DOM 조작보다 느릴 수도** 있음. 진짜 가치는 "**선언적으로 작성해도 합리적 성능**"을 보장하는 것. React 공식도 "충분히 빠르다"고 표현.

**🔥 예상 꼬리질문**
- Q. Fiber란? → A. React 16+의 재조정 엔진. 렌더링 작업을 작은 단위로 쪼개 중단·재개할 수 있게 해 동시성(Q61)의 토대가 됨.
- Q. 가상 DOM이 항상 실제 DOM보다 빠른가요? → A. 아닙니다. diffing 오버헤드가 있어, 선언적 편의 + 합리적 성능이 본질입니다.

<details><summary>📝 한 줄 요약</summary>실제 DOM을 본뜬 JS 객체. 변경 시 이전과 diff → 바뀐 부분만 실제 DOM에 반영(재조정). 선언적 작성 + 합리적 성능이 본질(항상 빠른 건 아님).</details>

## Q56. 클래스 컴포넌트와 함수형 컴포넌트의 차이점은 무엇인가요? 🟡

**💬 30초 답변**
> 클래스 컴포넌트는 `class`로 작성하고 `this.state`·생명주기 메서드(`componentDidMount` 등)를 쓰는 옛 방식이고, 함수형 컴포넌트는 함수로 작성하고 **Hooks**(`useState`, `useEffect`)로 상태·부수효과를 다루는 현재 표준입니다. 함수형이 더 간결하고 로직 재사용이 쉽습니다.

**📖 핵심 개념**

📌 **비교**

| 항목 | 클래스 컴포넌트 | 함수형 컴포넌트 |
|------|----------------|-----------------|
| 문법 | `class extends Component` | 함수 |
| 상태 | `this.state` / `setState` | `useState` |
| 생명주기 | `componentDidMount` 등 | `useEffect`로 통합 |
| 로직 재사용 | HOC, render props (복잡) | **커스텀 훅** (간결) |
| this | 바인딩 필요 | 불필요 |
| 현재 위상 | 레거시 | **표준(권장)** |

```jsx
// 클래스 (레거시)
class Counter extends React.Component {
  state = { count: 0 };
  componentDidMount() { /* ... */ }
  render() { return <button onClick={() => this.setState({count: this.state.count+1})}>{this.state.count}</button>; }
}

// 함수형 (표준)
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => { /* ... */ }, []);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

> 💡 함수형이 표준이 된 결정적 이유는 **Hooks**(React 16.8). 상태 로직을 컴포넌트 밖으로 추출해 재사용(커스텀 훅 — Q60)할 수 있게 됐고, this 바인딩 문제(Q42)도 사라짐.

**🔥 예상 꼬리질문**
- Q. 클래스 컴포넌트를 아직 쓰나요? → A. 신규 코드는 함수형 권장. 단 Error Boundary는 아직 클래스로만 구현 가능(Q62).
- Q. Hooks 도입 전 로직 재사용은? → A. HOC·render props로 했지만 래퍼 지옥·가독성 문제가 있었음.

<details><summary>📝 한 줄 요약</summary>클래스(this.state·생명주기, 레거시) vs 함수형(Hooks·커스텀 훅, 표준). Hooks 덕에 함수형이 로직 재사용·간결성에서 우위.</details>

## Q57. useEffect 훅의 동작 원리와 의존성 배열의 중요성을 설명할 수 있나요? 🔴

**💬 30초 답변**
> useEffect는 렌더링 이후 실행되는 **부수 효과(side effect)** 를 처리하는 훅으로, 데이터 패칭·구독·DOM 조작 등에 씁니다. 두 번째 인자인 **의존성 배열**의 값이 바뀔 때만 effect가 재실행되며, 이 배열을 잘못 관리하면 무한 루프나 stale(오래된) 값 버그가 생깁니다.

**📖 핵심 개념**

```jsx
useEffect(() => {
  // 실행할 부수 효과
  const sub = subscribe(id);
  return () => sub.unsubscribe();  // 클린업 (언마운트/재실행 직전)
}, [id]);                          // 의존성 배열
```

📌 **의존성 배열에 따른 동작**

| 배열 | 실행 시점 |
|------|-----------|
| 없음 (생략) | 매 렌더마다 |
| `[]` | 마운트 시 1회만 |
| `[a, b]` | a나 b가 바뀔 때마다 |

📌 **클린업 함수**: effect가 반환하는 함수. **다음 effect 실행 직전 + 언마운트 시** 호출 → 구독 해제, 타이머 정리, 이벤트 제거 등 누수 방지.

```
렌더 → effect 실행 → (의존성 변경) → 클린업 → 새 effect 실행 → ... → 언마운트 시 클린업
```

> ⚠️ **흔한 버그**
> - 의존성 누락 → **stale closure**(옛 값을 계속 참조). ESLint `exhaustive-deps`로 방지
> - 객체/함수를 의존성에 넣으면 매 렌더 새로 생성돼 무한 실행 → `useCallback`/`useMemo`로 안정화
> - effect 안에서 setState → 그 state를 의존성에 넣으면 무한 루프

> 💡 React 18 StrictMode(개발 모드)에서는 effect가 **마운트 시 2번** 실행됨 — 클린업이 올바른지 검증하기 위한 의도된 동작.

**🔥 예상 꼬리질문**
- Q. 클린업이 왜 필요한가요? → A. 구독·타이머·이벤트를 정리하지 않으면 메모리 누수와 중복 실행이 발생.
- Q. 데이터 패칭을 useEffect로? → A. 가능하나 경쟁 상태·로딩/에러 처리가 번거로움 → React Query, SWR, 또는 Next 서버 컴포넌트 권장(Q68, 8장).

<details><summary>📝 한 줄 요약</summary>렌더 후 부수 효과 실행. 의존성 배열 값이 바뀔 때만 재실행([]=1회). 클린업으로 누수 방지. 의존성 누락=stale 버그, 객체 의존성=무한 루프 주의.</details>

## Q58. 리액트에서 컴포넌트 간 통신 방법을 설명할 수 있나요? 🔴

**💬 30초 답변**
> 부모→자식은 **props**, 자식→부모는 **콜백 함수 props**(상태 끌어올리기), 멀리 떨어진 컴포넌트끼리는 **Context API**나 **전역 상태 관리 라이브러리**(Redux, Zustand)를 사용합니다. 통신 거리와 복잡도에 따라 도구를 선택합니다.

**📖 핵심 개념**

```
부모 ──props──▶ 자식           (하향 데이터)
자식 ──콜백 props──▶ 부모        (상태 끌어올리기, lifting state up)
형제 A ─▶ 공통 부모 ─▶ 형제 B    (부모 경유)
멀리 떨어진 트리 → Context / 전역 상태  (props drilling 회피)
```

📌 **방법별 정리**

| 방법 | 방향/범위 | 사용 |
|------|-----------|------|
| props | 부모→자식 | 기본 데이터 전달 |
| 콜백 props | 자식→부모 | 상태 끌어올리기 |
| Context API | 트리 전체 (구독) | 테마, 인증, 로케일 등 저빈도 전역 값 |
| 전역 상태(Redux/Zustand/Jotai) | 앱 전역 | 복잡·고빈도 공유 상태 |
| 서버 상태(React Query/SWR) | 서버 데이터 | 캐싱·동기화가 필요한 API 데이터 |

```jsx
// 자식 → 부모: 콜백 props
function Parent() {
  const [value, setValue] = useState("");
  return <Child onChange={setValue} />;  // 자식이 부모 상태 변경
}
```

> 💡 **props drilling**(중간 컴포넌트를 거쳐 깊이 전달)이 심해지면 Context나 전역 상태로 해결. 단 Context는 값이 바뀌면 구독한 모든 컴포넌트가 리렌더 → 자주 바뀌는 값엔 Zustand 같은 선택적 구독이 유리.

**🔥 예상 꼬리질문**
- Q. Context의 단점은? → A. 값 변경 시 구독 컴포넌트 전체 리렌더 → 고빈도 갱신엔 부적합, 분리하거나 전역 상태 사용.
- Q. 서버 상태와 클라이언트 상태를 구분하는 이유? → A. 서버 데이터는 캐싱·재검증·동기화가 핵심이라 React Query 류가 전용으로 처리하는 게 효율적.

<details><summary>📝 한 줄 요약</summary>부모→자식=props, 자식→부모=콜백(상태 끌어올리기), 원거리=Context/전역상태(Redux·Zustand), 서버데이터=React Query. props drilling은 Context로 회피.</details>

## Q59. 리액트의 성능 최적화를 위한 구체적인 방법은 무엇인가요? 🔴

**💬 30초 답변**
> 불필요한 리렌더링을 막는 게 핵심입니다. `React.memo`로 컴포넌트 메모이제이션, `useMemo`로 값 캐싱, `useCallback`으로 함수 캐싱을 하고, 리스트엔 안정적 **key**, 큰 화면엔 **코드 스플리팅(lazy)** 과 **가상화(virtualization)** 를 적용합니다.

**📖 핵심 개념**

📌 **리렌더 최적화**
```jsx
const Child = React.memo(function Child({ data }) { /* props 같으면 리렌더 skip */ });

const memoValue = useMemo(() => expensiveCalc(a), [a]);   // 값 캐싱
const handler = useCallback(() => doSomething(id), [id]); // 함수 캐싱 (자식 memo와 짝)
```

📌 **로딩/번들 최적화**
```jsx
const Heavy = React.lazy(() => import("./Heavy")); // 코드 스플리팅
<Suspense fallback={<Spinner />}><Heavy /></Suspense>
```

📌 **체크리스트**
- `React.memo` + `useCallback`/`useMemo`로 props 안정화
- 리스트에 **고유 key**(index 지양 — Q64)
- 긴 리스트는 **가상화**(react-window/virtuoso) — 보이는 항목만 렌더
- **코드 스플리팅**(lazy + Suspense)으로 초기 번들 축소
- 상태를 **필요한 최소 범위**에 두기(상태 끌어올리기 남발 X)
- 이미지 최적화(lazy loading, Next `<Image>` — Q69)

> ⚠️ **과최적화 주의**: `useMemo`/`useCallback`도 비용(메모리·비교)이 있음. 실제 병목을 **React DevTools Profiler**로 측정한 뒤 적용하는 게 정석. "측정 없는 최적화는 추측".
> 💡 **React 19의 React Compiler**가 자동 메모이제이션을 해줘 향후 수동 memo 필요성이 줄어드는 추세.

**🔥 예상 꼬리질문**
- Q. useMemo와 useCallback 차이? → A. useMemo는 **값**을, useCallback은 **함수**를 캐싱. `useCallback(fn,d) === useMemo(()=>fn,d)`.
- Q. React.memo가 효과 없을 때? → A. props로 매번 새 객체/함수를 넘기면 항상 다르다고 판단 → useCallback/useMemo로 안정화 필요.

<details><summary>📝 한 줄 요약</summary>불필요한 리렌더 차단: React.memo+useMemo/useCallback, 고유 key, 가상화, 코드 스플리팅(lazy+Suspense). 측정(Profiler) 후 적용. React 19 Compiler가 자동화.</details>

## Q60. 사용자 정의 훅을 만드는 목적이 무엇인가요? 🟡

**💬 30초 답변**
> 커스텀 훅은 **상태 로직(stateful logic)을 컴포넌트에서 분리해 재사용**하기 위해 만듭니다. `use`로 시작하는 함수 안에 여러 내장 훅을 조합해, 데이터 패칭·폼 처리·미디어 쿼리 같은 로직을 여러 컴포넌트가 공유할 수 있습니다.

**📖 핵심 개념**

```jsx
// 커스텀 훅: 로직만 추출 (UI 없음)
function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  useEffect(() => {
    let ignore = false;             // 경쟁 상태 방지
    fetch(url).then(r => r.json()).then(d => { if (!ignore) { setData(d); setLoading(false); } });
    return () => { ignore = true; };
  }, [url]);
  return { data, loading };
}

// 여러 컴포넌트에서 재사용
function Profile() { const { data, loading } = useFetch("/api/user"); /* ... */ }
```

📌 **목적**
- **로직 재사용**: 중복 제거 (DRY)
- **관심사 분리**: UI와 로직 분리 → 컴포넌트 간결
- **테스트 용이**: 로직만 따로 테스트
- **가독성**: `useFetch`, `useToggle`처럼 의도가 드러나는 이름

📌 **규칙 (Rules of Hooks)**
- 이름은 반드시 **`use`로 시작** (린트가 훅 규칙 적용)
- 최상위에서만 호출(조건문·반복문·중첩 함수 안 ❌)
- React 함수(컴포넌트/다른 훅) 안에서만 호출

> 💡 HOC·render props가 하던 로직 재사용을 훨씬 깔끔하게 대체. 상태 로직 공유이지 "상태 자체 공유"는 아님 — 각 컴포넌트는 **독립된 상태**를 가짐.

**🔥 예상 꼬리질문**
- Q. 커스텀 훅끼리 상태를 공유하나요? → A. 아닙니다. 호출할 때마다 독립된 상태가 생깁니다(로직만 공유).
- Q. use로 시작해야 하는 이유? → A. React 린트가 훅 규칙을 검사하고, 내부에서 훅을 호출함을 표시하기 위해서.

<details><summary>📝 한 줄 요약</summary>상태 로직을 컴포넌트에서 분리해 재사용하는 함수(use- 시작). 관심사 분리·테스트·가독성. 로직만 공유하고 상태는 각자 독립.</details>

## Q61. 리액트 18 버전에 도입된 동시성 기능을 설명할 수 있나요? 🟢

**💬 30초 답변**
> React 18의 동시성(Concurrency)은 렌더링을 **중단·재개·우선순위 조정**할 수 있게 한 기능입니다. 급한 업데이트(입력)를 먼저 처리하고 무거운 업데이트는 뒤로 미뤄, 끊김 없는 반응성을 제공합니다. `useTransition`, `useDeferredValue`, 자동 배칭, `Suspense` 개선이 대표적입니다.

**📖 핵심 개념**

📌 **주요 기능**
- **자동 배칭(Automatic Batching)**: 여러 setState를 한 번의 리렌더로 묶음 (Promise·setTimeout 안에서도)
- **`useTransition`**: 긴급하지 않은 상태 업데이트를 'transition'으로 표시 → 급한 업데이트에 양보
```jsx
const [isPending, startTransition] = useTransition();
startTransition(() => setSearchResults(heavyFilter(query))); // 입력은 즉시, 결과는 미룸
```
- **`useDeferredValue`**: 값의 업데이트를 지연시켜 무거운 렌더를 뒤로 (디바운스와 유사한 UX)
- **Suspense 개선**: 서버 사이드 스트리밍, 데이터 로딩 중 fallback

```
기존: 무거운 렌더 시작 → 끝까지 블로킹 → 입력 끊김
동시성: 무거운 렌더 중 급한 입력 들어옴 → 렌더 중단 → 입력 먼저 → 재개
```

> 💡 토대는 **Fiber 아키텍처**(Q55). 렌더 작업을 쪼개 중단·재개할 수 있어 우선순위 스케줄링이 가능. 동시성은 "병렬(멀티스레드)"이 아니라 "**중단 가능한 스케줄링**".

**🔥 예상 꼬리질문**
- Q. useTransition과 디바운싱 차이? → A. 디바운싱은 시간 지연, useTransition은 렌더 우선순위 조정(시간이 아닌 중요도 기반).
- Q. 자동 배칭이 18 이전과 다른 점? → A. 이전엔 이벤트 핸들러 안에서만 배칭, 18부턴 Promise·setTimeout·네이티브 핸들러에서도 배칭.

<details><summary>📝 한 줄 요약</summary>렌더를 중단·재개·우선순위 조정(Fiber 기반). 자동 배칭, useTransition(급한 업데이트 양보), useDeferredValue(지연), Suspense 스트리밍. 병렬이 아닌 스케줄링.</details>

## Q62. 리액트 컴포넌트의 오류 처리를 어떻게 구현할 수 있나요? 🟡

**💬 30초 답변**
> 렌더링 중 발생하는 오류는 **에러 바운더리(Error Boundary)** 로 잡습니다. 하위 컴포넌트의 에러를 포착해 앱 전체 크래시 대신 **폴백 UI**를 보여줍니다. 단, 이벤트 핸들러·비동기 코드의 에러는 바운더리가 못 잡아 `try/catch`로 따로 처리해야 합니다.

**📖 핵심 개념**

```jsx
// 에러 바운더리는 현재 클래스로만 구현 가능
class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; } // 폴백 렌더
  componentDidCatch(error, info) { logError(error, info); }        // 로깅
  render() {
    return this.state.hasError ? <h1>문제가 발생했습니다</h1> : this.props.children;
  }
}

// 사용
<ErrorBoundary><Profile /></ErrorBoundary>
```

📌 **바운더리가 잡는 것 / 못 잡는 것**

| 잡음 ✅ | 못 잡음 ❌ (try/catch 필요) |
|---------|---------------------------|
| 렌더링 중 에러 | 이벤트 핸들러 |
| 생명주기 메서드 | 비동기(setTimeout, fetch) |
| 자식 컴포넌트 트리 | 서버 사이드 렌더링 |
| | 바운더리 자신의 에러 |

> 💡 실무에선 직접 만들기보다 **`react-error-boundary`** 라이브러리(`onReset`, `fallbackRender`)를 많이 씀. 데이터 패칭 에러는 **Suspense + Error Boundary** 조합, React Query의 `error` 상태로도 처리.

**🔥 예상 꼬리질문**
- Q. 함수형으로 에러 바운더리를? → A. 아직 직접은 불가(클래스 필요). 라이브러리로 감싸 사용.
- Q. 이벤트 핸들러 에러는? → A. 바운더리가 못 잡으므로 핸들러 내부에서 try/catch.

<details><summary>📝 한 줄 요약</summary>렌더 에러는 Error Boundary(클래스)로 폴백 UI 표시. 이벤트·비동기·SSR 에러는 못 잡아 try/catch 필요. 실무는 react-error-boundary.</details>

## Q63. CSR의 개념과 한계점은 무엇인가요? 🔴

**💬 30초 답변**
> CSR(Client-Side Rendering)은 서버가 빈 HTML과 JS 번들을 보내면 **브라우저에서 JS가 화면을 그리는** 방식입니다. 페이지 전환이 빠르고 서버 부담이 적지만, **초기 로딩이 느리고 SEO에 불리**하다는 한계가 있습니다.

**📖 핵심 개념**

```
CSR 흐름
1. 빈 HTML + JS 번들 다운로드
2. JS 실행 → 데이터 fetch → 화면 렌더
   → 그 전까지 사용자는 빈 화면(흰 화면) 봄
```

✅ **장점**
- 최초 로드 후 **페이지 전환이 빠름**(필요한 데이터만 받아 갱신)
- 서버 부담 적음(정적 파일 + API)
- 풍부한 인터랙션(SPA)

❌ **한계**
- **초기 로딩 지연**: JS 다운로드·실행·패칭 후에야 콘텐츠 표시 → 느린 FCP/LCP
- **SEO 불리**: 검색 크롤러가 빈 HTML을 봐 콘텐츠 인식이 약할 수 있음
- **저사양 기기**에서 JS 실행 부담
- 자바스크립트 비활성화 시 동작 X

🎯 **해결책**: SSR/SSG(Next.js — Q66), 스트리밍 SSR, 사전 렌더링으로 초기 HTML에 콘텐츠를 담아 위 한계를 보완.

> 💡 비교: SSR은 서버가 완성된 HTML을 보내 초기 표시·SEO에 유리, CSR은 이후 상호작용에 유리 → Next.js는 둘을 **하이브리드**로 결합.

**🔥 예상 꼬리질문**
- Q. CSR의 SEO 문제를 어떻게? → A. SSR/SSG로 초기 HTML에 콘텐츠 포함, 또는 메타 태그 사전 렌더링.
- Q. SPA와 CSR 관계? → A. SPA는 보통 CSR로 구현되는 단일 페이지 앱. 라우팅을 클라이언트가 처리.

<details><summary>📝 한 줄 요약</summary>브라우저 JS가 화면을 그리는 방식. 전환 빠름·서버 부담↓ but 초기 로딩 느림·SEO 불리. SSR/SSG로 보완.</details>

## Q64. key 속성의 중요성과 정확한 사용법을 설명할 수 있나요? 🔴

**💬 30초 답변**
> key는 리스트를 렌더링할 때 React가 **각 항목을 식별**하는 값입니다. 재조정(Q55) 시 어떤 항목이 추가·삭제·이동됐는지 key로 판단해 최소한의 DOM 변경을 합니다. **고유하고 안정적인 값**(보통 id)을 써야 하며, **배열 index를 key로 쓰면** 순서 변경 시 버그가 납니다.

**📖 핵심 개념**

```jsx
// ✅ 안정적 고유 id
{items.map(item => <li key={item.id}>{item.name}</li>)}

// ❌ index를 key로 (순서 바뀌면 문제)
{items.map((item, i) => <li key={i}>{item.name}</li>)}
```

📌 **index를 key로 쓰면 안 되는 이유**
순서가 바뀌거나 중간 삽입/삭제될 때, index는 그대로라 React가 **다른 항목을 같은 것으로 오인**합니다. 결과: 입력값이 엉뚱한 행에 남거나, 잘못된 항목이 업데이트되는 버그.

```
[A(key0), B(key1), C(key2)] 에서 맨 앞에 Z 삽입
index key: [Z(0), A(1), B(2), C(3)] → React는 0,1,2가 그대로라 보고 내용만 갈아끼움 → A의 상태가 Z에 남음 ❌
고유 id : key가 달라 Z를 새 항목으로 인식, 나머지는 이동 처리 ✅
```

📌 **올바른 사용**
- 데이터의 **고유 id** 사용 (DB id, uuid)
- 형제 사이에서만 유일하면 됨(전역 유일 불필요)
- **정적이고 순서가 안 바뀌는 리스트**라면 index도 허용 가능(차선)

> 💡 key는 DOM에 전달되는 속성이 아니라 **React 내부 식별용**. 같은 컴포넌트에 key를 바꾸면 React가 **언마운트 후 재마운트**(상태 초기화)하는 트릭으로도 활용.

**🔥 예상 꼬리질문**
- Q. key에 Math.random()을 쓰면? → A. 매 렌더마다 달라져 전부 새로 마운트 → 성능 저하·상태 소실. 절대 금지.
- Q. key로 상태를 리셋한다? → A. 컴포넌트의 key를 바꾸면 React가 재마운트해 state가 초기화됨(폼 리셋 등에 활용).

<details><summary>📝 한 줄 요약</summary>리스트 항목을 식별하는 값. 고유·안정적 id 사용. index key는 순서 변경 시 상태 꼬임 버그. random key 금지. key 변경=재마운트(상태 초기화).</details>

## Q65. 넥스트.js를 사용하는 이유와 장점은 무엇인가요? 🟡

**💬 30초 답변**
> Next.js는 React 기반 프레임워크로, React만으로는 직접 설정해야 하는 **SSR/SSG, 파일 기반 라우팅, 이미지·폰트 최적화, 번들링**을 기본 제공합니다. 덕분에 SEO·초기 로딩 성능을 쉽게 확보하고 풀스택 앱까지 만들 수 있습니다.

**📖 핵심 개념**

📌 **React(라이브러리) vs Next.js(프레임워크)**
- React: UI 렌더링만. 라우팅·SSR·번들 설정은 직접 구성
- Next.js: 위 모든 것을 **관례로 제공**(convention over configuration)

📌 **주요 장점**
- **다양한 렌더링**: SSR / SSG / ISR / CSR을 페이지·컴포넌트 단위로 선택(Q66)
- **파일 기반 라우팅**: 폴더 구조가 곧 URL(Q71)
- **자동 최적화**: 코드 스플리팅, `<Image>`(Q69), 폰트, 프리패칭
- **SEO 친화**: 서버 렌더링 + 메타데이터 API(Q70)
- **풀스택**: Route Handlers / API Routes(Q73), 서버 액션
- **서버 컴포넌트(RSC)**: 서버에서 렌더해 번들 축소(Q68)

> 💡 한 줄 정의: "**프로덕션에 필요한 기능을 기본 탑재한 React 프레임워크**". Vercel이 개발하며 배포까지 매끄럽게 연결(Q74).

**🔥 예상 꼬리질문**
- Q. React로도 SSR 되는데 왜 Next? → A. 직접 구성은 복잡·반복적. Next는 검증된 관례와 최적화를 제공해 생산성·성능을 보장.
- Q. ISR이란? → A. Incremental Static Regeneration. 정적 페이지를 일정 주기로 백그라운드 재생성 → 정적 속도 + 최신 데이터.

<details><summary>📝 한 줄 요약</summary>SSR/SSG·파일 라우팅·이미지/폰트 최적화·풀스택을 기본 제공하는 React 프레임워크. SEO·초기 성능·생산성 확보. Vercel 제작.</details>

## Q66. CSR, SSR, SSG를 설명할 수 있나요? 🔴

**💬 30초 답변**
> 렌더링(HTML 생성) **위치와 시점**의 차이입니다. **CSR**은 브라우저에서 런타임에, **SSR**은 요청마다 서버에서, **SSG**는 빌드 시점에 미리 HTML을 생성합니다. SSR/SSG는 완성된 HTML을 보내 초기 표시·SEO에 유리합니다.

**📖 핵심 개념**

📌 **비교 (면접 핵심!)**

| 방식 | 생성 시점/위치 | 장점 | 단점 | 적합 |
|------|---------------|------|------|------|
| **CSR** | 런타임·브라우저 | 전환 빠름, 서버 부담↓ | 초기 느림, SEO 불리 | 대시보드, 로그인 후 앱 |
| **SSR** | 요청 시·서버 | 최신 데이터, SEO 좋음 | 요청마다 서버 연산(TTFB↑) | 자주 바뀌는 개인화 페이지 |
| **SSG** | 빌드 시·서버 | 가장 빠름(CDN), SEO 좋음 | 빌드 후 내용 고정 | 블로그, 문서, 마케팅 |
| **ISR** | 빌드+주기 재생성 | 정적 속도 + 최신화 | 약간의 지연 | 상품 목록 등 |

```
SSG: [빌드 시] HTML 미리 생성 → CDN 캐싱 → 요청 시 즉시 전달 (가장 빠름)
SSR: [요청 시] 서버가 그때그때 HTML 생성 → 항상 최신
CSR: [브라우저] 빈 HTML 받고 JS로 렌더 → 초기 지연
```

> 💡 공통 후속: SSR/SSG로 HTML을 받은 뒤 브라우저에서 JS를 입혀 상호작용 가능하게 만드는 과정이 **하이드레이션(hydration)**(Q72). Next App Router는 서버 컴포넌트로 이 모델을 더 세분화.

**🔥 예상 꼬리질문**
- Q. SSR vs SSG 선택 기준? → A. 데이터가 요청마다 달라지면(개인화·실시간) SSR, 모두에게 같고 자주 안 바뀌면 SSG.
- Q. TTFB가 뭔가요? → A. Time To First Byte. SSR은 서버 연산 때문에 SSG보다 TTFB가 늘 수 있음.

<details><summary>📝 한 줄 요약</summary>HTML 생성 위치·시점 차이. CSR=브라우저 런타임 / SSR=요청 시 서버 / SSG=빌드 시. SSR·SSG는 SEO·초기표시 유리. 이후 하이드레이션.</details>

## Q67. 앱 라우터와 페이지 라우터의 차이점은 무엇인가요? 🔴

**💬 30초 답변**
> 페이지 라우터(`pages/`)는 Next의 전통 방식으로 파일=페이지이며 모든 컴포넌트가 클라이언트 중심입니다. 앱 라우터(`app/`)는 Next 13+의 새 방식으로 **서버 컴포넌트를 기본**으로 하고, 레이아웃 중첩·스트리밍·서버 액션 등 최신 기능을 지원합니다.

**📖 핵심 개념**

📌 **비교**

| 항목 | 페이지 라우터 (`pages/`) | 앱 라우터 (`app/`) |
|------|--------------------------|--------------------|
| 도입 | 초기~ | Next 13+ (현재 권장) |
| 기본 컴포넌트 | 클라이언트 | **서버 컴포넌트** |
| 데이터 패칭 | `getServerSideProps`/`getStaticProps` | `async` 컴포넌트 + `fetch` |
| 레이아웃 | `_app`/`_document` | 중첩 `layout.js` |
| 로딩/에러 | 직접 구현 | `loading.js`/`error.js` 관례 |
| 스트리밍 | 제한적 | Suspense 기반 지원 |
| 라우팅 파일 | `pages/about.js` | `app/about/page.js` |

```
pages/about.js          → /about   (전통)
app/about/page.js       → /about   (앱 라우터, page.js 필수)
app/about/layout.js     → 공유 레이아웃 (중첩 가능)
app/about/loading.js    → 로딩 UI 자동
```

> 💡 둘은 **한 프로젝트에서 공존 가능**(점진적 마이그레이션). 신규 프로젝트는 앱 라우터 권장. 핵심 변화는 "**서버 컴포넌트 기본 + 파일 관례(layout/loading/error)**".

**🔥 예상 꼬리질문**
- Q. 앱 라우터의 가장 큰 변화는? → A. 서버 컴포넌트 기본화(Q68)와 중첩 레이아웃·스트리밍.
- Q. 기존 프로젝트는 다 바꿔야 하나요? → A. 아닙니다. 공존 가능하며 라우트 단위로 점진 전환.

<details><summary>📝 한 줄 요약</summary>pages/(전통, 클라이언트 중심, getServerSideProps) vs app/(13+, 서버 컴포넌트 기본·중첩 layout·loading/error·스트리밍). 신규는 앱 라우터, 공존 가능.</details>

## Q68. 서버 컴포넌트와 클라이언트 컴포넌트의 역할과 차이점을 설명할 수 있나요? 🔴

**💬 30초 답변**
> 서버 컴포넌트(RSC)는 **서버에서만 렌더**되어 JS 번들에 포함되지 않고, DB·파일·비밀키에 직접 접근하며 데이터 패칭에 유리합니다. 클라이언트 컴포넌트는 **브라우저에서 실행**되어 상태(`useState`)·이벤트·브라우저 API를 쓸 수 있습니다. 앱 라우터는 기본이 서버 컴포넌트이고, `"use client"`로 클라이언트 컴포넌트를 선언합니다.

**📖 핵심 개념**

📌 **비교**

| 항목 | 서버 컴포넌트 (기본) | 클라이언트 컴포넌트 (`"use client"`) |
|------|---------------------|-------------------------------------|
| 실행 위치 | 서버 | 브라우저 |
| JS 번들 | **포함 안 됨**(0kb) | 포함됨 |
| useState/useEffect | ❌ | ✅ |
| 이벤트 핸들러(onClick) | ❌ | ✅ |
| DB/파일/비밀키 직접 접근 | ✅ | ❌ (노출 위험) |
| async/await 직접 | ✅ | 제한 |

```jsx
// 서버 컴포넌트 (기본) — async로 직접 패칭, 번들에 미포함
async function ProductList() {
  const products = await db.query("SELECT * FROM products"); // 서버에서 직접
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

// 클라이언트 컴포넌트 — 상호작용 필요 시
"use client";
function LikeButton() {
  const [liked, setLiked] = useState(false);  // 상태·이벤트는 여기서
  return <button onClick={() => setLiked(!liked)}>{liked ? "♥" : "♡"}</button>;
}
```

🎯 **설계 원칙**: 기본은 서버 컴포넌트, **상호작용(상태·이벤트)이 필요한 말단(leaf)만** 클라이언트로. `"use client"`는 그 경계 아래 전체를 클라이언트로 만들므로 **가능한 트리 아래쪽에** 둠.

> 💡 효과: 데이터 패칭을 서버에서 처리해 워터폴 감소, 민감 로직 은닉, **클라이언트 번들 크기 축소** → 초기 로딩 개선. 서버 컴포넌트는 상호작용이 없고, 클라이언트 컴포넌트는 서버 컴포넌트를 **children/props로** 받을 수 있음.

**🔥 예상 꼬리질문**
- Q. 서버 컴포넌트에서 onClick이 안 되는 이유? → A. 서버에서 렌더되어 브라우저 이벤트·상태가 없기 때문. 상호작용은 클라이언트 컴포넌트로.
- Q. "use client"를 최상단에 두면? → A. 그 아래 전체가 클라이언트 번들에 포함돼 번들이 커짐. 경계를 말단으로 내려야 함.

<details><summary>📝 한 줄 요약</summary>서버 컴포넌트=서버 렌더·번들 미포함·DB/비밀키 접근·패칭 유리(기본). 클라이언트("use client")=상태·이벤트·브라우저 API. 상호작용 말단만 클라이언트로.</details>

## Q69. `<Image>` 컴포넌트를 사용하는 이유와 장점은 무엇인가요? 🟡

**💬 30초 답변**
> Next.js `<Image>`는 `<img>`를 대체해 **자동 최적화**를 제공합니다. WebP/AVIF 포맷 변환, 디바이스별 크기 조정(srcset 자동), 지연 로딩(lazy), 레이아웃 시프트 방지(CLS)를 기본 처리해 이미지 성능과 코어 웹 바이탈을 개선합니다.

**📖 핵심 개념**

```jsx
import Image from "next/image";
<Image src="/hero.jpg" width={800} height={600} alt="히어로" priority />
```

✅ **자동 처리 기능**
- **포맷 최적화**: 브라우저 지원 시 WebP/AVIF로 자동 변환(용량↓)
- **반응형 크기**: 디바이스별 적정 크기 생성(srcset/sizes 자동 — Q14 연결)
- **lazy loading**: 뷰포트 진입 시 로드(기본). 중요한 건 `priority`로 즉시
- **CLS 방지**: width/height(또는 fill)로 공간 예약 → 레이아웃 흔들림 방지(Q99 연결)
- **블러 플레이스홀더**: `placeholder="blur"`로 로딩 중 흐림 처리

📌 **`<img>` 대비**

| 구분 | `<img>` | Next `<Image>` |
|------|---------|----------------|
| 포맷 변환 | 수동 | 자동(WebP/AVIF) |
| 반응형 srcset | 수동 작성 | 자동 |
| lazy/CLS | 수동 | 자동 |

> 💡 주의: 외부 도메인 이미지는 `next.config`의 `images.remotePatterns`에 등록 필요. width/height 미지정 시 `fill` + 부모 `position:relative` 사용. LCP 이미지엔 `priority`로 lazy 해제.

**🔥 예상 꼬리질문**
- Q. CLS를 어떻게 막나요? → A. width/height로 공간을 미리 예약해 이미지 로드 시 레이아웃이 밀리지 않게 함.
- Q. priority는 언제? → A. 첫 화면 LCP 이미지(히어로 등) — lazy를 끄고 우선 로드해 LCP 개선.

<details><summary>📝 한 줄 요약</summary>img 대체 자동 최적화: WebP/AVIF 변환·반응형 srcset·lazy·CLS 방지·블러. 코어 웹 바이탈 개선. LCP 이미지엔 priority.</details>

## Q70. 넥스트.js에서 검색 엔진 최적화를 어떻게 개선할 수 있나요? 🟡

**💬 30초 답변**
> 가장 핵심은 **SSR/SSG로 완성된 HTML을 제공**해 크롤러가 콘텐츠를 읽게 하는 것입니다. 여기에 **메타데이터 API**(title·description·OG), 시맨틱 마크업, `sitemap.xml`/`robots.txt`, 구조화 데이터(JSON-LD), 이미지·성능 최적화를 더합니다.

**📖 핵심 개념**

📌 **SEO 개선 수단**
- **렌더링**: SSR/SSG로 초기 HTML에 콘텐츠 포함(CSR의 SEO 약점 보완 — Q63)
- **메타데이터 API**(App Router):
```jsx
export const metadata = {
  title: "상품 상세",
  description: "...",
  openGraph: { title: "...", images: ["/og.png"] },  // 소셜 공유
};
// 동적: export async function generateMetadata({ params }) { ... }
```
- **sitemap.xml / robots.txt**: `app/sitemap.ts`, `app/robots.ts`로 생성
- **구조화 데이터(JSON-LD)**: 검색 결과 리치 스니펫
- **시맨틱 태그·헤딩 계층**(Q4, Q12 연결), 이미지 `alt`
- **성능(코어 웹 바이탈)**: LCP/CLS 개선도 랭킹 요소(Q99)

> 💡 면접 핵심 한 줄: "**Next의 SSR/SSG 덕에 크롤러가 빈 페이지가 아닌 완성된 HTML을 보게 되는 것**"이 SEO의 출발점. 나머지는 메타데이터·사이트맵·성능으로 보강.

**🔥 예상 꼬리질문**
- Q. CSR이 SEO에 불리한 이유? → A. 크롤러가 JS 실행 전 빈 HTML을 보면 콘텐츠 인식이 약함 → SSR/SSG로 해결.
- Q. 동적 메타데이터는? → A. `generateMetadata`로 params·데이터 기반 title/OG를 페이지별 생성.

<details><summary>📝 한 줄 요약</summary>SSR/SSG로 완성 HTML 제공이 핵심 + 메타데이터 API(title/description/OG)·sitemap/robots·JSON-LD·시맨틱·코어 웹 바이탈.</details>

## Q71. 넥스트.js의 라우팅 시스템은 무엇인가요? 🟡

**💬 30초 답변**
> Next.js는 **파일·폴더 구조가 곧 URL**이 되는 파일 기반 라우팅을 씁니다. 앱 라우터에서는 `app/` 아래 폴더가 경로 세그먼트가 되고 `page.js`가 페이지를, `layout.js`가 공유 레이아웃을 정의합니다. 대괄호로 동적 경로를 만듭니다.

**📖 핵심 개념**

```
app/
├─ page.js                 → /
├─ about/page.js           → /about
├─ blog/[slug]/page.js     → /blog/:slug      (동적 경로)
├─ shop/[...all]/page.js   → /shop/a/b/c       (catch-all)
├─ (marketing)/page.js     → / (그룹: URL에 미포함)
├─ @modal/...              → 병렬 라우트
└─ layout.js               → 전 페이지 공유 레이아웃
```

📌 **특수 파일·규칙**
- `page.js`: 해당 경로의 UI (필수)
- `layout.js`: 중첩 공유 레이아웃(상태 유지)
- `loading.js`: Suspense 기반 로딩 UI
- `error.js`: 에러 바운더리 UI
- `[param]`: 동적 / `[...slug]`: catch-all / `(group)`: 라우트 그룹(URL 영향 X)

📌 **네비게이션**: `<Link href="/about">`로 클라이언트 라우팅 + **자동 프리패칭**(뷰포트의 링크 미리 로드). 프로그래밍 방식은 `useRouter().push()`.

> 💡 페이지 라우터는 `pages/` 기준 동일 개념(`pages/blog/[slug].js`). 앱 라우터는 폴더 기반 + `page.js` 관례라는 점이 차이(Q67).

**🔥 예상 꼬리질문**
- Q. `<Link>`와 `<a>` 차이? → A. `<Link>`는 전체 새로고침 없이 클라이언트 라우팅 + 프리패칭, `<a>`는 전체 페이지 리로드.
- Q. 라우트 그룹 `(name)`은? → A. 폴더로 묶되 URL엔 안 들어감 → 레이아웃 분리·코드 정리용.

<details><summary>📝 한 줄 요약</summary>파일/폴더=URL. app/ 폴더가 경로, page.js=UI, layout/loading/error 관례, [param] 동적·(group) URL제외. Link로 클라이언트 라우팅+프리패칭.</details>

## Q72. 넥스트.js의 하이드레이션 오류란 무엇인가요? 🔴

**💬 30초 답변**
> 하이드레이션은 서버가 보낸 HTML에 브라우저가 JS를 입혀 상호작용 가능하게 만드는 과정입니다. 하이드레이션 오류는 **서버에서 렌더한 HTML과 클라이언트가 처음 렌더한 결과가 일치하지 않을 때** 발생합니다. `Date.now()`, `Math.random()`, `window` 접근, 잘못된 HTML 중첩이 흔한 원인입니다.

**📖 핵심 개념**

```
SSR/SSG: 서버가 HTML 생성 → 전송 → 브라우저 표시(빠른 FCP)
하이드레이션: 브라우저가 같은 컴포넌트를 렌더해 HTML과 매칭 → 이벤트 연결
              ↑ 이때 서버 HTML ≠ 클라이언트 렌더면 오류!
```

📌 **흔한 원인**
- 시점에 따라 달라지는 값: `Date.now()`, `new Date()`, `Math.random()`
- 브라우저 전용 API를 렌더 중 접근: `window`, `localStorage`
- `typeof window !== "undefined"` 분기로 서버/클라 결과가 갈림
- 잘못된 HTML 중첩(`<p>` 안에 `<div>`, `<a>` 안에 `<a>`)
- 브라우저 확장 프로그램이 DOM 변경

```jsx
// ❌ 서버와 클라이언트 결과 불일치
function Clock() { return <p>{new Date().toLocaleTimeString()}</p>; }

// ✅ 클라이언트에서만 렌더(마운트 후)
function Clock() {
  const [time, setTime] = useState(null);
  useEffect(() => setTime(new Date().toLocaleTimeString()), []);
  return <p>{time ?? "로딩..."}</p>;
}
```

> 💡 해결: 클라이언트 전용 로직은 `useEffect`(마운트 후)로 미루기, `next/dynamic`의 `ssr:false`, 또는 `suppressHydrationWarning`(최후 수단). 근본은 "**서버와 클라 첫 렌더를 동일하게**".

**🔥 예상 꼬리질문**
- Q. 왜 일치해야 하나요? → A. React가 기존 HTML을 재사용(attach)하려는데 구조가 다르면 매칭 실패 → 경고·재렌더·깜빡임.
- Q. localStorage 값으로 초기 UI를 그리면? → A. 서버엔 없어 불일치 → 마운트 후 useEffect에서 읽어 반영.

<details><summary>📝 한 줄 요약</summary>서버 HTML에 JS를 입히는 게 하이드레이션. 서버≠클라 첫 렌더면 오류(Date/random/window/잘못된 중첩). 클라 전용은 useEffect·ssr:false로 분리.</details>

## Q73. 넥스트.js에서 API 루트를 사용하는 목적은 무엇인가요? 🟡

**💬 30초 답변**
> API 루트(페이지 라우터) / Route Handlers(앱 라우터)는 Next 프로젝트 안에서 **백엔드 API 엔드포인트를 만드는** 기능입니다. 별도 서버 없이 풀스택을 구성할 수 있고, 비밀키를 서버에서 안전하게 다루거나 외부 API 호출을 프록시·중계할 때 사용합니다.

**📖 핵심 개념**

```js
// 앱 라우터: app/api/users/route.js
export async function GET() {
  const users = await db.query("SELECT * FROM users");
  return Response.json(users);
}
export async function POST(req) {
  const body = await req.json();
  // 비밀키는 서버에서만 (process.env.SECRET) → 클라 노출 X
  return Response.json({ ok: true });
}
```

📌 **사용 목적**
- **백엔드 분리 불필요**: 한 프로젝트에서 프론트+API
- **비밀 정보 보호**: API 키·DB 접속을 서버에서 처리(클라이언트 노출 차단 — Q78 연결)
- **프록시/중계**: 외부 API를 감싸 CORS 우회·응답 가공
- **웹훅 수신**, 폼 처리 등

> 💡 앱 라우터는 `route.js`에 HTTP 메서드 함수(GET/POST...) export. 단순 데이터 표시는 **서버 컴포넌트에서 직접 패칭**(Q68)이 더 간단하고, **서버 액션**으로 변이(mutation)도 가능 → API 루트는 외부 공개 엔드포인트·웹훅 등에 적합.

**🔥 예상 꼬리질문**
- Q. 서버 컴포넌트 패칭이 있는데 API 루트가 왜? → A. 외부에 공개할 REST 엔드포인트, 웹훅, 클라이언트에서 직접 호출할 API가 필요할 때.
- Q. API 키를 클라이언트에 두면? → A. 번들에 노출돼 탈취 위험 → 서버(API 루트/서버리스)에서 다뤄야 함(Q78).

<details><summary>📝 한 줄 요약</summary>Next 안에서 백엔드 엔드포인트 생성(route.js의 GET/POST). 풀스택·비밀키 보호·프록시·웹훅. 단순 표시는 서버 컴포넌트, 변이는 서버 액션이 더 간단.</details>

## Q74. 넥스트.js 앱을 배포할 때 고려사항과 주로 쓰는 플랫폼은? 🟢

**💬 30초 답변**
> Next 제작사인 **Vercel**이 가장 매끄럽지만, AWS·Netlify·Cloudflare·Docker 셀프호스팅도 가능합니다. 고려할 점은 렌더링 방식(SSR은 서버 런타임 필요)·환경변수·이미지 최적화 지원·캐싱/ISR·서버리스 함수 제약 등입니다.

**📖 핵심 개념**

📌 **플랫폼**

| 플랫폼 | 특징 |
|--------|------|
| **Vercel** | Next 제작사, 무설정 배포·프리뷰·ISR·이미지 최적화 완벽 |
| AWS (Amplify/SST) | 세밀한 제어, 인프라 통합 |
| Netlify / Cloudflare | 정적·엣지 강점 |
| Docker 셀프호스팅 | `next start`로 직접 운영, 완전 제어 |

📌 **고려사항**
- **렌더링 방식**: SSR/서버 액션은 Node 런타임 필요(순수 정적 호스팅 불가). SSG는 정적 호스팅 가능
- **환경변수**: `NEXT_PUBLIC_` 접두사만 클라이언트 노출, 나머지는 서버 전용(비밀키)
- **이미지 최적화**: `<Image>` 최적화 서버 지원 여부(미지원 시 별도 로더)
- **캐싱·ISR**: 재검증 주기, CDN 캐시 전략(Q77 연결)
- **빌드/실행**: `next build` → `next start`(서버) 또는 정적 export

> 💡 면접 무난한 답: "**기본은 Vercel(무설정·최적화 완벽), 사내 인프라/비용/제어가 중요하면 AWS나 Docker 셀프호스팅**. 이때 SSR 런타임·환경변수·이미지 최적화 지원을 확인."

**🔥 예상 꼬리질문**
- Q. SSG 앱을 정적 호스팅에? → A. 가능(S3+CloudFront 등). 단 SSR/서버 액션/ISR은 서버 런타임이 필요.
- Q. 클라이언트에 환경변수를 노출하려면? → A. `NEXT_PUBLIC_` 접두사. 비밀키는 절대 붙이면 안 됨.

<details><summary>📝 한 줄 요약</summary>기본 Vercel(무설정·최적화), 그 외 AWS·Netlify·Docker. 고려: 렌더링 방식(SSR=서버 런타임)·환경변수(NEXT_PUBLIC_)·이미지 최적화·ISR/캐싱.</details>
