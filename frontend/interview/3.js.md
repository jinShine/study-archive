## Q35. 자바스크립트란 무엇인가요? 🟡

**💬 30초 답변**
> 자바스크립트는 웹 페이지에 **동적 동작**을 부여하는 프로그래밍 언어입니다. 원래 브라우저에서만 돌았지만, 지금은 Node.js 덕분에 서버에서도 동작하는 **싱글 스레드·인터프리터·프로토타입 기반**의 멀티패러다임 언어입니다.

**📖 핵심 개념**

🎯 **비유**: HTML(골조)·CSS(인테리어)에 이어 JavaScript는 집의 **전기·수도·스위치** — 버튼을 누르면 불이 켜지는 동작을 담당합니다.

📌 **특징**
- **싱글 스레드**: 한 번에 하나의 작업 (but 이벤트 루프로 비동기 처리 — Q46)
- **인터프리터 / JIT 컴파일**: 별도 컴파일 없이 실행 (V8 엔진은 JIT로 최적화)
- **동적 타입**: 변수 타입이 런타임에 결정
- **프로토타입 기반** 객체지향 (Q44)
- **일급 함수**: 함수를 값처럼 전달·반환 가능 (클로저·콜백의 기반)

> 💡 **자바 ≠ 자바스크립트**: 이름만 비슷할 뿐 전혀 다른 언어. 마케팅상 자바 인기에 편승한 이름.
> **ECMAScript(ES)**: 자바스크립트의 표준 명세. ES6(2015)부터 `let/const`, 화살표 함수, 클래스, 모듈 등이 도입됨.

**🔥 예상 꼬리질문**
- Q. 싱글 스레드인데 어떻게 비동기 처리를? → A. 브라우저/Node의 Web API + 이벤트 루프 + 큐 구조로 논블로킹 처리(Q46).
- Q. ES6의 주요 변화는? → A. let/const, 화살표 함수, 템플릿 리터럴, 구조 분해, 클래스, Promise, 모듈(import/export).

<details><summary>📝 한 줄 요약</summary>웹에 동적 동작을 주는 싱글 스레드·동적 타입·프로토타입 기반 언어. ECMAScript가 표준 명세. Java와 무관.</details>

## Q36. 자바스크립트는 어떤 데이터 타입을 가지고 있나요? 🔴

**💬 30초 답변**
> 크게 **원시 타입 7가지**(string, number, boolean, null, undefined, symbol, bigint)와 **객체 타입**(object — 배열·함수 포함)으로 나뉩니다. 원시 타입은 값 자체가 복사되고, 객체 타입은 참조(주소)가 복사된다는 점이 핵심 차이입니다.

**📖 핵심 개념**

📌 **원시 타입 (primitive) — 불변, 값으로 복사**

| 타입 | 예 | 비고 |
|------|-----|------|
| string | `"hi"` | 문자열 |
| number | `42`, `3.14`, `NaN` | 정수·실수 구분 없음 |
| boolean | `true/false` | |
| undefined | `undefined` | 값이 할당 안 됨 |
| null | `null` | 의도적 '없음' |
| symbol | `Symbol()` | 고유 식별자 (ES6) |
| bigint | `10n` | 아주 큰 정수 (ES2020) |

📌 **객체 타입 (reference) — 참조로 복사**: object, array, function, Date, ...

```js
// 원시: 값 복사 (독립적)
let a = 1; let b = a; b = 2;
console.log(a); // 1 (영향 없음)

// 객체: 참조 복사 (같은 주소 공유)
let o1 = { x: 1 }; let o2 = o1; o2.x = 2;
console.log(o1.x); // 2 (같이 변함!) → Q38 얕은/깊은 복사 연결
```

> ⚠️ **typeof 함정**: `typeof null === "object"` (언어 초기 버그, 하위호환 위해 유지). `typeof []==="object"` → 배열 판별은 `Array.isArray()`.

**🔥 예상 꼬리질문**
- Q. null과 undefined 차이? → A. undefined는 "할당 안 됨"(시스템적), null은 "비어있음을 의도적으로 명시"(개발자적).
- Q. NaN의 타입은? → A. number. 그리고 `NaN === NaN`은 false → `Number.isNaN()`으로 판별.

<details><summary>📝 한 줄 요약</summary>원시 7종(string·number·boolean·null·undefined·symbol·bigint, 값 복사) + 객체(참조 복사). typeof null="object" 함정 주의.</details>

## Q37. 객체란 무엇인가요? 🟡

**💬 30초 답변**
> 객체는 **키-값 쌍(프로퍼티)의 집합**으로, 관련된 데이터와 동작(메서드)을 하나로 묶는 참조 타입입니다. 자바스크립트에서 배열·함수·정규식 등도 모두 객체의 일종입니다.

**📖 핵심 개념**

```js
const user = {
  name: "Kim",           // 프로퍼티
  age: 30,
  greet() {              // 메서드 (함수인 프로퍼티)
    return `Hi, ${this.name}`;
  },
};

// 접근
user.name;        // 점 표기법
user["age"];      // 대괄호 표기법 (동적 키에 유용)

// 추가/삭제
user.email = "a@b.com";
delete user.age;
```

📌 **유용한 정적 메서드**
```js
Object.keys(user);      // ['name', 'greet', 'email']
Object.values(user);    // 값 배열
Object.entries(user);   // [[key, value], ...]
Object.freeze(user);    // 불변화 (Q52)
Object.assign({}, user);// 얕은 복사 (Q38)
```

> 💡 객체 프로퍼티 순회는 `for...in`(상속 포함, 주의)보다 `Object.keys().forEach`나 `Object.entries()`가 안전. 키 순서는 정수 키 오름차순 → 문자열 키 삽입 순.

**🔥 예상 꼬리질문**
- Q. 점 표기법 vs 대괄호 표기법? → A. 대괄호는 변수·공백·하이픈 키 등 **동적 키**에 사용 (`obj[key]`).
- Q. 객체를 복사하면? → A. 참조가 복사됨 → 얕은/깊은 복사 필요(Q38).

<details><summary>📝 한 줄 요약</summary>키-값 프로퍼티의 집합(참조 타입). 배열·함수도 객체. Object.keys/values/entries로 순회, freeze로 불변화.</details>

## Q38. 얕은 복사와 깊은 복사란 무엇인가요? 🔴

**💬 30초 답변**
> **얕은 복사**는 객체의 1단계(최상위) 프로퍼티만 복사해 중첩 객체는 여전히 참조를 공유합니다. **깊은 복사**는 모든 중첩 단계까지 완전히 새로 복사해 원본과 완전히 독립됩니다.

**📖 핵심 개념**

```
얕은 복사                        깊은 복사
원본 { a:1, nested:{x:1} }       원본 { a:1, nested:{x:1} }
복사 { a:1, nested:─┐ }          복사 { a:1, nested:{x:1} }
                    ↓                          ↑ 완전히 새 객체
원본.nested ←── 같은 주소 공유    독립적
```

```js
const orig = { a: 1, nested: { x: 1 } };

// ① 얕은 복사
const shallow = { ...orig };                  // 또는 Object.assign({}, orig)
shallow.a = 99;          // 원본 영향 X (1단계는 값 복사)
shallow.nested.x = 99;   // ⚠️ 원본도 변함! (중첩은 참조 공유)
console.log(orig.nested.x); // 99

// ② 깊은 복사
const deep = structuredClone(orig);           // 최신 표준 (권장)
// const deep = JSON.parse(JSON.stringify(orig)); // 전통 방식 (한계 있음)
deep.nested.x = 0;
console.log(orig.nested.x); // 99 (영향 없음)
```

📌 **깊은 복사 방법 비교**

| 방법 | 비고 |
|------|------|
| `structuredClone()` | 최신 표준, 순환참조·Date·Map/Set 지원 ✅ |
| `JSON.parse(JSON.stringify())` | 간단하나 함수·undefined·Date·순환참조 손실 ❌ |
| lodash `cloneDeep` | 라이브러리, 안정적 |

> 💡 React에서 상태 업데이트 시 얕은 복사(`{...state}`)를 쓰되, **중첩 객체를 바꿀 땐 그 단계까지 새로 복사**해야 함(불변성 — Q52). 이게 안 되면 리렌더 누락 버그 발생.

**🔥 예상 꼬리질문**
- Q. 스프레드(`...`)는 얕은 복사인가요? → A. 네, 1단계만 복사하는 얕은 복사입니다.
- Q. JSON 방식의 한계는? → A. 함수·undefined·Symbol 누락, Date가 문자열로, 순환참조 시 에러.

<details><summary>📝 한 줄 요약</summary>얕은 복사=1단계만(중첩은 참조 공유, <code>{...}</code>) / 깊은 복사=전 단계 독립(<code>structuredClone</code>). React 불변성과 직결.</details>

## Q39. 호이스팅이란 무엇인가요? 🔴

**💬 30초 답변**
> 호이스팅은 변수·함수 선언이 코드 실행 전에 **스코프 최상단으로 끌어올려진 것처럼 동작**하는 자바스크립트의 특성입니다. 단, `var`와 함수 선언문은 끌어올려지지만, `let/const`는 끌어올려져도 **TDZ(일시적 사각지대)** 때문에 선언 전 접근 시 에러가 납니다.

**📖 핵심 개념**

```js
// var: 선언만 호이스팅, 초기값은 undefined
console.log(a); // undefined (에러 아님!)
var a = 1;

// let/const: 호이스팅되지만 TDZ로 접근 불가
console.log(b); // ❌ ReferenceError
let b = 2;

// 함수 선언문: 전체가 호이스팅 → 선언 전 호출 가능
hi();           // ✅ "hi"
function hi() { console.log("hi"); }

// 함수 표현식: 변수 규칙 따름 → 호이스팅 X
bye();          // ❌ TypeError (bye is not a function)
var bye = function () {};
```

📌 **TDZ (Temporal Dead Zone)**: `let/const`가 선언된 스코프 시작 ~ 실제 선언문 도달 전까지의 구간. 이 구간에서 접근하면 ReferenceError.

```
스코프 시작 ─────[ TDZ ]─────→ let b 선언 ─────→ 사용 가능
            (접근 시 에러)
```

> 💡 면접 포인트: "let/const는 호이스팅이 **안 된다**"는 흔한 오해. **호이스팅은 되지만 TDZ 때문에 초기화 전 접근이 막힐 뿐**이라고 정확히 답하면 좋음.

**🔥 예상 꼬리질문**
- Q. var를 지양하는 이유? → A. 함수 스코프라 블록을 무시하고, 재선언 허용, undefined 호이스팅으로 버그 유발. → let/const 사용.
- Q. 함수 선언문 vs 표현식 호이스팅 차이? → A. 선언문은 전체가 올라가 선언 전 호출 가능, 표현식은 변수 규칙을 따라 불가.

<details><summary>📝 한 줄 요약</summary>선언이 스코프 최상단으로 끌어올려지는 특성. var=undefined로 초기화 / let·const=호이스팅되나 TDZ로 접근 시 에러 / 함수 선언문=전체 호이스팅.</details>

## Q40. 동등 연산자(==)와 일치 연산자(===)의 차이점은 무엇인가요? 🟡

**💬 30초 답변**
> `==`(동등)는 타입이 다르면 **타입을 강제 변환(coercion)한 뒤** 값을 비교하고, `===`(일치)는 **타입과 값을 모두** 비교합니다. 예측 가능성을 위해 실무에서는 항상 `===`를 사용하는 것이 권장됩니다.

**📖 핵심 개념**

```js
1 == "1";      // true  (문자열 "1"을 숫자로 변환)
1 === "1";     // false (number vs string → 타입 다름)

0 == false;    // true  (false → 0)
0 === false;   // false

null == undefined;  // true  (특별 규칙)
null === undefined; // false

"" == 0;       // true  ("" → 0)  ← 직관에 어긋나는 함정
[] == false;   // true  ([] → "" → 0)  ← 매우 헷갈림
```

📌 **왜 === 인가**: `==`의 암묵적 변환 규칙은 복잡하고 직관에 어긋나는 결과(`"" == 0`, `[] == ![]`)를 낳아 버그의 원인이 됩니다.

```
==  → 타입 변환 후 값 비교 (느슨)
=== → 타입 + 값 동시 비교 (엄격, 권장)
```

> 💡 예외적으로 `== null` 한 가지는 실무에서도 종종 씀: `x == null`은 `x === null || x === undefined`와 같아 "null이거나 undefined"를 간단히 검사.

**🔥 예상 꼬리질문**
- Q. `NaN === NaN`은? → A. false. NaN은 자기 자신과도 다름 → `Number.isNaN()`으로 판별.
- Q. 객체 비교는? → A. `==`/`===` 모두 **참조(주소)** 를 비교. 내용이 같아도 다른 객체면 false.

<details><summary>📝 한 줄 요약</summary>== = 타입 강제 변환 후 값 비교(함정 많음) / === = 타입+값 비교(권장). 객체는 둘 다 참조 비교.</details>

## Q41. 스코프 체인이란 무엇인가요? 🟡

**💬 30초 답변**
> 스코프는 변수에 접근할 수 있는 범위이고, 스코프 체인은 변수를 찾을 때 **현재 스코프 → 바깥 스코프 → ... → 전역 스코프** 순으로 거슬러 올라가며 탐색하는 연결 구조입니다. 안쪽에서 바깥 변수는 접근 가능하지만 그 반대는 불가능합니다.

**📖 핵심 개념**

```js
const global = "전역";
function outer() {
  const o = "outer";
  function inner() {
    const i = "inner";
    console.log(i, o, global); // 모두 접근 ✅ (안→밖 탐색)
  }
  inner();
  // console.log(i); // ❌ 바깥에서 안쪽 변수 접근 불가
}
```

```
inner 스코프 → outer 스코프 → 전역 스코프
   (i)          (o)           (global)
   변수 못 찾으면 한 단계씩 바깥으로 검색 →
```

📌 **렉시컬 스코프(정적 스코프)**: 스코프는 **함수를 어디서 호출했는지가 아니라, 어디서 선언(작성)했는지** 로 결정됩니다. 이게 클로저(Q47)의 토대.

📌 **스코프 종류**
- 전역 스코프 / 함수 스코프(`var`, function) / 블록 스코프(`let`, `const`, `{}`)

**🔥 예상 꼬리질문**
- Q. 렉시컬 스코프란? → A. 코드를 작성한 위치 기준으로 스코프가 정해지는 것. 호출 위치와 무관.
- Q. 스코프 체인과 클로저의 관계? → A. 클로저는 함수가 선언될 때의 스코프 체인을 기억해 바깥 변수에 계속 접근하는 것(Q47).

<details><summary>📝 한 줄 요약</summary>변수를 안쪽→바깥쪽 순으로 탐색하는 연결 구조. 렉시컬(작성 위치 기준) 스코프. 안→밖 접근 가능, 역방향 불가. 클로저의 토대.</details>

## Q42. this 키워드란 무엇인가요? 🔴

**💬 30초 답변**
> `this`는 **함수가 어떻게 호출되었는지(호출 방식)** 에 따라 동적으로 결정되는, 함수 실행 문맥을 가리키는 키워드입니다. 일반 함수는 호출 시점에 정해지고, 화살표 함수는 **선언 시점의 바깥 this**를 그대로 따릅니다.

**📖 핵심 개념**

📌 **호출 방식별 this (면접 핵심!)**

| 호출 방식 | this | 예 |
|-----------|------|----|
| 일반 함수 호출 | 전역(window) / strict면 undefined | `fn()` |
| 메서드 호출 | 그 객체 | `obj.fn()` → obj |
| 생성자 호출 | 새로 생성된 인스턴스 | `new Fn()` |
| 명시적 바인딩 | 지정한 객체 | `fn.call(obj)`, `bind` |
| 화살표 함수 | **상위 스코프의 this** (고정) | — |

```js
const obj = {
  name: "Kim",
  regular() { console.log(this.name); },     // obj (메서드 호출)
  arrow: () => { console.log(this.name); },  // 상위 this (여기선 undefined)
};
obj.regular(); // "Kim"
obj.arrow();   // undefined (화살표는 obj를 가리키지 않음!)

// 콜백에서 this 유실 → 화살표로 해결
class Timer {
  count = 0;
  start() {
    setInterval(() => { this.count++; }, 1000); // ✅ 화살표가 start의 this 유지
  }
}
```

> 💡 **흔한 버그**: 메서드를 콜백으로 넘기면 this가 끊김 → `bind(this)` 또는 화살표 함수로 해결. React 클래스 컴포넌트의 핸들러 바인딩 이슈가 대표 사례.

**🔥 예상 꼬리질문**
- Q. call/apply/bind 차이? → A. call/apply는 즉시 호출(인자 전달 방식 다름: call은 나열, apply는 배열), bind는 this 고정된 **새 함수 반환**.
- Q. 화살표 함수의 this는? → A. 자신만의 this가 없고 선언된 위치의 상위 this를 그대로 사용(렉시컬 this).

<details><summary>📝 한 줄 요약</summary>호출 방식으로 결정: 일반 호출=전역/undefined, 메서드=객체, new=인스턴스, call/bind=지정. 화살표=상위 this 고정.</details>

## Q43. 실행 컨텍스트를 들어 본 적 있나요? 🟢

**💬 30초 답변**
> 실행 컨텍스트는 코드가 실행될 때 자바스크립트 엔진이 만드는 **환경 정보 묶음**입니다. 변수·함수 선언(렉시컬/변수 환경), 스코프 체인, `this` 값을 담으며, 함수가 호출될 때마다 생성되어 **콜 스택**에 쌓입니다.

**📖 핵심 개념**

📌 **구성 요소**
- **렉시컬 환경 / 변수 환경**: 식별자(변수·함수)와 그 값
- **this 바인딩**: 해당 컨텍스트의 this
- **스코프 체인 정보**: 외부 환경 참조

📌 **종류**
- 전역 실행 컨텍스트(GEC): 최초 1개
- 함수 실행 컨텍스트(FEC): 함수 호출마다 생성

```js
function a() { b(); }
function b() { console.log("b"); }
a();
```
```
콜 스택 (LIFO)
┌──────────┐
│  b() EC  │ ← 마지막에 쌓이고 먼저 빠짐
├──────────┤
│  a() EC  │
├──────────┤
│ 전역 EC  │
└──────────┘
```

🎯 **호이스팅·스코프·this의 근원**: "왜 호이스팅이 일어나나, 왜 this가 호출 방식에 따라 바뀌나"의 답이 실행 컨텍스트 생성 단계(생성 → 실행)에 있음.

> 💡 콜 스택이 한계를 넘으면 `Maximum call stack size exceeded`(스택 오버플로 — 무한 재귀 등).

**🔥 예상 꼬리질문**
- Q. 콜 스택과 이벤트 루프의 관계? → A. 콜 스택이 비면 이벤트 루프가 큐의 콜백을 스택에 올림(Q46).
- Q. 호이스팅이 실행 컨텍스트와 무슨 관계? → A. 컨텍스트 '생성 단계'에서 선언을 먼저 등록하기 때문에 호이스팅 현상이 나타남.

<details><summary>📝 한 줄 요약</summary>코드 실행 환경 정보(변수·this·스코프 체인)의 묶음. 함수 호출마다 생성되어 콜 스택에 쌓임(LIFO). 호이스팅·this의 근원.</details>

## Q44. 자바스크립트의 프로토타입이란 무엇인가요? 🔴

**💬 30초 답변**
> 프로토타입은 자바스크립트 객체가 **다른 객체를 상속받는 메커니즘**입니다. 모든 객체는 `[[Prototype]]`이라는 숨은 링크로 부모 프로토타입 객체를 가리키고, 프로퍼티를 찾을 때 없으면 이 **프로토타입 체인**을 따라 올라가며 탐색합니다.

**📖 핵심 개념**

```js
const arr = [1, 2, 3];
arr.map(x => x);  // map은 arr에 없지만 Array.prototype에서 찾음
// arr → Array.prototype → Object.prototype → null
```

```
arr ──[[Prototype]]──▶ Array.prototype ──▶ Object.prototype ──▶ null
       (push, map...)        (toString...)
프로퍼티 못 찾으면 체인 따라 위로 탐색 →
```

📌 **prototype vs __proto__**
- `생성자함수.prototype`: 그 생성자로 만든 인스턴스들이 공유할 부모 객체
- `인스턴스.__proto__` (= `Object.getPrototypeOf(x)`): 실제 부모 링크

```js
function Animal(name) { this.name = name; }
Animal.prototype.speak = function () { return `${this.name} 운다`; };

const cat = new Animal("야옹이");
cat.speak();  // 인스턴스엔 없지만 prototype에서 찾음 → 메모리 절약(공유)
```

🎯 **왜 쓰나**: 메서드를 인스턴스마다 복제하지 않고 **프로토타입에 한 번만 정의해 공유** → 메모리 효율. `class` 문법도 내부적으로는 프로토타입 기반(문법적 설탕).

> 💡 클래스 기반 언어(Java)는 '클래스 → 인스턴스' 복제, JS는 '객체 → 객체' 위임(delegation) 방식이라는 게 본질적 차이.

**🔥 예상 꼬리질문**
- Q. class는 프로토타입과 다른가요? → A. 아닙니다. class는 프로토타입 상속을 쉽게 쓰게 한 문법적 설탕입니다(Q48).
- Q. 프로토타입 체인의 끝은? → A. `Object.prototype` → `null`. 여기까지 못 찾으면 undefined.

<details><summary>📝 한 줄 요약</summary>객체가 다른 객체를 상속하는 메커니즘. [[Prototype]] 링크로 체인을 따라 프로퍼티 탐색. 메서드 공유로 메모리 절약. class는 이 위의 문법적 설탕.</details>

## Q45. 콜백, 프로미스, async/await의 차이점과 각각의 장단점은 무엇인가요? 🔴

**💬 30초 답변**
> 셋 다 **비동기 처리** 방식입니다. 콜백은 가장 원시적이지만 중첩되면 콜백 지옥에 빠지고, 프로미스는 `.then` 체이닝으로 이를 완화하며, async/await는 비동기 코드를 **동기 코드처럼 직관적으로** 작성하게 해주는 프로미스 기반 문법입니다.

**📖 핵심 개념**

📌 **① 콜백** — 함수를 인자로 넘겨 완료 후 호출
```js
getUser(1, (user) => {
  getPosts(user.id, (posts) => {
    getComments(posts[0].id, (comments) => {
      // 콜백 지옥 (callback hell) — 깊은 중첩, 에러 처리 분산 ❌
    });
  });
});
```

📌 **② 프로미스** — 성공(resolve)/실패(reject) 상태를 가진 객체
```js
getUser(1)
  .then(user => getPosts(user.id))
  .then(posts => getComments(posts[0].id))
  .catch(err => console.error(err))   // 에러 한 곳에서 처리 ✅
  .finally(() => console.log("끝"));
```
- 상태: `pending → fulfilled / rejected`
- `Promise.all`(모두 성공), `allSettled`(개별 결과), `race`(가장 빠른 것)

📌 **③ async/await** — 프로미스를 동기처럼
```js
async function load() {
  try {
    const user = await getUser(1);
    const posts = await getPosts(user.id);
    return posts;
  } catch (err) {           // try/catch로 자연스러운 에러 처리 ✅
    console.error(err);
  }
}
```

📌 **비교**

| 방식 | 장점 | 단점 |
|------|------|------|
| 콜백 | 단순, 어디서나 동작 | 콜백 지옥, 에러 처리 분산 |
| 프로미스 | 체이닝, 통합 에러 처리, 병렬(`all`) | `.then` 길어지면 가독성 ↓ |
| async/await | 동기처럼 직관적, try/catch | 병렬 처리 시 주의(순차 await 남발 → 느림) |

> 💡 **병렬 처리 함정**: 독립 작업을 `await` 연속으로 하면 순차 실행되어 느림. `await Promise.all([a(), b()])`로 동시에.

**🔥 예상 꼬리질문**
- Q. async 함수의 반환값은? → A. 항상 Promise. `return x`는 `Promise.resolve(x)`.
- Q. await는 어디서 쓸 수 있나? → A. async 함수 내부(또는 모듈 최상위 top-level await).

<details><summary>📝 한 줄 요약</summary>콜백(중첩 지옥)→프로미스(.then 체이닝·통합 에러)→async/await(동기처럼·try/catch). 병렬은 Promise.all.</details>

## Q46. 자바스크립트의 이벤트 루프와 태스크 큐란 무엇인가요? 🔴

**💬 30초 답변**
> 자바스크립트는 싱글 스레드지만, 이벤트 루프가 **콜 스택이 비었을 때 큐에 대기 중인 콜백을 꺼내 실행**시킴으로써 비동기·논블로킹 동작을 가능하게 합니다. 이때 **마이크로태스크 큐(프로미스)** 가 **매크로태스크 큐(setTimeout 등)** 보다 우선 처리됩니다.

**📖 핵심 개념**

```
┌───────────┐   비동기 위임   ┌──────────────┐
│ Call Stack │ ─────────────▶ │  Web APIs    │
└───────────┘                 │ (timer,fetch)│
     ▲                        └──────┬───────┘
     │ 스택 비면 꺼내옴               │ 완료 시 콜백 등록
     │                              ▼
 [Event Loop] ◀── Microtask Queue (Promise) ← 우선!
              ◀── Macrotask Queue (setTimeout, 이벤트)
```

📌 **우선순위**: 콜 스택이 비면 → **마이크로태스크 큐를 전부 비운 뒤** → 매크로태스크 1개 실행 → 다시 마이크로태스크 확인 ...

```js
console.log("1");                          // 동기
setTimeout(() => console.log("2"), 0);     // 매크로태스크
Promise.resolve().then(() => console.log("3")); // 마이크로태스크
console.log("4");                          // 동기

// 출력: 1 → 4 → 3 → 2
// 동기 먼저 → 마이크로(3) → 매크로(2)
```

📌 **큐 분류**
- **마이크로태스크**: Promise `.then/catch/finally`, `queueMicrotask`, `MutationObserver`
- **매크로태스크**: `setTimeout`, `setInterval`, I/O, UI 렌더링, 이벤트

> 💡 면접 단골 출력 순서 문제의 핵심: **동기 → 마이크로태스크(프로미스) 전부 → 매크로태스크(타이머) 하나** 순. `setTimeout(fn, 0)`도 동기·프로미스 뒤에 실행됨.

**🔥 예상 꼬리질문**
- Q. setTimeout(fn, 0)이 즉시 실행 안 되는 이유? → A. 매크로태스크 큐에 들어가 콜 스택·마이크로태스크가 모두 비워진 뒤 실행되기 때문.
- Q. 싱글 스레드인데 안 멈추는 이유? → A. 오래 걸리는 작업은 Web API에 위임하고 콜백으로 받아 논블로킹 처리.

<details><summary>📝 한 줄 요약</summary>스택 비면 큐 콜백을 실행시키는 구조 → 싱글 스레드 비동기. 마이크로태스크(Promise) > 매크로태스크(setTimeout). 동기→마이크로→매크로 순.</details>

## Q47. 클로저란 무엇이고, 어떻게 활용하는지 설명할 수 있나요? 🔴

**💬 30초 답변**
> 클로저는 **함수가 선언될 당시의 외부 변수(렉시컬 환경)를 기억해, 그 함수가 외부에서 실행되어도 그 변수에 계속 접근할 수 있는 것**입니다. 데이터 은닉(private 변수), 상태 유지, 함수 팩토리 등에 활용합니다.

**📖 핵심 개념**

```js
function counter() {
  let count = 0;                 // 외부 함수의 지역 변수
  return function () {           // 이 함수가 count를 기억(클로저)
    count++;
    return count;
  };
}
const inc = counter();
inc(); // 1
inc(); // 2  ← count가 살아있음 (가비지 컬렉션 안 됨)
// count에 외부에서 직접 접근 불가 → 은닉됨
```

📌 **활용 사례**
1. **데이터 은닉 / private 변수**: 위 `count`처럼 외부 접근 차단
2. **상태 유지**: React `useState`의 내부 원리(렉시컬 환경에 값 보관)
3. **함수 팩토리 / 커링**
```js
const multiply = (a) => (b) => a * b;
const double = multiply(2);   // a=2 기억
double(5); // 10
```
4. **이벤트 핸들러·콜백에서 특정 값 캡처**

```
counter() 실행 종료 후에도
inc 함수가 count의 렉시컬 환경을 참조 유지 → 메모리에 살아있음
```

> ⚠️ **주의**: 클로저가 큰 데이터를 계속 참조하면 GC가 못 해 **메모리 누수** 가능. 또 반복문에서 `var`+클로저는 같은 변수를 공유하는 고전 함정(`let`으로 해결).

**🔥 예상 꼬리질문**
- Q. 반복문 `var`/클로저 함정? → A. `for(var i...)` + setTimeout이면 모두 마지막 i 출력 → 블록 스코프 `let`을 쓰면 각 반복마다 새 바인딩.
- Q. 클로저와 스코프 체인 관계? → A. 클로저는 함수가 선언 시점의 스코프 체인을 유지하는 것(Q41).

<details><summary>📝 한 줄 요약</summary>선언 시점의 외부 변수를 기억해 계속 접근하는 함수. 은닉(private)·상태 유지(useState 원리)·커링에 활용. 메모리 누수 주의.</details>

## Q48. 클래스를 사용하는 이유는 무엇인가요? 🟡

**💬 30초 답변**
> 클래스는 객체를 만드는 **틀(설계도)** 로, 동일한 구조의 객체를 일관되게 찍어내고 상속·캡슐화를 명확하게 표현하기 위해 사용합니다. ES6에서 도입됐으며, 내부적으로는 **프로토타입 기반 상속의 문법적 설탕**입니다.

**📖 핵심 개념**

```js
class Animal {
  #secret = "비밀";          // private 필드 (#)
  constructor(name) { this.name = name; }
  speak() { return `${this.name} 소리`; }   // 프로토타입에 정의됨
  static create(n) { return new Animal(n); } // 정적 메서드
}

class Dog extends Animal {     // 상속
  speak() { return `${super.speak()}: 멍멍`; } // super로 부모 호출
}
new Dog("바둑이").speak(); // "바둑이 소리: 멍멍"
```

📌 **장점**
- **일관성**: 같은 구조의 인스턴스 대량 생성
- **상속**(`extends`)·**다형성**(메서드 오버라이드)
- **캡슐화**: `#`private 필드로 내부 은닉
- **가독성**: 생성자 함수+prototype 방식보다 직관적

```
class 문법  ──(내부적으로)──▶  프로토타입 기반 상속
(설탕)                        (실제 동작 — Q44)
```

> 💡 React는 현재 **함수형 컴포넌트 + Hooks**가 주류라 클래스 컴포넌트는 거의 안 씀(Q56). 하지만 JS 언어 차원의 클래스는 여전히 유효(상태 모델링, 라이브러리 등).

**🔥 예상 꼬리질문**
- Q. 클래스는 호이스팅되나요? → A. 선언은 호이스팅되지만 TDZ가 적용되어 선언 전 사용 불가(let/const와 유사).
- Q. 생성자 함수 vs 클래스? → A. 동작은 같지만 클래스가 상속·private·정적 멤버를 더 명확하게 표현.

<details><summary>📝 한 줄 요약</summary>객체 생성 틀. 일관성·상속(extends)·캡슐화(#private)·가독성이 목적. 내부는 프로토타입의 문법적 설탕. React는 함수형+Hooks가 주류.</details>

## Q49. 이벤트 전파나 위임이란 무엇인가요? 🔴

**💬 30초 답변**
> **이벤트 전파**는 한 요소에서 이벤트가 발생하면 **캡처링(위→아래) → 타깃 → 버블링(아래→위)** 순으로 DOM 트리를 따라 퍼지는 것입니다. **이벤트 위임**은 이 버블링을 활용해, 자식마다 핸들러를 붙이지 않고 **부모에 하나만 붙여** 자식 이벤트를 처리하는 패턴입니다.

**📖 핵심 개념**

```
캡처링 단계 (window → target, 위→아래)
        │
      target (실제 클릭된 요소)
        │
버블링 단계 (target → window, 아래→위)  ← 기본 동작
```

```js
// 이벤트 위임: 부모 ul에 하나만
document.querySelector("ul").addEventListener("click", (e) => {
  if (e.target.matches("li")) {        // 실제 클릭된 자식 판별
    console.log("클릭:", e.target.textContent);
  }
});
// li가 100개여도, 나중에 추가돼도 핸들러 1개로 처리 ✅
```

📌 **위임의 장점**
- **성능·메모리**: 핸들러 1개로 N개 자식 처리
- **동적 요소 대응**: 나중에 추가된 자식도 자동으로 처리됨
- 코드 간결

📌 **전파 제어**
- `e.stopPropagation()`: 전파 중단
- `e.preventDefault()`: 기본 동작 취소(폼 제출, 링크 이동 등)
- `addEventListener(type, fn, true)`: 캡처링 단계에서 처리

> 💡 React의 합성 이벤트(SyntheticEvent)도 내부적으로 루트에 이벤트를 위임해 처리하는 구조 — "위임"은 React의 동작 원리이기도 함.

**🔥 예상 꼬리질문**
- Q. stopPropagation vs preventDefault? → A. 전자는 이벤트 전파를 멈추고, 후자는 브라우저 기본 동작(링크 이동 등)을 취소. 서로 다른 목적.
- Q. 위임이 안 되는 이벤트는? → A. `focus`, `blur` 등 버블링 안 하는 이벤트(대신 `focusin/focusout` 사용).

<details><summary>📝 한 줄 요약</summary>전파=캡처링→타깃→버블링. 위임=버블링을 이용해 부모에 핸들러 하나로 자식들 처리(성능·동적 요소 대응). React 합성 이벤트의 원리.</details>

## Q50. 일반 함수와 화살표 함수의 가장 큰 차이점은 무엇인가요? 🔴

**💬 30초 답변**
> 가장 큰 차이는 **this 바인딩**입니다. 일반 함수는 호출 방식에 따라 this가 동적으로 결정되지만, 화살표 함수는 자신만의 this가 없어 **선언된 위치의 상위 this를 그대로 사용**합니다. 또 화살표 함수는 `arguments`, `prototype`이 없고 생성자로 쓸 수 없습니다.

**📖 핵심 개념**

📌 **차이점 비교**

| 항목 | 일반 함수 | 화살표 함수 |
|------|-----------|-------------|
| this | 호출 방식에 따라 동적 | 상위 스코프 this 고정(렉시컬) |
| arguments 객체 | 있음 | 없음 (rest `...args` 사용) |
| 생성자(`new`) | 가능 | **불가** (TypeError) |
| prototype | 있음 | 없음 |
| 호이스팅 | 선언문은 전체 | 변수 규칙(표현식) |

```js
const obj = {
  name: "Kim",
  items: [1, 2],
  // ✅ 화살표: 콜백에서 obj의 this 유지
  print() { this.items.forEach(() => console.log(this.name)); },
  // ❌ 일반 함수 콜백: this가 undefined/전역
  printBad() { this.items.forEach(function () { console.log(this.name); }); },
};
```

🎯 **언제 무엇을?**
- **화살표**: 콜백, 배열 메서드, this를 상위에서 유지하고 싶을 때
- **일반 함수**: 메서드 정의(객체의 this 필요), 생성자, `arguments`가 필요할 때

> ⚠️ **객체 메서드를 화살표로 정의하면 안 됨**: `{ greet: () => this.name }`의 this는 객체가 아니라 상위(전역)를 가리킴(Q42 연결).

**🔥 예상 꼬리질문**
- Q. 화살표 함수를 메서드로 쓰면 안 되는 이유? → A. this가 객체가 아닌 상위 스코프를 가리켜 의도와 다르게 동작.
- Q. 화살표 함수로 생성자를 못 만드는 이유? → A. `[[Construct]]` 내부 메서드와 prototype이 없어서.

<details><summary>📝 한 줄 요약</summary>핵심 차이=this. 일반=호출 방식에 따라 동적 / 화살표=상위 this 고정·arguments/prototype 없음·생성자 불가. 콜백엔 화살표, 메서드·생성자엔 일반.</details>

## Q51. 스프레드 문법과 레스트 문법의 차이점은 무엇인가요? 🟡

**💬 30초 답변**
> 둘 다 `...` 기호를 쓰지만 방향이 반대입니다. **스프레드**는 배열·객체를 **펼쳐서 흩뿌리고**(전개), **레스트**는 여러 인자를 **하나의 배열로 모읍니다**(수집). 위치로 구분합니다 — 펼치는 쪽이면 스프레드, 받는 쪽이면 레스트.

**📖 핵심 개념**

```js
// 스프레드(spread): 펼치기
const arr = [1, 2, 3];
const copy = [...arr, 4];          // [1,2,3,4]  배열 복사·결합
const obj = { ...base, x: 1 };     // 객체 병합 (얕은 복사 — Q38)
Math.max(...arr);                  // 인자로 전개 → Math.max(1,2,3)

// 레스트(rest): 모으기
function sum(...nums) {            // 인자들을 배열로 수집
  return nums.reduce((a, b) => a + b, 0);
}
sum(1, 2, 3); // 6

const [first, ...others] = [1, 2, 3]; // others = [2,3] (구조 분해)
const { a, ...rest } = { a:1, b:2, c:3 }; // rest = {b:2,c:3}
```

```
스프레드: [...arr]    하나 → 여럿  (펼침)
레스트:   (...args)   여럿 → 하나  (모음)
```

📌 **구분 팁**: **함수 매개변수나 구조 분해의 왼쪽**에 있으면 레스트(수집), 그 외 펼치는 위치면 스프레드.

> 💡 레스트는 항상 **마지막**에 와야 함(`function f(a, ...rest)` ✅ / `(...rest, a)` ❌). 스프레드는 얕은 복사라 중첩 객체 주의(Q38).

**🔥 예상 꼬리질문**
- Q. arguments와 rest 차이? → A. arguments는 유사 배열(배열 메서드 X)이고 화살표 함수엔 없음. rest는 진짜 배열이라 권장.
- Q. 스프레드로 깊은 복사 되나요? → A. 안 됩니다. 1단계만 복사하는 얕은 복사.

<details><summary>📝 한 줄 요약</summary>같은 <code>...</code>지만 반대: 스프레드=펼치기(전개), 레스트=모으기(수집). 받는 쪽(매개변수·구조분해 왼쪽)=레스트. 레스트는 마지막에.</details>

## Q52. 불변성이란 무엇이고, 자바스크립트에서 중요한 이유는 무엇인가요? 🔴

**💬 30초 답변**
> 불변성(immutability)은 **데이터를 직접 수정하지 않고, 변경 시 새로운 값을 만들어 교체**하는 원칙입니다. 객체·배열이 참조 타입이라 직접 변경하면 예측 못 한 부작용이 생기는데, 불변성을 지키면 상태 변화 추적이 쉬워지고 특히 React의 리렌더링 판단이 정확해집니다.

**📖 핵심 개념**

```js
// ❌ 가변(mutation): 원본을 직접 변경
const arr = [1, 2, 3];
arr.push(4);              // 원본 변경 → React가 변화 감지 못 할 수 있음

// ✅ 불변: 새 배열/객체 생성
const next = [...arr, 4];          // 추가
const removed = arr.filter(x => x !== 2);  // 삭제
const updated = arr.map(x => x === 2 ? 20 : x); // 수정
const obj2 = { ...obj, name: "new" };       // 객체 수정
```

📌 **왜 중요한가 (특히 React)**
- **변화 감지**: React는 이전/다음 state의 **참조(===)** 만 얕게 비교. 직접 변경하면 참조가 같아 리렌더 누락
- **예측 가능성**: 원본이 안 바뀌니 어디서 바뀌었는지 추적 쉬움(디버깅·시간여행)
- **사이드 이펙트 방지**: 공유 객체를 모르게 바꾸는 버그 차단

```
가변: state.list.push(x)  → 같은 참조 → React "안 바뀜" 판단 → 화면 그대로 ❌
불변: setState([...list, x]) → 새 참조 → "바뀜" 감지 → 리렌더 ✅
```

📌 **불변 도구**: 스프레드(`...`), `map/filter/reduce`, `Object.freeze`(얕은 동결), Immer 라이브러리(복잡한 중첩 상태)

> 💡 가변 메서드(`push`, `splice`, `sort`)와 불변 메서드(`map`, `filter`, `concat`, `slice`, `toSorted`) 구분이 면접 포인트. `sort`는 원본 변경 → 복사 후 정렬.

**🔥 예상 꼬리질문**
- Q. React에서 직접 state를 바꾸면? → A. 참조가 그대로라 리렌더가 안 일어나거나 예측 불가 버그 발생.
- Q. Object.freeze의 한계는? → A. 얕은 동결이라 중첩 객체는 여전히 변경 가능(깊은 동결은 재귀 필요).

<details><summary>📝 한 줄 요약</summary>원본을 안 바꾸고 새 값으로 교체하는 원칙. React가 참조 비교로 변화 감지 → 불변성 안 지키면 리렌더 누락. 스프레드·map/filter 활용.</details>

## Q53. 디바운싱과 스로틀링의 차이점은 무엇이며, 언제 사용해야 하나요? 🔴

**💬 30초 답변**
> 둘 다 이벤트가 과도하게 발생할 때 **실행 횟수를 제한**하는 기법입니다. **디바운싱**은 마지막 이벤트 후 일정 시간이 지나야 한 번 실행하고, **스로틀링**은 일정 시간 간격마다 최대 한 번씩 실행합니다.

**📖 핵심 개념**

```
이벤트 연속 발생: │││││││││││  (예: 빠른 입력/스크롤)

디바운싱: ──────────────●   (멈춘 뒤 한 번)
          마지막 이벤트 후 delay 경과해야 실행

스로틀링: ●────●────●────●   (일정 간격마다 한 번)
          delay마다 최대 1회 보장
```

```js
// 디바운싱: 입력이 멈추면 실행
function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

// 스로틀링: 일정 간격마다 실행
function throttle(fn, delay) {
  let last = 0;
  return (...args) => {
    const now = Date.now();
    if (now - last >= delay) { last = now; fn(...args); }
  };
}
```

📌 **언제 무엇을?**

| 기법 | 사용 예 |
|------|---------|
| **디바운싱** | 검색어 자동완성(입력 멈추면 API 호출), 입력 유효성 검사, 윈도우 resize 완료 후 처리 |
| **스로틀링** | 스크롤 위치 추적, 무한 스크롤, 마우스 이동, 일정 주기 업데이트 |

🎯 **핵심 구분**: "**마지막 한 번**만 중요" → 디바운싱(검색). "**일정 주기로 계속** 반응 필요" → 스로틀링(스크롤).

> 💡 실무에선 lodash의 `debounce`/`throttle`을 많이 쓰고, React에서는 `useCallback`+커스텀 훅이나 `useDeferredValue`(Q61)로도 유사 효과.

**🔥 예상 꼬리질문**
- Q. 자동완성에 스로틀링을 쓰면? → A. 입력 중에도 계속 호출돼 불필요한 요청 발생 → 디바운싱이 적합.
- Q. 둘을 안 쓰면? → A. 이벤트마다 핸들러/API가 호출돼 성능 저하·과도한 네트워크 요청.

<details><summary>📝 한 줄 요약</summary>둘 다 실행 횟수 제한. 디바운싱=멈춘 뒤 한 번(검색 자동완성) / 스로틀링=일정 간격마다(스크롤). "마지막만"=디바운스, "주기적"=스로틀.</details>

## Q54. 타입스크립트를 사용하는 이유와 interface와 type의 차이점은 무엇인가요? 🔴

**💬 30초 답변**
> 타입스크립트는 자바스크립트에 **정적 타입**을 더해, 컴파일(작성) 시점에 타입 오류를 잡아 런타임 버그를 줄이고 자동완성·리팩토링 같은 개발 생산성을 높여줍니다. `interface`와 `type`은 비슷하지만, interface는 **선언 병합·extends 확장**에 강하고, type은 **유니온·교차·원시 타입 별칭** 등 더 폭넓은 표현이 가능합니다.

**📖 핵심 개념**

📌 **TypeScript를 쓰는 이유**
- **정적 타입 검사**: 런타임 전에 타입 오류 발견 (`undefined is not a function` 류 사전 차단)
- **자동완성·인텔리센스**: IDE 지원 강화 → 생산성
- **안전한 리팩토링**: 타입이 변경 영향 범위를 알려줌
- **문서화 효과**: 타입이 곧 명세

```ts
function add(a: number, b: number): number { return a + b; }
add(1, "2"); // ❌ 컴파일 에러 (런타임 전에 발견)
```

📌 **interface vs type**

| 항목 | interface | type |
|------|-----------|------|
| 객체 형태 정의 | ✅ | ✅ |
| 확장 | `extends` | `&`(교차 타입) |
| **선언 병합** | ✅ 같은 이름 자동 합쳐짐 | ❌ 중복 선언 에러 |
| 유니온 타입 | ❌ | ✅ `A \| B` |
| 원시·튜플·매핑 타입 별칭 | ❌ | ✅ |

```ts
// interface: 선언 병합 + extends
interface User { name: string; }
interface User { age: number; }   // 자동 병합 → { name, age }
interface Admin extends User { role: string; }

// type: 유니온·교차·별칭
type Status = "active" | "inactive";   // 유니온 (interface 불가)
type ID = string | number;
type Admin2 = User & { role: string };  // 교차
```

🎯 **선택 가이드**: 객체·클래스 형태이고 확장/병합이 필요하면 **interface**, 유니온·튜플·복잡한 타입 조합이면 **type**. 팀 컨벤션을 따르되, 헷갈리면 "확장 가능한 공개 API는 interface, 그 외는 type"이 무난.

> 💡 TS는 **컴파일 타임에만 존재** — 빌드되면 타입은 제거되고 순수 JS가 됨(런타임 타입 검사는 별도 `zod` 등 필요).

**🔥 예상 꼬리질문**
- Q. 선언 병합이 뭔가요? → A. 같은 이름의 interface를 여러 번 선언하면 자동으로 합쳐지는 기능(라이브러리 타입 확장에 유용).
- Q. any와 unknown 차이? → A. any는 검사 포기(위험), unknown은 사용 전 타입 좁히기를 강제(안전).

<details><summary>📝 한 줄 요약</summary>TS=정적 타입으로 런타임 버그↓·생산성↑(컴파일 후 제거). interface=선언 병합·extends / type=유니온·교차·별칭. 확장형 API는 interface, 복합 타입은 type.</details>
