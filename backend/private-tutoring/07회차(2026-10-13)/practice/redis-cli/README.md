## 0. Redis 띄우기

Redis를 내 컴퓨터에 설치하지 않고 **Docker 컨테이너**로 띄운다.

```bash
docker run -d --name redis-study -p 6380:6379 redis:7.4
```

| 옵션                | 의미                                                              |
| ------------------- | ----------------------------------------------------------------- |
| `-d`                | 백그라운드 실행                                                   |
| `--name redis-study` | 컨테이너 이름                                                    |
| `-p 6380:6379`      | **내 컴퓨터 6380 → 컨테이너 6379** 연결. Redis 기본 포트는 6379 |
| `redis:7.4`         | 사용할 이미지                                                     |

> 내 컴퓨터는 다른 프로젝트의 Redis가 이미 6379를 쓰고 있어서 6380으로 연결했다. 6379가 비어 있다면 `-p 6379:6379`도 된다.

또는 Spring 실습 프로젝트의 `compose.yaml`로 띄워도 같다.

```bash
cd ../spring/redis-cache-practice
docker compose up -d
```

### redis-cli 접속

`redis-cli`는 Redis에 명령을 보내는 터미널 클라이언트다. 컨테이너 안에 들어 있으므로 설치 없이 쓴다.

```bash
docker exec -it redis-study redis-cli
```

```text
127.0.0.1:6379> PING
PONG
```

`PONG`이 오면 연결 성공이다. 프롬프트의 `6379`는 **컨테이너 안쪽** 포트라서 6380이 아니라 6379로 보인다.

### 응답 형식 읽는 법

| 표시                | 의미                         |
| ------------------- | ---------------------------- |
| `OK`                | 성공                         |
| `"kim"`             | 문자열 값                    |
| `(integer) 3`       | 정수 (개수, 결과 숫자 등)    |
| `(nil)`             | 값 없음 (Java의 null)        |
| `1) ... 2) ...`     | 여러 값 (배열)               |
| `(empty array)`     | 빈 배열                      |

### 정리 (실습 끝나고)

```bash
docker stop redis-study    # 멈춤 (데이터는 컨테이너 안에 남음)
docker start redis-study   # 다시 시작
docker rm -f redis-study   # 컨테이너 삭제
```

## 이 문서에서 익힐 것

처음에는 아래 6가지면 충분하다. 실무에서 Redis를 쓰는 코드 대부분이 이 명령들로 되어 있다.

| 순서 | 주제          | 명령                           | 실무에서 쓰는 곳                 |
| ---- | ------------- | ------------------------------ | -------------------------------- |
| 1    | String        | `SET` `GET` `DEL` `EXISTS`     | 캐시, 세션 — **가장 많이 쓴다**  |
| 2    | 만료 시간     | `EX` `TTL` `EXPIRE`            | 캐시, 인증번호 — **거의 항상 같이 쓴다** |
| 3    | 숫자 세기     | `INCR` `DECR`                  | 조회수, 좋아요 수                |
| 4    | 없을 때만 저장 | `SET ... NX`                  | 중복 요청 방지, 분산 락          |
| 5    | Hash          | `HSET` `HGET` `HGETALL`        | 객체를 필드별로 저장             |
| 6    | 키 찾기       | `SCAN` (`KEYS` 금지)           | 운영 중 키 확인                  |

> 실습 중 데이터를 비우고 싶으면 `FLUSHALL` (전부 삭제 — 실습 환경에서만).

## 1. String — 키 하나에 값 하나

**한 줄 요약**: Java의 `Map<String, String>`에 `put`, `get` 하는 것과 같다.

| 명령             | 뜻                         | 결과                          |
| ---------------- | -------------------------- | ----------------------------- |
| `SET 키 값`      | 저장 (이미 있으면 덮어씀)  | `OK`                          |
| `GET 키`         | 조회                       | 값 / 없으면 `(nil)`           |
| `DEL 키`         | 삭제                       | 지운 개수                     |
| `EXISTS 키`      | 있는지 확인                | 있으면 `1`, 없으면 `0`        |

### 따라 치기

```text
127.0.0.1:6379> SET user:1:name kim
OK
127.0.0.1:6379> GET user:1:name
"kim"
127.0.0.1:6379> SET user:1:name lee        ← 같은 키에 다시 SET
OK
127.0.0.1:6379> GET user:1:name            ← 덮어써졌다
"lee"
127.0.0.1:6379> GET user:999:name          ← 없는 키
(nil)
127.0.0.1:6379> EXISTS user:1:name
(integer) 1
127.0.0.1:6379> DEL user:1:name
(integer) 1
127.0.0.1:6379> EXISTS user:1:name
(integer) 0
```

### 키 이름은 `종류:id:필드`로 짓는다

```text
SET  user:1:name  kim
     └── 키 ───┘  └값┘
```

- Redis는 **공백**을 기준으로 명령을 나눈다. 그래서 `user:1:name` **전체가 키 하나**다.
- `:`은 Redis에게 **아무 의미 없는 그냥 글자**다. `user_1_name`, `user.1.name`으로 써도 똑같이 동작한다.
- 그래도 `:`을 쓰는 이유는 **업계 관례**라서다. `종류:id:필드` 형태라 **이름만 봐도 무슨 데이터인지** 알 수 있다.
  - `user:1:name` → 1번 사용자의 이름
  - `post:1:views` → 1번 게시글의 조회수
  - `product::1` → Spring Cache가 만드는 키 (`캐시이름::id`)

⚠️ `user:1:name`과 `user:1:age`는 이름만 비슷한 **완전히 별개의 키 2개**다. `user:1`이라는 폴더 같은 것은 없다. 하나로 묶고 싶으면 5장의 Hash를 쓴다.

⚠️ 값에 **공백**이 있으면 따옴표로 감싼다: `SET greeting "hello redis"` (따옴표가 없으면 `ERR syntax error`)

## 2. 만료 시간(TTL) — 정해진 시간 뒤 자동 삭제

**한 줄 요약**: 저장할 때 "몇 초 뒤에 지워 줘"를 같이 적는다. 시간이 지나면 **Redis가 알아서 지운다.**

**왜 실무에서 중요한가**: 캐시는 원본(DB)의 복사본이라 시간이 지나면 틀릴 수 있다. TTL을 두면 **최대 그 시간만큼만** 틀린다. 그래서 **캐시에는 거의 항상 TTL을 붙인다.**

| 명령                 | 뜻                                |
| -------------------- | --------------------------------- |
| `SET 키 값 EX 초`    | 저장 + 만료 시간 지정 (가장 많이 씀) |
| `TTL 키`             | 남은 시간(초) 확인                |
| `EXPIRE 키 초`       | 이미 있는 키에 만료 시간 지정     |

`TTL` 결과 읽는 법 — 이 3가지만 기억하면 된다.

| 결과   | 뜻                                         |
| ------ | ------------------------------------------ |
| 양수   | 남은 초                                    |
| `-1`   | 키는 있지만 **만료 시간이 없음** (영원히 남음) |
| `-2`   | **키가 없음** (만료돼서 지워졌거나 처음부터 없음) |

### 따라 치기 — 인증번호 (5초 뒤 사라짐)

```text
127.0.0.1:6379> SET auth:code:1 123456 EX 5
OK
127.0.0.1:6379> TTL auth:code:1
(integer) 5
```

6초 기다린 뒤:

```text
127.0.0.1:6379> GET auth:code:1            ← 자동으로 지워졌다
(nil)
127.0.0.1:6379> TTL auth:code:1
(integer) -2
```

### 따라 치기 — 만료 없는 키에 나중에 TTL 붙이기

```text
127.0.0.1:6379> SET user:1:name kim
OK
127.0.0.1:6379> TTL user:1:name            ← EX 없이 저장 → 만료 없음
(integer) -1
127.0.0.1:6379> EXPIRE user:1:name 60
(integer) 1
127.0.0.1:6379> TTL user:1:name
(integer) 60
```

## 3. INCR — 숫자 세기

**한 줄 요약**: 저장된 숫자를 1씩 올리거나 내린다. 키가 없으면 0에서 시작한다.

| 명령             | 뜻          |
| ---------------- | ----------- |
| `INCR 키`        | +1          |
| `DECR 키`        | -1          |
| `INCRBY 키 n`    | +n          |

### 따라 치기 — 게시글 조회수

```text
127.0.0.1:6379> INCR post:1:views          ← 키가 없었으므로 0 → 1
(integer) 1
127.0.0.1:6379> INCR post:1:views
(integer) 2
127.0.0.1:6379> INCRBY post:1:views 10
(integer) 12
127.0.0.1:6379> DECR post:1:views
(integer) 11
127.0.0.1:6379> GET post:1:views
"11"
```

### 왜 `GET` 해서 +1 하고 `SET` 하면 안 되나

```text
❌ GET → +1 → SET : 명령 2개. 두 사람이 동시에 GET하면 같은 값을 읽어서 하나가 사라진다
✅ INCR           : 명령 1개. Redis는 명령을 하나씩 처리하므로 끼어들 틈이 없다
```

[8회차 Spring 실습](<../../../08회차(2026-10-21)/practice/spring/README.md>)에서 직접 비교한다. 재고 100개를 동시에 100번 차감하면 GET→SET은 **57~83개가 남고**(유실), DECR은 정확히 **0**이다. 6회차 `count++` 문제와 같은 원리다.

## 4. SET NX — 없을 때만 저장

**한 줄 요약**: `NX`를 붙이면 **키가 없을 때만** 저장된다. 이미 있으면 아무것도 하지 않는다. 여러 명이 동시에 시도해도 **딱 한 명만 성공**한다.

**실무에서 쓰는 곳**: 결제 버튼 두 번 클릭 같은 **중복 요청 막기**, **분산 락**([8회차 PRESTUDY](<../../../08회차(2026-10-21)/PRESTUDY.md>)).

실무에서는 거의 항상 **`EX`와 함께** 쓴다. 처리하던 서버가 죽어도 키가 영원히 남지 않게 하기 위해서다.

### 따라 치기 — 주문 1번 결제 중복 방지 (10초)

```text
127.0.0.1:6379> SET order:1:paying 1 NX EX 10    ← 첫 번째 요청
OK
127.0.0.1:6379> SET order:1:paying 1 NX EX 10    ← 두 번째 요청 (중복)
(nil)
127.0.0.1:6379> TTL order:1:paying
(integer) 10
```

- `OK` → 처음 온 요청. 결제를 진행한다.
- `(nil)` → 이미 누가 처리 중. 이 요청은 거절한다.
- 10초 뒤에는 키가 자동으로 지워진다.

## 5. Hash — 객체 하나를 필드별로

**한 줄 요약**: 키 하나 안에 `필드 → 값`을 여러 개 둔다. Java의 `Map<String, Map<String, String>>`에서 안쪽 Map 하나라고 보면 된다.

```text
String 방식 — 키 2개               Hash 방식 — 키 1개
user:1:name → "kim"                user:2 → { name: "lee", age: "25" }
user:1:age  → "30"
```

| 명령                          | 뜻                    |
| ----------------------------- | --------------------- |
| `HSET 키 필드 값 [필드 값 ...]` | 필드 저장 (여러 개 가능) |
| `HGET 키 필드`                | 필드 하나 조회        |
| `HGETALL 키`                  | 모든 필드 조회        |

### 따라 치기

```text
127.0.0.1:6379> HSET user:2 name lee age 25
(integer) 2                                ← 새로 생긴 필드 수
127.0.0.1:6379> HGET user:2 name
"lee"
127.0.0.1:6379> HGETALL user:2              ← 필드, 값, 필드, 값 순서로 나온다
1) "name"
2) "lee"
3) "age"
4) "25"
127.0.0.1:6379> HSET user:2 age 26          ← 필드 하나만 수정
(integer) 0                                ← 새 필드가 아니라 수정이라 0
127.0.0.1:6379> HGET user:2 age
"26"
127.0.0.1:6379> DEL user:2                  ← 키 하나라 한 번에 전부 삭제
(integer) 1
```

**String(JSON)과 Hash 중 무엇을 쓰나**

| 상황                                   | 선택                           |
| -------------------------------------- | ------------------------------ |
| 객체를 통째로 저장하고 통째로 읽는다   | String에 JSON (Spring Cache 방식) |
| 필드 하나만 자주 읽거나 바꾼다         | Hash                           |

## 6. 키 찾기 — SCAN (KEYS는 운영 금지)

**한 줄 요약**: 패턴에 맞는 키를 찾을 때는 `SCAN`을 쓴다.

```text
127.0.0.1:6379> SCAN 0 MATCH user:*
1) "0"                                     ← 다음 커서. 0이면 끝까지 다 찾았다는 뜻
2) 1) "user:3:name"
   2) "user:1:name"
```

`*`는 "아무 글자나"라는 뜻이다. `user:*` = user:로 시작하는 모든 키.

⚠️ **`KEYS 패턴`은 운영 서버에서 쓰지 않는다.** 결과는 같지만, 모든 키를 한 번에 훑는 동안 **다른 모든 요청이 멈춘다.** Redis는 명령을 하나씩 처리하기 때문이다. 키가 수백만 개면 서비스 전체가 몇 초씩 멈출 수 있다. `SCAN`은 조금씩 나눠서 찾으므로 안전하다. (실습 환경에서 `KEYS *`로 확인하는 것은 괜찮다.)

## 7. 나머지 자료구조 — 지금은 이름만

필요해질 때 찾아보면 된다. 어떤 문제에 쓰는지만 알아 둔다.

| 자료구조       | 한 줄 설명                    | 대표 용도               | 예                                  |
| -------------- | ----------------------------- | ----------------------- | ----------------------------------- |
| **Sorted Set** | 점수 순으로 자동 정렬되는 집합 | **랭킹**                | `ZADD rank 100 kim` → `ZREVRANGE rank 0 9` (상위 10명) |
| List           | 순서 있는 목록                | 최근 본 상품, 간단한 큐 | `LPUSH recent:1 p1` → `LRANGE recent:1 0 9` |
| Set            | 중복 없는 집합                | 좋아요 누른 사람        | `SADD like:post:1 kim` → `SCARD like:post:1` (개수) |

## 정리 — 오늘 꼭 기억할 명령

```text
SET 키 값 EX 초          저장 + 자동 만료       ← 캐시의 기본형
GET 키                   조회 (없으면 nil)
DEL 키                   삭제
TTL 키                   남은 시간 (-1 만료 없음, -2 키 없음)
INCR 키                  +1 (동시에 호출해도 안전)
SET 키 값 NX EX 초       없을 때만 저장 (중복 방지, 락)
HSET 키 필드 값          Hash 필드 저장
HGET 키 필드             Hash 필드 조회
SCAN 0 MATCH 패턴        키 찾기 (KEYS 대신)
```
