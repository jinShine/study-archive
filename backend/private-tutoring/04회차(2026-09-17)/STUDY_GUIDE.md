# 1. Transaction Propagation (트랜잭션 전파)

## 1.1 문제 정의

`@Transactional` 메서드가 **또 다른 `@Transactional` 메서드를 호출**할 때.

```java
@Transactional
public void b() {
    cService.d();     // 이것도 @Transactional
}
```

`b()`는 이미 트랜잭션이 열려 있다. `d()`에 들어갈 때 선택은 둘이다.

```
부모(b)의 트랜잭션을 그대로 쓸 것인가?    → REQUIRED
부모와 별개로 새로 만들 것인가?           → REQUIRES_NEW
```

이 규칙이 **Propagation**이다. 옵션은 7개지만 실무에서는 이 둘이 거의 전부다.

참고: [Spring 공식 문서 — Transaction Propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

## 1.2 전제 — 트랜잭션은 커넥션 하나 위에서 산다

> MySQL에서 트랜잭션은 **세션(= 커넥션) 단위**다. 커넥션 A에서 시작한 트랜잭션의 쿼리와 COMMIT은 전부 커넥션 A로 보내야 한다.

따라서 **"같은 트랜잭션" = "같은 커넥션 객체를 쓴다"**, **"새 트랜잭션" = "다른 커넥션을 빌린다"**. 전파는 결국 커넥션을 공유할지의 문제다.

## 1.3 REQUIRED — 부모에 참여 (기본값)

| 트랜잭션이 있으면    | 없으면        |
| -------------------- | ------------- |
| 그 커넥션에 **참여** | **새로 시작** |

```
b() 진입    커넥션 C1 획득, 트랜잭션 T1 시작
  d() 진입    C1 그대로 사용
  d() 종료    commit 안 함 — 시작한 쪽이 아니므로
b() 종료    T1 commit
```

물리 트랜잭션은 하나. commit/rollback은 **시작한 가장 바깥 메서드**만 한다.

### 함정 — 자식 예외를 부모가 catch하면

```
d()에서 RuntimeException
  → d()의 프록시가 T1에 rollback-only 표시
  → b()가 catch해서 삼킴 → b() 정상 종료 → commit 시도
  → rollback-only 발견 → 실제로는 rollback + UnexpectedRollbackException
```

예외를 잡은 것과 롤백 표시를 지운 것은 다르다. 하나의 트랜잭션에서 "d()만 롤백, b()는 커밋"은 불가능하므로 Spring은 전체를 롤백하고 예외로 알린다.

## 1.4 REQUIRES_NEW — 항상 새 트랜잭션

| 트랜잭션이 있으면                                      | 없으면    |
| ------------------------------------------------------ | --------- |
| 부모를 **일시 중단**하고 **새 커넥션으로 새 트랜잭션** | 새로 시작 |

```
b() 진입        C1 획득, T1 시작
  addLog() 진입   T1 중단 (C1은 계속 점유), C2 획득, T2 시작
  addLog() 종료   T2 commit, C2 반납, T1 재개
b() 종료        T1 commit 또는 rollback
```

부모와 자식이 **각자 commit/rollback**. 부모가 실패해도 자식 결과는 남는다.

### 비용

- **커넥션 2개 점유**: 이 경로는 풀 계산에서 동시 요청 × 2. 풀이 10인데 동시 요청 10개가 모두 두 번째 커넥션을 요청하면 전부 대기 → 일괄 타임아웃.
- **같은 행을 건드리면 교착**: DB 입장에서 T1과 T2는 다른 세션. T2는 T1의 락을, T1은 T2 메서드의 리턴을 기다린다. → REQUIRES_NEW 안에서는 **부모가 건드린 행을 건드리지 않는다.**

### 실무에서 쓰는 경우

기준: **부모가 롤백되어도 이 기록은 반드시 남아야 하는가.**

| 사례                               | 이유                                                    |
| ---------------------------------- | ------------------------------------------------------- |
| 실패 이력, 외부 API 호출 시도 기록 | 부모가 롤백될 때 함께 사라지면 "실패했다"는 사실이 증발 |
| 감사 로그                          | 결과와 무관하게 "누가 무엇을 시도했는가"가 요건인 경우  |
| 배치의 건별 처리                   | 1건 실패해도 나머지는 커밋되어야 함                     |
| 채번(주문번호 발급)                | 부모가 롤백돼도 번호는 소비된 것으로 처리(중복 방지)    |

### 쓰지 않아야 하는 경우

- 성공했을 때만 의미 있는 후속 작업(알림, 통계) → `@TransactionalEventListener(phase = AFTER_COMMIT)`
- 부모와 같은 행을 건드리는 작업 → 교착
- "빨리 커밋하고 싶어서" → 트랜잭션 범위가 크다는 신호. 메서드를 나눈다
- 트래픽 많은 로그성 경로 → 메시지 큐로 보낸다

## 1.5 나머지 옵션 (참고)

| 옵션          | 있을 때                                         | 없을 때            |
| ------------- | ----------------------------------------------- | ------------------ |
| NESTED        | savepoint 생성, 자식 실패 시 그 지점까지만 롤백 | 새로 시작          |
| SUPPORTS      | 참여                                            | 트랜잭션 없이 실행 |
| NOT_SUPPORTED | 부모 중단 후 트랜잭션 없이                      | 트랜잭션 없이      |
| MANDATORY     | 참여                                            | 예외               |
| NEVER         | 예외                                            | 트랜잭션 없이      |

# 2. Thread와 ThreadLocal

## 2.1 Thread

프로세스가 **메모리 공간**이라면 스레드는 그 안에서 코드를 **실행하는 흐름**이다. 하나의 프로세스에 여러 스레드가 동시에 돈다.

| 공유                                  | 각자                       |
| ------------------------------------- | -------------------------- |
| 힙(모든 객체), static 변수, 열린 소켓 | 스택(지역 변수, 호출 기록) |

힙을 공유하므로 두 스레드가 같은 객체를 동시에 바꾸면 깨진다(race condition). 그래서 `synchronized`, `Lock`, `Atomic*`이 있다.

## 2.2 서버에서의 스레드

Tomcat은 스레드 풀(기본 200)을 두고, 요청마다 스레드 하나를 배정한다. **컨트롤러 → 서비스 → 레포지토리 → 응답까지 전부 그 스레드 하나**에서 실행되고, 끝나면 풀로 돌아가 재사용된다.

두 가지가 중요하다.

1. **한 요청은 끝까지 같은 스레드** — 스레드에 무언가 붙여두면 그 요청 어디서든 꺼낼 수 있다.
2. **스레드는 재사용된다** — 붙여둔 것을 안 치우면 다음 요청이 물려받는다.

> 스레드 풀과 커넥션 풀은 별개다. 스레드는 응답까지 계속 점유하지만, 커넥션은 DB를 치는 구간에만 빌리고 반납한다. 그래서 스레드 200 : 커넥션 10~20이 정상이고, 초과한 스레드는 커넥션 반납을 기다린다.

## 2.3 ThreadLocal

`static` 변수는 프로세스에 하나, 모든 스레드가 같은 값을 본다.
**ThreadLocal은 변수는 하나지만 값은 스레드마다 따로 저장된다.**

```java
private static final ThreadLocal<String> currentUser = new ThreadLocal<>();

// 스레드 #7          currentUser.set("alice");  currentUser.get();  // "alice"
// 스레드 #12 (동시)   currentUser.set("bob");    currentUser.get();  // "bob"
```

값은 **각 Thread 객체 안의 Map**에 저장되고, ThreadLocal 객체는 그 Map의 **키**다.

```
Thread #7  → { currentUser → "alice" }
Thread #12 → { currentUser → "bob"   }
```

용도: **요청 처리 중 어디서든 필요하지만 메서드 인자로 계속 넘기기 싫은 값.** 요청 시작 시 넣어두면 같은 스레드의 모든 코드가 인자 없이 꺼내 쓴다.

## 2.4 Spring이 ThreadLocal에 넣어두는 것

| 무엇                     | 어디에                              |
| ------------------------ | ----------------------------------- |
| **트랜잭션의 커넥션**    | `TransactionSynchronizationManager` |
| 로그인 사용자            | `SecurityContextHolder`             |
| 요청 ID 등 로그 컨텍스트 | `MDC`                               |

### 트랜잭션의 커넥션

`@Transactional` 메서드가 시작될 때:

```
① 풀에서 커넥션 C1을 빌린다
② C1.setAutoCommit(false)
③ C1을 현재 스레드의 ThreadLocal에 등록          ← 핵심
④ 메서드 실행
⑤ 정상이면 commit, 예외면 rollback
⑥ ThreadLocal에서 제거, C1 반납
```

`JdbcTemplate`, JPA, MyBatis는 커넥션이 필요할 때 풀에 직접 가지 않고 **먼저 현재 스레드의 ThreadLocal을 확인**한다. 등록된 C1이 있으면 그것을 쓴다.

```
@Transactional test(), 스레드 #7    ThreadLocal: { dataSource → C1 }
   ├─ memberRepository.findById()   → C1
   ├─ pointRepository.save()        → C1
   └─ logService.addLog()           → C1 (REQUIRED)
```

서로를 모르는 Repository들이 인자 없이도 **같은 커넥션 = 같은 트랜잭션**이 되는 장치가 이것이다.

## 2.5 주의점

- **풀에서는 반드시 `remove()`** — 안 지우면 같은 스레드가 처리하는 다음 요청이 이전 값을 본다. 다른 사용자의 인증 정보가 새는 사고. `finally`에서 지운다. (Spring이 넣은 것은 Spring이 정리한다.)
- **다른 스레드로 넘어가지 않는다** — 값은 스레드에 있다. 실행 스레드가 바뀌면 그쪽 ThreadLocal은 비어 있다. → 3절

# 3. new Thread가 트랜잭션을 깨는 이유

## 3.1 수업 코드

```java
@Transactional
public void test() {
    memberRepository.findById(...);
    new Thread(() -> pointRepository.save(point)).start();   // "최적화"
    new Thread(() -> logService.addLog()).start();            // @Transactional
}
```

## 3.2 왜 깨지는가

트랜잭션 커넥션 C1은 **현재 스레드의 ThreadLocal**에 있다. `new Thread()`는 다른 스레드고, 그 ThreadLocal은 **비어 있다.**

```
[요청 스레드]                     [새 스레드]
ThreadLocal: { → C1 }             ThreadLocal: { }
test() 실행 중                    save() → ThreadLocal 없음 → 풀에서 C2 새로 빌림
                                          → autoCommit = true → 즉시 커밋
```

새 스레드의 `save()`는 **C2로, 트랜잭션 없이** 실행된다. `addLog()`에 `@Transactional`이 있어도 마찬가지 — 새 스레드에는 진행 중인 트랜잭션이 없으니 REQUIRED가 "새로 시작"으로 동작해 **부모와 무관한 독립 트랜잭션**이 된다.

## 3.3 깨지는 방향은 둘이다

|     | 상황                                               | 결과                                    |
| --- | -------------------------------------------------- | --------------------------------------- |
| ①   | 부모 롤백, 자식은 이미 커밋                        | member 작업은 취소, point는 저장됨      |
| ②   | 자식 예외, 부모는 모름 (예외는 스레드를 넘지 못함) | point 저장 실패, test()는 성공으로 커밋 |

둘 다 all or nothing 위반이다. 문제는 평소엔 안 보이고 **롤백이 일어나는 예외 상황에서만** 불일치로 나타나 발견이 늦다.

## 3.4 추가 문제

- 응답이 나간 뒤에도 새 스레드가 실행 중 — 사용자는 성공을 봤는데 저장은 실패할 수 있다
- 스레드마다 커넥션을 추가로 빌림 → 풀 고갈
- `new Thread()`는 풀링되지 않아 상한 없이 늘어남
- C1을 새 스레드에 넘겨도 안 된다 — `Connection`은 스레드 안전하지 않고, 부모가 반납한 뒤 쓰면 다른 요청의 커넥션에 쓰는 것이 된다

## 3.5 같은 이유로 깨지는 것들

`new Thread` · `@Async` · `CompletableFuture.runAsync` · `ExecutorService.submit` · `parallelStream` — **스레드가 바뀌는 모든 것.** `@Transactional` 안에서 호출하면 그 안의 DB 작업은 트랜잭션 밖이다.

## 3.6 올바른 방법

원칙: **트랜잭션 안에서 스레드를 바꾸지 않는다. 비동기는 커밋 이후로 미룬다.**

**커밋 후 이벤트로 실행**

```java
@Transactional
public void test() {
    pointRepository.save(point);
    eventPublisher.publishEvent(new PointSavedEvent(point.getId()));
}

@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPointSaved(PointSavedEvent e) {
    logService.addLog(e.getPointId());   // 커밋 성공 후에만, 다른 스레드에서
}
```

롤백되면 실행되지 않는다(① 해결). 핸들러 실패는 이미 커밋된 부모에 영향이 없고, 재시도 정책으로 따로 다룬다. 핸들러 안에서 DB를 쓰려면 `REQUIRES_NEW`가 필요하다 — 부모 트랜잭션은 이미 끝났으므로.

**트랜잭션 범위를 좁힌다**

```java
public void handle() {           // @Transactional 없음
    pointService.saveInTx();     // @Transactional — 여기서 커밋 완료
    asyncService.addLog();       // @Async — 커밋 후
}
```

**메시지 큐** — 로그·통계·알림은 Kafka 등으로 보내고 별도 컨슈머가 처리. 발행은 커밋 후에(또는 Outbox 패턴).

# 4. 연결고리

```
트랜잭션은 커넥션 단위 (MySQL 세션)
    ↓
"같은 트랜잭션" = "같은 커넥션 객체"
    ↓
Spring은 그 커넥션을 현재 스레드의 ThreadLocal에 둔다
    ↓
JdbcTemplate / JPA는 ThreadLocal을 먼저 확인 → 같은 스레드의 DB 작업은 자동으로 같은 트랜잭션
    ↓
스레드가 바뀌면 ThreadLocal이 비어 있다 → 다른 커넥션, 트랜잭션 밖
→ new Thread / @Async 안의 DB 작업은 all or nothing에서 제외
    ↓
Propagation = 다른 @Transactional을 만났을 때 이 커넥션을 이어 쓸지(REQUIRED),
              잠시 치우고 새 커넥션을 둘지(REQUIRES_NEW)
```

> **한 줄**: Spring은 트랜잭션 커넥션을 스레드의 ThreadLocal에 두므로 같은 스레드의 DB 작업은 같은 트랜잭션이 되고, 스레드를 바꾸면 트랜잭션 밖이 된다. Propagation은 그 커넥션을 이어 쓸지 새로 만들지의 규칙이다.

# 5. Transaction Isolation Level (격리 수준)

## 5.1 문제 정의

트랜잭션은 여러 개가 **동시에** 실행된다. 그러면 이런 상황이 생긴다.

> 내가 어떤 값을 읽는 동안, **다른 트랜잭션이 그 값을 바꾸고 있다.** 나는 무엇을 봐야 하는가?

선택지는 둘이다.

- 바꾸는 중인 값을 그대로 보여준다 → 빠르지만 틀린 값을 볼 수 있다
- 상대가 끝날 때까지 기다린다 → 안전하지만 느리다

격리 수준은 이 사이에서 **"어디까지 보여줄지"를 4단계로 정한 것**이다.

## 5.2 격리가 낮으면 생기는 문제

세 가지 현상이 있다. 전부 "TX1이 쓰고 있는데 TX2가 읽는다"는 상황이다.

### ① Dirty Read — 커밋 안 된 값을 읽음

![read uncommitted vs read committed](isolation-read-uncommitted-vs-committed.png)

```
        TX1 (승진)                      TX2 (저)
   ─────────────────────────────────────────────────────
   잔액 1,000
   UPDATE +500 → 1,500                                    아직 커밋 안 함
                                      SELECT → 1,500 ?    ← TX1의 미확정 값이 보임
   ROLLBACK                                               1,500은 없던 일이 됨
```

TX2가 읽은 1,500은 **존재한 적이 없는 값**이다. TX1이 롤백했으니 DB에 1,500이었던 순간은 없다. 이 값으로 계산하거나 화면에 보여줬다면 전부 틀렸다.

### ② Non-Repeatable Read — 같은 행을 두 번 읽었는데 값이 다름

```
        TX1                              TX2
   ─────────────────────────────────────────────────────
   SELECT → 10,000
                                       UPDATE +100
                                       COMMIT → 10,100
   SELECT (같은 행) → 10,100             ← 아까와 다르다
```

TX2는 정상적으로 커밋했으니 10,100이 틀린 값은 아니다. 문제는 **TX1 입장에서 한 트랜잭션 안의 두 읽기가 다르다**는 것. "잔액 확인 → 그 잔액 기준으로 출금"처럼 첫 읽기를 믿고 진행하는 로직이 깨진다.

### ③ Phantom Read — 같은 조건인데 행 개수가 다름

```
        TX1                              TX2
   ─────────────────────────────────────────────────────
   SELECT WHERE balance > 80 → 3건
                                       INSERT (balance 90)
                                       COMMIT
   SELECT WHERE balance > 80 → 4건      ← 없던 행이 나타남
```

②는 **기존 행의 값**이 바뀐 것, ③은 **행이 추가/삭제**된 것. 그래서 따로 구분한다.

## 5.3 4단계

위로 갈수록 빠르고, 아래로 갈수록 안전하다.

| 수준             | ① Dirty | ② Non-Repeatable | ③ Phantom | 무엇을 보는가                                                               |
| ---------------- | ------- | ---------------- | --------- | --------------------------------------------------------------------------- |
| READ UNCOMMITTED | 발생    | 발생             | 발생      | 커밋 안 된 값도 보인다                                                      |
| READ COMMITTED   | 방지    | 발생             | 발생      | 다른 트랜잭션이 **커밋해 둔 값**만. 기준 시점은 **SELECT 문장마다** 새로    |
| REPEATABLE READ  | 방지    | 방지             | (발생)    | 다른 트랜잭션이 **커밋해 둔 값**만. 기준 시점은 **첫 SELECT 때 한 번** 고정 |
| SERIALIZABLE     | 방지    | 방지             | 방지      | 동시에 실행되지 않는 것처럼                                                 |

기본값: **MySQL(InnoDB) = REPEATABLE READ**, **Oracle = READ COMMITTED**. PostgreSQL, SQL Server도 READ COMMITTED.

## 5.4 READ COMMITTED vs REPEATABLE READ

실무에서 만나는 것은 이 둘이다. 같은 상황을 두 수준에서 각각 따라간다.

### 상황

계좌 100번의 잔액은 10,000원. TX1은 두 번 조회하고, 그 사이에 TX2가 100원을 입금하고 커밋한다.

### READ COMMITTED (Oracle 기본)

```
        TX1                                TX2
   ─────────────────────────────────────────────────────
   SELECT id=100 → 10,000                                  ← 이 SELECT 시점의 커밋 값
                                         UPDATE +100
                                         COMMIT → 10,100
   SELECT id=100 → 10,100                                  ← 이 SELECT 시점의 커밋 값
```

규칙: **"SELECT 문장이 실행되는 순간에 커밋되어 있는 값"** 을 보여준다.

- 첫 SELECT 때 커밋된 값은 10,000
- 두 번째 SELECT 때 커밋된 값은 10,100 (TX2가 이미 커밋했으므로)
- 커밋 안 된 값은 절대 안 보인다 → Dirty Read 방지
- 그러나 문장마다 기준 시점이 바뀌므로 두 결과가 다를 수 있다 → Non-Repeatable Read 발생

### REPEATABLE READ (MySQL 기본)

![repeatable read](isolation-repeatable-read.png)

```
        TX1                                TX2
   ─────────────────────────────────────────────────────
   SELECT id=100 → 10,000                                  ← 여기서 "사진"을 찍는다
                                         UPDATE +100
                                         COMMIT → 10,100
   SELECT id=100 → 10,000                                  ← 사진을 본다. 실제 DB는 10,100
```

규칙: **"트랜잭션의 첫 SELECT 시점에 커밋되어 있던 값"** 을 트랜잭션이 끝날 때까지 보여준다.

- 첫 SELECT에서 기준 시점이 고정된다 (그림의 "개신!" 표시)
- 이후 TX2가 커밋하든 말든 TX1의 기준 시점은 바뀌지 않는다
- 그래서 두 번째 SELECT도 10,000 → 반복해서 읽어도 같은 값(Repeatable)
- TX1이 끝나고 **새 트랜잭션**을 열어 조회하면 그때는 10,100이 나온다

### 차이를 한 문장으로

> READ COMMITTED는 **문장마다** 기준 시점을 새로 잡고, REPEATABLE READ는 **트랜잭션 전체**가 하나의 기준 시점을 쓴다.

어느 쪽이 맞다가 아니라 용도가 다르다.

- 한 트랜잭션 안에서 여러 번 조회한 결과가 서로 일관되어야 한다(보고서, 집계) → REPEATABLE READ
- 항상 지금의 최신 값을 봐야 한다 → READ COMMITTED

## 5.5 MVCC — "기다리지 않고" 이걸 하는 방법

### 의문

5.4의 REPEATABLE READ에서 TX1은 10,000을 보는데 실제 DB에는 10,100이 있다. **10,000은 어디서 나오는가?**
그리고 TX2가 UPDATE하는 동안 TX1은 왜 멈추지 않는가?

### 답 — 값을 덮어쓰지 않고 버전을 남긴다

MVCC는 MySQL만의 것이 아니라 Oracle, PostgreSQL 등 현대 RDB 대부분이 쓰는 방식이다. InnoDB의 경우 UPDATE할 때 **이전 값을 지우지 않는다.** Undo log에 남겨둔다(트랜잭션 원리에서 본 것).

```
TX2가 UPDATE +100 하면:

   실제 행:     balance = 10,100   (TX2가 쓴 것, 버전 2)
   Undo log:    balance = 10,000   (이전 값, 버전 1)
```

그래서 같은 행에 **여러 버전이 동시에 존재**한다. 이것이 **Multi-Version**이다.

### 읽을 때 — 자기 기준 시점에 맞는 버전을 고른다

각 트랜잭션은 "내 기준 시점"을 갖고 있다. 읽을 때 InnoDB는 그 시점에 커밋되어 있던 버전을 찾아 보여준다.

```
TX1 (기준 시점: 첫 SELECT 때, TX2 커밋 전)
   실제 행을 본다 → 버전 2 (10,100). 내 기준 시점 이후에 커밋된 것 → 안 됨
   Undo log를 따라간다 → 버전 1 (10,000). 내 기준 시점에 커밋되어 있던 것 → 이것을 보여준다

TX3 (TX2 커밋 후에 새로 시작)
   실제 행을 본다 → 버전 2 (10,100). 내 기준 시점 전에 커밋된 것 → 이것을 보여준다
```

- REPEATABLE READ: 기준 시점 = 트랜잭션 첫 SELECT 때. 끝까지 고정
- READ COMMITTED: 기준 시점 = 각 SELECT 문장 때. 문장마다 갱신

두 수준의 차이는 **기준 시점을 언제 잡는가**뿐이고, 버전을 고르는 방식은 같다.

### 왜 기다리지 않는가

- TX2가 쓰는 동안 TX1이 읽어도 충돌이 없다. TX2는 새 버전을 만들고, TX1은 옛 버전을 본다. **서로 다른 것을 보고 있으니 막을 이유가 없다.**
- 읽기는 락을 걸지 않는다. 쓰기만 행 락을 건다(같은 행에 두 트랜잭션이 동시에 쓰는 것은 막아야 하므로).

이 방식이 **MVCC (Multi-Version Concurrency Control)**: 락으로 막는 대신 **버전을 여러 개 두고 각자 자기 것을 보게 해서** 격리를 구현한다.

### 정리

| 질문                     | 답                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 10,000은 어디서 나오나   | Undo log에 남은 이전 버전                                                                                      |
| 왜 TX1은 멈추지 않나     | TX2는 새 버전을 쓰고 TX1은 옛 버전을 읽으니 충돌이 없다                                                        |
| RC와 RR의 차이는         | 버전을 고르는 기준 시점을 문장마다 잡는지, 트랜잭션마다 잡는지                                                 |
| Undo log는 언제 지워지나 | 그 버전을 볼 수 있는 트랜잭션이 전부 끝나면 (그래서 긴 트랜잭션은 Undo log를 키운다)                           |
| 다른 DB도 같은가         | Oracle은 Undo segment, PostgreSQL은 테이블 안에 옛 행을 남기고 VACUUM으로 청소. 보관 위치만 다르고 원리는 같다 |

## 5.6 MySQL의 REPEATABLE READ는 Phantom도 거의 막는다

표준은 REPEATABLE READ에서 Phantom을 허용하지만, InnoDB는 두 가지로 막는다.

- 일반 SELECT: 기준 시점의 버전을 보므로, 그 이후 INSERT된 행은 애초에 안 보인다
- `SELECT ... FOR UPDATE` 같은 잠금 읽기: 조건 범위에 **Gap Lock**(행 사이 빈 공간에 걸리는 락)을 걸어 INSERT 자체를 막는다

그래서 MySQL은 REPEATABLE READ로 충분하고, SERIALIZABLE까지 올리는 일은 드물다.

## 5.7 Spring에서

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
```

지정하지 않으면 `DEFAULT` = DB 기본값. 트랜잭션 시작 시 그 커넥션에 `SET TRANSACTION ISOLATION LEVEL ...`을 실행하고, 끝나면 원복한다.

---

> **한 줄**: 격리 수준은 "남이 쓰는 중인 값을 나는 어떻게 볼 것인가"의 4단계. READ COMMITTED는 **문장마다**, REPEATABLE READ는 **트랜잭션마다** 기준 시점을 잡는다. MySQL은 REPEATABLE READ, Oracle은 READ COMMITTED가 기본. 둘 다 Undo log의 이전 버전을 보여주는 **MVCC**로 구현되어, 읽는 쪽과 쓰는 쪽이 서로 기다리지 않는다.

# 6. Index

## 6.1 인덱스란

> **빠른 READ를 위해, WRITE 시점에 미리 만들어 두는 자료구조.**

테이블의 특정 컬럼 값을 **정렬된 상태로 따로 저장**하고, 각 값이 실제 어느 행에 있는지를 함께 기록한다.

```sql
CREATE INDEX idx_user_email ON user (email);
SELECT * FROM user WHERE email = 'a@b.com';
```

|           | 인덱스 없음                                | 인덱스 있음                                          |
| --------- | ------------------------------------------ | ---------------------------------------------------- |
| 찾는 방법 | 모든 행을 처음부터 끝까지 확인 (Full Scan) | 정렬된 인덱스에서 빠르게 위치를 찾은 뒤 그 행만 읽음 |
| 비용      | 행 수에 비례                               | 행 수가 10배 늘어도 거의 안 늘어남                   |

대가가 있다. INSERT / UPDATE / DELETE마다 **인덱스도 함께 갱신**해야 하므로 쓰기가 느려지고, 저장 공간을 추가로 쓴다. 인덱스는 "읽기를 빠르게 하기 위해 쓰기 비용을 지불하는 것"이다.

RDB는 이 자료구조로 일반적으로 **B+Tree**를 쓴다. 왜 B+Tree인지는 단순한 구조부터 올라가면 보인다.

## 6.2 왜 B+Tree인가 — 세 단계

### 1단계. Binary Search Tree (이진 탐색 트리)

"정렬해서 빨리 찾자"를 가장 단순하게 구현한 것. 각 노드는 자식이 최대 2개이고, **왼쪽은 작은 값, 오른쪽은 큰 값**이다.

```
          50
        /    \
      30      70
     /  \    /  \
   20   40  60   80
```

40을 찾으려면 50 → 30 → 40. 절반씩 좁혀가므로 N개 중에서 약 log₂N번 비교로 찾는다.

**문제 — 편향(skew)**
삽입 순서에 따라 트리가 한쪽으로 쏠린다. 10, 20, 30, 40, 50을 순서대로 넣으면:

```
  10
    \
     20
       \
        30
          \
           40
             \
              50
```

트리가 아니라 연결 리스트다. 50을 찾으려면 5번 전부 거친다. 정렬된 데이터(auto increment PK 등)를 넣을수록 이렇게 되므로, DB에서는 그대로 쓸 수 없다.

### 2단계. B-Tree (Balanced Tree)

두 가지를 바꿨다.

**① 균형을 스스로 유지한다.** 노드가 꽉 차면 둘로 쪼개고(split) 중간 값을 부모로 올린다. 어떤 순서로 넣어도 **모든 리프의 깊이가 같다.** 편향이 생기지 않는다.

**② 노드 하나에 키를 여러 개 넣는다.** 자식이 2개가 아니라 수백 개다.

```
              [ 30 | 60 ]
            /     |      \
      [10|20]  [40|50]  [70|80]
```

왜 키를 많이 넣는가 — **디스크 때문이다.** 디스크는 값 하나를 읽어도 16KB 페이지 단위로 통째로 읽고, 이 읽기 한 번이 메모리 연산의 수만 배 느리다. 그러니 성능은 "비교 몇 번"이 아니라 **"페이지를 몇 번 읽었나"** 로 결정된다.

노드 하나 = 페이지 하나로 맞추고 그 안에 키 수백 개를 넣으면, 한 번 읽어서 수백 갈래 중 하나로 좁힌다.

```
높이 1 :  1,000건
높이 2 :  1,000 × 1,000 = 100만 건
높이 3 :  10억 건
```

**10억 건이어도 디스크 읽기 3번.** 이진 트리였다면 약 30번이다. 이것이 "낮고 넓다"는 뜻이다.

참고: [B-Trees — btechsmartclass](http://www.btechsmartclass.com/data_structures/b-trees.html)

### 3단계. B+Tree (B-Tree의 진화형) — DB가 실제로 쓰는 것

B-Tree에서 두 가지를 더 바꿨다.

**① 데이터는 리프에만 둔다.** B-Tree는 모든 노드에 키와 데이터가 섞여 있다. B+Tree는 위쪽 노드(루트, 중간)에는 **"어디로 가라"는 안내 키만** 두고, 실제 데이터는 전부 **맨 아래 리프**에만 둔다. 위쪽 노드가 가벼워지니 안내 키를 더 많이 넣을 수 있고, 트리가 더 낮아진다.

**② 리프들을 옆으로 연결한다.**

```
                    [ 300 | 600 ]                     루트 — 안내판만
                  /       |       \
        [100|200]     [400|500]     [700|800]         중간 — 안내판만
        /   |   \     /   |   \     /   |   \
   [1..99][100..][200..] ... ... ...  [800..899]      리프 — 실제 데이터, 정렬됨
      ⇄      ⇄      ⇄      ⇄      ⇄      ⇄           리프끼리 연결
```

리프가 연결되어 있어서 되는 것:

| 쿼리                          | 동작                                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| `WHERE age BETWEEN 20 AND 30` | 20을 찾아 내려간 뒤(3번 읽기), 트리를 다시 타지 않고 **리프에서 옆으로 쭉 읽는다.** 30에서 멈춤 |
| `ORDER BY age`                | 리프를 왼쪽부터 따라가면 이미 정렬된 결과. 별도 정렬 불필요                                     |

B-Tree는 리프가 연결되어 있지 않아 범위 검색 때 트리를 오르내려야 한다. 해시 인덱스는 `=`는 빠르지만 25 옆에 무엇이 있는지 모르므로 범위·정렬이 불가능하다. **범위 검색과 정렬이 흔한 DB 쿼리의 특성 때문에 B+Tree가 표준이 됐다.**

## 6.3 세 단계 요약

|                    | 자식 수 | 균형 | 데이터 위치 | 리프 연결 | 문제                         |
| ------------------ | ------- | ---- | ----------- | --------- | ---------------------------- |
| Binary Search Tree | 2       | X    | 모든 노드   | X         | 편향되면 연결 리스트가 됨    |
| B-Tree             | 수백    | O    | 모든 노드   | X         | 범위 검색 시 트리를 오르내림 |
| **B+Tree**         | 수백    | O    | **리프만**  | **O**     | —                            |

## 6.4 인덱스 쓰기 비용의 실체

6.1에서 "쓰기가 느려진다"고 했다. B+Tree로 보면 이유가 구체적이다.

- INSERT마다 리프의 **정렬된 위치**에 끼워 넣어야 한다
- 리프가 꽉 차면 **쪼개고(split)** 부모에 안내 키를 추가한다. 부모도 꽉 차면 연쇄
- 인덱스가 3개면 이 작업을 3번 한다

PK가 auto increment면 항상 맨 오른쪽 끝에만 붙어 split이 거의 없다. UUID처럼 랜덤이면 여기저기 중간 삽입이 일어나 split이 잦다. **PK는 단조 증가가 좋다**는 원칙이 여기서 나온다.

---

> **한 줄**: 인덱스는 빠른 읽기를 위해 쓰기 시점에 정렬된 자료구조를 만들어 두는 것. 이진 트리는 편향되고, B-Tree는 균형을 잡고 노드를 페이지 크기로 넓혀 디스크 읽기를 3~4번으로 줄였고, B+Tree는 데이터를 리프에만 두고 리프를 연결해 범위 검색과 정렬까지 빠르게 했다. 그래서 RDB 인덱스는 B+Tree다.
