# 5회차 — 스레드 이해하기

이번 회차는 "스레드가 정확히 무엇인가"를 OS 바닥에서부터 올라오는 내용이라, 순서가 곧 논리다.

```
① 프로세스의 메모리 구조 (code / data / stack / heap)
② fork — 프로세스를 복제하는 시스템콜
③ COW — 복제를 싸게 만드는 트릭
④ clone — 복제할 때 "무엇을 공유할지" 고르게 해주는 시스템콜
⑤ thread = clone에 CLONE_VM을 켜고 함수·스택을 지정해 만든 프로세스
```

⑤가 결론이고 ①~④는 그 결론을 이해하기 위한 재료다.

---

## ① 프로세스의 메모리 구조

프로그램 파일(.jar, 실행 파일)은 디스크에 있는 죽은 데이터다. 이걸 실행하면 OS가 **프로세스**를 만드는데, 프로세스란 "실행 중인 프로그램 + 그것이 쓰는 메모리 공간"이다. 그 메모리 공간은 네 영역으로 나뉜다.

```
높은 주소
┌──────────────┐
│    STACK     │ ↓  지역 변수, 함수 호출 기록
├──────────────┤
│              │    (비어 있음. 양쪽이 이 공간을 향해 자란다)
├──────────────┤
│     HEAP     │ ↑  동적으로 할당한 객체
├──────────────┤
│     DATA     │    전역 변수, static 변수
├──────────────┤
│     CODE     │    기계어 명령어
└──────────────┘
낮은 주소
```

| 영역      | 들어가는 것                            | 특징                                                   |
| --------- | -------------------------------------- | ------------------------------------------------------ |
| **CODE**  | 컴파일된 명령어                        | 읽기 전용. 실행 중 안 바뀜                             |
| **DATA**  | 전역 변수, static 변수                 | 프로그램 시작 시 만들어져 끝까지 존재                  |
| **HEAP**  | `new`로 만든 객체                      | 실행 중 커졌다 작아졌다 함. 프로그래머(또는 GC)가 관리 |
| **STACK** | 지역 변수, 매개변수, "어디로 돌아갈지" | 함수 호출 시 쌓이고 리턴 시 걷힘. 자동 관리            |

### STACK

함수를 호출할 때마다 **프레임** 하나가 위에 쌓인다. 프레임 안에 그 함수의 지역 변수와, 끝나면 어디로 돌아갈지(리턴 주소)가 있다.

```java
void a() { int x = 1; b(); }
void b() { int y = 2; c(); }
void c() { int z = 3; }
```

```
c() 실행 중:        c() 끝난 뒤:       b() 끝난 뒤:
┌──────────┐
│ c: z=3   │
├──────────┤       ┌──────────┐
│ b: y=2   │       │ b: y=2   │
├──────────┤       ├──────────┤       ┌──────────┐
│ a: x=1   │       │ a: x=1   │       │ a: x=1   │
└──────────┘       └──────────┘       └──────────┘
```

리턴하면 프레임이 걷히고 지역 변수는 사라진다. 그래서 스택은 관리가 자동이고 빠르다. 대신 크기 상한이 있어서(보통 1MB 근처) 재귀가 너무 깊으면 `StackOverflowError`.

### HEAP

`new User("kim")`을 하면 User 객체는 **힙**에 만들어지고, 그 객체의 **주소만** 스택의 지역 변수에 들어간다.

```java
void m() {
    int n = 10;               // 스택: n = 10
    User u = new User("kim"); // 스택: u = 0x7f3a (주소)   힙: 0x7f3a에 User 객체
}
```

`m()`이 끝나면 스택의 `u`는 사라지지만 힙의 User 객체는 그대로 남는다. 아무도 참조하지 않게 되면 나중에 GC가 회수한다. 힙은 **"함수가 끝나도 살아남아야 하는 것"** 을 두는 곳이다.

### 지금 이걸 왜 보는가

다음 단계들에서 계속 이 질문이 나온다.

> 프로세스를 복제하면 이 네 영역이 **전부 복사**되는가? 아니면 일부를 **공유**할 수 있는가?

- 전부 복사 → **fork** (멀티프로세스)
- CODE·DATA·HEAP은 공유, STACK만 따로 → **thread** (멀티스레드)

그러니까 **"스레드는 스택만 따로 갖고 나머지는 공유한다"** 는 문장이 이번 회차의 목적지이고, 그 문장을 읽으려면 네 영역이 각각 뭔지 알아야 한다. 강사님이 여기서 시작한 이유다.

## ② fork — 프로세스를 복제하는 시스템콜

### 시스템콜

> **프로그램이 OS에게 기능을 요청하는 통로.**

왜 필요한가 — 프로그램은 하드웨어(메모리, 디스크, 네트워크)를 직접 만질 수 없기 때문이다.

예) 파일 열기(`open`), 소켓 만들기(`socket`), 프로세스 만들기(`fork`)

### fork가 하는 일

> **fork를 호출한 프로세스를 통째로 복제해서, 똑같은 프로세스를 하나 더 만든다.**

호출한 쪽을 **부모(parent)**, 새로 생긴 쪽을 **자식(child)** 이라 부른다.

```
fork() 전              fork() 후

[부모 프로세스]        [부모 프로세스]           [자식 프로세스]
┌──────────┐          ┌──────────┐             ┌──────────┐
│  STACK   │          │  STACK   │   복사 →    │  STACK   │
│  HEAP    │          │  HEAP    │   복사 →    │  HEAP    │
│  DATA    │          │  DATA    │   복사 →    │  DATA    │
│  CODE    │          │  CODE    │   복사 →    │  CODE    │
└──────────┘          └──────────┘             └──────────┘
                           별개의 메모리 공간. 서로 못 봄
```

①에서 던진 질문에 대한 첫 번째 답이다. **fork는 네 영역을 전부 복사한다.** 복사가 끝나면 두 프로세스는 완전히 남남이고, 한쪽이 변수를 바꿔도 다른 쪽은 모른다.

### fork는 두 번 리턴한다

호출은 한 번인데, 리턴은 **부모에서 한 번, 자식에서 한 번**, 총 두 번 일어난다. 자식은 부모의 스택까지 복사받았으니 "fork()를 호출하던 중"이라는 상태까지 그대로 가져가고, 거기서부터 이어 실행되기 때문이다.

둘을 구분하는 방법이 리턴 값이다.

| 누가 받나 | 리턴 값           |
| --------- | ----------------- |
| 부모      | 자식의 PID (양수) |
| 자식      | 0                 |
| 실패 시   | -1                |

### 멀티프로세스 — fork로 일을 나누는 방식

fork로 자식을 여러 개 만들어 일을 나눠 맡기는 구조가 **멀티프로세스**다.

| 장점                                                             | 단점                                                                      |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 메모리가 완전히 분리 → 한 프로세스가 죽어도 다른 프로세스는 멀쩡 | 메모리를 통째로 복사 → 생성이 무겁다                                      |
| 서로의 데이터를 망가뜨릴 수 없다 → 동시성 문제 없음              | 서로의 데이터를 볼 수 없다 → 주고받으려면 **IPC**(pipe, socket 등)가 필요 |

지난 회차에 본 IPC가 여기서 다시 나온다. IPC가 필요한 이유가 바로 이것 — **fork된 프로세스들은 메모리가 분리되어 있어서, 대화하려면 OS가 제공하는 별도 통로가 필요하다.**

실제 사례:

- **Chrome**: 탭마다 별도 프로세스. 탭 하나가 죽어도 브라우저 전체는 산다
- **PostgreSQL**: 클라이언트 연결마다 백엔드 프로세스를 fork (MySQL은 스레드 방식이라 대조적)
- **Nginx**: 마스터 프로세스가 워커 프로세스들을 fork
- **쉘**: 터미널에서 `ls`를 치면 쉘이 자기를 fork하고, 자식이 `exec`로 자기 자신을 `ls` 프로그램으로 갈아치운다. 모든 명령 실행이 fork + exec

### fork의 문제 — 다음 주제로

부모가 메모리를 2GB 쓰고 있다면, fork 한 번에 2GB를 복사해야 할까? 게다가 쉘처럼 fork 직후 바로 exec하는 경우엔, 힘들게 복사한 2GB를 쓰지도 않고 곧장 버린다.

> "복사해야 하긴 하는데, 정말 필요할 때까지 미룰 수는 없을까?"

이 질문의 답이 다음 주제 **COW(Copy-On-Write)** 다.

---

## ③ COW (Copy-On-Write)

### 먼저 알아야 할 것 — 메모리는 "페이지" 단위로 관리된다

①에서 본 네 영역은 프로세스 입장에서 보이는 모습이다. 실제로 OS는 메모리를 **4KB짜리 조각(페이지)** 으로 잘라서 관리한다. 그리고 프로세스가 쓰는 주소는 진짜 물리 메모리 주소가 아니라 **가상 주소**다. OS가 프로세스마다 **페이지 테이블**이라는 표를 두고, "이 가상 페이지는 물리 메모리의 몇 번 칸"이라고 연결해 준다.

```
프로세스의 가상 메모리       페이지 테이블             물리 메모리(RAM)
[ 페이지 0 ] ────────────▶  0 → 물리 #52  ──────▶  [ #52 ]
[ 페이지 1 ] ────────────▶  1 → 물리 #17  ──────▶  [ #17 ]
[ 페이지 2 ] ────────────▶  2 → 물리 #88  ──────▶  [ #88 ]
```

이 구조 덕분에 **두 프로세스의 페이지 테이블이 같은 물리 칸을 가리키게** 만들 수 있다. COW는 이걸 이용한다.

### COW가 하는 일

> **fork할 때 메모리를 복사하지 않는다. 대신 둘이 같은 물리 메모리를 가리키게 하고, 누군가 "쓰려는 순간"에 그 페이지 하나만 복사한다.**

### 중요한 점 — 논리적으로는 여전히 "전부 복사"다

COW는 **구현 트릭**이지 fork의 의미를 바꾸지 않는다.

- 부모·자식 입장에서는 여전히 **각자 자기 메모리**를 가진 것처럼 보인다
- 자식이 값을 바꾸는 순간 그 페이지는 분리되므로, **부모는 자식이 바꾼 값을 절대 못 본다**
- 즉 ②의 결론(서로 못 본다, 대화하려면 IPC)은 그대로

COW는 **"복사를 미뤄서 싸게 만든 것"** 이지, "공유하게 해준 것"이 아니다.

### 다음 주제로

COW로 fork는 싸졌다. 하지만 여전히 **쓰는 순간 분리된다.** 멀티프로세스끼리 데이터를 나누려면 여전히 IPC가 필요하다.

> "복사를 미루는 게 아니라, **처음부터 아예 같은 메모리를 공유**하게 할 수는 없을까?"

이 질문에 "공유할지 말지를 옵션으로 고르게 해주는" 시스템콜이 다음 주제 **clone**이다.

---

## ④ clone — 무엇을 공유할지 고르는 시스템콜

### fork와 무엇이 다른가

fork는 선택지가 없다. **항상 "전부 복사"** 다(COW로 미룰 뿐).
clone은 프로세스를 만들 때 **"이건 복사하고, 이건 공유해"를 옵션(flag)으로 고르게** 해준다. fork를 일반화한 버전이다.

```c
int clone(int (*fn)(void *), void *stack, int flags, void *arg);
//        ─────────────────  ───────────  ─────────  ─────────
//        자식이 시작할 함수    자식이 쓸 스택   공유 옵션    fn에 넘길 인자
```

fork에 없던 인자가 셋(fn, stack, flags) 생겼다. 핵심은 flags다.

### flags — 무엇을 공유할지

| 옵션         | 켜면                                                         | 끄면                |
| ------------ | ------------------------------------------------------------ | ------------------- |
| **CLONE_VM** | **메모리 공간 전체를 공유** (CODE·DATA·HEAP 한 벌을 같이 씀) | fork처럼 복사 (COW) |
| CLONE_FILES  | 열린 파일·소켓 목록을 공유                                   | 복사                |
| CLONE_FS     | 현재 디렉터리 등을 공유                                      | 복사                |
| CLONE_THREAD | 같은 프로세스 그룹으로 묶음 (같은 PID로 보임)                | 별개 프로세스       |

핵심은 **CLONE_VM** 하나다.

- **CLONE_VM 끔** → 메모리를 복사(COW). ②·③의 fork와 같다. 실제로 리눅스의 fork는 내부적으로 "아무것도 공유하지 않는 clone"으로 구현되어 있다
- **CLONE_VM 켬** → **복사도, COW도 없다.** 처음부터 같은 메모리를 본다. 자식이 변수를 바꾸면 부모도 바로 보인다

### 왜 스택과 함수를 따로 줘야 하나

CLONE_VM을 켜면 스택까지 공유된다. 둘이 한 스택에 프레임을 쌓으면 서로의 지역 변수와 리턴 주소를 덮어써 망가진다. 그래서 **자식 전용 스택**을 넘겨야 한다.
새 스택은 비어 있어 돌아갈 곳이 없으므로, **어디서부터 실행할지(함수)** 도 지정해야 한다.

### 정리 (강사님 필기)

- **CLONE_VM** 옵션을 제공 → 처음부터 메모리를 공유할지 말지 선택
- **function, stack**을 파라미터로 → 자식의 시작점과 자기 스택을 지정
- 이렇게 프로세스를 만들어주는 시스템콜이 **clone**

### 이게 곧 스레드다 — 다음 주제로

CLONE_VM을 켜고, 함수와 스택을 지정해서 만든 것을 다시 보면:

- CODE·DATA·HEAP은 **공유**
- STACK만 **각자**
- 각자 다른 함수에서 **실행을 시작**

①에서 세운 목적지 문장 **"스레드는 스택만 따로 갖고 나머지는 공유한다"** 와 정확히 같다. 다음 주제 ⑤에서 이걸 "스레드"라는 이름으로 확정하고, Java의 `new Thread()`가 실제로 이 clone으로 이어진다는 걸 본다.

## ⑤ Thread — CLONE_VM으로 만든 프로세스

### 정의

> **스레드 = CLONE_VM 옵션을 켜고, 함수와 스택을 지정해서 만든(복제한) 프로세스.**

①~④를 거쳐 온 결론이다.

```
fork                          clone(CLONE_VM, fn, stack)
= 프로세스                     = 스레드

[부모]        [자식]            [스레드 A]    [스레드 B]
┌──────┐     ┌──────┐          ┌──────┐     ┌──────┐
│STACK │     │STACK │          │STACK │     │STACK │   ← 각자
│HEAP  │     │HEAP  │          └──┬───┘     └──┬───┘
│DATA  │     │DATA  │             └─────┬──────┘
│CODE  │     │CODE  │              ┌──────┐
└──────┘     └──────┘              │HEAP  │
  전부 따로                          │DATA  │   ← 한 벌 공유
                                   │CODE  │
                                   └──────┘
```

리눅스 커널 입장에서는 프로세스와 스레드가 **같은 종류의 것(task)** 이다. 차이는 오직 **"무엇을 공유하느냐"** 뿐이고, 그걸 정하는 게 clone의 flags다. 그래서 스레드를 **경량 프로세스(LWP, Light-Weight Process)** 라고도 부른다 — 메모리를 복사하지 않으니 가볍게 만들어지는 프로세스라는 뜻.

### Java의 `new Thread()`는 어떻게 clone까지 가나

```
Thread t = new Thread(task);
t.start();
   │
   ▼  JVM (C++ 코드)
os::create_thread()
   │
   ▼  C 라이브러리 (glibc)
pthread_create()
   │   ① 스택용 메모리를 할당 (크기 = -Xss, 보통 1MB)
   │   ② clone(fn, stack,
   │           CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_THREAD | ...)
   ▼  커널
새 task 생성 — 메모리는 공유, 스택은 ①에서 받은 것
```

- `t.start()` 한 번이 결국 **clone 시스템콜 한 번**이다
- Java 스레드 하나 = OS 스레드 하나(1:1). 그래서 Java 스레드를 **플랫폼 스레드**라고도 부른다
- `-Xss`로 정하는 스택 크기가 위 ①번에서 쓰인다. 스레드 200개면 스택만 약 200MB — **"스레드 생성은 비싸다"의 근거**가 여기서 나온다

(참고: Java 21의 가상 스레드는 이 1:1을 깨고 JVM이 OS 스레드 몇 개 위에 수많은 가상 스레드를 올리는 방식이다. 지금은 이름만 알아둔다.)

### 프로세스 vs 스레드

|                 | 멀티프로세스 (fork)                 | 멀티스레드 (clone + CLONE_VM)                  |
| --------------- | ----------------------------------- | ---------------------------------------------- |
| 메모리          | 각자 따로                           | HEAP·DATA·CODE 공유, STACK만 따로              |
| 생성 비용       | 무겁다 (COW여도 페이지 테이블 복사) | 가볍다 (스택만 새로)                           |
| 데이터 주고받기 | IPC 필요                            | 같은 힙 객체를 그냥 읽고 씀                    |
| 하나가 죽으면   | 나머지는 멀쩡                       | **프로세스 전체가 죽음** (메모리를 공유하므로) |
| 동시성 문제     | 없음 (못 건드리니까)                | **있음** (같은 힙을 동시에 건드리니까)         |

표의 마지막 두 줄이 멀티스레드의 대가다. **공유해서 편한 만큼, 공유해서 위험하다.**

### 이 결론이 앞으로 쓰이는 곳

| 사실                            | 연결되는 것                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------- |
| STACK은 스레드마다 따로         | 지역 변수는 다른 스레드가 못 본다 → **지역 변수는 동기화 불필요**                        |
| HEAP은 공유                     | 객체 필드, static 변수, 싱글톤 빈은 모든 스레드가 같이 본다 → **동시성 문제**(다음 수업) |
| 스레드 생성 = clone + 스택 할당 | 비싸다 → **스레드 풀**                                                                   |
| Tomcat 요청 하나 = 스레드 하나  | 요청들이 같은 힙(같은 Spring 빈)을 공유 → 빈에 상태를 두면 안 되는 이유                  |
| ThreadLocal                     | 공유되는 힙 안에서 "스레드마다 따로"를 흉내 내는 장치 (지난 회차)                        |

### 전체 흐름 정리

```
① 네 영역 이해                                   ✔
② fork   = 네 영역 전부 복사                        ✔  안전하지만 무겁다
③ COW    = 복사를 쓸 때까지 미룸                    ✔  싸졌지만 여전히 분리
④ clone  = CLONE_VM으로 공유 선택, 스택·함수 지정       ✔
⑤ thread = 그렇게 만든 프로세스                      ✔  스택만 따로, 나머지 공유
```

①에서 세운 목적지 문장에 도착했다.

> **스레드는 스택만 따로 갖고 나머지는 공유한다.**

## ⑥ 스레드 생성 방법 — extends Thread vs implements Runnable

### 두 가지 방법

**방법 1. Thread를 상속**

```java
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("실행: " + Thread.currentThread().getName());
    }
}

new MyThread().start();
```

**방법 2. Runnable을 구현해서 Thread에 넘기기**

```java
class MyTask implements Runnable {
    @Override
    public void run() {
        System.out.println("실행: " + Thread.currentThread().getName());
    }
}

new Thread(new MyTask()).start();

// 람다로 줄이면
new Thread(() -> System.out.println("실행")).start();
```

둘 다 결과는 같다. 새 스레드가 만들어지고, 그 스레드에서 `run()`이 실행된다.

### ⑤와 연결 — clone의 인자와 대응시켜 보면

④에서 clone은 **"자식이 시작할 함수(fn)"** 를 따로 받았다. Java에서 그 fn에 해당하는 게 `run()`이고, **Runnable은 "fn 하나만 담은 객체"** 다.

| clone의 인자     | Java에서                          |
| ---------------- | --------------------------------- |
| fn (시작할 함수) | `run()` — Runnable이 담고 있는 것 |
| stack            | JVM이 `-Xss` 크기로 알아서 할당   |
| flags            | JVM이 CLONE_VM 등으로 고정        |
| clone 호출       | `Thread.start()`                  |

역할이 이렇게 나뉜다.

- **Runnable = 무엇을 실행할지** (작업)
- **Thread = 어떻게 실행할지** (OS 스레드를 만들어 그 작업을 돌리는 수단)

### Thread 내부를 보면 둘은 같은 것이다

`Thread` 클래스는 Runnable을 구현하고 있고, 받은 Runnable을 필드에 들고 있다. (단순화한 소스)

```java
public class Thread implements Runnable {
    private Runnable target;

    public Thread(Runnable target) { this.target = target; }

    @Override
    public void run() {
        if (target != null) target.run();   // 넘겨받은 작업을 실행
    }

    public void start() { /* native → pthread_create → clone → 새 스레드에서 run() 호출 */ }
}
```

- 방법 1(상속): `run()`을 **직접 덮어씀**
- 방법 2(Runnable): `target`을 넘겨서 기본 `run()`이 **target.run()을 부르게** 함

어느 쪽이든 `start()` → clone → 새 스레드가 `run()`을 실행하는 경로는 같다.

### 왜 Runnable을 권장하나

| 이유                         | 설명                                                                                                                |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **단일 상속**                | Java는 클래스를 하나만 상속할 수 있다. Thread를 상속하면 다른 클래스를 상속할 수 없다                               |
| **역할 분리**                | 작업(Runnable)과 실행 수단(Thread)이 분리된다. 작업 코드가 스레드 관리에 묶이지 않는다                              |
| **스레드 풀에 넘길 수 있다** | `ExecutorService.submit()`은 **Runnable을 받는다**, Thread를 받지 않는다. 작업만 넘기면 풀의 기존 스레드가 실행한다 |
| **람다**                     | Runnable은 메서드가 하나인 함수형 인터페이스라 람다로 쓸 수 있다                                                    |

세 번째가 가장 중요하다. Thread를 상속한 객체는 "그 자체가 스레드"라서 한 번 쓰고 끝이지만, Runnable은 "작업"이라서 **아무 스레드에게나 맡길 수 있다.** 스레드를 재사용하는 스레드 풀이 가능한 이유다.

### 흔한 실수 두 가지

**① `run()`을 직접 부르기**

```java
Thread t = new Thread(task);
t.run();     // 새 스레드 안 생김. 현재 스레드에서 그냥 메서드 호출
t.start();   // 이것만 clone을 부른다
```

**② `start()`를 두 번 부르기**

```java
t.start();
t.start();   // IllegalThreadStateException
```

한 번 시작한 Thread 객체는 끝나면 재사용할 수 없다. 끝난 스레드는 TERMINATED 상태로 가고, 거기서 되돌아올 길이 없다(생명주기에서 다룸).

### 결과가 필요하면 — Callable (참고)

Runnable의 `run()`은 리턴값이 없고 checked exception을 던질 수 없다. 결과가 필요하면 `Callable<T>`를 쓰는데, Callable은 **Thread에 직접 못 넘기고 스레드 풀에 넘겨야** 한다. 스레드 풀에서 같이 본다.

## ⑦ 데몬 스레드 / 논데몬 스레드

### 질문 — 프로그램은 언제 끝나는가

`main()`이 끝나면 프로그램이 끝날까? **아니다.** 이걸 결정하는 규칙이 이 구분이다.

> **JVM은 논데몬 스레드가 하나도 남지 않으면 종료된다. 데몬 스레드는 남아 있어도 무시하고 종료한다.**

```java
public static void main(String[] args) {
    new Thread(() -> {
        while (true) { /* 무한 루프 */ }
    }).start();

    System.out.println("main 끝");
}
// "main 끝"이 찍혀도 프로그램은 안 끝난다
// → 워커 스레드가 논데몬이고, 아직 돌고 있으니까
```

```java
Thread t = new Thread(() -> {
    while (true) { }
});
t.setDaemon(true);       // 데몬으로 지정
t.start();
System.out.println("main 끝");
// "main 끝" 찍히고 바로 종료
// → 남은 건 데몬뿐이니 JVM이 기다리지 않는다
```

### 비교

|                 | 논데몬 (기본값)                     | 데몬                                         |
| --------------- | ----------------------------------- | -------------------------------------------- |
| JVM 종료에 영향 | 이 스레드가 끝나야 JVM이 끝남       | 이 스레드가 돌고 있어도 JVM이 끝남           |
| 종료 방식       | 스스로 `run()`을 마치고 끝남        | JVM이 끝날 때 **하던 일 도중에 그냥 사라짐** |
| 용도            | 프로그램의 본 작업                  | 본 작업을 보조하는 백그라운드 작업           |
| 예              | main 스레드, 직접 만든 스레드(기본) | GC, JIT 컴파일러 등 JVM 내부 스레드          |

이름의 유래: 데몬(daemon)은 유닉스에서 "뒤에서 조용히 도는 서비스 프로세스"를 부르는 말이다. 주인공이 아니라 조수라서, 주인공(논데몬)이 다 퇴장하면 같이 퇴장한다.

### 규칙 세 가지

**① `start()` 전에 지정해야 한다**

```java
t.start();
t.setDaemon(true);   // IllegalThreadStateException
```

**② 만든 스레드의 속성을 물려받는다**
논데몬이 만든 스레드는 논데몬, 데몬이 만든 스레드는 데몬이 기본값이다. main이 논데몬이라 우리가 만드는 스레드는 보통 논데몬이다.

**③ 데몬은 정리 없이 죽는다**
JVM이 종료될 때 데몬 스레드는 `finally` 블록도 실행되지 않고 그 자리에서 사라진다. 파일을 쓰던 중이면 파일이 깨지고, DB에 쓰던 중이면 중간에 끊긴다. **끝까지 해야 하는 일은 데몬으로 만들지 않는다.**

### ⑤와 연결 — OS는 이 구분을 모른다

데몬/논데몬은 OS 수준 개념이 아니다. OS 입장에서는 둘 다 똑같이 clone으로 만든 스레드다. **JVM이 "종료할 때 누구를 기다릴지" 판단하려고 붙여둔 표시**일 뿐이다.

### 실무에서 만나는 곳

**스레드 풀을 `shutdown()` 안 하면 프로그램이 안 끝난다**

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.submit(() -> System.out.println("작업"));
// pool.shutdown();  ← 이걸 빼면 main이 끝나도 JVM이 안 끝남
```

기본 스레드 풀이 만드는 스레드는 논데몬이다. 작업이 없어도 다음 작업을 기다리며 살아 있으니, JVM은 그 스레드들을 계속 기다린다. 테스트 코드나 배치에서 "프로그램이 안 끝나요"의 흔한 원인.

**Spring Boot 서버가 안 꺼지는 이유**
Tomcat의 요청 처리 스레드(`http-nio-8080-exec-1` 같은 것)는 사실 **데몬**이다. 그런데도 서버가 계속 떠 있는 건, Spring Boot가 Tomcat을 띄울 때 **아무 일도 안 하고 기다리기만 하는 논데몬 스레드**를 하나 따로 세워두기 때문이다. 이 스레드가 살아 있는 동안 JVM이 안 끝나고, 서버를 종료하면 이 스레드가 끝나면서 JVM도 내려간다.

즉 "서버가 계속 살아 있다"는 것도 이 규칙 하나로 설명된다.

## ⑧ 스레드 생명주기

스레드는 만들어진 순간부터 끝날 때까지 상태가 바뀐다. Java는 이를 `Thread.State`의 **6가지 값**으로 구분하고, `t.getState()`로 확인할 수 있다.

### 6개 상태

| 상태              | 의미                                           | 들어가는 계기                       |
| ----------------- | ---------------------------------------------- | ----------------------------------- |
| **NEW**           | 객체만 만들어짐. 아직 OS 스레드 없음           | `new Thread(...)`                   |
| **RUNNABLE**      | 실행 중이거나, CPU 차례를 기다리는 중          | `start()`, 대기 종료                |
| **BLOCKED**       | 다른 스레드가 가진 `synchronized` 락을 기다림  | `synchronized` 진입 시도            |
| **WAITING**       | 다른 스레드의 신호·종료를 **기한 없이** 기다림 | `wait()`, `join()`                  |
| **TIMED_WAITING** | **정해진 시간까지만** 기다림                   | `sleep(ms)`, `wait(ms)`, `join(ms)` |
| **TERMINATED**    | `run()`이 완전히 끝남                          | 정상 종료 또는 처리 안 된 예외      |

### 흐름

```
NEW ── start() ──▶ RUNNABLE ── run() 종료 ──▶ TERMINATED
                    │   ▲
      락 대기 ──────┤   ├────── 락 획득                    → BLOCKED
      무기한 대기 ──┤   ├────── 신호 / 대상 종료            → WAITING
      시간 대기 ────┘   └────── 시간 경과 / 신호            → TIMED_WAITING
```

핵심 두 문장:

> **기다림이 끝난 스레드는 바로 종료되지 않고 다시 RUNNABLE로 돌아간다.**
> **`run()`이 완전히 끝났을 때만 TERMINATED가 된다.**

예를 들어 `sleep(3000)` 후에는 `TIMED_WAITING → RUNNABLE`로 돌아와 `sleep()` 다음 코드를 실행하고, `run()`을 다 마쳐야 TERMINATED다.

### 상태별 포인트

**NEW → RUNNABLE**
NEW일 때는 Java 객체만 있다. `start()`가 ⑤의 경로(pthread_create → clone)를 타면서 실제 스레드가 생기고 RUNNABLE이 된다. `run()`을 직접 부르면 새 스레드가 생기지 않고 상태도 NEW 그대로다(⑥).

**RUNNABLE = 실행 중 + 실행 대기**
Java에는 별도의 RUNNING 상태가 없다. 코어 8개에 스레드 200개면 192개는 차례를 기다리지만 전부 RUNNABLE이다. 소켓에서 데이터를 기다리는 중(`read()`)도 Java에서는 RUNNABLE로 보인다.

**BLOCKED = 락이 필요해서 못 들어감**
한 스레드가 `synchronized` 블록 안에 있으면 나머지는 입구에서 BLOCKED로 대기한다. 락이 풀리면 획득하고 RUNNABLE로 돌아간다.

**WAITING = 기한 없이 기다림**
`worker.join()`을 호출하면 WAITING이 되는 것은 worker가 아니라 **join()을 호출한 쪽(main)** 이다. worker가 끝나면 main이 RUNNABLE로 돌아온다.

**TERMINATED = 되돌아올 수 없음**
최종 상태다. 같은 작업을 다시 하려면 새 Thread를 만들어야 한다(clone + 스택 할당을 다시). → **스레드 풀**의 출발점.

### `sleep()` vs `wait()`

둘 다 기다리지만 **락 처리**가 다르다.

|               | `Thread.sleep()`     | `Object.wait()`                                |
| ------------- | -------------------- | ---------------------------------------------- |
| 목적          | 일정 시간 쉬기       | 다른 스레드의 신호 기다리기                    |
| 상태          | TIMED_WAITING        | WAITING (또는 시간 지정 시 TIMED_WAITING)      |
| 락            | **반납하지 않음**    | **반납함**                                     |
| 호출 조건     | 어디서든             | 그 객체의 `synchronized` 안에서만              |
| 깨어나는 계기 | 시간 경과, interrupt | `notify()`/`notifyAll()`, 시간 경과, interrupt |

`sleep()` 중인 스레드가 락을 쥐고 있으면, 다른 스레드는 그동안 계속 BLOCKED다.

### interrupt — 강제 종료가 아니라 "중단 요청" 신호

```java
worker.interrupt();
```

- `sleep()`, `wait()`, `join()`으로 대기 중이면 `InterruptedException`이 나면서 깨어난다
- 실행 중인 스레드는 **자동으로 멈추지 않는다.** 코드가 직접 확인해야 한다

```java
while (!Thread.currentThread().isInterrupted()) {
    // 반복 작업
}
```

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // 예외가 나면 인터럽트 표시가 지워지므로 다시 세워 상위에 알린다
}
```

## ⑨ 스레드 풀 필요성

### 요청마다 `new Thread()`의 문제

| 문제              | 근거                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------- |
| 생성이 비싸다     | ⑤ `start()` = clone + 스택 1MB 할당                                                           |
| 재사용이 안 된다  | ⑧ 끝나면 TERMINATED                                                                           |
| 상한이 없다       | 요청 1만 개 = 스레드 1만 개 = 스택만 약 10GB                                                  |
| 많을수록 느려진다 | 코어보다 스레드가 훨씬 많으면 **컨텍스트 스위칭**(스레드 전환 시 상태 저장·복원)에 CPU를 쓴다 |

### 해결 — 미리 만들어 두고 재사용

> **스레드를 미리 N개 만들어 두고, 작업을 큐에 넣으면 놀고 있는 스레드가 꺼내서 실행한다.**

```
작업 제출 ──▶ [ 작업 큐 ] ──▶ [스레드 1] [스레드 2] ... [스레드 N]
                              끝나면 큐에서 다음 작업을 꺼냄 (죽지 않음)
```

커넥션 풀과 같은 발상 — 만들기 비싼 것을 미리 만들어 빌려 쓴다.

### 스레드가 죽지 않는 이유

```java
// 풀 스레드의 run() (단순화)
while (true) {
    Runnable task = queue.take();   // 큐가 비면 WAITING
    task.run();                     // 그냥 메서드 호출 (⑥)
}                                   // run()이 끝나지 않으니 TERMINATED가 안 된다 (⑧)
```

풀에는 Thread가 아니라 **Runnable(작업)** 만 넘긴다. 이미 있는 스레드가 그 작업을 실행한다.

## ⑩ ThreadPoolExecutor

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        10,                                   // corePoolSize
        10,                                   // maximumPoolSize
        1L, TimeUnit.MINUTES,                 // keepAliveTime
        new LinkedBlockingQueue<>(10),        // workQueue
        Executors.defaultThreadFactory(),     // threadFactory
        new ThreadPoolExecutor.AbortPolicy()  // rejection handler
);
pool.prestartAllCoreThreads();
```

| 설정                       | 뜻                                                                               |
| -------------------------- | -------------------------------------------------------------------------------- |
| corePoolSize               | 기본으로 유지하는 스레드 수                                                      |
| maximumPoolSize            | 최대 스레드 수. **큐가 꽉 찼을 때만** 여기까지 늘린다                            |
| keepAliveTime              | core를 넘어 추가된 스레드가 이 시간 놀면 제거                                    |
| workQueue                  | 스레드가 전부 바쁠 때 작업이 기다리는 곳                                         |
| threadFactory              | 스레드 생성 방식 (기본: `pool-1-thread-1`, 논데몬)                               |
| rejection handler          | 스레드·큐가 모두 꽉 찼을 때의 처리                                               |
| `prestartAllCoreThreads()` | core 스레드를 시작 시 미리 전부 생성 (워밍업). 기본은 작업이 올 때 하나씩 만든다 |

위 코드는 실행 10 + 대기 10 = **20개까지** 받고, 21번째는 예외.

### 판단 순서 — 가장 중요

```
core 미만   → 스레드 생성
큐에 자리   → 큐에 넣음        ← 스레드를 늘리지 않는다
max 미만    → 스레드 생성
전부 꽉 참  → reject
```

**큐를 무제한으로 두면 max에 절대 도달하지 않는다.** 그래서 무제한 큐를 쓰는 `Executors.newFixedThreadPool()`(OOM 위험), max가 무제한인 `newCachedThreadPool()`(스레드 폭증 위험) 대신 **큐 크기·max·reject를 직접 정한다.**

### Rejection 정책

| 정책                   | 동작                                                                   |
| ---------------------- | ---------------------------------------------------------------------- |
| **AbortPolicy** (기본) | `RejectedExecutionException`                                           |
| **CallerRunsPolicy**   | 제출한 스레드가 직접 실행 → 제출 속도가 자연히 느려짐. 버리면 안 될 때 |
| DiscardPolicy          | 조용히 버림                                                            |
| DiscardOldestPolicy    | 가장 오래된 대기 작업을 버리고 넣음                                    |

### 자주 쓰는 것

- `execute(Runnable)` / `submit(Runnable·Callable)` → `submit`은 `Future`를 돌려주고, **예외가 Future 안에 갇힌다.** `get()`을 불러야 드러난다
- `shutdown()` → 새 작업 거절, 남은 작업은 처리 후 종료. 안 부르면 논데몬이라 JVM이 안 끝난다(⑦)
- `shutdownNow()` → 실행 중인 스레드에 interrupt(⑧)
- Spring의 `ThreadPoolTaskExecutor`는 이걸 감싼 것. **`queueCapacity` 기본값이 무제한**이라 반드시 지정한다
