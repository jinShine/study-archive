# 11장. 고가용성 2 — Cluster

> **이 장을 마치면**: Redis 여러 대에 데이터를 나눠 저장할 때 **키가 어느 서버로 가는지**(슬롯) 설명하고, 그 때문에 **코드에서 조심할 것**(CROSSSLOT, 해시 태그)을 안다.

| 주제 | 한 줄 | 중요도 |
| ---- | ----- | ------ |
| 슬롯 | 키 이름으로 계산하는 번호. 이 번호로 저장할 서버가 정해진다 | 🔴 |
| CROSSSLOT | 키 여러 개를 한 명령에 쓰는데 슬롯이 다르면 나는 에러 | 🔴 코드에 영향 |
| 해시 태그 | `{ }`로 같이 쓸 키들을 같은 슬롯에 모으는 방법 | 🔴 코드에 영향 |
| Replica 필수 | Replica 없는 서버가 죽으면 클러스터 전체가 멈춘다 | 🔴 |

**실습 준비물**: [infra/cluster/](./infra/cluster) 의 `start.sh`, `stop.sh`

---

## 1. Cluster란 — 왜 필요한가

10장의 Sentinel 구성은 **Master가 1대**다. 그래서 두 가지가 그 1대에 묶인다.

- 저장할 수 있는 데이터 = Master 1대의 메모리만큼
- 처리할 수 있는 쓰기 = Master 1대가 감당하는 만큼

Replica를 늘려도 Replica는 Master의 **복사본**이라 용량은 늘지 않는다.

> **Cluster = Master를 여러 대 두고, 데이터를 나눠서 저장하는 구성.** Master 3대면 데이터를 3등분해서 저장한다.

```text
               ┌─ Master 7000 ── Replica
데이터 전체 ───┼─ Master 7001 ── Replica       각 Master는 전체의 1/3만 가진다
               └─ Master 7002 ── Replica       각 Master는 자기 Replica도 가진다 (10장과 같은 복사본)
```

그러면 바로 질문이 생긴다. **`SET user:1 kim`을 보내면 3대 중 어디에 저장하나? 나중에 `GET user:1`은 어디로 찾으러 가나?** 이걸 정하는 규칙이 슬롯이다.

## 2. 🔴 슬롯 — 키가 갈 서버를 정하는 규칙

### 슬롯이란

**슬롯 = 0번부터 16383번까지, 16384개의 번호표.** 클러스터를 만들 때 이 번호표를 Master들이 나눠 맡는다.

```text
Master 7000: 0번 ~ 5460번
Master 7001: 5461번 ~ 10922번
Master 7002: 10923번 ~ 16383번
```

### 키 → 슬롯 번호 계산

```text
슬롯 번호 = CRC16(키) % 16384
```

| 조각 | 뜻 |
| ---- | -- |
| `CRC16(키)` | 문자열을 숫자로 바꾸는 계산(해시 함수). **같은 문자열은 항상 같은 숫자**가 나오고, 비슷한 문자열이어도 숫자는 전혀 다르게 나온다 |
| `% 16384` | 16384로 나눈 **나머지**. 그래서 결과는 항상 0~16383 사이 = 슬롯 번호 |

계산은 Redis와 Spring(Lettuce)이 알아서 한다. 개발자는 **"키 이름이 같으면 항상 같은 서버로 간다"** 만 알면 된다.

### 실제 키로 보기

`CLUSTER KEYSLOT 키`로 슬롯 번호를 확인할 수 있다 (아래는 실제로 계산한 값).

| 키 | 슬롯 번호 | 저장되는 서버 |
| -- | --------- | ------------- |
| `user:3` | 2648 | 7000 (0 ~ 5460) |
| `user:2` | 6777 | 7001 (5461 ~ 10922) |
| `user:1` | 10778 | 7001 (5461 ~ 10922) |
| `user:123` | 12893 | 7002 (10923 ~ 16383) |

`SET user:123 kim`을 보내면:

```text
1. user:123 → 슬롯 12893
2. 12893은 10923 ~ 16383 범위 → 7002 담당
3. 7002에 저장
```

`GET user:123`도 같은 계산 → 같은 12893 → 같은 7002로 찾으러 간다.

### 서버 수(3)가 아니라 16384로 나누는 이유

`해시 % 3`으로 서버를 바로 고르면, 서버를 4대로 늘리는 순간 `해시 % 4`로 바뀌어 **거의 모든 키의 서버가 달라진다.** 데이터 대부분을 옮겨야 한다.

슬롯은 **항상 16384개로 고정**이다. 서버를 늘리면 기존 서버들이 맡던 번호표 **일부만** 새 서버에 넘겨주면 된다.

## 3. 🔴 CROSSSLOT — 키 여러 개를 한 명령에 쓸 때

### 규칙

> **명령 하나에 들어간 키들은 모두 같은 슬롯이어야 한다.** 아니면 `CROSSSLOT` 에러가 난다.

키를 여러 개 받는 명령이 해당된다: `MSET`, `MGET`, 여러 키 `DEL`, **Lua 스크립트**(6장), Transaction(6장).

### 예

```text
MSET user:1:name kim user:1:age 20     ← 키 2개를 한 번에 저장
```

| 키 | 슬롯 |
| -- | ---- |
| `user:1:name` | 12440 |
| `user:1:age` | 13180 |

슬롯이 다르다 → 거부된다.

```text
(error) CROSSSLOT Keys in request don't hash to the same slot
        (요청한 키들이 같은 슬롯이 아니다)
```

### 왜 이런 규칙이 있나

- Redis는 명령 하나를 **서버 한 대 안에서** 끊김 없이 실행한다.
- 슬롯은 서버를 늘리거나 줄일 때 **하나씩 따로** 다른 서버로 옮겨질 수 있다.
- 12440과 13180은 지금은 둘 다 7002에 있지만, 나중에 다른 서버로 갈라질 수 있다.
- 그래서 Redis는 서버가 아니라 **슬롯이 같은지**로 판단해 미리 막는다.

## 4. 🔴 해시 태그 `{ }` — 같은 슬롯으로 모으기

### 규칙

> **키 이름에 `{ }`가 있으면, 중괄호 안의 글자만으로 슬롯을 계산한다.**

| 키 | 계산에 쓰는 글자 | 슬롯 |
| -- | ---------------- | ---- |
| `user:1` | `user:1` | 10778 |
| `{user:1}:name` | `user:1` | **10778** |
| `{user:1}:age` | `user:1` | **10778** |

중괄호 안이 같으면 슬롯이 같다. 이제 한 명령에 같이 쓸 수 있다.

```text
MSET {user:1}:name kim {user:1}:age 20     → OK
```

### 실무 예 — 6장 선착순 쿠폰

6장의 쿠폰 Lua 스크립트는 키 2개를 한 번에 쓴다.

| 키 | 슬롯 | 서버 |
| -- | ---- | ---- |
| `coupon:stock` (남은 수량) | 5777 | 7001 |
| `coupon:issued` (받은 사람) | 14874 | 7002 |

슬롯도 서버도 다르다 → Cluster에서는 이 스크립트가 **CROSSSLOT 에러로 실패**한다. 키 이름을 바꾼다.

| 키 | 계산에 쓰는 글자 | 슬롯 |
| -- | ---------------- | ---- |
| `{coupon}:stock` | `coupon` | 7577 |
| `{coupon}:issued` | `coupon` | 7577 |

> ⚠️ 모든 키를 `{같은 것}`으로 묶으면 데이터가 한 서버에 몰려서 나눠 저장하는 의미가 없어진다. **같은 명령에 같이 쓰는 키끼리만** 묶는다.

## 5. MOVED — 다른 서버에 물어봤을 때

클라이언트가 `user:123`(7002 담당)을 7000에 보내면 7000은 직접 처리하지 않고 이렇게 알려 준다.

```text
MOVED 12893 127.0.0.1:7002
(그 키는 12893번 슬롯이고, 7002가 담당이다. 거기로 가라)
```

Spring(Lettuce)은 이 응답을 받으면 **알아서** 7002로 다시 보내고, 다음부터는 처음부터 7002로 보낸다. 코드에서 할 일은 없다.

## 6. 🔴 Master가 죽으면

| 상황 | 결과 |
| ---- | ---- |
| Replica가 **있는** Master가 죽음 | 그 Replica가 자동으로 Master가 되어 슬롯을 이어받는다. 데이터 그대로 |
| Replica가 **없는** Master가 죽음 | 그 슬롯을 맡을 서버가 없다 → **클러스터 전체가 모든 요청을 거부** (`CLUSTERDOWN`) |

두 번째가 중요하다. 3대 중 1대만 죽었는데 **살아 있는 서버의 키까지** 전부 거부된다. 그래서 운영에서는 **Master 3대 + Replica 3대**가 최소 구성이다.

Sentinel은 필요 없다. Cluster의 서버들이 서로 상태를 확인하고, Master들의 투표로 Replica를 승격한다.

## 7. Spring 설정

```yaml
spring:
  data:
    redis:
      cluster:
        nodes:              # 서버 몇 개만 적으면 나머지는 Lettuce가 알아낸다
          - 10.0.0.1:7000
          - 10.0.0.2:7001
          - 10.0.0.3:7002
```

`StringRedisTemplate` 코드는 그대로다. **바뀌는 건 여러 키를 한 명령에 같이 쓰는 곳의 키 이름(해시 태그)뿐**이다.

| | 서버 1대 / Sentinel | Cluster |
| --- | --- | --- |
| 여러 키 명령 | 자유 | 같은 슬롯끼리만 |
| DB 번호 (`SELECT 1`) | 0~15 | **0번만** |

## 🧪 실습 — 따라 하기

### 1단계. 클러스터 띄우기

```bash
cd infra/cluster
./start.sh
```

```text
클러스터 준비 완료 (포트, 역할, 맡은 슬롯)
127.0.0.1:7000 master 0-5460
127.0.0.1:7001 master 5461-10922
127.0.0.1:7002 master 10923-16383
127.0.0.1:7003 slave
127.0.0.1:7004 slave
127.0.0.1:7005 slave
```

Master 3대가 슬롯을 나눠 맡았고, `slave`(Replica) 3대가 붙었다.

### 2단계. 접속

```bash
docker exec -it redis-cluster-test redis-cli -c -p 7000
```

`-c`는 Cluster 모드다. MOVED를 받으면 알아서 담당 서버로 옮겨 간다 (Spring과 같은 동작).

### 3단계. 아래 명령을 하나씩 쳐 보기

| 입력 | 결과 | 확인할 것 |
| ---- | ---- | --------- |
| `CLUSTER KEYSLOT user:123` | `(integer) 12893` | 슬롯 번호 계산 |
| `SET user:123 kim` | `-> Redirected to slot [12893] located at 127.0.0.1:7002`<br>`OK` | 7002로 자동 이동해서 저장. 프롬프트가 `7002>`로 바뀐다 |
| `GET user:123` | `"kim"` | |
| `MSET user:1:name kim user:1:age 20` | `(error) CROSSSLOT ...` | 슬롯이 달라서 거부 |
| `CLUSTER KEYSLOT user:1:name` | `(integer) 12440` | |
| `CLUSTER KEYSLOT user:1:age` | `(integer) 13180` | 슬롯이 다르다 |
| `CLUSTER KEYSLOT {user:1}:name` | `(integer) 10778` | 중괄호 안(`user:1`)만 계산 |
| `CLUSTER KEYSLOT {user:1}:age` | `(integer) 10778` | 같은 슬롯 |
| `MSET {user:1}:name kim {user:1}:age 20` | `-> Redirected to slot [10778] ...`<br>`OK` | 해시 태그로 성공 |

`exit`로 나온다.

### 4단계. Master 하나 죽이기

`user:123`을 가진 7002를 끈다.

```bash
docker exec redis-cluster-test redis-cli -p 7002 SHUTDOWN NOSAVE
```

10초쯤 기다린 뒤 다시 접속해서 확인한다.

```bash
docker exec -it redis-cluster-test redis-cli -c -p 7000
```

| 입력 | 결과 | 확인할 것 |
| ---- | ---- | --------- |
| `GET user:123` | `-> Redirected to slot [12893] located at 127.0.0.1:7004`<br>`"kim"` | 7002의 Replica가 Master가 되어 데이터를 이어받았다. 어느 Replica인지(7003~7005)는 매번 다르다 |
| `CLUSTER NODES` | `... 7002 ... master,fail ...` | 7002는 장애로 표시된다 |

### 5단계. 정리

```bash
./stop.sh
```

## 🎯 실습 문제

**문제 1.** 장바구니 키 `cart:1`과 수정 시각 키 `cart:1:updated`를 Lua 스크립트 하나로 같이 바꾸려 한다. Cluster에서 실패하지 않으려면 두 키 이름을 어떻게 지어야 할까?

<details>
<summary>정답</summary>

`{cart:1}`, `{cart:1}:updated`. 중괄호 안이 `cart:1`로 같아서 슬롯이 같다.

```text
CLUSTER KEYSLOT {cart:1}           → (integer) 1420
CLUSTER KEYSLOT {cart:1}:updated   → (integer) 1420
```

</details>

**문제 2.** 비용을 아끼려고 Replica 없이 Master 3대로만 Cluster를 만들었다. Master 1대가 죽으면?

<details>
<summary>정답</summary>

그 Master의 슬롯을 이어받을 Replica가 없어서 클러스터 전체가 `CLUSTERDOWN`으로 모든 요청을 거부한다. 살아 있는 2대의 키도 못 쓴다. 1대 장애가 전체 장애가 된다.

</details>

## 정리

```text
슬롯      = 키 이름으로 계산하는 0~16383 번호. 이 번호로 저장할 서버가 정해진다
CROSSSLOT = 키 여러 개를 한 명령에 쓰는데 슬롯이 다르면 나는 에러
해시 태그 = {중괄호 안}만 계산하게 해서, 같이 쓸 키들을 같은 슬롯에 모은다
Replica   = Cluster에서는 필수. 없으면 1대 장애가 전체 장애
```

## 면접 한 줄

- **Cluster**: 키를 CRC16 해시로 16384개 슬롯에 배정하고, 슬롯을 여러 Master가 나눠 가져서 용량과 쓰기를 확장한다.
- **CROSSSLOT**: 여러 키를 쓰는 명령은 모든 키가 같은 슬롯이어야 한다. 해시 태그 `{ }`로 같은 슬롯에 묶는다.
- **Sentinel vs Cluster**: Sentinel은 Master 1대에 모든 데이터를 두고 자동 전환만 하고, Cluster는 여러 Master에 나눠 저장하면서 자동 전환도 한다.
