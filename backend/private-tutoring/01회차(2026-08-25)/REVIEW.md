# 1회차 REVIEW — 백엔드 시스템의 구조와 확장

- 원본 정리: [STUDY_GUIDE.md](./STUDY_GUIDE.md)
- 복습일: 2026-10-04
- 설명 방식: 정의 → 왜 필요한가 → 동작 원리 → 한계

1회차 전체는 하나의 인과 사슬이다. 각 개념은 바로 앞 개념의 한계를 해결하려고 등장한다.

```text
서버 1대 한계 → Scale up → SPOF 문제 → Scale out → LB 필요 + stateless 필요
→ DB가 병목 → Primary/Replica → Replication lag → read-your-own-writes
→ 읽기 부하 → Redis 캐시 / 응답 지연 → Message Queue
→ 쓰기·용량 한계 → Sharding → 조직·도메인 확장 → MSA
```

---

## 1. 기본 요청 흐름

**정의**: 클라이언트가 HTTP 요청을 보내면 서버가 비즈니스 로직을 처리하고, 필요하면 DB에 쿼리를 보낸 뒤 결과를 응답으로 가공해 돌려준다.

**역할 구분**

- **서버**: 요청을 해석하고 규칙을 적용한다. 계산하는 곳.
- **DB**: 데이터를 영속적으로 저장하고 조회한다. 기억하는 곳.

이 구분이 뒤의 모든 확장 전략의 기준이다. **계산하는 쪽은 쉽게 늘릴 수 있고, 기억하는 쪽은 늘리기 어렵다.**

---

## 2. Stateless

**정의**: 서버가 요청 사이에 특정 클라이언트의 상태를 **자기 메모리에 보관하지 않는** 설계.

**왜 필요한가**: 서버가 여러 대면 같은 사용자의 요청이 매번 다른 서버로 갈 수 있다. 상태(로그인 세션, 장바구니 등)가 Server A 메모리에만 있으면 Server B는 그 상태를 모른다. 사용자 입장에서는 상태가 사라진 것처럼 보인다.

**원리**: 상태를 서버 밖의 공유 저장소에 둔다.

- 영속 데이터 → DB
- 휘발돼도 되고 빠르게 읽어야 하는 데이터(세션 등) → Redis
- 클라이언트가 상태를 들고 오게 하는 방식 → JWT

**결과**: **어느 서버가 요청을 받아도 같은 결과**가 나온다. 그래서 서버를 자유롭게 추가·제거할 수 있다. **Stateless는 Scale out의 전제 조건**이다.

---

## 3. Scale up

**정의**: 서버 대수는 그대로 두고, 한 대의 하드웨어 성능(CPU, 메모리)을 높이는 방식.

**장점**: 코드·아키텍처 변경 없이 즉시 적용할 수 있다.

**한계**

1. **물리적 상한**이 있다.
2. 성능이 높아질수록 **비용 대비 효율**이 떨어진다.
3. **SPOF(Single Point of Failure)** 가 그대로다. 그 한 대가 죽으면 전체가 멈춘다.

→ Scale up은 **성능** 문제를 다루지만 **가용성** 문제는 해결하지 못한다.

**한계에 가까워지는 대표 자원**

| 자원               | 한계 시 증상                 |
| ------------------ | ---------------------------- |
| CPU                | 계산 지연, 응답 시간 증가    |
| Memory             | GC 부담 증가, OOM            |
| Thread pool        | 동시에 처리할 요청이 대기    |
| DB connection pool | DB에 접근하려는 요청이 대기  |
| Network            | 외부 API·DB·서버 간 통신 지연 |

> Thread pool과 Connection pool은 3~5회차의 주제로 다시 나온다.

## 4. 병목 진단 — APM과 지표

### APM (Application Performance Monitoring)

**정의**: 요청 단위로 **어느 구간(코드, DB 쿼리, 외부 API)에서 시간이 소요됐는지** 추적하는 도구.

**왜 필요한가**: 응답이 느린 원인은 여러 가지이고, 원인마다 해결책이 다르다. 원인을 모르고 대응하면 비용만 쓰고 문제는 남는다.

| 병목                               | 해결 방향                                 |
| ---------------------------------- | ----------------------------------------- |
| CPU                                | Scale up/out, 코드 최적화                 |
| DB 쿼리                            | 인덱스, 쿼리 튜닝, N+1 제거               |
| 읽기 부하                          | 캐시, Read Replica                        |
| 외부 API                           | Timeout, Retry, Circuit Breaker, 비동기화 |
| Thread pool / Connection pool 포화 | 처리 시간 단축, 풀 크기 조정              |

### Percentile (p50 / p95 / p99)

**정의**: 응답 시간을 오름차순으로 정렬했을 때 하위 N%가 위치하는 값. p99 = 300ms면 요청의 99%가 300ms 이하로 끝났다는 뜻.

**왜 평균만 보면 안 되나**: 평균은 소수의 극단적으로 느린 요청(**Tail Latency**)을 희석한다. p95/p99는 그 느린 구간을 드러낸다. 트래픽이 크면 1%도 절대 수로는 많은 사용자다.

**주의**: 트래픽이 아주 적으면 p99는 몇 건의 이상치에도 크게 흔들린다. 그래서 Average, p50, p95, p99를 **같이** 본다.

### Golden Signals / RED

| Golden Signals | 의미                                        |
| -------------- | ------------------------------------------- |
| Latency        | 응답 시간 (p95, p99)                        |
| Traffic        | 요청량 (RPS)                                |
| Errors         | 실패율                                      |
| Saturation     | 자원이 한계에 얼마나 가까운가 (CPU, 풀, 큐) |

RED(Rate, Errors, Duration)는 API 서비스용 축약 버전이다.

**주의**

- **4xx는 클라이언트 오류**(401, 404 등), **5xx는 서버 오류**. 장애 판단은 5xx 비율로 한다.
- **RPS ≠ TPS**: RPS는 HTTP 요청 수, TPS는 처리된 비즈니스 트랜잭션 수. 주문 1건에 API 3번이면 RPS 3, TPS 1.

## 5. Scale out과 Load Balancer

**정의**: 동일한 서버를 여러 대 두고 요청을 분산하는 방식.

**목적**

1. **처리량 증가**: 서버 수에 비례해 처리량이 늘어난다.
2. **고가용성(High Availability)**: 일부 서버가 죽어도 나머지가 처리한다. SPOF 제거.
3. **무중단 배포**: 서버를 한 대씩 내려서 배포해도 서비스가 유지된다.

**Load Balancer의 기능**

- **분산**: 라운드로빈 등의 알고리즘으로 요청을 나눈다.
- **Health check**: 주기적으로 각 서버의 `/health` 같은 엔드포인트를 호출하고, 응답이 없거나 비정상인 서버는 **라우팅 대상에서 제외**한다.

→ 고가용성은 서버 대수만으로 생기지 않는다. **health check로 죽은 서버를 빼야** 실제로 성립한다.

**전제**: 서버가 stateless여야 한다(2절).

## 6. DB 확장이 어려운 이유

앱 서버는 stateless라 복제해도 문제가 없다. DB는 **상태 그 자체**라서 여러 대에 쓰기가 분산되면 **정합성**이 깨진다.

- DB1에 쓰고 DB2에서 읽으면 데이터가 안 보인다.
- 두 DB에서 같은 잔액을 동시에 차감하면 이중 차감이 일어난다.

그래서 DB 확장은 **"쓰기는 한 곳, 읽기는 여러 곳"** 에서 출발한다.

---

## 7. Primary / Replica (Replication)

**정의**

- **Primary**: 쓰기(INSERT/UPDATE/DELETE)를 받는 유일한 DB.
- **Replica**: Primary의 데이터를 복제해 **읽기만** 담당하는 DB.

> 용어: Master/Slave는 옛 표현이다. 지금은 Primary/Replica(Writer/Reader)를 쓴다.

**왜 효과가 있나**: 대부분의 서비스는 읽기 비율이 압도적으로 높다. 읽기만 분산해도 Primary 부하가 크게 준다.

**복제 원리 (MySQL 기준)**

```text
[Primary]  쓰기 실행 → binlog에 변경 이력 기록 → commit → 앱에 응답
[Replica]  binlog 수신 → relay log 저장 → 순서대로 재생(replay) → 자기 데이터에 반영
```

- 복제는 **데이터 파일 복사가 아니라 변경 이력 재생**이다.
- 복제는 **DB끼리** 한다. 앱 서버는 Primary에만 쓴다.
- **비동기 복제**: Primary는 Replica 반영을 기다리지 않고 응답한다.

**왜 비동기인가**

- 동기라면 **가장 느린 Replica가 모든 쓰기의 속도를 결정**한다.
- **Replica 하나가 장애 나면 쓰기 전체가 멈출 수 있다.**
- 읽기 확장을 위해 Replica를 늘렸는데 쓰기가 느려지면 목적에 어긋난다.

→ **확장성을 얻는 대신 일관성 지연을 감수하는 트레이드오프.**

---

## 8. Replication Lag

**정의**: Primary에 커밋된 변경이 Replica에 반영되기까지의 시간 차이.

**문제**: 쓰기 직후 조회가 Replica로 가면 방금 쓴 데이터가 안 보인다(**Read-after-write 불일치**). 평소엔 lag가 작아 안 보이다가, 트래픽 급증이나 대량 배치 중 lag가 커지면 간헐적으로 발생한다.

**해결**

- **Read-your-own-writes**: 쓰기 직후의 조회(또는 일정 시간 동안의 조회)는 Primary로 라우팅한다.
- Replication lag를 지표로 모니터링한다.

---

## 9. Multi-Master

**정의**: 쓰기를 받는 DB를 여러 대 두는 구조.

**문제**: 같은 행이 서로 다른 Master에서 동시에 수정되면 **쓰기 충돌**이 생기고, 어느 값을 채택할지 정하는 충돌 해결 정책이 필요하다. 잘못 설계하면 정합성이 깨진다.

→ 일반적으로는 Primary/Replica를 먼저 쓰고, 쓰기 한계는 다른 방법(샤딩 등)으로 접근한다.

---

## 10. Sharding

**정의**: 데이터를 **여러 DB에 나눠 저장**해 쓰기 부하와 데이터 용량까지 분산하는 방식.

| 분할 방식                              | 의미                                       |
| -------------------------------------- | ------------------------------------------ |
| **Vertical Partitioning**              | 테이블·도메인 단위로 DB 분리 (회원 DB, 주문 DB) |
| **Horizontal Partitioning (Sharding)** | 같은 테이블의 **행**을 여러 DB로 나눔       |

실무에서는 보통 수직 분할을 먼저 하고, 그래도 특정 테이블이 감당되지 않을 때 수평 샤딩을 고려한다.

### Shard Key

어느 샤드에 저장할지 결정하는 기준 컬럼. 조건:

- **분포가 균일**해야 한다. 특정 샤드로 몰리면(hot spot) 안 된다.
- **조회 조건에 자주 등장**해야 한다. 그래야 한 샤드만 조회하면 된다.
- **값이 잘 바뀌지 않아야** 한다. 바뀌면 데이터가 다른 샤드로 이동해야 한다.
- 예: `user_id`, `tenant_id`는 적합. 가입일은 최근 데이터가 한 샤드에 몰려 부적합.

### Modulo Sharding과 리샤딩

`shard = key % N`

- 장점: 계산이 단순하고 분포가 균일하다.
- 치명적 단점: **N이 바뀌면 대부분 키의 샤드 위치가 바뀐다.**

`% 3` → `% 4`로 바꾸면:

| key | % 3 | % 4 | 이동?    |
| --- | --- | --- | -------- |
| 0   | 0   | 0   | 유지     |
| 1   | 1   | 1   | 유지     |
| 2   | 2   | 2   | 유지     |
| 3   | 0   | 3   | **이동** |
| 4   | 1   | 0   | **이동** |
| 5   | 2   | 1   | **이동** |
| 6   | 0   | 2   | **이동** |
| 7   | 1   | 3   | **이동** |
| 8   | 2   | 0   | **이동** |
| 9   | 0   | 1   | **이동** |
| 10  | 1   | 2   | **이동** |
| 11  | 2   | 3   | **이동** |

12개 중 **9개(75%)가 이동**한다. 샤드 하나 추가했을 뿐인데 데이터 대부분을 옮겨야 한다 → **리샤딩 문제**. 이동 중에도 쓰기가 계속 들어오므로 데이터 이동, 이동 중 읽기 위치, 롤백 전략까지 설계해야 한다.

> 참고: 이 이동량을 줄이는 기법으로 **Consistent Hashing**이 있다. 수업 범위 밖이라 이름만 알아둔다.

**추가 비용**: 여러 샤드에 걸친 조회(cross-shard query), 샤드 간 트랜잭션, 운영 복잡도 → **최후의 수단**.

## 11. Redis 캐시

**정의**: 메모리 기반 Key-Value 저장소. 자주 읽는 데이터의 **복사본**을 두어 DB 조회를 생략한다.

**빠른 이유**

- 디스크가 아니라 메모리에서 읽는다.
- Key-Value라 조회 연산이 단순하다.
- 단일 스레드 이벤트 루프라 락 경합이 적다.

**핵심 원리**: DB를 빠르게 하는 게 아니라 **DB에 가지 않게** 한다. 무거운 계산 결과(랭킹, 추천)를 **미리 계산해 저장**해 두고 요청 시 꺼낸다.

**한계 — 캐시 정합성**

- 캐시는 원본이 아니라 복사본이다. 원본이 바뀌면 오래된 값(stale data)이 남는다.
- 대응: **TTL**(만료 시간), 원본 변경 시 **캐시 무효화(삭제)**.
- 캐시는 넣는 시점보다 **지우는 시점** 설계가 더 어렵다.

## 12. Message Queue

**정의**: 생산자(Producer)가 메시지를 큐에 넣고, 소비자(Consumer/Worker)가 **비동기로** 꺼내 처리하는 구조.

**왜 필요한가**: 한 요청 안에 **응답 전에 반드시 끝나야 하는 작업**(결제, 재고 차감)과 **나중에 해도 되는 작업**(이메일, SMS, 포인트)이 섞여 있다. 전부 동기로 처리하면:

- 응답 시간이 가장 느린 작업까지 합산된다.
- 외부 서비스(이메일 발송) 장애가 **핵심 요청 실패로 전파**된다.

**효과**

- 응답 시간 감소
- 결합도 감소 = **외부 서비스 장애가 핵심 요청(주문) 실패로 전파되지 않는다** (장애 격리)

**새로 생기는 문제**: 비동기 처리 실패, **중복 처리**, **재시도**, **순서 보장**을 따로 설계해야 한다.

| 제품          | 특징                                    |
| ------------- | --------------------------------------- |
| Kafka         | 대용량 이벤트 스트리밍, 메시지 보존·재처리 |
| RabbitMQ      | 전통적 브로커, 유연한 라우팅             |
| AWS SQS       | 관리형, 운영 부담 적음                   |
| Redis Streams | 이미 Redis를 쓰고 요구가 단순할 때      |

## 13. MSA (Microservice Architecture)

**정의**: 시스템을 **도메인 단위의 독립 서비스**(회원, 주문, 결제 등)로 나누고, 각 서비스가 독립적으로 배포·확장되는 구조.

**핵심 원칙 — Database per Service**

- 각 서비스는 자기 DB만 직접 접근한다.
- 다른 서비스 데이터는 **API나 메시지**로만 가져온다.
- 이유: 다른 서비스의 DB를 직접 읽으면 스키마 변경이 서로 묶여 **독립 배포가 불가능**해진다.

| 장점                | 단점                            |
| ------------------- | ------------------------------- |
| 독립 배포·독립 확장 | 분산 트랜잭션이 어렵다          |
| 장애 격리           | 네트워크 호출 실패를 고려해야 함 |
| 팀별 소유권         | 로그·모니터링·추적이 복잡       |

→ MSA는 **조직과 도메인 규모가 커져 독립 배포가 필요할 때** 선택하는 구조다. 작은 팀에서는 모놀리식이 더 합리적일 수 있다.

| Scale up        | 단일 서버 성능       | 물리 한계, SPOF          |
| Scale out + LB  | 처리량, 가용성, 무중단 배포 | stateless 설계 필요 |
| Primary/Replica | DB 읽기 부하         | Replication lag          |
| Redis           | 반복 조회 비용       | 캐시 정합성              |
| Message Queue   | 응답 지연, 장애 전파 | 중복·재시도·순서         |
| Sharding        | 쓰기·용량 한계       | 리샤딩, cross-shard      |
| MSA             | 조직·배포 확장       | 분산 트랜잭션, 운영 복잡도 |

이 표의 **"새로 생기는 문제" 열**이 1회차의 핵심이다. 백엔드의 모든 해결책에는 대가가 따른다.

## 확인 질문

### Q1. Stateless가 Scale out의 전제 조건인 이유는?

<details><summary>모범 답안</summary>

상태를 서버 메모리가 아니라 외부 저장소(DB/Redis/JWT)에 두면 **어느 서버가 요청을 받아도 같은 결과**가 나온다. 그래서 LB가 아무 서버에나 요청을 보낼 수 있고, 서버를 자유롭게 추가·제거할 수 있다.

</details>

> 내 답: "상태를 몰라야 복제가 쉽다" → 방향은 맞음. "모른다"가 아니라 **"외부에 둔다"**, 그리고 **"어느 서버가 받아도 같은 결과"** 를 말해야 한다.

### Q2. MySQL 복제는 어떻게 동작하고, Primary는 왜 Replica 반영을 기다리지 않나?

<details><summary>모범 답안</summary>

Primary는 쓰기 후 binlog에 변경 이력을 기록하고 커밋 후 응답한다. Replica는 binlog를 받아 relay log에 저장하고 순서대로 재생한다. 즉 **데이터 복사가 아니라 변경 이력 재생**이다.

기다리지 않는 이유: 동기라면 가장 느린 Replica가 쓰기 속도를 결정하고, Replica 장애 시 쓰기가 멈출 수 있다. 읽기 확장이 목적인데 쓰기가 느려지면 안 되므로 비동기로 하고, 대신 replication lag를 감수한다.

</details>

> 내 답: Primary 쪽 흐름만 말함 → **Replica 쪽(수신 → relay log → 재생)** 이 빠졌다.

### Q3. 아래 상황에서 서버 사양부터 올리면 안 되는 이유와 먼저 확인할 것은?

```text
RPS 동일, p95 200ms → 2s, CPU 40%, 5xx 변화 없음, DB query duration 증가
```

<details><summary>모범 답안</summary>

- CPU 40% → CPU 병목이 아니라 사양을 올려도 효과가 없다.
- 5xx 변화 없음 → 장애가 아니라 지연 문제다.
- DB query duration 증가 → 병목은 DB 쪽이다.

먼저 확인할 것: 슬로우 쿼리와 실행 계획(인덱스 사용 여부), 락 대기, Connection pool 대기, 최근 배포 변경.

</details>

> 내 답: 쿼리 튜닝, 인덱스, N+1 → 결론은 맞음. **지표로 근거**를 대고, 추측 전에 **확인**이 먼저다.

### Q4. Modulo Sharding에서 샤드를 3개 → 4개로 늘리면?

<details><summary>모범 답안</summary>

`key % N`의 N이 바뀌어 대부분 키의 샤드 위치가 바뀐다(0~11 기준 75% 이동). 대량 데이터 이동(리샤딩)이 필요하고, 이동 중 쓰기·읽기 위치·롤백까지 설계해야 한다.

</details>

> 내 답: 몰랐음 → 10절 표 다시 보기.

### Q5. Message Queue를 도입하면 해결되는 문제와 새로 생기는 문제는?

<details><summary>모범 답안</summary>

해결: 나중에 해도 되는 작업을 응답 경로에서 분리해 응답 시간이 줄고, 외부 서비스 장애가 핵심 요청 실패로 전파되지 않는다(결합도 감소).

새 문제: 비동기 처리 실패, 중복 처리, 재시도, 순서 보장.

</details>

> 내 답: 거의 맞음. **재시도·순서 보장**이 빠졌다.
