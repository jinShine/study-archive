## 오늘의 핵심 한 문장

백엔드는 "요청을 받아서 DB에 저장하고 응답한다"에서 시작하지만, 실무로 가면 "요청이 많아져도 빠르고, 장애가 나도 버티고, 데이터가 틀어지지 않게 만드는 일"로 확장됩니다.

프론트엔드 관점으로 말하면, 지금까지는 `fetch()`의 왼쪽, 즉 화면과 사용자 경험을 주로 봤다면 이제는 `fetch()`의 오른쪽 세계를 공부하는 것입니다.

```text
Client -> Server -> Database
       <-        <-
```

이 단순한 그림에서 시작해서 서버가 여러 대가 되고, DB가 Primary/Replica로 나뉘고, Redis와 메시지 큐가 붙고, 나중에는 서비스 단위로 쪼개지는 흐름을 배웠습니다.

## 1. 클라이언트, 서버, DB의 기본 흐름

가장 기본 구조는 다음과 같습니다.

```text
Client -> Server -> MySQL
Client <- Server <- MySQL
```

흐름은 이렇게 읽으면 됩니다.

1. 클라이언트가 HTTP 요청을 보냅니다.
2. 서버가 요청을 받습니다.
3. 서버가 비즈니스 로직을 처리합니다.
4. 데이터가 필요하면 DB에 쿼리를 보냅니다.
5. DB가 결과를 돌려줍니다.
6. 서버가 JSON 같은 응답 형태로 가공해서 클라이언트에 돌려줍니다.

프론트엔드에서는 보통 "API 응답이 어떤 모양인가", "로딩과 에러를 어떻게 처리할까"가 중요했습니다. 백엔드에서는 같은 요청을 보고 질문이 달라집니다.

- 이 요청이 초당 1개가 아니라 5,000개 오면 어떻게 되는가?
- DB 커넥션이 부족하면 어떤 일이 생기는가?
- 요청 처리 중 서버가 죽으면 사용자는 어떤 응답을 받는가?
- 방금 저장한 데이터가 바로 조회되지 않는 상황은 가능한가?

여기서 중요한 감각은 서버와 DB의 역할 구분입니다. 서버는 요청을 해석하고 규칙을 적용하는 곳이고, DB는 데이터를 안정적으로 저장하고 조회하는 곳입니다.

## 2. 상태는 어디에 둘 것인가

백엔드에서 아주 중요한 말이 `stateless`입니다.

`stateless`는 서버가 특정 사용자의 상태를 자기 메모리에만 들고 있지 않는다는 뜻입니다. 예를 들어 로그인 여부, 장바구니, 주문 상태 같은 중요한 정보를 특정 서버 한 대의 메모리에만 저장하면 문제가 생깁니다.

서버가 한 대일 때는 우연히 잘 돌아갈 수 있습니다. 하지만 서버가 여러 대가 되면 사용자의 첫 요청은 Server A로 가고, 다음 요청은 Server B로 갈 수 있습니다. 만약 로그인 상태가 Server A 메모리에만 있으면 Server B는 사용자가 로그인했는지 모릅니다. 사용자 입장에서는 갑자기 로그인이 풀린 것처럼 보입니다.

그래서 백엔드에서는 상태를 외부 저장소에 둡니다.

- 영구 데이터: MySQL, PostgreSQL 같은 DB
- 빠르게 읽고 지워도 되는 데이터: Redis
- 세션/토큰 관련 상태: Redis, DB, 또는 JWT 전략

서버를 stateless하게 만들수록 서버를 여러 대로 늘리기 쉬워집니다. 이게 뒤에서 배우는 Scale out의 전제입니다.

## 3. Scale up - 서버 한 대를 더 강하게 만들기

`Scale up`은 서버 대수는 그대로 두고, 한 서버의 성능을 높이는 방식입니다.

예를 들어 AWS에서 작은 인스턴스를 쓰다가 더 CPU와 메모리가 많은 인스턴스로 바꾸는 것입니다. 코드 구조를 크게 바꾸지 않아도 되고, 배포 구조도 단순합니다. 그래서 서비스가 느려졌을 때 가장 먼저 떠올리기 쉬운 방법입니다.

하지만 서버가 느려졌다고 바로 Scale up부터 하면 안 됩니다. 먼저 병목을 찾아야 합니다.

```text
서비스가 느림
-> 모니터링/APM 확인
-> CPU 병목인지, DB 병목인지, 외부 API 병목인지 확인
-> 원인에 맞는 해결책 선택
```

서버에서 한계에 가까워지는 대표 자원은 다음과 같습니다.

| 자원 | 한계가 오면 생기는 일 |
| --- | --- |
| CPU | 계산이 밀리고 응답 시간이 증가 |
| Memory | GC 부담 증가, OOM 위험 |
| Thread pool | 동시에 처리할 요청이 대기 |
| DB connection pool | DB에 접근하려는 요청이 대기 |
| Network | 외부 API, DB, 다른 서버 통신이 지연 |

Scale up의 한계도 분명합니다.

- 물리적으로 계속 키울 수 없습니다.
- 비용 대비 성능 향상이 점점 낮아질 수 있습니다.
- 서버가 한 대라면 여전히 SPOF입니다.

`SPOF`는 `Single Point of Failure`입니다. 하나가 죽으면 전체가 멈추는 지점을 뜻합니다. 아무리 비싼 서버 한 대를 써도 그 서버가 죽으면 서비스는 중단됩니다.

그래서 Scale up은 성능 문제에는 도움이 되지만, 가용성 문제까지 해결하지는 못합니다.

## 4. APM - 느리다는 말에서 원인을 찾기

`APM`은 `Application Performance Monitoring`입니다. 단순히 "서버가 느리다"를 알려주는 것이 아니라, "어떤 요청이, 어디에서, 왜 느린지"를 찾게 해주는 도구입니다.

실무에서는 감으로 튜닝하면 위험합니다.

```text
느리다
-> CPU가 높아 보인다
-> 서버 사양을 올린다
```

이렇게 가면 실제 병목이 DB 쿼리였을 때 돈만 쓰고 문제는 남습니다.

더 좋은 흐름은 이렇습니다.

```text
느리다
-> APM/로그/메트릭 확인
-> 병목 지점 파악
-> 원인별 해결
```

예시는 다음과 같습니다.

| 병목 | 가능한 해결 |
| --- | --- |
| CPU 병목 | Scale up, Scale out, 코드 최적화 |
| DB Query 병목 | 인덱스, 쿼리 튜닝, N+1 제거 |
| Read 부하 | Redis 캐시, Read Replica |
| 외부 API 병목 | Timeout, Retry, Circuit Breaker, 비동기 처리 |
| Thread pool 포화 | 처리 시간 단축, 풀 크기 조정, 비동기 구조 검토 |

## 5. 평균만 보면 위험하다 - Tail Latency

응답 시간은 평균만 보면 착각하기 쉽습니다.

예를 들어 요청 10개가 다음처럼 걸렸다고 해봅니다.

```text
100ms, 110ms, 120ms, 100ms, 130ms, 110ms, 120ms, 100ms, 150ms, 5000ms
```

대부분은 빠르지만 하나가 5초입니다. 평균만 보면 "조금 느린가?" 정도로 보일 수 있지만, 실제 사용자 한 명은 5초를 기다렸습니다.

그래서 `p95`, `p99` 같은 percentile을 봅니다.

| 지표 | 의미 |
| --- | --- |
| Average | 전체 평균 |
| p50 | 50%의 요청이 이 값 이하 |
| p95 | 95%의 요청이 이 값 이하 |
| p99 | 99%의 요청이 이 값 이하 |

중요한 포인트는 평균을 버리라는 뜻이 아닙니다. 평균만 보지 말라는 뜻입니다.

트래픽이 큰 서비스에서 p99가 나쁘면 일부 사용자 문제가 아니라 많은 사용자 문제가 됩니다. 반대로 트래픽이 아주 적은 서비스에서는 p99가 몇 건의 이상치에 크게 흔들릴 수 있으므로 Average, p50, p95, p99를 같이 봐야 합니다.

## 6. Golden Signals와 RED

시스템 상태를 볼 때 자주 쓰는 기준이 있습니다.

`Golden Signals`는 Google SRE에서 자주 언급되는 네 가지 신호입니다.

| 신호 | 보는 질문 | 예시 |
| --- | --- | --- |
| Latency | 얼마나 걸리는가 | 평균, p95, p99 |
| Traffic | 얼마나 들어오는가 | RPS, TPS |
| Errors | 얼마나 실패하는가 | 5xx, timeout, exception |
| Saturation | 한계에 얼마나 가까운가 | CPU, thread pool, queue, DB connection |

Spring 백엔드 API에서는 `RED Method`도 자주 씁니다.

| 항목 | 의미 |
| --- | --- |
| Rate | 요청량 |
| Errors | 실패율 |
| Duration | 응답 시간 |

여기서 조심할 점이 있습니다.

`4xx`와 `5xx`를 같은 장애로 보면 안 됩니다. `401`, `403`, `404`는 클라이언트 요청 문제인 경우가 많습니다. 서버 장애를 볼 때는 보통 `5xx Error Rate`를 따로 봅니다.

또 `RPS`와 `TPS`도 완전히 같은 말이 아닙니다.

- RPS: 초당 HTTP 요청 수
- TPS: 초당 처리된 트랜잭션 수

주문 1건에 API 호출이 3번 필요하면 RPS는 3이고 TPS는 1일 수 있습니다.

## 7. Scale out - 서버를 여러 대로 늘리기

`Scale out`은 서버 한 대를 더 강하게 만드는 것이 아니라, 서버 대수를 늘리는 방식입니다.

```text
Client -> Load Balancer -> Server A
                        -> Server B
                        -> Server C
```

Scale out은 단순히 트래픽을 더 받기 위한 방법만은 아닙니다. 서버 한 대가 죽어도 다른 서버가 요청을 받을 수 있게 해서 고가용성을 확보하는 목적도 큽니다.

면접에서 "왜 Scale out을 했나요?"라는 질문을 받으면 "트래픽이 늘어서요"만 말하면 절반입니다. 더 좋은 답은 다음과 같습니다.

> 트래픽 증가에 대응하고, 특정 서버 장애가 전체 서비스 장애로 이어지지 않도록 고가용성을 확보하기 위해 Scale out을 고려했습니다.

## 8. Load Balancer의 핵심 - 분산과 헬스체크

`Load Balancer`는 요청을 여러 서버로 나눠주는 역할을 합니다. 하지만 실무에서 정말 중요한 역할은 `health check`입니다.

LB는 서버들에게 주기적으로 `/health` 같은 요청을 보내서 살아 있는지 확인합니다. 응답이 없거나 비정상인 서버는 라우팅 대상에서 제외합니다.

```text
정상 서버 -> 요청 전달
비정상 서버 -> 요청 제외
```

이게 있어야 "서버 한 대가 죽어도 서비스가 산다"가 실제로 성립합니다. 죽은 서버로 계속 요청을 보내면 사용자는 계속 에러를 보게 됩니다.

## 9. DB는 앱 서버처럼 쉽게 늘릴 수 없다

앱 서버는 stateless하게 만들면 여러 대로 늘리기 쉽습니다. 하지만 DB는 다릅니다. DB는 데이터를 기억하는 것이 존재 이유입니다.

DB를 단순히 여러 대로 복사해서 아무 곳에나 쓰기 요청을 보내면 데이터 정합성이 깨질 수 있습니다.

예를 들어:

```text
DB 1에 주문 저장
DB 2에서 주문 조회
-> 주문이 안 보임
```

또는:

```text
DB 1에서 잔액 차감
DB 2에서도 잔액 차감
-> 이중 차감 위험
```

그래서 DB 확장은 앱 서버 확장보다 훨씬 조심스럽습니다.

## 10. Primary/Replica - 읽기와 쓰기를 분리하기

대부분의 서비스는 쓰기보다 읽기가 많습니다.

예를 들어 상품 페이지는 수많은 사용자가 조회하지만, 실제 주문이나 상품 수정은 조회보다 훨씬 적습니다. 그래서 읽기만 여러 DB로 분산해도 DB 부하를 크게 줄일 수 있습니다.

```text
write -> Primary
read  -> Replica 1
read  -> Replica 2
read  -> Replica 3
```

요즘은 `Master/Slave`보다 `Primary/Replica`, `Writer/Reader`라는 표현을 권장합니다. 다만 예전 자료나 면접에서는 Master/Slave라는 표현도 나올 수 있으니 둘 다 알아두면 좋습니다. 말할 때는 Primary/Replica를 쓰는 편이 안전합니다.

핵심은 이겁니다.

- 앱 서버는 쓰기를 Primary에만 보냅니다.
- Replica는 읽기 부하를 분산합니다.
- 복제는 앱 서버가 하는 게 아니라 DB끼리 합니다.

## 11. 복제는 데이터 복사가 아니라 변경 이력 재생이다

DB 복제를 "데이터 파일을 통째로 복사한다"라고 이해하면 오해가 생깁니다.

MySQL 기준으로는 Primary가 변경 이력을 `binlog`에 기록하고, Replica가 그 로그를 받아서 자기 DB에 다시 반영합니다.

```text
Primary:
  write 실행
  binlog 기록
  commit
  앱 서버에 응답

Replica:
  binlog 수신
  relay log 저장
  순서대로 재생
  자기 데이터에 반영
```

중요한 점은 Primary가 Replica 반영 완료를 기다리지 않는다는 것입니다. 그래서 보통 비동기 복제라고 말합니다.

왜 기다리지 않을까요?

기다리면 Replica 하나가 느려질 때 모든 쓰기가 느려집니다. Replica 하나가 죽으면 쓰기가 멈출 수도 있습니다. 읽기 확장을 위해 Replica를 늘렸는데, 늘릴수록 쓰기가 느려진다면 목적이 무너집니다.

그래서 확장성을 얻는 대신, 약간의 지연과 일관성 문제를 감수합니다. 백엔드에서는 이런 교환이 자주 나옵니다.

## 12. Replication Lag - 방금 쓴 데이터가 안 보이는 문제

`Replication lag`는 Primary에는 반영됐지만 Replica에는 아직 반영되지 않은 시간입니다.

문제 상황은 다음과 같습니다.

```text
1. 사용자가 글 작성
2. 서버가 Primary에 저장
3. 서버가 저장 완료 응답
4. 사용자가 목록 조회
5. 조회가 Replica로 감
6. Replica에는 아직 글이 없음
```

사용자는 "저장됐다고 했는데 왜 안 보여?"라고 느낍니다.

이 문제는 개발 환경에서는 잘 안 보이다가 운영 환경에서 간헐적으로 터질 수 있습니다. 트래픽이 많거나 대량 배치가 도는 동안 Replica 반영이 밀릴 수 있기 때문입니다.

대표 해결책은 `read-your-own-writes`입니다.

쓰기 직후 일정 시간 또는 같은 요청 흐름의 조회는 Replica가 아니라 Primary에서 읽게 하는 방식입니다.

면접용으로는 이렇게 말할 수 있습니다.

> Primary/Replica 구조에서는 복제가 비동기로 진행되기 때문에 쓰기 직후 Replica에서 읽으면 방금 쓴 데이터가 보이지 않을 수 있습니다. 이런 경우 쓰기 직후 조회는 Primary로 라우팅하는 read-your-own-writes 전략을 사용하고, replication lag 지표를 모니터링합니다.

## 13. Multi-Master를 조심해야 하는 이유

읽기는 Replica를 추가하면 분산됩니다. 하지만 쓰기는 여전히 Primary 한 대에 몰립니다. 그래서 "Primary도 여러 대 두면 안 되나?"라는 생각이 자연스럽게 듭니다.

이 구조를 `Multi-Master`라고 합니다.

```text
Master A <-> Master B
write A      write B
```

이론적으로는 쓰기 처리량이 늘어날 것 같지만, 실무에서는 충돌 문제가 큽니다.

예를 들어 같은 사용자 잔액을 Master A와 Master B에서 동시에 수정하면 어느 값이 맞는지 결정해야 합니다. 충돌 해결 정책이 필요하고, 잘못 설계하면 데이터 정합성이 깨집니다.

그래서 일반적인 서비스에서는 Primary/Replica 구조를 먼저 쓰고, 쓰기 부하가 정말 감당되지 않을 때 다른 설계를 검토합니다.

## 14. Sharding - 데이터를 쪼개서 쓰기까지 분산하기

`Sharding`은 데이터를 여러 DB에 나누어 저장하는 방식입니다. 특히 같은 테이블의 행을 여러 DB로 나누는 수평 분할을 보통 샤딩이라고 부릅니다.

먼저 분할 방향을 구분해야 합니다.

| 방식 | 의미 | 예시 |
| --- | --- | --- |
| Vertical Partitioning | 도메인/테이블 단위로 DB 분리 | 회원 DB, 주문 DB, 상품 DB |
| Horizontal Partitioning | 같은 테이블의 행을 여러 DB로 분리 | 주문 테이블을 Shard 0, 1, 2로 분산 |

실무에서는 보통 수직 분할을 먼저 생각하고, 그래도 특정 테이블의 크기나 쓰기 부하가 감당되지 않을 때 수평 샤딩을 고려합니다.

샤딩에서 가장 중요한 것은 `Shard Key`입니다. 어떤 값을 기준으로 데이터를 나눌지 정하는 것입니다.

좋은 Shard Key의 조건은 다음과 같습니다.

- 값이 골고루 분포되어야 합니다.
- 조회 조건에 자주 등장해야 합니다.
- 잘 바뀌지 않아야 합니다.

예를 들어 `user_id`, `tenant_id`는 자주 후보가 됩니다. 반대로 가입 날짜를 기준으로 나누면 최근 가입자가 특정 샤드에 몰릴 수 있습니다.

## 15. Modulo Sharding과 리샤딩 문제

손그림에 나온 `% 0`, `% 1`, `% 2`는 modulo 기반 샤딩입니다.

```text
user_id = 1001 -> 1001 % 3 = 2 -> Shard 2
user_id = 1002 -> 1002 % 3 = 0 -> Shard 0
user_id = 1003 -> 1003 % 3 = 1 -> Shard 1
```

계산이 단순하고 빠르며 분포도 비교적 균일합니다. 하지만 치명적인 문제가 있습니다. 샤드 개수가 바뀌면 대부분의 데이터 위치가 바뀝니다.

예를 들어 `% 3`에서 `% 4`로 바뀌면 같은 `user_id`라도 다른 샤드로 가게 됩니다. 샤드 하나를 추가했을 뿐인데 엄청난 양의 데이터를 옮겨야 할 수 있습니다.

그래서 샤딩은 "서버 한 대 추가"처럼 쉽게 끝나는 작업이 아닙니다. 데이터 이동, 읽기 위치, 이동 중 들어오는 쓰기, 롤백 전략까지 설계해야 하는 큰 프로젝트입니다.

이 감각이 중요합니다. 샤딩은 강력하지만 최후의 수단에 가깝습니다.

## 16. Redis - DB에 가지 않게 만드는 캐시

성능을 높이는 가장 좋은 방법 중 하나는 DB를 빠르게 만드는 것이 아니라, DB에 아예 가지 않는 것입니다. Redis 캐시가 하는 일이 이것입니다.

```text
캐시 없음:
요청 1,000,000건 -> DB 조회 1,000,000번

캐시 있음:
요청 1,000,000건 -> DB 조회 1번 + Redis 조회 999,999번
```

Redis가 빠른 이유는 다음과 같습니다.

- 메모리에 데이터를 둡니다.
- Key-Value 구조라 조회가 단순합니다.
- 단일 스레드 이벤트 루프 기반이라 락 경쟁이 적습니다.

하지만 캐시는 항상 조심해야 합니다. 캐시는 원본이 아니라 복사본입니다. 그래서 "언제 넣을지"보다 "언제 지울지", "언제 갱신할지"가 더 어렵습니다.

예를 들어 상품 가격이 DB에서는 바뀌었는데 Redis에 예전 가격이 남아 있으면 사용자는 잘못된 가격을 볼 수 있습니다. 그래서 캐시에는 만료 시간인 TTL을 두거나, 원본 데이터 변경 시 캐시를 삭제하는 전략을 사용합니다.

쿠팡, 배민 같은 메인 페이지가 빠른 이유도 이 관점으로 이해할 수 있습니다. 사용자가 들어올 때마다 추천 상품, 인기 검색어, 랭킹을 전부 계산하면 늦습니다. 미리 계산해서 Redis에 넣어두고, 요청이 오면 이미 만들어진 결과를 꺼내는 방식이 훨씬 빠릅니다.

핵심은 "빠르게 계산한다"가 아니라 "미리 계산해 둔 결과를 꺼낸다"입니다.

## 17. Message Queue - 지금 당장 안 해도 되는 일을 뒤로 빼기

주문 처리 예시를 보면 서버가 할 일이 많습니다.

```text
결제
재고 차감
이메일 발송
SMS 발송
포인트 적립
```

사용자가 주문 완료 화면을 보기 위해 반드시 기다려야 하는 일과, 나중에 처리해도 되는 일이 섞여 있습니다. 이메일이나 SMS는 몇 초 늦게 와도 주문 자체가 실패한 것은 아닙니다.

메시지 큐는 급하지 않은 일을 요청-응답 경로에서 분리합니다.

```text
API 서버:
  핵심 처리 완료
  "이메일 보내기" 메시지를 큐에 넣음
  사용자에게 응답

Worker:
  큐에서 메시지 꺼냄
  이메일 발송
```

대표 제품은 다음과 같습니다.

| 제품 | 느낌 |
| --- | --- |
| Kafka | 대용량 이벤트 스트리밍, 재처리 강점 |
| RabbitMQ | 전통적인 메시지 브로커, 라우팅 유연 |
| AWS SQS | 관리형 큐, 운영 부담 적음 |
| Redis Streams | 이미 Redis를 쓰고 요구가 단순할 때 후보 |

메시지 큐를 쓰면 응답 시간이 줄고, 외부 서비스 장애가 핵심 요청 실패로 바로 이어지는 것을 줄일 수 있습니다. 대신 비동기 처리 실패, 중복 처리, 재시도, 순서 보장 같은 새로운 문제가 생깁니다.

면접용으로는 이렇게 말할 수 있습니다.

> 주문 완료 후 이메일, SMS 발송처럼 사용자가 기다릴 필요 없는 작업을 메시지 큐로 분리했습니다. 덕분에 응답 시간이 줄고 외부 발송 서비스 장애가 주문 성공 여부에 직접 영향을 주지 않도록 결합도를 낮출 수 있습니다.

## 18. MSA - 지금까지 배운 구조를 도메인별로 나누기

지금까지 쌓은 구조를 하나의 서비스 단위로 보면 다음과 같습니다.

```text
Load Balancer
-> Server N대
-> Redis
-> Primary/Replica DB
-> Message Queue
```

`MSA`, 즉 Microservice Architecture는 이 덩어리를 도메인별로 여러 개 두는 구조입니다.

예를 들어:

```text
회원 서비스
주문 서비스
상품 서비스
결제 서비스
알림 서비스
```

MSA에서 중요한 원칙은 `Database per Service`입니다. 서비스마다 자기 DB를 가지고, 다른 서비스의 DB를 직접 조회하지 않는 것입니다.

다른 서비스의 데이터가 필요하면 API나 메시지 큐 같은 인터페이스를 통해 가져와야 합니다.

MSA의 장점은 다음과 같습니다.

- 서비스별 독립 배포
- 서비스별 독립 확장
- 장애 격리
- 팀별 소유권 분리

하지만 단점도 큽니다.

- 분산 트랜잭션이 어려워집니다.
- 서비스 간 통신 실패를 고려해야 합니다.
- 로그와 모니터링이 복잡해집니다.
- 데이터 정합성 모델이 어려워집니다.

그래서 팀이 작고 도메인이 단순하면 모놀리식이 정답일 수 있습니다. MSA는 멋있어서 쓰는 구조가 아니라, 조직과 서비스 규모가 커져서 독립 배포와 독립 확장이 필요할 때 꺼내는 카드입니다.

## 19. 이번 회차를 하나의 이야기로 다시 말하기

처음에는 서버 한 대와 DB 한 대로 시작합니다.

```text
Client -> Server -> DB
```

요청이 늘면 서버 자원이 부족해집니다. 먼저 Scale up으로 서버 사양을 올릴 수 있습니다. 하지만 서버 한 대에 의존하면 장애에 약하고, 비용 대비 효율에도 한계가 있습니다.

그래서 서버를 여러 대로 늘립니다. 이때 Load Balancer가 필요하고, 서버는 stateless해야 합니다.

서버가 늘어나면 앱 서버 병목은 줄지만 DB가 병목이 됩니다. DB는 데이터를 기억해야 하므로 앱 서버처럼 쉽게 늘릴 수 없습니다. 그래서 읽기와 쓰기를 분리해서 Primary/Replica 구조를 사용합니다.

읽기는 Replica로 분산하지만, 쓰기는 Primary로 모읍니다. 복제는 비동기이므로 replication lag가 생길 수 있고, 쓰기 직후 조회는 Primary로 보내는 전략이 필요합니다.

읽기 부하가 더 크면 Redis 캐시를 사용해서 DB에 가지 않게 만듭니다. 요청 중 당장 안 해도 되는 작업은 메시지 큐로 분리합니다.

그래도 데이터가 너무 크거나 쓰기 부하가 너무 커지면 샤딩을 고려합니다. 하지만 샤딩은 리샤딩, 쿼리, 트랜잭션, 운영 복잡도가 크므로 최후의 수단에 가깝습니다.

이런 서비스 단위가 도메인별로 쪼개지면 MSA가 됩니다.

## 20. 프론트엔드 경험과 연결해서 이해하기

프론트엔드에서 이미 익숙한 개념들이 백엔드와 연결됩니다.

| 프론트엔드 경험 | 백엔드 연결 |
| --- | --- |
| API 호출 | 서버 요청 처리, 라우팅, Controller |
| 로딩 상태 | 서버 응답 시간, latency |
| 에러 UI | 4xx/5xx, timeout, exception |
| 낙관적 업데이트 | replication lag 대응 UX |
| 캐싱 | Redis, CDN, HTTP cache |
| 상태 관리 | stateless 서버, 세션, 토큰 |
| 배포 후 장애 | health check, rollback, monitoring |

특히 낙관적 업데이트 경험은 백엔드에서도 도움이 됩니다. "저장 요청이 성공했는데 목록에서 바로 안 보이는 문제"는 Replica lag와 연결됩니다. 프론트에서 화면에 먼저 반영하고, 백엔드에서는 쓰기 직후 조회를 Primary로 보내면 사용자 경험을 더 안정적으로 만들 수 있습니다.

## 21. 실무에서 자주 나오는 오해

### 오해 1. 서버가 느리면 무조건 서버 사양을 올리면 된다

아닙니다. DB 쿼리, 외부 API, connection pool, thread pool, 캐시 미스 등 원인이 다를 수 있습니다. 먼저 모니터링으로 병목을 찾아야 합니다.

### 오해 2. Scale out은 트래픽 처리 때문에만 한다

아닙니다. 고가용성 확보와 무중단 배포를 위해서도 서버를 여러 대 둡니다.

### 오해 3. 서버가 Replica에도 같이 write한다

아닙니다. 앱 서버는 Primary에만 write합니다. 복제는 DB끼리 binlog 같은 변경 이력을 통해 진행됩니다.

### 오해 4. Redis를 쓰면 무조건 좋아진다

아닙니다. 캐시는 데이터가 오래될 수 있습니다. TTL, 무효화, 갱신 전략이 없으면 틀린 데이터를 빠르게 보여주는 시스템이 됩니다.

### 오해 5. MSA는 무조건 좋은 구조다

아닙니다. MSA는 분산 시스템 복잡도를 가져옵니다. 작은 팀과 초기 서비스에서는 잘 만든 모놀리식이 더 좋은 선택일 수 있습니다.

## 22. 면접 답변으로 정리하기

### Q. Scale up과 Scale out의 차이는 무엇인가요?

Scale up은 서버 한 대의 CPU, 메모리 같은 성능을 높이는 방식이고, Scale out은 서버 대수를 늘려 요청을 분산하는 방식입니다. Scale up은 빠르게 적용할 수 있지만 물리적 한계와 SPOF 문제가 있고, Scale out은 처리량과 가용성을 높일 수 있지만 Load Balancer와 stateless 설계가 필요합니다.

### Q. Load Balancer는 어떤 역할을 하나요?

요청을 여러 서버로 분산하고, health check를 통해 비정상 서버를 라우팅 대상에서 제외합니다. 그래서 서버 일부에 장애가 생겨도 정상 서버가 요청을 처리할 수 있게 도와줍니다.

### Q. Primary/Replica 구조에서 왜 복제 지연이 생기나요?

앱 서버는 Primary에 write하고, Primary는 커밋 후 바로 응답합니다. Replica 반영은 binlog 같은 변경 이력을 받아 비동기로 재생하면서 진행되기 때문에 Primary와 Replica 사이에 시간 차이가 생길 수 있습니다.

### Q. 복제 지연으로 어떤 문제가 생기고 어떻게 해결하나요?

쓰기 직후 Replica에서 조회하면 방금 저장한 데이터가 보이지 않을 수 있습니다. 이를 막기 위해 쓰기 직후 조회는 Primary로 라우팅하는 read-your-own-writes 전략을 사용하고, replication lag를 모니터링합니다.

### Q. Redis 캐시는 왜 쓰나요?

반복 조회가 많은 데이터를 DB 대신 메모리 기반 저장소에서 빠르게 읽기 위해 사용합니다. DB 부하와 응답 시간을 줄일 수 있지만, 캐시 만료와 무효화 전략을 함께 설계해야 합니다.

### Q. 메시지 큐는 왜 도입하나요?

사용자가 기다릴 필요 없는 작업을 요청-응답 흐름에서 분리하기 위해 사용합니다. 예를 들어 주문 후 이메일 발송을 큐로 넘기면 응답 시간이 줄고, 외부 발송 서비스 장애가 주문 처리 자체에 미치는 영향을 줄일 수 있습니다.

### Q. 샤딩은 왜 어렵나요?

데이터를 여러 DB로 나누면 쓰기 부하와 데이터 크기 문제를 해결할 수 있지만, 샤드 키 설계, cross-shard query, 트랜잭션, 리샤딩, 운영 복잡도가 크게 증가합니다. 특히 샤드 개수가 바뀌면 많은 데이터를 이동해야 할 수 있습니다.

### Q. MSA에서 Database per Service가 왜 중요한가요?

각 서비스가 자기 DB를 가져야 독립 배포와 독립 확장이 가능합니다. 다른 서비스 DB를 직접 조회하기 시작하면 서비스 간 결합도가 높아지고, 사실상 분리된 서비스의 장점이 줄어듭니다.

## 24. 작은 실습 아이디어

아직 Spring을 깊게 들어가지 않았더라도, 지금 내용은 작은 코드로 연결해볼 수 있습니다.

### 실습 1. 요청 흐름 말로 설명하기

아래 API를 만든다고 상상하고 흐름을 말로 써봅니다.

```text
POST /posts
GET /posts
```

생각해볼 것:

- `POST /posts`는 write인가 read인가?
- write는 어느 DB로 가야 하는가?
- `POST /posts` 직후 `GET /posts`는 어느 DB로 보내야 안전한가?
- 목록 조회가 너무 많아지면 Redis를 어디에 둘 수 있는가?

### 실습 2. 병목 판단하기

상황:

```text
RPS는 그대로인데 p95가 갑자기 200ms에서 2s로 증가했다.
CPU는 40%다.
DB query duration이 증가했다.
5xx는 늘지 않았다.
```

바로 Scale up할 문제가 아닙니다. 먼저 DB 쿼리, 인덱스, 락, connection pool, 최근 배포 변경을 확인해야 합니다.

### 실습 3. 프론트 UX와 백엔드 일관성 연결하기

상황:

```text
글 작성 성공 응답은 받았는데 목록에는 바로 안 보인다.
새로고침하면 몇 초 뒤 보인다.
```

가능한 원인:

- 목록 조회가 Replica로 갔다.
- replication lag가 있었다.
- 캐시에 예전 목록이 남아 있었다.

가능한 해결:

- 쓰기 직후 조회는 Primary로 보낸다.
- 캐시를 무효화한다.
- 프론트에서 낙관적 업데이트로 작성한 글을 먼저 보여준다.

## 25. 다음 수업 키워드와 연결

다음 예습 키워드는 Spring Bean, Bean 생성 방법, Dependency/DI, Bean 라이프사이클입니다.

오늘 수업이 "서버가 전체 시스템 안에서 어떤 역할을 하는가"였다면, 다음 수업은 "Spring 서버 내부에서 객체들이 어떻게 만들어지고 연결되는가"입니다.

연결해서 보면 이렇게 됩니다.

```text
외부 세계:
Client -> Load Balancer -> Spring Server -> DB/Redis/MQ

Spring Server 내부:
Controller -> Service -> Repository
              ^          ^
              DI로 연결된 Bean들
```

Spring Bean은 Spring 컨테이너가 관리하는 객체입니다. Controller, Service, Repository 같은 객체를 개발자가 직접 `new`로 만들지 않고, Spring이 생성하고 연결해줍니다.

DI는 Dependency Injection, 즉 의존성 주입입니다. Service가 Repository를 필요로 할 때 직접 만들지 않고 외부에서 주입받는 방식입니다.

다음 회차에서는 이 질문을 중심으로 공부하면 좋습니다.

- 왜 객체를 직접 `new`하지 않고 Spring에게 맡길까?
- Bean은 언제 생성되고 언제 사라질까?
- Controller, Service, Repository는 어떻게 서로 연결될까?
- DI를 쓰면 테스트와 유지보수에 어떤 이점이 있을까?

## 26. 오늘 꼭 가져가야 할 문장

- 백엔드는 요청을 처리하는 코드이면서 동시에 병목, 장애, 데이터 정합성을 다루는 일이다.
- 서버를 늘리려면 stateless가 중요하다.
- Scale up은 빠르지만 한계가 있고, Scale out은 가용성과 처리량을 같이 본다.
- 느리면 먼저 APM으로 원인을 찾는다.
- DB는 앱 서버처럼 쉽게 늘릴 수 없어서 읽기와 쓰기를 분리한다.
- Primary/Replica 구조에서는 replication lag를 반드시 이해해야 한다.
- Redis는 DB에 가지 않게 해주지만 캐시 무효화 문제가 생긴다.
- 메시지 큐는 사용자가 기다릴 필요 없는 일을 뒤로 빼는 도구다.
- 샤딩은 강력하지만 운영 복잡도가 커서 최후의 수단에 가깝다.
- MSA는 기술 자랑이 아니라 독립 배포와 조직 확장을 위한 선택이다.
